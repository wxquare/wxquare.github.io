# /td-review — 技术方案设计文档审查

对技术方案设计文档（TD / Technical Design）进行结构化审查，确保文档完整性、决策质量和风险覆盖度。审查框架源自《系统设计与架构实战》第 1 章的设计方法论。

## 使用方式

```
/td-review <方案文档内容或文件路径>          # 默认检查
/td-review quick <方案文档内容或文件路径>     # 快速检查（仅 A + E 维度）
/td-review deep <方案文档内容或文件路径>      # 深度审查（全量）
```

## 审查维度

### Dimension A：骨架完整性（8 段式检查）

对照第 2.7 节 8 段式骨架，检查每段是否覆盖了核心问题：

| 段落 | 核心问题 | 通过标准 |
|------|---------|---------|
| 1. Background / Objective / Scope | 为什么现在做？成功标准？不做什么？ | 有明确背景、目标和边界声明 |
| 2. Current State / Problem Statement | 当前痛点是什么？是否真实可验证？ | 有现状描述，痛点是实际存在的而非假设 |
| 3. Key Decisions | 关键决策有几个？有选项和分析吗？ | ≥ 2 个决策，每个有选项+依据+代价+fallback |
| 4. End-to-End Flow / Responsibility Split | 核心链路怎么走？谁负责什么？ | 有流程图或时序图，标注同步/异步边界 |
| 5. API / Data Contract | 字段含义清楚？幂等、版本、精度说了吗？ | 关键字段有语义说明，幂等键有定义 |
| 6. Dependency / Rollout / Risk / Rollback | 依赖谁？怎么上？出问题怎么退？ | 依赖集中列出，灰度有维度，回滚可执行 |
| 7. Open Questions / Assumptions | 哪些没定？基于什么假设？ | 开放问题有显式出口，假设有验证条件 |
| 8. Work Breakdown / Owner / Timeline | 工作怎么拆？谁负责？依赖什么？ | 有任务拆分、Owner 和先后依赖 |

严重度判定：
- 🔴 Critical：完全缺少某一段，或该段无实质内容
- 🟡 Warning：该段存在但深度不够（如只有一句话描述）
- 🟢 Suggestion：该段覆盖了核心问题，但可补充细节
- ✅ Pass：该段完整，不需要修改

### Dimension B：六维设计画布覆盖度

对照第 2.6 节六维画布，检查设计阶段是否覆盖了六个维度。检查每个维度是否回答了其核心问题：

| 维度 | 核心问题 | 检出标准 |
|------|---------|---------|
| **Model** | 事实源是谁？状态怎么流转？核心实体边界在哪？ | 检测文档中是否有实体描述、状态机、事实源声明 |
| **Process** | 主链路怎么走？事务边界在哪？失败了怎么补偿？ | 检测是否有时序图/流程图、事务范围、异常处理 |
| **Capability** | 模块怎么划分？为什么选这个组件？依赖方向合理吗？ | 检测是否有模块职责声明、选型决策记录 |
| **Governance** | 最坏情况是什么？怎么兜底？对账和补偿怎么做？ | 检测是否有风险清单、限流/熔断策略、对账方案 |
| **Measurement** | 怎样算正常？出了事怎么发现？怎么定位？ | 检测是否有 SLI/SLO、监控埋点、告警规则 |
| **Evolution** | 今天的设计会不会堵死明天的路？旧数据怎么迁移？ | 检测是否有兼容策略、非目标假设、迁移路径 |

严重度判定：
- 🔴 Critical：某个维度完全未被覆盖，且该维度对方案至关重要（如支付场景缺 Governance）
- 🟡 Warning：某个维度被提及但描述过浅，缺少具体产出
- 🟢 Suggestion：覆盖了核心但可进一步深化

### Dimension C：决策质量评估

对照第 2.8 节，检查每个关键决策的完整度。每条决策检查五项：

- [ ] **候选方案**：是否列出了可行的替代方案？（至少 2 个）
- [ ] **选择结果**：是否明确写了选哪个？
- [ ] **选择依据**：是否有对比分析，而不是只说"方案 B 更好"？
- [ ] **明确代价**：选这个方案放弃/牺牲了什么？
- [ ] **Fallback**：选错了怎么退？有后续迁移路径吗？

判定：
- 缺失 ≥ 3 项 → 🔴 Critical
- 缺失 2 项 → 🟡 Warning
- 缺失 1 项 → 🟢 Suggestion
- 全部完整 → ✅ Pass

### Dimension D：风险/灰度/回滚可执行性检查

对照第 2.9 节，检查 rollout 和 rollback 是否可执行而非模板占位。

**风险检查（每项风险应回答）**：
- [ ] 风险是什么？（具体而非概括）
- [ ] 何时会发生？
- [ ] 影响范围是什么？
- [ ] 如何发现？
- [ ] 如何缓解？
- [ ] 缓解失败怎么回滚？

**灰度检查**：
- [ ] 是一次性切换还是灰度放量？
- [ ] 灰度维度是什么？（用户/流量/市场/开关）
- [ ] 观测指标是什么？
- [ ] 失败阈值是什么？
- [ ] 谁负责拍板？

**回滚检查**：
- [ ] 回滚对象是什么？（版本/快照/开关/配置/数据）
- [ ] 回滚动作由谁执行？
- [ ] 回滚前需要检查什么？
- [ ] 回滚后如何确认恢复到稳定态？

判定：
- 只要有一个检查项不可执行（如只有"出问题回滚"四个字）→ 🔴 Critical
- 大部分可执行但缺少 1-2 项细节 → 🟡 Warning
- 全部可执行 → ✅ Pass

### Dimension E：反模式检测

对照第 2.11 节，检查是否落入了以下 7 种反模式：

| 反模式 | 判断方法 | 严重度 |
|--------|---------|--------|
| 方案写成实施手册 | 命令/SQL/接口细节很多，但缺少主设计决策 | 🟡 Warning |
| 选项列了但没有决策标准 | A/B 方案并列展示，没有为什么选这个 | 🟡 Warning |
| 字段语义不统一 | 金额/状态在不同章节含义漂移 | 🔴 Critical |
| 依赖和 blocker 散落正文 | 读者需要自己拼图 | 🟡 Warning |
| rollout/rollback 模板占位 | 看起来写了，实际上不可执行 | 🔴 Critical |
| 开放问题没有显式出口 | 未定内容埋在自然语言里 | 🟡 Warning |
| 设计与运行手册混写 | 评审想看系统行为，却被后台操作步骤淹没 | 🟢 Suggestion |

## 注意事项

- **不审查代码正确性**：本 skill 只评估方案文档的结构完整性和设计覆盖度，不审查代码实现是否正确
- **不替代人评审**：本 skill 是评审辅助工具，帮助在评审前自查，或在评审中提供结构化检查清单，不替代架构师的专业判断
- **评估材料完整度而非方案好坏**：一份骨架完整的方案不一定是好方案，但骨架残缺的方案几乎肯定会在评审会上被打回
- **优先识别结构性缺失**：优先指出段落缺失、决策不完整、反模式等结构性问题，其次是内容深度问题
- **关于上下文**：如果你对本书内容不清楚，用户应提供文档内容供你审查。如果用户只给了需求描述而非法方案文档，先确认是缺文档还是想要输出一份模板，本 skill 不应自主创作方案内容
