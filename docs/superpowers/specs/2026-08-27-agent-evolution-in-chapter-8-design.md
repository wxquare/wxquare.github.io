## 读者问题与写作原则

新增内容需要回答两个问题：

1. Agent 的技术形态经历了哪些阶段，分别解决了什么问题？

内容以工程决策为中心，而不是罗列产品或框架。特别是“自我演化”必须定义为一个由 Evals、人工审核、灰度发布和回滚控制的改进闭环，不能描述为模型无边界地自行修改自身。

## 新增 8.1 的内容设计

### 8.1.1 两条并行主线

技术形态演化：

```text
Chatbot → Prompt Application → Tool-using Agent → Workflow Agent
→ Runtime Agent → Multi-Agent → 受控持续改进系统
```

工程能力演化：

```text
Prompt → Context → Harness → API / Tools → Knowledge / Memory
→ Orchestration → Evals / Guardrails / Observability
```

用映射表解释每一个形态阶段的价值、限制、所需工程能力和新增风险；工程能力只作为后续章节的导航，不重复后续章节的实现细节。

### 8.1.2 贯穿案例

使用“企业告警与知识答疑”作为同一任务的升级样本：

1. 对话系统解释告警术语；
2. Prompt 应用生成初步排障建议；
3. 工具型 Agent 查询指标、日志和 Runbook；
4. 工作流 Agent 按步骤取证、归因、生成工单草稿；
5. Runtime Agent 在权限、审批和验证边界内执行受限操作；
6. 多 Agent 将调查、变更审查和交付拆给不同角色；
7. 通过评测、复盘、审核和灰度发布改进 Skill 与策略。

该案例只建立演化直觉，详细的企业实践仍由第 22 章承担。

### 8.1.3 升级边界

新增“何时不应升级为 Agent”检查：固定规则或确定性工作流能可靠完成的任务，应优先采用传统后端或工作流。只有任务存在模糊目标、多源上下文、动态路径和可验证动作时，才需要引入 Agent Runtime。
