## 1. 背景

当前 Hermes 章节已经积累了大量高价值材料，尤其是 Prompt System、Memory、Session、Tool Runtime、Gateway、Profiles、Research Pipeline 等部分，已经包含较强的源码级证据和运行时判断。

但当前稿件也有三个明显问题：

- 章节主线偏弱，读者容易从“系统解析”读成“模块和源码材料堆叠”。
- 小节编号仍混用 `20.x`，与第 21 章定位不一致。
- 有些源码证据非常强，但还没有被组织成稳定结论；也有些内容过细，影响书稿节奏。

这次优化不追求“删细节换可读性”，而是重构为：**用更强的章节主线承载现有技术证据**。

---

## 2. 目标

本次重构的目标有三项：

1. 把 Hermes 章节改造成更适合书稿阅读的“问题驱动型系统解析”。
2. 保留并在必要处补强源码级技术证据，确保关键判断能落到实现。
3. 删除偏离主线的独立章节，但把其中有价值的知识回收到正文与“设计启示”中。

成功标准：

- 章节目录统一为 `21.x`。
- 正文结构围绕长期 Agent Runtime 的几条主线展开，而不是逐模块罗列。
- 关键架构判断都至少有一种源码级证据支撑：机制、调用链、存储边界或运行时约束。
- 删除独立的“自研 Hermes 类系统的最小可行架构”章节，但不丢失其中高价值结论。

---

## 3. 非目标

- 不把 Hermes 章节改写成源码逐文件导读。
- 不为了压缩篇幅而删除 Prompt、Memory、Session 等核心证据。
- 不在本轮设计中重写整本书结构，只聚焦 Hermes 这一章。
- 不追求把每个内部函数都逐一展开说明，避免书稿节奏被实现细节拖垮。

## 5. 重构原则

### 5.1 主线优先，源码证据不丢

章节重构后，正文的一级目标是把 Hermes 解释成一个长期运行的 Agent Runtime。源码证据的角色不是消失，而是从“主结构本身”调整为“支撑判断的证据层”。

每个关键判断尽量遵循同一种写法：

```text
结论
  -> 机制解释
  -> 源码证据
  -> 设计含义
```

### 5.2 压缩噪声，不压缩信息

以下内容允许压缩表达，但不应删除信息本身：

- 超长表格；
- 过细的伪代码；
- 重复的架构图和重复解释；
- 同一结论在不同小节重复出现的铺垫语句。

### 5.3 只删除偏题结构，不删除有效知识

独立的“自研 Hermes 类系统的最小可行架构”章节将删除，因为它会把系统解析拉向另一条半独立叙事线。

但其中有价值的知识需要保留：

- 哪些能力是 Hermes 的核心骨架；
- 哪些能力体现长期 Agent 的最低必要条件；
- 哪些机制应该后置治理；
- 从个人 Agent 到更强治理形态的演进判断。

这些内容将回收到 `21.11 设计启示` 和相关正文小结中。

## 6. 源码证据保留与补强策略

### 6.1 必须保留的证据类型

本章保留三类源码级证据：

| 证据类型 | 用途 | 典型内容 |
|:---|:---|:---|
| 机制级证据 | 证明系统如何工作 | Prompt 三层分层、memory frozen snapshot、session rotation、FTS5 检索、tool dispatch |
| 调用链证据 | 证明判断不是静态推测 | Agent Loop 到 transport 到 provider 调用链，tool call 到 backend 执行链 |
| 存储与边界证据 | 证明长期 runtime 的落地形态 | `USER.md` / `MEMORY.md`、SQLite session store、profile 隔离、toolset gating、backend 选择 |

### 6.2 优先补强的源码区域

需要优先补强或重新组织的区域如下：

1. `Prompt System`
   当前材料很强，但需要更明确服务于“长期稳定上下文”结论。
   重点保留：
   - stable / context / volatile 三层结构；
   - SOUL.md、AGENTS.md、USER.md、MEMORY.md 的职责差异；
   - frozen snapshot 与 prompt caching 的关系。

2. `Memory`
   重点保留：
   - MEMORY / USER 的文件落盘与读取方式；
   - memory 更新为何不会立刻改变本轮 system prompt；
   - MemoryProvider 抽象与可插拔边界。

3. `Session`
   重点保留：
   - SQLite SessionDB；
   - FTS5 双索引；
   - session 创建、恢复、压缩、旋转路径；
   - 多入口共用会话状态的机制。

4. `Tool Runtime / Action Engine`
   重点保留：
   - Tool Registry 与 Toolsets；
   - 参数校验、调用分发、结果回传；
   - backend 选择与失败恢复逻辑。

5. `Gateway / Profiles`
   重点保留：
   - Gateway 作为多入口事件接入边界；
   - Profiles 作为身份、环境、长期记忆隔离边界。

6. `Research Pipeline`
   重点保留：
   - 轨迹如何成为研究和训练资产；
   - 为什么学习闭环必须受验证约束。

### 6.3 允许降级的证据形式

以下内容可以从“详细展开”改成“摘要式证据”：

- 特别长的字段枚举；
- 对同一层调用链的重复展示；
- 不直接支撑核心判断的工具名称罗列；
- 对单个实现细节的过多旁枝说明。

原则不是删证据，而是把证据转换成更适合书稿的形式。

## 8. 章节写法规范

为兼顾书稿可读性与技术可信度，本章正文建议统一采用以下写法：

### 8.1 先讲架构问题，再讲 Hermes 的实现回答

例如：

- 长期 Agent 为什么需要 frozen snapshot；
- 多入口 Agent 为什么必须有 session persistence；
- 自我进化为什么不能直接把所有成功轨迹写回长期能力层。

### 8.2 证据只保留能支撑结论的最短路径

源码不是越多越好。正文中只保留能证明判断成立的最短证据链，避免把章节写成源码陪读。

### 8.3 表格为结论服务

保留表格，但每张表都必须回答一个明确问题，例如：

- 哪几层上下文分别解决什么问题；
- Memory、Session、Skill 的边界是什么；
- Toolsets、Profiles、Backends 分别治理哪一类风险。

## 9. 执行顺序

实际改稿建议按以下顺序进行：

1. 统一章节编号为 `21.x`。
2. 先重排目录与一级主线。
3. 合并相关小节，形成“运行时 / 上下文 / 记忆 / 行动 / 多入口 / 安全 / 学习闭环”七条主线。
4. 在重排后的结构中回填现有源码证据。
5. 补强证据薄弱但结论重要的部分。
6. 删除独立“最小可行架构”章节，并把其中有效知识回收到相关小节。
7. 统一引言、本章问题列表、本章小结与参考资料口径。

## 10. 风险与控制

### 风险 1：为了可读性削弱证据

控制方式：
明确把源码证据当成硬约束，不允许只保留空泛架构判断。

### 风险 2：为了保留证据继续失去节奏

控制方式：
把证据组织成“机制说明”而不是“实现清单”。

### 风险 3：删除独立章节后丢失作者判断

控制方式：
先迁移有效结论，再删除结构，不做纯删除。

## 11. 预期结果

重构完成后，这一章应当同时满足两件事：

- 读者能把 Hermes 理解成一种长期运行、自我进化、多入口 Agent Runtime 的代表性系统。
- 读者能看到这些判断不是抽象概括，而是有具体源码机制支撑的工程结论。

换句话说，最终成稿应该既像一本书，也像一份经得起追问的系统分析。
