# 高交互异步的 Excel 批量任务设计和实现

## 一、背景 / 痛点

这个场景的核心诉求是：运营或商家上传一份 Excel 后，希望系统能批量创建或批量更新商品，并且在几分钟内持续反馈处理进度。它表面上看像“文件导入”，但本质上是一个**高交互、长链路、允许部分成功的异步任务系统**。

它的主要痛点有六个：

- **批量任务天然允许部分成功**：用户通常能接受“部分成功、部分失败”，但必须给出明确的失败原因和错题本。
- **文件规模不稳定**：小文件可能只有几十行，大文件可能达到几万行，不能用单机内存一次性吃下。
- **下游写入能力有限**：商品中心、审核链路、库存价格链路通常都有 QPS 和并发约束，不能靠单机线程池硬顶。
- **任务生命周期长且跨进程**：解析文件、消费 MQ、生成结果文件是三个完全不同的阶段，任何一个阶段中断都需要可恢复。
- **创建和更新会混在同一批文件里**：同一份 Excel 里，既可能有新建行，也可能有编辑行，两者的治理逻辑并不一样。
- **用户交互预期高**：用户上传后不会离开页面，而是会盯着进度条看结果，期望分钟级反馈。


所以，这不是一个“上传文件后开个线程从头跑到尾”的问题，而是一个需要任务化、分阶段和强治理的批量处理系统。

## 二、主方案设计

### 1. 总体思路

我会把整条链路拆成四个阶段：

1. **提交任务**：只收单，不做重活，秒级返回 `task_id`
2. **解析 Excel**：流式解析文件，把每一行落成 `task_item`
3. **处理任务**：通过 MQ 按行解耦，异步调用下游
4. **结果归档**：汇总成功、失败、跳过，生成错题本

这四个阶段分别解决不同问题：

- 提交阶段解决“前端快速响应”
- 解析阶段解决“大文件安全落盘”
- 处理阶段解决“削峰填谷和行级隔离”
- 归档阶段解决“批量任务怎么优雅收尾”

整体上我会设计两层状态机：

- **任务级状态机**：描述整批任务当前走到哪一步
- **行级状态机**：描述每一行为什么成功、失败或被跳过

### 2. 提交任务阶段

提交阶段只做三件事：

- 校验文件格式、模板版本和操作者权限
- 创建 `product_supply_task`
- 返回 `task_id / receipt_id`

这个阶段不直接解析 Excel，也不直接写正式商品表。原因是用户最需要的是**立即得到受理回执**，而不是等待后端把整个文件处理完。

任务表在这里会先进入 `PENDING` 状态，表示“系统已经接单，但还没有真正开始解析”。

### 3. 解析 Excel 阶段

解析阶段由独立的 Parser Worker 负责，它的边界要非常克制：**只解析，不发布**。

它的主要职责包括：

- 通过数据库 CAS 抢占 `PENDING` 任务
- 写入 `worker_id / lease_token / lease_until / heartbeat_at`
- 流式读取 Excel，避免大文件 OOM
- 把每一行落成 `product_supply_task_item`
- 持续推进 `parse_checkpoint`
- 解析完成后把任务切换到 `PROCESSING`

这里我会强调两个设计点：

- **同一时刻只能有一个 Parser Worker 解析同一份文件**
- **解析进度必须持久化 checkpoint**

这样即使容器重启、进程 OOM 或机器故障，新 Worker 也能从最近一次 `parse_checkpoint` 继续解析，而不是整份文件从头再来。

### 4. 处理任务阶段

解析完成后，系统不是直接在本机线程池里把所有行跑完，而是把每个 `task_item_id` 投递到 MQ，由 Consumer 集群异步处理。

这样做的目标是：

- 用 MQ 做削峰和背压
- 让行级失败和整批任务解耦
- 让处理能力可以横向扩展

这一阶段的关键是：**创建和更新虽然共用同一套跑批外壳，但处理内核必须分流。**

#### 创建行的处理逻辑

创建更关注“完备性与防冗余”，主要步骤是：

- 行级字段校验和模板校验
- 标准化输入
- 基于业务指纹做防重检查
- 调用创建草稿或创建商品 RPC
- 回填行级结果

如果对象已经存在，这一行应直接失败并进入错题本，防止重复建品。

#### 更新行的处理逻辑

更新更关注“增量安全与抗并发”，主要步骤是：

- 行级字段校验和模板校验
- 反查正式对象和当前版本
- 补齐 `base_publish_version`
- 计算 Diff
- 做字段主导权裁剪
- 调用更新草稿或更新商品 RPC

这里不能直接拿 Excel 空字段覆盖线上已有值，所以更新本质上是“瘦报文 + 增量补丁”，而不是“整对象覆盖”。

### 5. 结果归档阶段

批量任务的最后一个难点，不是“再处理一批数据”，而是**如何判断整批已经处理完成，并可靠地产出结果文件**。

我的做法是：

- 解析完成后，初始化 Redis 计数器 `task:count:{task_id}=total_count`
- 每个 `task_item` 处理结束后，无论成功、失败还是跳过，都执行一次 `DECR`
- 谁把计数器减到 `0`，谁就触发结果归档

结果归档线程负责：

- 汇总 `success_count / failed_count / skipped_count`
- 如果存在失败行，基于原始行数据和错误信息生成错题本 Excel
- 上传错题本并回填 `error_file_url`
- 把任务状态更新为 `DONE` 或 `PARTIAL_SUCCESS`

同时我还会保留一个 DB 旁路兜底：

- 如果 Redis 计数异常、Consumer 猝死或计数器悬空
- 定时器扫描 `PROCESSING / GENERATING_RESULT` 任务
- 只要数据库聚合显示所有行都处理完，就补触发一次归档

这样就能避免“所有行都跑完了，但任务永远卡在处理中”的尴尬问题。

## 三、主要难点与应对措施（决策点）

### 1. 为什么不用传统串行流程？

传统串行流程的路径通常是：上传文件后，一个线程完成解析、校验、调用商品中心、汇总结果，再一次性返回。

这个方案的问题是：

- 用户长时间无反馈
- 大文件容易拖垮单机内存和线程池
- 任意一行失败都容易影响整批
- 进程重启后恢复困难

所以我选择的是**提交、解析、处理、归档四阶段解耦**。它让链路从“黑盒串行任务”变成“可观测、可恢复、可治理的任务系统”。

### 2. 为什么一定要拆 task 和 task_item 两层？

因为批量任务最怕一句话描述不清楚结果。

如果只有任务级状态，系统最多只能说“这批任务失败了”，但回答不了：

- 到底是哪一行失败
- 失败发生在校验、版本冲突还是下游 RPC
- 哪些行已经成功
- 哪些行可以单独重试

所以必须拆成：

- `product_supply_task`：管理整批生命周期
- `product_supply_task_item`：管理每一行的独立命运

这样错题本、局部补偿和人工修复才有抓手。

### 3. 为什么解析阶段要单独拆出来？

因为 Excel 解析本身就是一个独立问题。

它有几个很强的工程约束：

- 文件可能很大，必须流式读取
- 解析过程可能很慢，必须有心跳和租约
- 容器可能重启，必须能从 checkpoint 恢复
- 解析产物要持久化，否则中间态会蒸发

如果把解析和下游处理混成一个阶段，恢复和治理会非常痛苦。所以我会单独拆 Parser Worker，只让它做“抢任务、切文件、落盘、投递 MQ”。

### 4. 为什么创建和更新不能走同一个处理内核？

因为它们要解决的是两个方向完全不同的问题：

- **创建**：对象原本不该存在，核心是完备性、防重和最小必填集
- **更新**：对象必须已存在，核心是版本保护、Diff 裁剪和字段主导权

一句话总结就是：

> 创建防冗余，更新防并发。

它们可以共用同一套批量任务底座，但阶段三的业务内核一定要分流。

### 5. 为什么处理阶段要通过 MQ 解耦？

如果解析完成后直接在本机线程池处理所有行，会遇到几个问题：

- 大批量时对商品中心形成瞬时洪峰
- 单机故障会让整批任务停摆
- 没有天然背压能力
- 无法优雅做重试和死信治理

MQ 的价值在于：

- 匀速顶下游
- 支持消费重试
- 便于扩缩容
- 让行级失败天然隔离

因此，这里不是“为了用 MQ 而用 MQ”，而是为了把批量任务从单机执行模型升级为分布式消费模型。

### 6. 为什么结果文件生成要单独治理？

批量任务和普通异步任务最大的区别之一，就是它不仅要把数据处理完，还要给用户一个**可下载、可追责、可复盘**的结果产物。

如果不单独治理结果归档阶段，就很容易出现两个问题：

- 行级消费都成功了，但没人负责收尾
- 错题本依赖日志拼凑，结果不准确也不可追溯

所以结果文件必须基于 `task_item` 的权威状态生成，而不是基于日志猜测生成。

## 四、可能的异常与处理

### 1. Parser Worker 抢占后宕机

处理方式：

- 依赖 `lease_until + heartbeat_at` 判断租约是否过期
- 新 Worker 只能接管过期任务
- 从 `parse_checkpoint` 附近恢复解析

### 2. Excel 文件过大导致解析 OOM

处理方式：

- 强制流式解析
- 每批次落盘 `task_item`
- 周期推进 checkpoint
- 对超规格文件做上传前限制和模板约束

### 3. 某些行校验失败

处理方式：

- 只把对应 `task_item` 更新为 `FAILED`
- 记录 `error_code / error_message`
- 不影响同批其他行继续执行

### 4. 下游 RPC 超时或临时失败

处理方式：

- 交给 MQ 自动重试
- 超过阈值后进入 DLQ 或回填 `FAILED`
- 后续支持按行重试，而不是整批重跑

### 5. 更新行发生版本冲突

处理方式：

- 在消费阶段实时反查正式对象版本
- 显式携带 `base_publish_version`
- 由下游乐观锁拒绝旧版本覆盖
- 冲突行回填为 `FAILED` 或 `SKIPPED`

### 6. 解析任务恢复后重复扫描，导致创建请求重复下发

处理方式：

- 不把 `parse_checkpoint` 当成绝对去重手段，而是接受恢复时可能会重复扫描一小段
- 为每一行创建请求生成稳定的 `idempotency_key`
- 这个键必须跨重试、跨恢复保持不变，推荐基于 `merchant_id + source_file_hash + row_fingerprint` 生成
- 批量侧在调用商品域创建接口时，显式透传这个 `idempotency_key`
- 商品域落幂等请求表，记录 `idempotency_key -> product_id`
- 第一次创建成功后保存映射关系，后续同一个 `idempotency_key` 再次请求时，直接返回第一次创建成功的 `product_id`

这样即使解析恢复导致某一行被再次投递和再次消费，最终也不会真的重复创建商品，而是会命中商品域的幂等收敛逻辑。

在结果文件层面，这类场景应该记为：

- `SUCCESS`

因为它不是业务失败，而是系统把重复请求正确收敛成了一次幂等成功。

### 7. Redis 计数器未归零，导致任务无法收尾

这是批量任务里一个很典型的分布式收尾问题。

主链路里，我会用 Redis 计数器去快速判断“最后一个完成者”：

- 解析阶段结束后，初始化 `task:count:{task_id}=total_count`
- 每个 `task_item` 无论最终结果是 `SUCCESS`、`FAILED` 还是 `SKIPPED`，都必须在本地事务提交后执行一次 `DECR`
- 谁把计数器减到 `0`，谁就尝试把任务从 `PROCESSING` 切到 `GENERATING_RESULT`
- 抢到这个状态迁移的线程，负责汇总结果并生成错题本

这个方案性能很好，但它不是绝对可靠的。Redis 计数器不归零，通常有几类原因：

- Consumer 在更新完 `task_item` 后、执行 `DECR` 前宕机
- 某条消息重复消费，导致有的行被多次处理，有的行没有真正完成
- Redis key 过期、被误删，或者初始化失败
- 最后一个 Consumer 已经拿到 `0`，但在切换 `GENERATING_RESULT` 前崩溃

所以我不会把 Redis 计数器当成“唯一真相”，而是把它定位成：

- **高性能的快速收尾信号**

真正兜底的“最终真相”，仍然以数据库中的 `task_item` 状态聚合为准。也就是要额外设计一个 **DB 旁路盘点定时器**。

#### 旁路盘点器的职责

这个定时器不是为了替代主链路，而是为了处理“主链路本该收尾，但没有成功收尾”的尾部异常。

它只扫描这些任务：

- `PROCESSING`
- `GENERATING_RESULT`

并且只扫运行时间超过阈值的任务，例如：

- 任务处于 `PROCESSING` 已超过 10 分钟仍未结束
- 任务处于 `GENERATING_RESULT` 已超过 5 分钟仍未完成

这样可以避免它去干扰正常还在执行中的任务。

#### 旁路盘点器怎么判断任务是否真的完成

旁路盘点器拿到一个 `task_id` 后，不看 Redis，而是直接聚合 `product_supply_task_item`：

- `total_count`
- `success_count`
- `failed_count`
- `skipped_count`
- `unfinished_count`

其中 `unfinished_count` 的定义通常是：

- `INIT`
- `PROCESSING`
- 其他还未进入终态的状态

只要 `unfinished_count > 0`，说明这批任务还没有真正结束，定时器不做收尾，只记录一条巡检日志后退出。

只有当：

- `success_count + failed_count + skipped_count = total_count`

时，才认为这批任务在数据库意义上已经全部完成，可以进入补收尾逻辑。

#### 补收尾时如何避免重复生成结果文件

这里不能简单地“扫到完成就直接生成”，否则多个定时器实例、或者主链路和定时器并发触发时，会重复归档。

我会再加一层任务级 CAS 状态迁移：

- 只有满足 `status in ('PROCESSING', 'GENERATING_RESULT')` 的任务，才允许尝试补收尾
- 定时器通过数据库 CAS 把任务状态切成 `GENERATING_RESULT`
- 例如：`update ... set status='GENERATING_RESULT', result_worker=?, result_started_at=? where id=? and status='PROCESSING'`
- `rows_affected = 1` 才表示本次抢收尾成功
- `rows_affected = 0` 说明已经被别的线程或主链路抢先处理，当前定时器直接退出

这样主链路和旁路盘点器就能共享同一套“谁抢到谁归档”的收尾语义。

#### 补收尾线程具体做什么

一旦旁路盘点器抢到归档权，它就执行和主链路终结者相同的动作：

- 聚合 `success_count / failed_count / skipped_count`
- 如果存在失败行，基于 `task_item` 的原始行数据、`error_code` 和 `error_message` 生成错题本 Excel
- 上传结果文件并回填 `error_file_url`
- 根据最终统计结果回写 `product_supply_task`

状态回写建议是：

- 全部成功：`DONE`
- 有失败或跳过：`PARTIAL_SUCCESS`
- 理论上所有行都失败，也可以根据业务语义记为 `FAILED` 或 `PARTIAL_SUCCESS`

我个人更倾向于：

- 只要整批流程完整结束，就优先区分“全部成功”与“部分成功”
- 真正的 `FAILED` 更多留给“解析阶段致命失败”或“整批根本没跑起来”

#### 为什么要用“Redis 快速收尾 + DB 最终兜底”双轨设计

因为两者解决的是不同问题：

- Redis 负责低成本、低延迟地找到最后一个完成者
- DB 负责在异常情况下给出最终真相

只有 Redis，没有 DB 旁路，就会出现：

- 任务其实都跑完了，但计数器没归零，整批永远卡在 `PROCESSING`

只有 DB 扫表，没有 Redis，又会出现：

- 每批任务都靠定时器轮询收尾，时效性太差
- 扫表成本高，用户看进度和结果会更慢

所以更合理的设计不是二选一，而是：

- **主链路依赖 Redis 做快速收尾**
- **异常场景依赖 DB 旁路盘点做最终兜底**

一句话总结就是：

> Redis 负责“尽快收尾”，DB 负责“保证一定能收尾”。


## 五、后续可优化项（后续可以演进）

- **对象级 `trace_id`**：每一行进入主链路时生成 `trace_id`，贯穿解析、消费、RPC 和结果归档，方便端到端排查。
- **更细粒度的字段主导权矩阵**：把更新从“对象级覆盖”演进到“字段级覆盖”，避免误改运营手工维护内容。
- **热点对象顺序路由**：按 `merchant_id / product_id` 做局部 Hash 顺序消费，降低热点更新的锁竞争。
- **行级修复台**：支持运营只修失败行，不必重新上传整份 Excel。
- **结构化错误体系**：把 `error_code` 标准化，便于后续统计模板问题、权限问题、数据质量问题和下游故障问题。

## 六、其它需要考虑的问题

### 1. 幂等与防重

批量链路里，至少要保证三层幂等：

- 任务提交幂等：避免用户重复点击造成重复建任务
- 行级处理幂等：避免 MQ 重复消费造成重复写入
- 下游命令幂等：避免 RPC 超时后重复提交产生双写

对于创建场景，我更推荐把幂等主键统一收口到 `idempotency_key`：

- 批量侧为每一行生成稳定的业务幂等键
- 调用商品域时显式透传这个 `idempotency_key`
- 商品域基于 `idempotency_key -> product_id` 做最终幂等收敛

这样即使解析恢复导致重复扫描，或者 MQ 出现重复投递，也不会把同一条创建意图真正执行两次。

更具体地说，我会把这套幂等方案拆成四层：

#### 第一层：任务提交幂等

同一个用户可能因为页面卡顿、重复点击或前端超时重试，把同一份文件连续提交多次。所以提交阶段不能只看 HTTP 请求是否到了，而要识别“这是不是同一批导入意图”。

常见做法是：

- 前端提交时带 `client_request_id`
- 后端结合 `operator_id + file_hash + template_version` 做一次任务去重
- 如果短时间内发现是同一份文件、同一模板、同一操作者的重复提交，就直接返回已存在的 `task_id`

这样可以避免用户还没进入解析阶段，就已经造出多份完全一样的批量任务。

#### 第二层：行级解析幂等

`parse_checkpoint` 只能保证“恢复时少量重跑”，不能保证“绝对不重复解析”。所以 Parser Worker 在恢复后，重复扫到某几行是允许发生的。

这一层的关键不是消灭重复扫描，而是把重复扫描收敛成同一个 `task_item`：

- 为每一行生成稳定的行级唯一键，例如 `task_id + sheet_no + row_no`
- 或者更稳一点，用 `task_id + row_fingerprint`
- `product_supply_task_item` 上建立唯一索引
- Parser 落盘时采用 `insert ignore`、`upsert` 或等价幂等写法

这样即使恢复后重复扫到同一行，也只会命中已有 `task_item`，而不会生成第二条行记录。

#### 第三层：创建命令幂等

创建场景里，最重要的是不要把“同一条创建意图”真的执行两次。所以我会为每一行生成稳定的 `idempotency_key`，并把它透传到商品域。

这个 `idempotency_key` 的设计要求是：

- 同一条创建意图，无论重试多少次，都生成同一个 key
- 不依赖数据库自增 ID，不依赖本次进程内存状态
- 跨容器重启、跨 MQ 重投、跨 Consumer 重试都保持稳定

比较常见的生成方式是：

- `merchant_id + source_file_hash + row_fingerprint`

其中：

- `source_file_hash` 用来标识这份原始文件
- `row_fingerprint` 用来标识这一行的业务语义
- `merchant_id` 用来隔离不同商家的命名空间

`row_fingerprint` 本身也不能简单拼整行原文，而应该基于真正决定“这是同一条创建意图”的业务字段生成。比如商品名、类目、外部业务主键、规格组合、酒店唯一编码等。否则用户只改了一个无关字段，也可能被错误识别成同一条请求。

#### 第四层：商品域最终幂等收敛

批量侧生成 `idempotency_key` 只是上半场，真正的收口点必须在商品域。因为只有商品域自己最清楚“这次创建到底有没有真正成功落库”。

商品域需要做三件事：

- 接口入参显式接收 `idempotency_key`
- 落一张幂等请求表，记录 `idempotency_key -> product_id`
- 如果收到相同 `idempotency_key` 的重复请求，直接返回第一次成功创建的结果，而不是再次执行创建

这样链路就会变成：

1. 第一次请求到商品域，创建成功，落幂等映射
2. 由于解析恢复或 MQ 重投，第二次请求又到了
3. 商品域发现 `idempotency_key` 已存在
4. 直接返回第一次的 `product_id`
5. 批量侧把该行记为 `SUCCESS`

这也是为什么我不建议把“商品名唯一”直接当成幂等方案。商品名唯一只能拦住重复创建，但它不知道这是不是“同一条请求的重试”，也没法稳定返回第一次结果。真正的幂等，必须靠明确的 `idempotency_key` 来表达。

最后，在结果文件的语义上，我也会做一个明确约束：

- 命中 `idempotency_key` 并复用第一次创建结果，记为 `SUCCESS`
- 真正的数据校验失败、权限失败、模板失败、下游硬失败，才记为 `FAILED`

也就是说，结果文件反映的是“这条业务最终有没有成功达成”，而不是“中间有没有发生过重复投递或重试”。

### 2. 可观测性

我会重点观察这些指标：

- 任务级：待解析数、处理中数、完成数、失败数、平均耗时
- 行级：成功率、失败率、跳过率、重试次数
- 解析级：解析速度、checkpoint 推进速度、租约过期次数
- 消费级：MQ 堆积量、消费延迟、DLQ 数量
- 结果级：错题本生成耗时、归档卡住任务数

### 3. 文件生命周期治理

上传原始文件、行级快照和错题本都需要明确保留周期：

- 原始 Excel 用于追溯，但不应长期无限保留
- 错题本通常保留一个排障周期即可
- 如果后续引入对象快照或行级中间态，也要明确 TTL 和清理策略

### 4. 权限与模板治理

批量任务的很多失败，其实不是技术失败，而是模板治理失败。所以系统还要考虑：

- 模板版本控制
- 不同角色的字段编辑权限
- 模板字段和商品模型的一致性校验

## 七、面试里可以怎么收束

如果面试官问一句“你觉得这个设计最核心的价值是什么”，我会这样总结：

> 我做的不是一个简单的 Excel 导入功能，而是一套高交互异步的批量任务系统。它通过任务化、分阶段、行级解耦和结果归档，把原本不可恢复、不可追责、不可扩展的串行流程，升级成了一个可观测、可恢复、可局部补偿的工业级批量处理链路。
