# 长链路的供应商商品同步流水线设计和实现

## 一、背景 / 痛点

这个项目的背景是：我们需要从外部供应商同步酒店商品、房型、价格和上下架状态等数据到平台内部系统。表面上看，它像一个普通的数据同步任务，但实际上它是一个**典型的超长链路、慢源、高风险**系统。

它的核心痛点主要有五个：

- **数据量大**：一次全量同步可能涉及大量酒店、房型、价格日历和上下架对象，天然带来长任务、批量写入、MQ 堆积和状态跟踪压力。
- **上游慢且不稳定**：供应商接口 QPS 受限，容易出现限流、超时、5xx、游标失效等问题。
- **任务生命周期很长**：一次全量同步可能持续数小时，甚至超过 10 小时，任务很容易因为容器重启、进程退出或网络抖动而中断。
- **下游发布有资损风险**：因为上游拉取与下游发布之间存在时间差，MQ 堆积期间平台侧可能已经发生人工修改，存在“旧数据覆盖新数据”的风险。
- **缺席数据处理风险高**：在全量同步模式下，如果供应商少传数据，系统可能错误地把正常商品识别成“缺席”，从而触发误下线。

我对这个问题的理解是：这不是一个简单的“拉一批 JSON 再写库”的任务，而是一条需要强治理能力的长链路数据流水线。

## 二、主方案设计

### 1. 总体思路

主方案上，我没有采用“一个 Worker 从头跑到尾”的纯串行黑盒架构，而是采用了**分阶段流水线**的设计。这样做的目标是把“拉取的不稳定”“转换的复杂性”“发布的治理权”拆开处理。

为了让这个方案更容易解释，我借用了 ETL 的经典心智：

- **Extract（抽取）**：稳定地从供应商侧把原始数据拉回来
- **Transform（转换）**：把外部语义翻译成平台标准语义
- **Load（加载）**：把标准对象安全落到平台正式主域

这个表达方式的好处是，技术评审和面试时认知成本更低，听众能快速建立理解。

### 2. Extract：抽取阶段

Extract 阶段的目标是“**忠实搬运，不改语义**”。

主要职责包括：

- 调用供应商 API
- 处理鉴权、限流、超时、重试
- 维护任务级 `current_checkpoint`
- 容器重启或任务迁移后，从 `current_checkpoint` 自动续跑
- 将原始响应保存为 `RAW snapshot`
- 额外落一份原始数据到 HBase，作为可回放底座

这里我做了一个重要约束：

- **同一时刻只允许一个 Fetcher 运行**

原因很简单：供应商属于典型慢源，并发拉取只会把外部接口打挂，不会真正提升吞吐。

此外，如果供应商侧能提供更新时间、水位或版本号，我会把它作为**候选短路信号**，辅助识别“可能未变化”的对象。但这里我不会直接根据它做最终跳过，因为“本次没变化”不代表“上次已经成功落地”。

还有一个关键约束是：**版本号要在 Fetch 阶段就带上。**  
也就是说，对象在被拉取下来时，就会绑定本次同步使用的时间戳版本 `publish_version`，后续在 Transform、Load、错误治理链路里持续透传，而不是等到最终写入时再临时生成。这样做的好处是整条链路对“这份数据属于哪个版本”有统一认知，也更方便后续做写前保护、冲突判断和问题追踪。

### 3. Transform：转换阶段

Transform 阶段的目标是“**消除异构，形成平台标准对象**”。

它的输入是 `RAW snapshot`，输出是平台标准酒店模型。

主要职责包括：

- 外部字段映射
- 数据标准化
- 基础校验与风险标注
- 生成标准对象快照

这里我刻意控制了边界：

- **Transform 只负责翻译，不负责最终发布裁决**

原因是它虽然看得到原始数据，但看不到最终正式商品主权，因此不适合在这里直接做线上覆盖判断。

在这一阶段，我会额外生成两类辅助信息：

- `normalized_hash`：标准化后的对象哈希，用于语义级去重
- `field_version_map`：记录本次变更涉及哪些字段，用于后续字段主导权判断

### 4. Load：加载阶段

Load 阶段的目标是“**版本保护，安全落盘**”。

它的输入是标准酒店模型，输出是持久化与发布结果。

主要职责包括：

- 投递发布消息或调用商品主域写侧
- 基于时间戳版本 `publish_version`、锁定状态、字段主导权做写前保护，并通过乐观锁控制最终写入
- 记录 `SUCCESS / FAILED / SKIPPED`

这里的版本策略我倾向于设计成：

- 在 Fetch 阶段以时间戳生成 `publish_version`
- 每次写入前先读取线上当前版本
- 只有当本次版本新于线上版本时，才允许继续写入
- 最终通过乐观锁更新，防止并发写覆盖

这一步是整条链路中最重要的治理关口，因为它决定了：

- 这条数据能不能真正进入正式系统
- 会不会覆盖平台人工数据
- 会不会把旧数据重新写回线上

## 三、主要难点与应对措施（决策点）

### 1. 为什么不用纯串行 Worker？

纯串行架构看起来简单，但它会把抽取、转换、发布、治理四种不同复杂度的问题，全部锁死在一个执行上下文里。

我选择分阶段架构，主要是因为它能带来几个关键收益：

- **失败域更小**：拉取失败、转换失败、发布失败可以分开治理
- **恢复成本更低**：从“整任务重跑”降级为“从 checkpoint 续跑”
- **上游与下游解耦**：上游慢拉保护稳定性，下游异步并发消峰
- **语义边界更清晰**：谁负责采集，谁负责翻译，谁负责发布，一目了然

### 2. 为什么要坚持单 Fetcher 串行？

因为这个场景的瓶颈不在平台内部，而在外部供应商。

如果并发拉取：

- 会加速打满供应商 QPS
- 会放大超时和限流问题
- 会让失败恢复更复杂

所以我的策略是：

- **Extract 串行慢拉**
- **Load 之后再用 MQ 并发消峰**

这是典型的“上游保稳定、下游吃吞吐”的设计。

### 3. 为什么要落 HBase RAW snapshot？

因为长链路任务最怕中间态丢失。

把原始数据额外落到 HBase，有几个价值：

- 可断点续传
- 可离线复算
- 可问题追责
- 可全链路回放

这样系统就不是“失败了只能重拉”，而是“失败了还能基于已拉取的原始数据恢复”。

这里还有一个很重要的落地细节：**HBase 作为 RAW snapshot 存储时，必须自带清理策略。**

因为随着时间推移，HBase 会累积大量过期 snapshot，如果没有自动清理机制，就会带来：

- 存储膨胀
- HFile 碎片增多
- Compaction 压力上升
- 运维成本变高

我的做法是：

- 把这些 RAW snapshot 明确定位成“用于断点续传、离线复算和故障回放的中间态数据”
- 它们的生命周期通常只需要覆盖 `1 ~ 2` 个全量同步周期
- 例如按 7 ~ 14 天保留即可

所以在 HBase 表设计上，我会直接在对应的 Column Family 上配置 TTL，例如：

- `TTL = 14 Days`

让 HBase 自动淘汰过期 snapshot，而不是依赖人工清理脚本。这样可以让这套 RAW snapshot 机制具备更强的自愈能力和更低的长期维护成本。

### 4. 为什么要做语义级去重？

我不希望系统把“没变化的数据”也一遍遍往下游推。

所以我做的是**平台标准语义去重**，而不是简单的主键去重：

- Extract 层防重复拉取
- Transform 层通过 `normalized_hash` 判断语义是否真的变化
- Load 层结合 `state_ledger` 和 `field_version_map` 做最终跳过判断

这样可以明显减少：

- 无效 MQ 消息
- 无意义落库
- 下游索引刷新
- 同步噪音

### 5. 为什么前置过滤不能直接做最终跳过？

这是一个很容易被忽略的坑。

如果只看“供应商侧更新时间没变”，就直接在前面过滤掉，可能会出现这种问题：

- 上一次后链路处理失败
- 本次源数据刚好也没变化
- 结果本次被前置过滤
- 这条数据就永远没有机会再更新

所以我的原则是：

- 前置过滤只能作为**弱信号**
- 最终是否跳过，必须结合 `state_ledger` 中最近一次是否 `SUCCESS` 一起判断

也就是说：

> 不能把“没变化”当成“没必要处理”；只有“没变化 + 上次成功落地”才能安全跳过。

#### 补充：轻量版任务管理

如果项目早期更重视快速落地，那么治理层可以先简化成：

- `supplier_sync_task`
- `supplier_sync_batch`
- 错误重试队列

这样先解决：

- 主链路失败不阻塞
- 失败对象可以异步回放

#### 补充：链路可观测性与 `trace_id`

我会在对象进入主链路时生成一个对象级 `trace_id`，并在 Extract、Transform、Load、错误治理链路里全程透传。这样原始抓取、HBase 快照、标准化结果、最终发布和失败重试都能被同一个 `trace_id` 串起来。出现“为什么没更新、为什么被跳过、为什么发布失败”这类问题时，就可以基于一条 trace 做端到端排查，而不是靠对象主键和时间戳在多个系统里盲查。

## 四、可能的异常与处理

### 1. 供应商接口超时、限流、5xx

处理方式：

- 限流保护
- 重试
- checkpoint 续跑
- 必要时进入错误重试队列

### 2. 容器重启或任务漂移

处理方式：

- 基于 `current_checkpoint` 自动恢复
- 不人工从头重启整条链路

### 3. 数据在 MQ 中排队太久，平台侧已发生新修改

处理方式：

- Load 阶段实时反查 `publish_version`
- 判断锁定状态
- 配合 CAS 做写前保护
- 命中冲突后执行 `REJECT_STALE_OR_LOCKED`

### 4. 全量同步少传导致误下线

处理方式：

- 不在行级消费时直接做下线裁决
- 改成批次级收尾动作
- 基于批次起始时间识别缺席集
- 增加比例熔断
- 超阈值报警并人工介入

### 5. 局部对象处理失败

处理方式：

- 主链路只负责写失败证据
- 失败对象进入 `supplier_sync_error_task`
- 由异常治理模块判断：
  - 自动重试
  - 延迟重试
  - 人工接管
  - 柔性补偿

## 五、后续可优化项（后续可以演进路径）

### 1. 不同阶段通过 MQ 串联，如何处理丢数据和重复数据？

这三个阶段通过 MQ 串联时，理论上既可能出现**消息丢失**，也可能出现**消息重复**。但这两个问题的处理思路不一样：

- **丢消息**的核心是“这条数据后来完全没有机会被处理”
- **重复消息**的核心是“这条数据被重复处理了多次”

在工程实践里，我通常会默认：

- **重复消息是常态，要靠幂等消化**
- **消息丢失是高风险问题，要靠补偿和对账兜底**

具体处理方式如下：

#### 对重复消息的处理

MQ 天然可能出现至少一次投递，所以重复消费不能完全避免。这时重点不在“禁止重复”，而在“重复也不出错”：

- Extract 阶段依赖 `current_checkpoint`，避免重复拉取同一页
- Transform 阶段依赖 `normalized_hash`，避免重复翻译无变化对象
- Load 阶段依赖 `state_ledger`、`publish_version`、乐观锁和字段主导权判断，确保重复消费不会重复落库或错误覆盖

也就是说，**MQ 重复消息本身不可怕，只要下游是幂等的，它最终只会收敛成一次有效状态变更。**

#### 对消息丢失的处理

消息丢失更麻烦，因为它意味着某条对象可能根本没进入下一个阶段。这个问题通常不能只靠 MQ 自己解决，而要靠“消息 + 状态 + 补偿”联合兜底：

- 关键中间态先落地，例如 `RAW snapshot` 落 HBase
- 投递消息前后要有状态记录，至少能知道“该发没发、发了没消费”
- 消费侧处理完成后要回写状态，避免链路静默断掉
- 定时做批次级对账，扫描“应该处理但迟迟没有成功状态”的对象
- 对缺失对象补发消息，或者进入 `supplier_sync_error_task`

所以更准确地说，**MQ 只负责阶段解耦，不负责最终一致性；最终一致性要靠状态台账、重试补偿和批次对账来保证。**

#### 总结这个问题

如果面试官问“MQ 串联会不会丢数据或重复数据”，我会直接回答：

> 会，重复和丢失都可能发生。重复是典型的至少一次投递问题，所以要靠幂等设计解决；丢失则不能只靠 MQ，要结合 RAW snapshot、状态记录、批次对账和错误补偿机制一起兜底。换句话说，MQ 解决的是解耦问题，不单独解决最终一致性问题。

### 2. 轻量版治理先行

如果项目早期更重视快速落地，那么治理层可以先简化成：

- `supplier_sync_task`
- `supplier_sync_batch`
- 错误重试队列

这样先解决：

- 主链路失败不阻塞
- 失败对象可以异步回放

### 3. 再升级到对象级状态台账

当系统进入强治理阶段，再补：

- `supplier_sync_state_ledger`

它能承接：

- 对象级状态归档
- 对账
- 全量缺席识别
- 写前保护
- 审计与人工介入

### 4. 增加 Change Detector

可以在 `Transform` 和 `Load` 之间增加独立的 `Change Detector` / `Delta Filter`：

- 专门判断“这条数据值不值得继续推”
- 进一步减少无效推送和下游写放大

### 5. 字段主导权划分

不是所有字段都应该由供应商覆盖。

例如：

- 价格、房态、上下架状态，供应商主导
- 标题、卖点、运营标签，平台主导

这要求系统在 Load 阶段具备字段级主导权判断，而不是做整对象粗暴覆盖。

### 6. 幂等性

整个链路都要考虑幂等：

- 重复拉取不能重复处理
- 重复消费不能重复落库
- 重复发布不能污染正式状态

### 7. 可观测性

至少要能看到：

- 任务级进度
- 批次级水位
- 对象级 `SUCCESS / FAILED / SKIPPED`

否则长链路任务很容易重新退化成黑盒。
