System Design Primer

第 5 章 长生命周期业务流程方法论：状态机、编排、审批与恢复

本章讨论的不是“某个关键节点怎么一次性做对”，而是“一个业务对象如何在多个阶段中被持续推进、暂停、回退、超时、审批、恢复和审计”。读完这一章，你应该能区分：什么问题只是一个大事务，什么问题已经演化成长生命周期业务流程，以及状态机、Workflow、事件驱动和人工介入分别该放在什么位置。

上一章讲的是大事务。大事务解决的是一个关键时刻的一致性问题，例如创单时锁库存、占优惠、落订单，或者发布时更新主数据、推送索引、发送事件。

这一章讨论的是另一个层次的问题：

当一个业务对象要跨创单、支付、履约、售后，或者跨 Draft、审核、发布、下线等多个阶段持续推进时，系统该如何管理它的生命周期。

这里要明确一个边界：

  • 大事务，关注的是某个关键业务动作怎么最终收敛。
  • 长生命周期业务流程，关注的是业务对象如何跨阶段推进、治理和恢复。
  • Workflow，只是长生命周期业务流程的一种实现手段，而不是总概念本身。

例如：

  • 订单从创单到支付、履约、售后，是长生命周期业务流程。
  • 其中“创单”这一步里的锁库存、占优惠、落订单，是大事务。
  • 商品从 Draft -> QC Approval -> Publish -> Unpublish，也是长生命周期业务流程。
  • 其中 Publish 节点内部的数据更新与下游同步，则可能用 Saga 处理。

5.1 问题定义：什么叫长生命周期业务流程

长生命周期业务流程，指的是一个业务对象不会在一次请求内闭环完成，而是要跨多个阶段、多个系统、多个角色、多个时间窗口持续推进。

它通常具有几个共同特征：

  1. 有明确阶段：例如待创建、待支付、待履约、已完成。
  2. 有等待点：要等用户支付、等供应商响应、等人工审批、等外部回调。
  3. 有角色切换：用户、系统、运营、客服、风控、审核员都可能参与。
  4. 有暂停与恢复：流程可能挂起几分钟、几小时，甚至几天。
  5. 有治理要求：必须知道现在走到哪一步、为什么卡住、谁能继续推进。

所以长生命周期业务流程的核心问题不是“接口怎么调”，而是：

如何让业务对象在跨时间、跨角色、跨系统的现实里，仍然保持可解释、可推进、可恢复。

5.2 约束与指标：为什么不能用大事务思维替代长流程思维

很多团队在系统早期，会把所有复杂问题都理解成“大事务再加几个状态”。这在短期内看起来省事，但一旦流程拉长，就会开始失控。

原因在于，大事务和长流程关注的是两个不同的问题：

维度大事务长生命周期业务流程
关注对象一个关键业务动作一个业务对象的完整生命周期
时间跨度通常秒级到分钟级分钟、小时、天甚至更长
核心问题如何最终一致如何持续推进与治理
典型能力补偿、幂等、回滚、对账状态流转、审批、超时、人工介入、恢复
实现手段Saga、TCC、Outbox状态机、Workflow、编排器、事件驱动

如果把长流程只当成一个加长版大事务，通常会出现几类问题：

  • 把所有状态都塞进一个“超大 Saga”里，最后没人能解释流程边界。
  • 为了等支付、等审核、等供应商，长期持有“事务进行中”的语义，系统状态越来越脆弱。
  • 审批、驳回、重提、超时取消、人工补单这些动作没有被建模成正式流转，只能靠脚本和人工改库兜底。

所以必须建立一个判断：

当问题的核心从“这一步怎么做对”变成“整个生命周期怎么治理”时，就应该切换到长流程方法论。

5.3 完整案例：哪些场景天然属于长生命周期业务流程

5.3.1 订单生命周期管理

订单并不是“创单成功”就结束，而是会继续进入：

  • 创单
  • 支付
  • 风控审核
  • 履约
  • 签收
  • 售后
  • 关闭

这里的复杂度主要来自：

  • 每个阶段都可能由不同系统主导。
  • 支付和履约之间有明显等待点。
  • 售后、退款、逆向履约会把流程重新拉回中间阶段。
  • 客服、运营、仓库都可能参与人工处理。

所以订单本质上是一个长生命周期业务对象。

5.3.2 商品生命周期管理

商品系统里也经常有类似链路：

  • Draft
  • Editing
  • Submitted
  • QC Approval
  • Published
  • Archived 或 Unpublished

它的复杂度来自：

  • 商家编辑可能持续几天。
  • 审核节点通常需要人工或半自动处理。
  • 审核不通过会退回前一个阶段。
  • 发布后还会涉及搜索、推荐、详情、运营活动等下游同步。

这显然不是一个大事务，而是一个典型的生命周期流程。

5.3.3 退款、入驻、审批与结算流程

还有一些场景天然带有流程属性：

  • 退款申请 -> 审核 -> 退款执行 -> 回写结果
  • 商家入驻 -> 资料提交 -> 风控校验 -> 合同审批 -> 开店
  • 账单生成 -> 对账 -> 差异确认 -> 结算付款

这些流程的共同点是：

  • 阶段边界清晰。
  • 等待和审批很多。
  • 经常需要人工接管。
  • 需要正式审计记录。

5.4 核心模型：长流程系统真正要设计的是什么

很多人说“我们上个 Workflow 就好了”，但这句话跳过了最关键的设计层。

长流程系统真正要设计的，不是某个引擎，而是下面这几件事。

5.4.1 流程阶段

先定义清楚业务对象一生要经历哪些阶段。

例如订单可以是：

  • PENDING_CREATE
  • PENDING_PAYMENT
  • PAYMENT_PROCESSING
  • PENDING_FULFILLMENT
  • IN_FULFILLMENT
  • COMPLETED
  • CANCELLED

例如商品可以是：

  • DRAFT
  • SUBMITTED
  • UNDER_REVIEW
  • REJECTED
  • PUBLISHED
  • UNPUBLISHED

没有阶段定义，就不会有后面的治理能力。

5.4.2 流转规则

不是所有状态都能互相跳转。系统必须显式定义：

  • 哪些状态可以进入下一个状态
  • 哪些状态允许回退
  • 哪些状态只能人工推进
  • 哪些状态在超时后自动转移

这一步本质上是在设计生命周期状态机。

5.4.3 等待点与唤醒条件

长流程一定会遇到等待：

  • 等支付回调
  • 等审核员处理
  • 等物流回传
  • 等外部系统补数

每个等待点都必须回答：

  1. 等的是什么事件？
  2. 最长等多久？
  3. 超时后转到什么状态？
  4. 谁有权限继续推进？

5.4.4 人工介入与审计

长流程一旦进生产，人工介入几乎不可避免。真正成熟的设计不会回避它，而是会把它纳入正式模型：

  • 谁可以审批、驳回、跳过、重试、关闭
  • 每次人工动作是否有理由、操作者和时间
  • 哪些动作需要双人复核
  • 人工介入后如何恢复自动推进

也就是说，人工介入不是“系统失败后的非正式补丁”，而是流程治理的一部分。

5.5 参考架构：四种主流实现路线

围绕长生命周期业务流程，常见实现路线大致有四种。

5.5.1 纯数据库状态机

做法是把生命周期状态放在业务主表里，由应用服务按规则推进。

优点：

  • 简单直接。
  • 与业务模型贴合。
  • 适合阶段有限、主控方明确的流程。

缺点：

  • 流程一复杂，状态转移逻辑会散落在多个服务里。
  • 超时、审批、回放、观察能力需要自己补齐。
  • 长期容易演化成一堆难维护的条件分支。

它适合较短但明显分阶段的流程。

5.5.2 应用层编排器

做法是引入一个专门的 Orchestrator，由它负责推进主流程，业务服务负责完成各节点动作。

优点：

  • 主流程视角更清晰。
  • 超时、重试、补偿、通知更容易集中治理。
  • 很适合订单履约、退款审批、发布编排这类主控方明确的流程。

缺点：

  • 编排器本身会成为一个复杂系统。
  • 状态、权限、审计、重试策略都要认真设计。

它适合流程复杂度已经超出单个业务服务承载能力的场景。

5.5.3 Workflow 引擎

做法是把流程状态持久化、等待、超时、回放、人工任务等能力，进一步交给专门的工作流系统承载，例如 Temporal、Camunda、Zeebe。

优点：

  • 对长期运行流程很友好。
  • 更容易提供可视化、审计、人工任务、超时和恢复能力。
  • 能更系统地处理“等待外部事件再唤醒”的模式。

缺点：

  • 引入成本更高。
  • 团队需要建立新的建模和运维能力。
  • 如果流程并不复杂，可能过度设计。

这里要再次强调：Workflow 只是方法，不是总概念。

5.5.4 事件驱动流程

做法是多个系统通过事件彼此驱动，不一定有一个强中心编排器。

优点：

  • 系统耦合低。
  • 能沿着领域边界自然扩展。
  • 对多团队自治环境友好。

缺点：

  • 全局可见性较弱。
  • 审计、排障、人工介入更难。
  • 没有强约束时，流程边界容易失控。

它更适合主控方不强、但领域事件天然存在的场景。

5.6 长流程里的关键能力

无论采用哪种实现路线，真正决定系统是否可生产的，往往是下面这些能力。

5.6.1 状态持久化

系统必须记住：

  • 当前处在哪个阶段
  • 已完成哪些动作
  • 正在等待什么
  • 最近一次失败原因是什么

5.6.2 超时治理

每个阶段都要考虑：

  • 正常多久完成
  • 超时后自动取消、重试还是转人工
  • 超时是否影响上下游协同

5.6.3 恢复与重入

流程中断后，系统必须能回答：

  • 能不能从当前状态继续
  • 能不能安全重试
  • 哪些动作已经产生副作用，不能重复执行

5.6.4 观察与审计

要能快速看到：

  • 一个流程实例当前卡在哪
  • 上一步是谁推进的
  • 为什么失败
  • 最近一次人工介入做了什么

5.6.5 子节点内的大事务

这也是和上一章最重要的连接点：

长流程的每个关键节点内部，往往还会嵌套一个大事务。

例如：

  • 订单生命周期里的“创单”节点，内部可能用 Saga 处理库存、营销、订单创建。
  • 商品生命周期里的“发布”节点，内部可能用 Saga 处理主数据、索引、缓存、事件。
  • 退款生命周期里的“执行退款”节点，内部可能用补偿事务处理支付、权益、账务回冲。

所以实际系统中常见的组合不是二选一，而是：

  • 长流程方法论 管生命周期
  • 大事务方法论 管关键节点一致性

5.7 方案选型：一个务实的选型框架

可以用下面几个问题来判断是否应该升级为长流程系统：

  1. 这个业务对象是否要跨多个阶段存在，而不是一次请求内结束？
  2. 是否存在等待点，例如支付回调、审核、外部响应？
  3. 是否需要回退、驳回、重提、暂停、恢复？
  4. 是否经常要人工介入？
  5. 是否需要对外解释“它现在卡在哪、下一步是谁处理”？

如果上面大部分答案都是“是”，那它已经不再只是一个大事务，而是长生命周期业务流程。

进一步选型时，可以参考：

场景特征推荐方案
阶段有限、等待少、主控服务明确数据库状态机
阶段较多、超时和通知复杂、需要统一主视角应用层编排器
长等待、审批多、恢复和审计要求高Workflow 引擎
多系统自治、领域事件天然存在、中心编排意愿弱事件驱动流程

5.8 方法论沉淀：如何在真实系统中做出选择

到这里可以把整章压缩成一组可复用判断。

5.8.1 五个判断句

  1. 只要一个业务对象要跨多个阶段长期存在，它就不是单次请求问题，而是生命周期问题。
  2. 只要流程里有等待、审批、驳回和人工接管，就不要再用“大事务延长版”去硬扛。
  3. 生命周期系统的核心不是“接口调用顺序”，而是“阶段、流转规则、等待点和恢复点”。
  4. Workflow 只是长流程的一种实现方式，不是总概念；先定义流程治理模型，再决定是否引入引擎。
  5. 真实系统里最常见的组合是：用长流程管理生命周期，用大事务保证关键节点一致性。

5.8.2 面试与评审中的一句话表达

如果要把这一章压缩成一句可直接复用的话，可以这样讲：

长生命周期业务流程方法论，解决的不是某个关键动作怎么一次做完，而是一个业务对象如何跨阶段被持续推进、被明确治理、在异常时被安全恢复；状态机、编排器和 Workflow 只是不同复杂度下的实现手段。

5.9 先建模“业务状态”，再选择引擎

很多流程项目的起点是“需要一个审批流”或“需要接入 Workflow 引擎”。这种起点很容易把技术工具放在业务模型之前。更稳妥的顺序是：先定义业务对象在什么状态、谁能发起什么动作、动作满足什么条件、动作发生后会产生什么事实；只有这些确定后，才判断是否需要编排器或流程引擎。

以订单为例，状态不是一串展示给前端的枚举，而是一份业务契约。一个相对清晰的模型可以分为三层：

层次示例作用
主生命周期状态PENDING_PAYMENT、FULFILLING、COMPLETED、CLOSED表达订单对外可见的阶段
子流程状态支付处理中、拣货中、退款审核中表达并行或局部流程的推进位置
原因与上下文关闭原因、拒绝理由、超时时间、操作人解释为什么进入当前状态

不要把所有细节压进一个 status 字段。例如“订单已关闭”不能说明它是用户主动取消、支付超时、风控拒绝还是履约失败；这些原因会决定后续能否重开、是否释放资源、是否允许退款和谁有操作权限。主状态应保持稳定而有限，原因、版本、期限和外部引用应以独立字段或事件记录保存。

状态变化应该由命令触发，由事件记录，而不是让任意服务直接更新状态。可以把三者区分为：

  • 命令表达意图，例如“提交支付”“审核通过”“申请取消”。命令有发起者、权限和校验条件。
  • 状态是当前已被确认的业务事实，例如“等待支付”“履约中”。
  • 事件描述已发生的变化，例如 PaymentSucceeded、OrderCancelled。事件可供通知、统计和下游协同使用。

这种区分会让“谁有权改变订单状态”变得可评审。支付服务可以提交“支付成功”事实，但不应随意将订单置为“已完成”；订单域根据当前状态、订单版本和履约条件决定是否接受该事件，并写下正式的状态迁移。

5.10 故障与治理：流转规则、并发控制与不可达状态

一张状态图只有画出箭头还不够，每一条箭头都需要明确四件事：触发动作、守卫条件、产生的副作用和失败后的去向。以“待支付订单取消”为例，规则不应只是 PENDING_PAYMENT -> CLOSED，而应说明：

  1. 触发者可以是用户取消请求，也可以是支付超时定时器。
  2. 守卫条件是订单仍处于可取消状态、未被支付成功回调确认、当前版本未发生冲突。
  3. 副作用包括关闭支付入口、触发库存与优惠释放等关键节点；这些副作用由第 4 章的大事务机制收敛。
  4. 如果释放资源结果未知，订单进入 CLOSING 或“待确认”子状态，而不是直接宣称关闭完成。

把状态迁移写成受控规则后，系统自然会避免一些不可达或矛盾的状态：已关闭订单不能再次发货，已完成订单不能直接跳回待支付，已拒绝的商品不能绕过重新提交直接发布。复杂流程往往不是因为状态数量多，而是因为这些禁止路径没有被明确表达，最后变成散落在 Controller、定时任务和运营脚本里的条件判断。

并发控制是长流程不可缺少的一部分。支付回调、用户取消、客服补单和超时任务可能同时到达。推荐至少使用一种乐观并发策略：

UPDATE orders
SET status = 'CLOSED', version = version + 1
WHERE order_id = :order_id
  AND status = 'PENDING_PAYMENT'
  AND version = :expected_version;

受影响行数为零时，不应立即报系统错误，而应重新读取权威状态，判断是重复请求、正常竞态还是业务冲突。版本号、状态条件和幂等键共同构成迁移保护：版本防止旧请求覆盖新事实，状态条件防止非法跳转，幂等键防止同一命令重复产生副作用。

5.11 等待、定时器与外部事件：长流程如何“活着但不占用资源”

长流程的本质不是让线程一直等待，而是把等待条件持久化，在条件满足时重新唤醒。因此每一个等待点都应成为正式模型的一部分，而不是某个 RPC 的超时参数。

等待类型等待对象唤醒方式超时后的默认策略
用户行为支付、确认收货、补充材料页面操作或回调取消、提醒或转人工
外部系统物流回传、供应商确认、风控结果事件、轮询或回调查询、有限重试、冻结流程
人工处理审核、客服裁决、财务复核待办完成升级、转派或按规则终止
时间窗口支付截止、售后时效、发布窗口定时器自动迁移并生成审计事件

定时器必须和业务状态绑定。仅靠一个每天扫描数据库的 Cron，往往会出现重复触发、扫描延迟和处理范围不可控的问题。更可靠的做法是为流程实例保存 next_action_at、超时策略和定时任务标识；调度器负责把“到期的意图”投递为幂等命令，业务状态机仍然负责决定该命令在当前状态下是否有效。

外部事件同样不能默认可信。迟到的物流事件、重复的支付回调和顺序颠倒的供应商通知都很常见。处理事件时至少要验证：事件关联的业务主键、来源身份、事件版本或发生时间、当前流程状态，以及该事件是否已经处理。对于可能乱序的事件，不能简单按收到时间覆盖状态，而应依据权威版本、领域规则或补偿流程收敛。

5.12 人工任务不是例外：权限、审计与回到自动化

审批、驳回、人工补单和客服裁决经常被当成“系统自动化失败后的兜底”。实际上，人工节点是很多业务流程的正常组成部分。将其正式建模，可以避免权限越权、责任不清和人工操作后流程停滞。

一个可治理的人工任务至少需要包含：任务所属流程实例、当前处理阶段、候选处理人或角色、可执行动作、截止时间、处理结果、理由和证据链接。动作必须受状态机约束。例如审核员可以“通过、驳回、要求补件”，但不能直接把商品从草稿设为已发布；客服可以申请人工关闭订单，但高价值订单可能还需要风控或财务复核。

权限设计应同时考虑角色和对象范围：谁能处理什么类型的流程、在什么组织或商家范围内处理、金额或风险等级超过阈值时是否需要升级。所有人工动作需要记录操作者、时间、前后状态、理由和关联附件。审计记录不是为了追责才保留，它也是恢复自动流转的输入：一个被驳回的入驻申请，必须知道需要补什么材料；一次人工放行，必须让下游知道它是例外路径而非正常规则。

人工节点完成后，流程不应依赖运营人员再去“点一下继续”。系统应把结果转换成正式命令或事件，按既定规则进入下一阶段；如果需要人工确认后才触发关键大事务，也应由流程实例发起可追踪的编排，而不是由后台脚本越过业务边界。

5.13 恢复、重放与流程演进

长流程运行数天甚至数月时，恢复不能依赖内存，也不能假设流程定义永远不变。需要分别处理执行中断、历史重放和规则升级三类问题。

执行中断时，系统先恢复流程实例的持久化状态、最近成功的动作和正在等待的条件，再决定是否重试当前动作。重试必须沿用原有幂等键，不能生成一笔新的业务意图。对于已产生外部副作用但结果未知的节点，应先查询或对账，而不是直接从前一步重新执行。

事件重放常用于修复投影、补发通知或重建审计视图。它要求事件具有稳定标识和明确语义，也要求消费方幂等。不要把“重放事件”误解为“重新执行全部业务动作”；会产生外部副作用的命令必须有独立的重放策略和审批边界。

流程演进则要求流程定义版本化。比如商品发布流程从“一次人工审核”升级为“质检 + 合规双审核”时，存量实例不能被新规则强行解释。流程实例应保留 process_definition_version，新建实例使用新版本；历史实例可以继续按旧版本完成，或在明确迁移规则和审计记录下转入新版本。没有版本策略的 Workflow，很容易在一次规则发布后让在途流程全部卡住。

5.14 实现路线的真正取舍

选择数据库状态机、应用编排器、工作流引擎或事件驱动，并不是在“简单”和“高级”之间做选择，而是在控制权、运行时能力和治理成本之间取舍。

路线最适合的前提主要代价升级信号
数据库状态机阶段有限、业务主控清晰、等待少定时器、待办、审计要自行建设状态逻辑散落到多个服务
应用编排器主流程明确，跨服务协调逐渐复杂编排服务需要高可用和严格状态管理长等待、人工任务和版本管理显著增多
Workflow 引擎流程长期运行、等待和审批多、需可视化治理新的建模、运维和迁移成本任务调度与流程定义成为平台能力
事件驱动协作多领域自治、没有单一主控方全局可见性和排障成本较高需要补充流程视图、审计和编排边界

无论选择哪条路线，业务状态的权威性都应留在领域模型中。工作流引擎可以托管等待、定时和任务编排，但不应成为所有业务事实的唯一来源；事件总线可以传播变化，但不应替代状态迁移规则。技术平台服务于生命周期模型，而不是反过来定义业务语义。

5.15 流程设计评审清单

在进入实现前，至少逐项回答下面的问题：

  1. 流程对象是什么？它的主状态、子状态和原因字段分别是什么？
  2. 每一条迁移由什么命令或事件触发？谁有权限发起？守卫条件是什么？
  3. 哪些节点要等待？等待条件、截止时间、超时策略和唤醒方式是什么？
  4. 并发命令、重复回调和迟到事件如何处理？
  5. 哪些节点内部存在第 4 章所说的大事务？它们成功或未知时如何反馈给主流程？
  6. 哪些动作需要人工处理、升级或双人复核？审计记录包含什么？
  7. 流程中断、重放和定义版本升级时，如何保持历史实例可解释、可恢复？

把这些问题回答清楚，流程才不是一张“看起来完整”的状态图，而是一套能跨时间、故障、人员变化和规则演进持续运行的业务机制。

5.16 方法论总结：让流程状态成为可治理的业务事实

长流程设计同样可以沿八个问题展开：先定义流程对象与生命周期问题；明确时效、角色、等待和审计约束；再建立状态、命令、事件、版本与守卫条件；用状态存储、定时器、待办和编排器组织执行架构；根据运行时治理需求选择状态机、编排器、引擎或事件协作；通过订单、商品发布等完整案例验证状态迁移；最后用并发控制、重放、版本演进、人工接管和审计应对故障与变化。

流程的本质不是画出更多节点，而是让每一个节点都回答得清：现在处于什么业务事实，谁能推动它，凭什么能推动，等待什么，超时后怎样收敛。第 4 章的大事务保证关键节点内部副作用正确，第 5 章的生命周期模型保证对象跨阶段可治理；两者组合，才能支撑真正长期运行的业务系统。

衡量流程是否设计良好，也不应只看“主路径能否跑通”。更有价值的指标是：在途实例的停留时长、超时节点比例、重复命令被正确拒绝或吸收的比例、人工任务逾期量、状态迁移失败率，以及从异常发现到恢复完成的时间。把这些指标与状态、权限和审计记录关联起来，流程治理才会从经验判断变成可持续改进的工程能力。
