System Design Primer

第 7 章 高准确性与强一致性系统设计方法论：支付、库存与账务场景

当系统面对支付、库存、账务、钱包、积分等“结果必须正确”的业务时，设计重点不再只是流程能不能跑通，而是事实能不能被严格定义、状态能不能被安全推进、错误能不能被可审计地恢复。

前面的章节讨论了大事务、长流程和任务处理。本章进一步收紧问题范围：有些业务流程即使暂时延迟几秒，最终也可以收敛；但有些业务一旦发生重复扣款、库存超卖、账务不平或金额丢失，事后再补偿也无法完全消除影响。

因此，本章不讨论“所有系统都应该强一致”，而是讨论一个更准确的问题：

在高并发、网络不可靠、依赖不确定的条件下，如何识别不可出错的业务事实，如何把这些事实保护在正确的事务边界内，又如何让跨系统流程在失败后继续可解释、可恢复、可对账。

本章采用八步方法：先定义问题，再确定约束和指标；然后建立业务不变量与状态模型；在此基础上设计参考架构，用 ADR 记录方案取舍，最后通过完整交易案例和故障治理验证设计是否真的可落地。

7.1 问题定义：高准确性不等于整条链路都强一致

7.1.1 先区分三个容易混淆的概念

高准确性关注业务结果是否正确。例如：支付金额是否正确、库存是否被重复扣减、账本借贷是否平衡、优惠券是否被重复核销。

强一致性关注多个副本或多个并发操作对外呈现的状态是否满足某种严格的可见性语义。例如，读请求是否能看到已经提交的最新状态，两个并发请求是否会观察到互相矛盾的结果。

业务一致性关注跨多个业务对象或多个服务的整体目标是否最终达成。例如，订单、库存和支付不一定由一个全局事务同时提交，但系统必须最终收敛到“已支付、库存已确认、订单可履约”或者“支付失败、订单取消、库存已释放”。

这三个概念有交集，但不能互相替代。

  • 一个本地数据库事务可能具备很强的隔离性，但如果金额计算规则错误，业务结果仍然不准确。
  • 一个跨系统流程可能不是全局强一致，但只要每个核心事实有唯一权威源、每个状态迁移可验证、每个异常都有补偿和对账，业务仍然可以正确收敛。
  • 一个系统如果只说“最终一致”，却没有定义最终要一致到什么状态、由谁修复、多久必须收敛，那么这不是设计，只是把问题延后。

7.1.2 典型场景和核心风险

场景不可接受的结果可以接受的延迟或中间态
支付重复扣款、金额错误、支付成功但无法识别渠道回调延迟，短时间处于处理中或待查单
库存超卖、重复释放、库存变负、已付款却无货库存预占后等待支付，外围库存视图短暂延迟
账务借贷不平、流水丢失、余额凭空增加或减少统计报表延迟，余额快照异步重算
钱包与额度重复扣减、冻结金额丢失、额度穿透非核心展示延迟，异步通知延迟
积分与优惠券重复发放、重复核销、撤销后无法回收发放通知延迟，营销展示短暂不一致

设计的第一步不是选择数据库或消息队列，而是把“不能错”和“可以晚一点”分别写出来。

7.1.3 本章的范围与非目标

本章聚焦以下问题：

  1. 如何识别不可出错的业务事实和不变量。
  2. 如何选择本地事务、Outbox、预占、TCC、Saga 或对账补偿的组合。
  3. 如何处理请求重试、回调重复、状态未知、消息乱序和跨系统失败。
  4. 如何建立审计、对账、人工接管和恢复机制。

本章不试图展开完整的数据库实现、支付渠道接入协议或财务会计制度。数据库隔离级别、Redis 细节、Kafka 消费模型和订单系统的完整实现，应分别结合本书后续基础设施和电商实战章节阅读。

关于大事务、Saga 和 Outbox 的通用流程可参见第 4 章《大事务处理方法论》；订单和支付的完整领域实现可参见订单系统实战与支付系统实战。本章只保留跨场景的判断框架和关键取舍。

7.2 约束与指标：先把正确性写成可以验证的条件

高准确性系统不能只用“成功率”和“接口延迟”衡量。它必须同时有业务正确性指标、状态收敛指标和恢复能力指标。

7.2.1 四类约束

规模约束：峰值请求量、并发事务数、单资源竞争度、单账户写入频率、跨地域复制距离。

时间约束：支付确认时限、库存预占 TTL、回调等待时间、对账周期、人工接管时限。

正确性约束：金额不能错、库存不能超卖、状态不能逆向跳转、同一幂等键不能产生两个副作用。

治理约束：每条事实必须可查询、可追踪、可对账、可重放；出现差异时必须能定位责任边界。

7.2.2 推荐的指标集合

指标类别示例指标设计用途
业务不变量借贷差额、库存差额、重复扣款数判断事实是否被破坏
状态收敛待支付、处理中、待查单、待补偿数量判断中间态是否堆积
幂等与重复重复请求率、重复回调率、重复消费率判断重试和客户端行为
恢复能力补偿成功率、补偿延迟、人工接管量判断异常闭环质量
对账质量对账差异数、差异金额、自动修复率判断权威事实是否分叉
业务链路支付成功率、库存预占成功率、订单履约成功率连接技术指标与业务结果
性能与容量锁等待、事务耗时、写入吞吐、事件积压判断强一致边界是否成为瓶颈

这些指标不能只看平均值。对于资金和库存，少量严重错误也可能比大量普通请求失败更重要；对于补偿任务，则要同时关注积压数量和最老任务年龄。

7.2.3 用“可验证不变量”替代口号

一个好的不变量必须可以通过约束、查询或对账验证。

  • 库存不变量：可用 + 预占 + 已售 = 总量，且每个分量不能小于零。
  • 账务不变量：每笔记账必须有借方和贷方，借贷金额相等，业务流水号不可重复入账。
  • 支付不变量：同一业务订单在同一支付意图下不能产生两个有效成功扣款。
  • 状态不变量：支付成功不能回退为待支付，库存已确认不能被普通取消动作再次释放。
  • 补偿不变量：每次补偿动作必须关联原始动作，并且重复执行不能制造新的副作用。

《Designing Data-Intensive Applications》将系统记录、派生数据、复制和一致性放在同一套数据系统权衡中讨论，这对本章很重要：先确定哪份数据是事实，再决定哪些数据可以异步派生，而不是先选择一个“看起来可靠”的中间件。《Designing Data-Intensive Applications》第 2 版

7.3 核心模型：事实、状态、不变量和权威源

7.3.1 业务事实必须有唯一权威源

系统中经常同时出现订单状态、支付状态、渠道回调状态、账户余额、账务流水和缓存状态。如果每一层都被当成“真相”，系统就会在异常时陷入争论：到底应该相信哪个状态？

建议为每类关键事实明确权威源：

事实权威源示例其他系统的角色
支付渠道结果支付单和渠道查单结果订单系统消费支付事实
订单状态订单聚合或订单状态机履约、通知、营销读取派生状态
库存数量库存账或库存服务搜索和详情展示缓存视图
资金流水不可变账本余额、报表和风控是派生结果
事件投递Outbox 或事件日志MQ 是传输通道，不是业务事实

缓存、消息和搜索索引都可以很快，但它们通常不应该成为支付金额、库存事实或账本流水的唯一权威源。

7.3.2 状态机比一个布尔字段更可靠

高准确性场景通常不是“成功 / 失败”两个状态，而是包含等待、未知和补偿中的中间态。

支付状态可以抽象为：

待支付 → 支付中 → 支付成功
             ├→ 支付失败
             ├→ 待查单
             └→ 已关闭

库存预占可以抽象为：

可预占 → 已预占 → 已确认
            └→ 已释放

状态机至少应定义：

  • 允许的状态集合。
  • 每个状态的进入条件和退出条件。
  • 哪些迁移由同步请求触发，哪些由事件或定时任务触发。
  • 重复迁移如何返回幂等结果。
  • 发生未知结果时进入什么状态。
  • 超时、补偿和人工操作能否改变状态。

7.3.3 预占模型是资源生命周期模型

“预占 + 确认 / 取消”不是简单的两次接口调用，而是资源生命周期的显式建模。

预占记录至少要包含：资源 ID、业务单号、数量、预占时间、过期时间、当前状态、幂等键和释放原因。确认和释放都必须带上版本或状态条件，避免旧请求把已经确认的资源再次释放。

对于库存、额度、余额冻结和优惠券占用，这种模型通常比“直接扣减、失败再猜测如何回滚”更容易审计。代价是系统需要维护超时扫描、释放任务、重复请求和人工修复。

7.3.4 账本优先于余额字段

余额通常是账本流水的投影，而不是唯一事实。直接修改余额字段会让系统失去解释能力：无法说明余额为什么变化，也无法在发现错误后重放和重算。

更稳妥的结构是：

业务事件 → 记账凭证 → 借贷分录 → 余额投影 → 查询缓存 / 报表

每个记账动作要有唯一业务流水号、金额、币种、账户、来源事件和时间。余额可以被缓存，但账本流水必须可追溯、不可随意覆盖。

7.4 参考架构：核心事实本地原子提交，外围流程可靠收敛

7.4.1 一条可落地的总体链路

高准确性系统的通用链路可以表示为：

请求入口
  → 鉴权、参数校验、幂等校验
  → 核心服务本地事务
       ├─ 写入业务事实
       ├─ 推进状态机
       ├─ 写入预占 / 账本 / 审计记录
       └─ 写入 Outbox 事件
  → 事件可靠投递
  → 下游本地事务和幂等消费
  → 超时扫描、查单、补偿、对账
  → 结果查询与人工接管

这条链路没有试图把所有系统放进一个全局事务，而是把问题拆成三个边界：

  1. 事实边界：关键事实在自己的权威服务内原子提交。
  2. 传播边界：本地提交后的事实通过 Outbox 或日志可靠传播。
  3. 收敛边界：跨系统的业务目标通过状态机、补偿、查单和对账最终收敛。

7.4.2 本地事务与 Outbox 的配合

如果服务需要同时更新业务数据并发布事件，直接先写数据库再发消息会产生双写窗口：数据库提交成功但进程在发消息前崩溃，或者消息发送成功但数据库随后回滚。

Transactional Outbox 的做法是把业务事实和待发送事件写在同一个本地事务中，再由独立 relay 投递到消息系统。该模式不能让消息“只发送一次”，relay 可能在发送成功后、记录发送结果前崩溃，因此消费者仍然必须幂等。Transactional Outbox 和 Idempotent Consumer 对这一点有明确说明。

7.4.3 跨系统流程的主控与补偿

当订单、库存、支付和履约分别拥有自己的数据库时，主控方需要保存流程状态和每一步的结果，而不是只保存一个“订单处理中”字段。

每一步最好记录：

  • 请求和业务幂等键。
  • 发送时间、响应时间和超时时间。
  • 下游返回的业务状态与技术状态。
  • 已执行的动作及其补偿动作。
  • 当前重试次数、下一次重试时间和失败原因。

Saga 适合把跨服务业务事务拆成多个本地事务，并为失败设计补偿；它不是全局原子提交，也不能自动保证补偿一定成功。Saga Pattern

7.4.4 可观测性必须跟随业务事实

只记录 HTTP 状态码不足以排查支付和库存问题。日志、链路和指标必须携带：订单号、支付单号、库存预占号、账务流水号、幂等键、事件 ID 和状态版本。

对于一个“支付成功但订单未更新”的事件，系统至少要能够回答：

  1. 支付事实是否已经落地？
  2. Outbox 事件是否生成？
  3. relay 是否投递？
  4. 订单消费者是否收到并处理？
  5. 订单状态是否因为版本冲突或状态不允许而拒绝更新？
  6. 是否进入补偿、查单或人工队列？

7.5 方案选型：用 ADR 记录获得了什么、牺牲了什么

7.5.1 ADR 不只是写“选择了某个组件”

本章的方案选型必须回答一个问题：在当前约束下，为什么接受一种取舍，而不是另一种取舍。

ADR 至少包含：

  1. 背景和问题。
  2. 决策驱动因素。
  3. 候选方案。
  4. 最终决策。
  5. 获得的能力。
  6. 主动牺牲的能力。
  7. 已接受的风险和缓解措施。
  8. 验证指标与重新评估条件。

7.5.2 方案对比

方案主要获得主要牺牲适用前提
单库本地事务原子性强、语义简单、延迟低跨服务能力弱、扩展边界受限事实可以收敛在一个服务和数据库内
本地事务 + Outbox避免业务数据与事件双写丢失需要 relay、重复投递和消费者幂等核心事实已在本地确定，需要可靠传播
预占 + 确认 / 取消资源生命周期清晰，失败可释放状态更多，需要 TTL、扫描和补偿资源可预留，确认和释放边界明确
TCCTry、Confirm、Cancel 语义显式参与方改造成本高，接口复杂多参与方都有资源预留能力
Saga跨服务流程可推进，参与方自治没有全局瞬时原子性，补偿可能失败每一步有本地事务和可执行补偿
分布式锁解决局部并发互斥不解决事件丢失、账本和跨系统提交只需要保护短时单资源临界区
XA / 2PC统一提交语义直接长事务、锁竞争、可用性和运维成本高参与方受控且确实需要统一提交

7.5.3 示例 ADR：电商创单采用局部原子 + 可靠事件

背景：订单、库存和支付属于不同服务；库存需要预占，支付渠道存在回调延迟和未知状态，外围通知和积分不影响交易事实。

决策驱动因素：不能超卖，不能重复扣款，支付结果必须可查；同时需要承受活动期并发，不能让第三方支付或通知系统成为全局事务参与者。

候选方案：三方 XA / 2PC、TCC、全链路同步 RPC、Saga + Outbox、订单服务单体化。

最终决策：订单服务在本地事务中创建订单和 Outbox；库存采用预占、确认、释放；支付以支付单和渠道查单作为权威事实；跨服务推进使用 Saga 或显式状态机；通知、积分、推荐和报表全部异步化。

获得的能力：

  • 订单事实可以在本地事务内原子落地。
  • 库存有明确的预占和释放语义。
  • 支付未知状态可以通过查单继续推进。
  • 事件可以重试，消费者可以幂等，外围系统可以独立扩缩容。
  • 对账和人工接管有明确的业务对象。

主动牺牲的能力：

  • 不再追求订单、库存、支付三方瞬时原子提交。
  • 用户可能短暂看到“支付处理中”或“订单待确认”。
  • 系统需要维护更多状态、补偿任务和对账任务。
  • 设计和运维复杂度高于单体本地事务。

已接受风险：支付渠道或消息系统发生长时间故障时，订单会积累在处理中；补偿逻辑可能因为下游再次故障而延期；业务需要给用户明确的待确认语义。

验证指标：重复扣款为零，超卖差异为零，Outbox 积压可控，待查单任务在目标时间内收敛，对账差异自动修复率达到目标，人工接管任务有上限。

重新评估条件：单库事务已经成为容量瓶颈、跨地域合规要求改变、支付和库存需要独立扩展，或当前补偿复杂度已经超过引入受控分布式事务的成本。

这个 ADR 的重点不是证明某个方案“最好”，而是让读者看到：设计获得了什么，也明确放弃了什么。

7.6 完整案例：电商创单、支付与库存如何闭环

7.6.1 正常链路

用户提交订单时，结算服务先生成一次结算快照，订单服务验证价格版本、用户资格和幂等键。库存服务创建预占记录，支付服务创建支付单，订单服务把状态置为“待支付”，并通过 Outbox 发布订单创建事件。

用户完成支付后，支付服务先落支付事实，再发布支付成功事件。订单服务消费事件并使用支付单号和事件版本做幂等更新；库存服务收到确认指令，将预占转为已确认；订单进入可履约状态。

这条链路中的关键点是：支付成功不能仅以 HTTP 回调成功为依据，库存确认不能仅以 Redis 预扣为依据，订单成功也不能仅以前端收到响应为依据。每个核心状态都必须有自己的持久化事实。

7.6.2 重复请求与重复回调

客户端可能因为网络超时重复提交订单，支付渠道可能重复发送回调，消息 relay 可能重复投递事件。系统必须把这些重复行为当作正常输入。

入口幂等可以使用业务幂等键和唯一约束；支付回调幂等可以使用“支付单号 + 渠道事件号”；消息消费幂等可以使用事件 ID、状态版本或已处理消息表。

重复请求的结果不应该简单返回“重复错误”，而应返回原始业务结果。例如第一次请求已经创建订单，第二次请求应返回同一个订单号，而不是重新创建订单或让用户陷入未知状态。Stripe 的幂等请求设计也采用保存第一次请求结果的方式，说明幂等键不仅用于去重，还用于在网络失败后恢复一致的响应语义。Stripe Idempotent Requests

7.6.3 超时和未知结果

最危险的情况不是明确失败，而是请求在服务端可能已经成功执行，但客户端没有收到响应。

例如支付请求发出后连接断开，客户端不能立即认为支付失败，也不能无限次用新支付单重试。正确的处理是：保留原支付单号，进入“待查单”，通过渠道查询、回调或人工核验确认最终结果。

同理，库存确认超时后不能立即重复扣减；订单创建超时后不能只依据客户端响应判断。所有未知结果都需要显式状态和后续确认任务。

7.6.4 失败与补偿

常见失败路径如下：

失败点已完成事实后续动作
预占失败订单草稿可能存在订单置为库存不足，禁止进入支付
支付失败库存已预占关闭支付单，释放库存，订单取消
支付成功但订单未更新支付事实已落地重投支付事件或主动查支付状态
支付成功但库存确认失败资金事实和订单可能已成功进入异常履约或退款流程，不能静默丢失
订单创建成功但 Outbox 未投递本地订单事实已落地relay 重试，不能重新创建订单
预占超时资源仍被锁定释放任务按状态版本安全释放

补偿不是简单的“把状态改回去”。退款、库存释放和账务冲正都可能是新的业务动作，因此补偿动作本身也必须有幂等键、流水和审计记录。

7.7 故障与治理：把异常闭环做成一等能力

7.7.1 对账设计

对账应先明确三件事：比较双方、比较口径和允许窗口。

  • 支付对账：渠道成功记录与本地支付事实逐笔比较。
  • 订单对账：订单状态与支付、履约结果比较。
  • 库存对账：库存账、预占记录、订单已售记录比较。
  • 账务对账：业务流水、总账分录、余额快照比较。

差异至少分为：数据延迟、重复记录、缺失记录、金额差异、状态冲突、超时未收敛和无法自动判断。自动修复只能覆盖确定性差异；金额不明或跨系统冲正必须进入人工队列。

7.7.2 审计和人工接管

人工接管不是承认系统失败，而是高准确性系统在不可判定状态下的安全边界。人工操作必须：

  • 使用专门的操作类型，不能直接修改核心字段。
  • 记录操作者、原因、审批单和原始事实。
  • 经过状态机校验，不能绕过不变量。
  • 支持撤销或追加冲正，而不是覆盖历史记录。

7.7.3 监控、告警和演练

至少应该监控：支付未知状态年龄、库存预占超时、Outbox 积压、消息重复率、补偿失败率、对账差异金额、账本借贷差额和人工队列最老任务年龄。

发布前应演练：支付回调重复、回调乱序、消息积压、数据库主从切换、Redis 预处理失败、支付渠道不可用、对账任务中断和补偿任务重复执行。

7.8 方法论总结

7.8.1 八个判断句

  1. 高准确性首先保护的是业务不变量，而不是某个组件的“强一致”标签。
  2. 强一致边界应围绕不可出错的事实划定，而不是覆盖整条用户链路。
  3. 本地事务能解决的问题，不要用跨系统事务解决。
  4. 可靠事件只能保证事实传播，不能自动保证下游业务正确；消费者仍需幂等。
  5. 预占、确认和释放是一套资源生命周期模型，不能只实现成功路径。
  6. 支付、库存和账务都必须显式建模未知状态。
  7. Saga 解决流程收敛，不等于全局原子提交。
  8. 没有对账、补偿、审计和人工接管，就没有完整的高准确性系统设计。

7.8.2 一句话表达

高准确性与强一致性系统设计的核心，不是把整条链路做成昂贵的全局事务，而是先识别不可错的业务事实，再用本地事务、状态机、预占模型、幂等、可靠事件、账本、补偿和对账，把核心事实保护住，把跨系统流程收敛住。
