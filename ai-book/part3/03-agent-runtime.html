AI Engineering：大模型与智能体系统工程

第14章 Agent Runtime：架构、执行编排与可靠性工程

Agent Runtime 负责把用户目标转成受控的执行过程：建立任务契约，绑定身份、能力和预算，驱动模型与工具，保存已经确认的进度，并在失败、等待或中断后决定怎样继续。模型提供候选判断，Runtime 使这些判断成为可追踪、可恢复和可验收的行动。

本章采用一套通用参考设计，完整解释组成、核心对象、启动与受理、执行循环、可靠性和渐进实现。文中的组件可以合并在一个进程中，也可以按需要拆分；对象名、字段、JSON、SQL 和数值均是教学示例，不是统一标准。故障时序用于解释设计约束，不代表已经完成真实系统的故障注入或性能测试。所有未注明实测来源的限额与时间都仅为示例。

14.1 Runtime 的职责与边界

从目标到交付的责任边界；模型提议、执行裁决与业务事实分别确认。本书参考设计，点击图片查看 SVG。

Runtime 的设计从任务承诺开始。用户交付一个目标，系统需要说明是否受理、当前做到哪里、正在等待什么、哪些动作需要批准、结果依据什么成立。一次模型请求成功，只能说明获得了输出；任务是否允许继续、动作是否已生效、结果能否交付，需要应用维护的事实和规则来回答。

这里用一个普通任务辅助说明：读取指定范围内的资料，解释问题并形成建议；如果建议涉及修改外部记录，先生成草稿，在获得有效批准后执行。它只用来区分读取、推理、授权、写入和验收几个边界。短问答可以直接完成，长任务可以跨请求等待；两者共享责任模型，实现强度由实际承诺决定。

14.1.1 从模型输出到任务承诺

模型具备选择工具、综合证据和修订计划的能力，为动态任务提供了基础。早期关于模块组合与学习调用工具的研究说明了能力如何组合，但能力描述本身不赋予模型资源访问权。[1][2] Runtime 要把模型可提出的行动限制在可信系统允许执行的范围内。

承诺Runtime 必须维护什么可检查的结果
明确目标输入对象、范围、约束、完成条件及其版本组件使用同一份任务契约，缺失字段有澄清状态
控制行动当前主体、资源范围、策略和必要批准每次动作具有可核对的裁决，不因模型换路线而越权
有界执行时间、调用次数、费用、并发和取消意图重试与委派共用总预算，达到边界后停止新增工作
保存进度已接受的结果、未决动作、等待条件和执行责任进程退出后仍知道哪些事实成立，哪些需要核验
验证并交付验收依据、产物版本、访问资格和交付状态可以区分计算完成、业务生效与通知结果

这些承诺可以由普通函数和请求内状态实现，也可以依靠持久调度。关键是如实声明故障后的行为：只支持请求内计算时，不能把响应中的“处理中”当作重启后仍可继续的承诺；只有完成持久受理后，才可以向调用方承诺任务身份和查询入口长期有效。

任务目标还会发生变化。用户补充一个条件，可能是在修改当前任务，也可能是在提出独立目标。系统应保存被接受的修订，并使未来动作采用新约束；已经发生的外部动作不能因目标改变而从历史中消失。持续触发的任务还需规定触发条件、有效期限、资源访问范围和通知方式，一次授权不能自动延伸成无限期行动权。

14.1.2 Agent Loop、Harness、Workflow 与 Runtime

这几个术语观察的是不同层次，实际实现可以重叠。先区分它们的职责，有助于判断某个 SDK 或自建模块究竟提供了什么。

概念关注的问题与 Runtime 的关系
Agent Loop如何根据当前观察提出下一步行动，何时继续或结束是决策与行动循环，不独立拥有用户授权和业务事实
Harness如何为模型组织上下文、工具、约束、验证和反馈是围绕模型的工作环境，可以承担 Runtime 的部分实现
Workflow步骤之间有什么顺序、分支、依赖和失败出口定义路径，可嵌入一个或多个有界 Agent 节点
Orchestrator谁激活节点、分配分支并汇总结果承担协调职责，需要依赖状态与执行权机制
Runtime一个任务如何从受理走到执行、等待、恢复和交付负责端到端生命周期与责任边界

固定 Workflow 的路径由代码预先规定，动态 Agent 的下一步由模型结合观察决定；复杂任务可以将两者组合。[3] Runtime 同时支撑这两种执行方式，不要求所有任务都动态规划，也不要求有工具的任务都循环多轮。

模型适合解释、摘要、候选计划、证据归纳和允许范围内的路径选择。身份认证、租户归属、额度预留、状态提交和业务回执核验则需要明确规则。工具返回“已执行”、模型输出“已完成”、界面收到最后一段文本，都需要放到任务契约中判断其真实含义。

Runtime 与宿主环境也有边界。Runtime 决定动作资格和执行限制，操作系统、容器、沙箱以及资源端负责真正限制文件、进程、网络和业务资源的可达范围。目录命名、角色提示词和工具列表可以减少误用，但不能替代底层访问控制。

14.1.3 设计约束与责任边界

模型负责基于当前输入提出候选解释、计划、工具动作或结束建议；Runtime 负责检查这些提议是否满足任务契约、权限、预算和验收要求。模型可以帮助理解意图，但不能自行补造用户授权；可以建议任务完成，但不能仅凭自己的判断改写权威终态。

因此必须区分三种权力：提出下一步、批准执行、确认事实。Agent Loop 与 Planner 承担提议职责，Policy 与人工控制承担授权职责，状态管理与 Verifier 接受有证据的结果，业务后端提供外部动作的事实依据。任何替代工具或子 Agent 都沿用这些边界。

这些特性解释了为何需要独立的状态、授权与验收组件；“让模型参与判断，由系统承担责任”是本书的设计原则，不能理解为模型天然具备可靠风险判断能力。

上述约束决定三个设计原则。第一，系统记录的状态必须能解释模型当前依据什么继续；第二，每个动作都在实际派发时核验资格，不能把循环入口的一次检查当作永久许可；第三，失败状态要保留不确定性，超时和取消不能证明外部动作没有发生。

可靠性也包含活性：系统既要阻止错误动作，也要让正常工作能够完成，让阻塞有责任人和处理期限。对所有失败一律暂停会造成无人处理的积压；对所有失败一律重试则会扩大成本和副作用。后续架构与状态模型要同时表达自动推进、持久等待、人工处理及最终收敛。

14.2 架构与核心对象

组件按职责协作，状态、事件与资源端回执承担不同事实责任。本书参考设计，点击图片查看 SVG。

Runtime 可以按逻辑责任拆成控制面、执行面与横切设施，再通过共同的对象模型协作。本节采用“版本化状态与事件共同提交”的参考实现：状态库负责当前事实，事件保留变化过程，Worker 提交结果提案，由受控状态接口决定是否接受。它并不要求每个组件成为独立服务。

14.2.1 控制面、执行面与组件分工

通用组件参考设计。控制面持有任务权威状态，执行面运行受控步骤；预算与观测贯穿各组件，宿主环境落实实际隔离。点击图片查看 SVG。

控制面：管理任务事实与执行条件

控制面持有 Task / Run 的权威状态，决定任务契约、依赖关系、执行资格与完成条件。入口路由与意图归一负责把请求变成明确的任务；能力目录提供可选的模型、工具、Skill 与数据源；规划与循环控制提出候选步骤；Policy 与人工控制决定哪些动作获准执行；调度与状态管理负责执行权及状态提交。模型可以参与意图理解和规划，但候选计划、候选动作与已提交事实必须分开保存。

执行面：完成受控计算并返回证据

执行面包括上下文装配、模型调用、工具适配、实际执行、结果检查与交付适配。它根据控制面提供的任务、版本和权限工作，返回结构化观察、验证结果、产物与回执。执行 Worker 可以保留当前调用句柄、进程信息和局部缓存，但这些局部状态不能替代持久任务事实，也不能成为它自行推进全局 Run 状态的依据。

横切能力：约束并记录各组件的工作

预算与生命周期控制贯穿模型调用、工具执行和委派；身份与凭证管理限定资源访问范围；Trace、Audit 与指标记录因果、用量和裁决证据。它们通过统一接口作用于各组件，各自的预算、授权和审计记录仍须有明确归属，不能形成另一套相互冲突的任务状态。数据库、消息系统、对象存储和沙箱提供底层支撑，Runtime 负责在它们之上建立一致的任务语义。

下表进一步定义各组件管理的信息。“管理状态”不代表组件拥有一套独立数据库；权威状态应通过统一的提交边界维护，执行组件可以只保存局部句柄与受控引用。

执行后端（Execution Backend）执行 Shell、沙箱任务或业务 API 请求进程、工作区、资源端状态及业务回执实际隔离与副作用由后端落实，Runtime 中的声明不能替代它们

身份与凭证管理（Identity / Credentials）绑定租户与主体，提供受限资源访问凭证主体映射、凭证引用、作用域与有效期凭证可用不代表业务批准，密钥值不进入模型上下文
观测与审计（Observability / Audit）关联执行过程、裁决、成本与诊断证据Trace、审计事件、指标与关联标识诊断日志不替代领域状态、Operation 账本或业务事实

这里的 Runtime 是上述职责的整体，而不是与 Agent Loop、Execution Engine 并列的另一个执行节点。同样，“控制面 / 执行面”划分的是决策与执行责任，不是按组件名称机械划分进程：例如 Verifier 的规则归控制面管理，检查可以在 Worker 中运行，检查结果由控制面接受；上下文访问规则与实际检索也可以分别部署。

逻辑上的控制面可以直接调用同进程执行器，也可以通过持久调度驱动远程 Worker。网络边界增加了失败窗口，拆分部署后还需要明确请求去重、调用超时与结果未知的处理，不能把进程内函数调用的假设直接搬到 RPC 上。

14.2.2 模块接口与执行契约

组件间传递的是带身份、版本和约束的数据，不是一份共享可变字典。接口至少应明确调用方、输入引用、版本前提、返回分类，以及是否可能改变外部状态。一个组件可以兼任多种职责，但不能自行放宽上游已经确定的权限和完成条件。

接口输入与前提输出及提交责任
accept_request可信身份信封、请求键、规范化输入原任务或新受理身份；受理服务提交去重与初始状态
assemble_run任务契约、能力快照、授权和剩余配额不可变执行包与引用；敏感凭证仅在受控端解析
propose_step已提交状态、上下文包、允许请求的能力候选动作、答案或计划变更；不直接提交业务成功
evaluate_action主体、目标资源、参数、审批和当前状态允许、拒绝、请求批准或升级，以及执行约束
claim_step就绪节点、版本前提和调度资格Attempt、执行权代次和租约；认领由状态库原子接受
execute_action有效派发授权、Operation 或只读调用身份结构化观察、外部引用和可能的未知结果
commit_step当前版本、执行权、输出引用和检查结果新状态、事件、Checkpoint及后续调度意图
verify_result任务完成条件、候选产物、外部证据通过、需要修复或拒绝；状态接口决定是否提交终态

接口中的身份都要在接收方验证。载荷中出现 tenant_id 或 authorization_ref，不等于调用方有资格使用它们。执行器可接收服务端签发的短期授权引用，但不能接收模型任意拼出的凭证路径、连接地址或处理函数名称。适配器把逻辑能力映射到受信实现，执行后返回相同对象链上的结果。

错误通道与成功通道也应具有稳定结构。错误至少说明发生层次、可否重试、是否可能产生副作用和关联对象；协议或进程异常不能被包装成一段普通答案。等待属于一种可持久恢复的控制结果，应返回等待对象与触发条件，不能只保留一个永远没有返回的调用栈。

当外层编排器嵌套内层 Agent Loop 时，必须提前约定谁分配预算、谁决定重试、谁传播取消、谁验收父节点。内层可以修复局部问题，不能重置总额度、修改根目标或直接宣布父任务完成。模块边界清楚后，替换模型适配器或执行后端才能保留同一套任务语义。

Artifact文件、报告、上下文包等版本化载荷通过受控引用与任务关联，内容哈希不代替访问权限

对象身份还要绑定租户与作用域。state_version 表示状态版本，owner_epoch 表示特定对象的执行权代次，两者解决不同问题，不能混用；Trace / Span、模型请求标识和工具调用标识用于关联具体调用，不能替代 Task、Run 或 Operation 的业务身份。

这些身份必须分开的原因在于，它们在不同的时机变化。一个 Run 可以由不同 worker 接续，经历多次重连才完成，所以线程、进程、连接与 Run 不能共用一个身份字段。如果把 Task 和 Run 混为一个 id，系统就无法区分“重试”和“重新运行”，计费会出错，不同版本的执行历史也会互相覆盖。

本章使用以下术语：

  • 执行权代次（owner_epoch）：某个 Step 的执行权每成功转移一次就递增的单调整数。持有最新代次的执行者才有权提交该 Step 的结果，旧代次的写入一律拒绝。
  • 规范化载荷（canonical payload）：把请求参数按固定规则整理后的形式，例如字段排序、去除无语义的空白、统一默认值。对它计算的哈希（payload hash）用来判断两次请求的参数是否真正相同。
  • 幂等键（idempotency key）：调用方为同一意图提供的稳定标识，重复提交时据此返回同一结果。本章区分两种范围：接入层的任务幂等键（字段 request_key），用于避免重复创建 Task；Operation 传给下游的操作幂等键（字段 idempotency_key），用于避免同一业务动作重复生效。

14.2.4 状态机与条件提交

状态机定义对象允许处于哪些状态，以及哪些变化具有业务意义。Run 的执行状态、Step 的推进状态、Operation 的外部结果和用户界面的展示状态是不同维度：例如 Run 已取消，仍可能存在需要核验的在途 Operation；界面中的“处理中”也不应成为后端状态的权威来源。下表先说明事实归属，随后定义状态迁移与提交规则。

WAITING 另存 wait_kind，区分等待输入、审批、工具作业和定时器；FAILED 另存错误与恢复分类。结果完整性、通知状态和 Operation 事实通过独立字段表达，避免把几十种组合塞进同一状态枚举。运行仍在进行时，已经有部分产物也不表示进入完成终态。

Step 的状态可以细化为等待依赖、可运行、执行中、等待外部结果、已完成和失败；其迁移需要满足计划版本、输入版本及验收条件。Attempt 只记录本次尝试的开始、结果和用量，Operation 则独立记录外部动作是否发生。子 Step 的失败不一定使整个 Run 失败，是否允许修复或部分交付由父契约决定。

除 Task 与 Run 外，Step、Operation、Artifact、事件与幂等索引均绑定 tenant_id；查询和唯一约束包含租户，不能仅靠全局随机 ID 代替隔离。

同一个 Run 可能同时被多方更新：恢复 worker、用户的取消请求、工具回调和定时器都可能在同一时刻写入。如果不加约束，后到的旧写入会覆盖新状态。本章采用“单写者”原则来约束这种并发。**单写者（single writer）**指在任一时刻，某个状态对象只有一个被授权的写入方，其他参与者只能提交事件或请求，由这个写入方决定是否接受。单写者可以由 actor 模型实现，也可以由数据库条件更新实现；无论哪种方式，都需要持久化当前执行权，并处理执行者失效的情况。

本章以数据库条件更新作为参考实现。一次状态迁移在同一个事务中完成以下检查：当前状态是否符合迁移前提，状态版本（state_version）是否与调用方读取时一致，执行权代次是否仍是最新。检查全部通过后，事务更新状态并追加事件；任何一项不符，写入都会失败。这种做法也称为比较并设置（compare-and-set，CAS）。每次更新都返回新的版本号，冲突时调用方重新读取，再决定合并还是失败。事件表按 run_seq 建立唯一约束，因果顺序由服务端分配的序号决定，客户端的墙钟时间不参与判断。

条件更新之外，还要检查业务前提。获得授权并不代表前提会一直有效：人工批准之后，目标资源可能已被修改，任务可能已被取消，租户权限也可能已被收回。因此，在真正执行之前仍要重新校验资源版本和当前授权，不能把一次旧的批准当作无限期的通行证。

分布式锁无法单独解决这些问题。锁会超时，worker 会崩溃，外部副作用也可能在锁释放后才完成。只有把状态机、租约、幂等键和外部查询接口组合起来，系统才能安全恢复。此外，事件处理器本身必须幂等，由事件派生的投影（projection）必须可以重建。多个 Agent 共享任务状态时，要明确哪些字段只能由协调者写入，哪些内容是只追加的消息。

Runtime 的事实由追加式事件组成，例如 RUN_CREATED、STEP_STARTED、MODEL_COMPLETED、TOOL_REQUESTED、TOOL_SUCCEEDED、APPROVAL_REQUIRED、RETRY_SCHEDULED、RUN_PAUSED 和 RUN_COMPLETED。当前状态可以由事件派生，也可以保存为带版本的状态快照。重复事件、乱序事件和迟到 worker 的回报，都要通过序号、Attempt 和状态版本加以校验。

状态机定义哪些迁移是合法的。例如，RUNNING 可以进入 WAITING、PAUSED、CANCELLING、FAILED 或 COMPLETED；WAITING 通过 wait_kind 说明是在等工具、批准还是输入。COMPLETED 不能被迟到的失败事件覆盖；进入 CANCELLED 之后，新的普通业务动作必须被拒绝。持久工作流可以依据有序事件历史重建推进位置。[4] 状态机执行一次、消息投递一次与外部动作生效一次属于不同保证；本章通过状态条件、稳定 Operation 和资源端契约分别处理，不能用一个“exactly-once”标签概括。

运行终态与业务事实要分开保存。CANCELLED 表示不再继续这次执行，而外部工具晚到的成功仍然是真实发生的事实。系统可以追加核验事件或补偿事件来解释它，但不能为了让界面看起来整齐而删除它。反过来，远端成功也不能让已取消的 Run 自动回到 RUNNING 并继续后续动作。终态保护的是执行承诺，账本保留的是业务世界中已经发生的变化。

普通 Trace 可能被采样、脱敏或截断，不能替代持久状态。本章以一致提交的状态与领域事件为恢复依据，派生投影可以重建；外部动作是否生效仍需核对资源端证据。

14.2.5 存储职责、事件与观测

四类存储保存的内容各不相同。对话历史保存“说过什么”，记忆（Memory）保存经过治理的跨任务信息，执行事件保存已经被接受的状态变化，Operation 账本保存外部动作的意图与事实。摘要里可以写着“已经创建工单”，但恢复 worker 必须通过对应的 Operation 和外部对象来确认这一点。模型记忆中的一句“已成功”，没有足够的身份、版本和证据，不能作为再次执行或宣布完成的依据。

状态表也不必承载所有内容。任务目标、当前版本、依赖关系、执行权和未决操作需要可查询，因此放在状态表中；长文本、文件、工具原始载荷和报告进入受控的 Artifact 仓库；事件则保留状态变化的因果。读取 Artifact 时要再次检查当前权限，曾经进入过某个 Run 的内容，并不意味着永远可见。内容哈希可以证明载荷是否发生变化，但它不能代替鉴权，也不能证明业务含义正确。

单次执行的恢复状态与跨任务共享信息应采用不同的存储契约；内存实现可以验证接口，但无法证明进程重启后的耐久性。[5] 在本章的参考设计中，状态、事件、Artifact 与记忆可以共用底层存储，但各自的提交、删除、权限和保留规则必须分别定义。

Runtime 也不应把全部历史消息直接拼进每一次提示词。消息存储（message store）保存原始消息及其来源、时间、权限、哈希和父消息；上下文构建器（context builder）则根据当前 Step 的预算、任务、工具、记忆和安全策略，选择模型可见的内容，并记录最终提示词的版本和组成摘要，以便回放与审计。超出窗口时，安全约束和用户目标不能被静默删除。上下文的优先级与压缩策略见上下文组装。

ReAct 的结构化候选动作和观察必须由状态机接受；不保存或展示完整思维链，也不把自由文本当作迁移。循环判据见Agent Loop，模式定义见14.4.3。

Trace 记录一次执行经过哪些组件、各次调用耗时以及用量，Audit 保存谁触发、批准或执行了什么。两者需要关联 Task、Run 和 Operation，但普通诊断记录可能采样、截断或延迟导出，不能据此推导完整业务事实。强审计要求的行动记录要进入可确认的持久路径，再异步导出诊断视图。

可以为每个 Run 建立可查询的执行账本：任务版本、状态序号、当前节点、Attempt、调用输入摘要、裁决、外部动作和产物引用都能相互定位。账本不保存模型完整思维链；需要解释的是使用了哪些证据、采取了哪些动作、为什么通过或停止。敏感正文存放受控载荷，日志仅保留必要索引，访问日志本身也需要权限管理。

运行指标应从这些对象派生：排队时长与执行时长分开，模型、工具、审批等待和交付各有耗时；成功任务成本包含失败尝试与核验；UNKNOWN Operation 的数量和年龄独立于 Run 成功率。否则进程都正常、终态都好看，也可能掩盖长期无人处理的外部事实。

14.3 启动与任务受理

上半部分准备实例能力，下半部分在本次身份与资源范围内建立任务承诺。本书参考设计，点击图片查看 SVG。

启动建立实例可以提供的能力，受理把这些能力收窄为一次具体任务的承诺。前者处理部署配置、实现版本和依赖，后者处理用户身份、目标、资源和本次预算。两阶段不能混同：实例拥有一个可执行工具，不代表当前用户可以调用它。

14.3.1 配置、版本与基础设施

输入包括部署配置、环境覆盖项与版本清单。先按确定的优先级合并配置，再做 Schema 和语义检查：模型标识存在，工具绑定齐全，环境与数据源匹配，必需依赖与可选依赖有明确声明。凭证只保存引用，由凭证提供方解析，不能把密钥值放进快照、日志或模型输入。

版本清单（manifest）至少关联工作流、模型与 Prompt、工具 Schema、适配器、Skill、Policy、Verifier、预算模板及存储格式。配置快照说明“本实例实际采用什么”，版本清单说明“这些配置与制品属于哪个经过验收的版本组合”。不能只记录代码 commit，却让策略和工具在后台无记录地变化。

产物是经过校验的配置快照、manifest 标识及制品绑定。模型别名或远程工具无法固定实现时，记录实际返回的标识、契约快照和限制，不据此承诺可复现。无效配置应阻断相应能力；涉及必需承诺时阻断启动。

根据角色建立状态库、事件、待发消息表（Outbox）、接收去重记录（Inbox）和产物存储的客户端，以及日志、Trace、指标和审计通道。长任务要求进程外持久状态；内存实现只适用于明确接受进程退出后无法恢复的场景。初始化阶段确认连接与格式兼容，数据库迁移由受控发布流程执行，普通 Worker 不应在启动时竞争修改 Schema。

同时加载关联字段与脱敏规则，使启动失败也能留下诊断信息。普通遥测可以按部署契约缓冲或降级；要求强审计的业务写入若无法可靠保存审计事实，应禁用该能力，或使依赖它的部署保持未就绪。日志服务不可达不应使进程失去所有本地诊断路径。

产物是可用的存储句柄、记录接口和兼容性报告。这里不预先创建用户任务，也不读取全量消息、Memory 或知识库；后续按 Run 的身份与访问范围读取。

连接与记录接口初始化后，还要把存储位置、状态格式、事件版本和初始化结果纳入健康报告。启动日志应能直接定位配置、存储或连接错误；只有“客户端对象已创建”不算依赖检查通过。初始化阶段准备资源，必需依赖的最终准入统一由能力检查与发布过程决定。

合并配置时要保留来源与最终值。可以采用默认配置、部署配置、显式环境覆盖的优先级，但应在实现中固定顺序，拒绝同一作用域内无法解释的冲突。列表、空值和删除语义尤其需要明确：空工具列表是禁止所有工具，还是回退到默认工具，不能由不同组件自行解释。

启动形成的制品清单应可读取但不可被在途请求原地改写。共享连接池、无会话状态客户端和不可变工具描述可以复用；消息数组、当前用户、可写目录和会话凭证不属于全局配置。将它们混进一个单例对象，会让并发请求互相覆盖上下文。

基础设施检查还要覆盖失败路径。状态提交超时后，应能查询是否已经落库；产物写入失败不能留下虚假引用；观测后端不可用时，要有本地最小诊断路径。检查采用专用资源与无副作用操作，不使用真实业务写入作为启动探针。

14.3.2 能力目录、策略与验收规则

从静态配置、插件清单或发现协议读取能力描述，依次完成解析、名称与版本校验、Schema 校验、适配器绑定及依赖登记。模型、工具、Skill、数据源和验证器分别保留其类型，不能因为都叫“能力”就使用相同的授权语义。

目录注册时保存什么需要检查的关联
Model Registry端点、能力声明、上下文限制、超时与候选模型调用适配器及部署策略
Tool Registry输入输出 Schema、读写性质、风险、版本及处理函数Connector、凭证作用域、Policy 与验证规则

发现远程工具时，先完成协议初始化、枚举与契约检查，再绑定策略；延迟连接只登记待发现状态，不能把未知工具发布为已可执行。注册描述来自外部时视为不可信输入，Skill 内容也不能直接变成启动命令或额外权限。产物是版本化目录与依赖图；注册成功仅说明能力可被后续校验，不表示任意用户可以调用。

能力生命周期还需区分五个事实：

事实表示什么不表示什么
已安装本地存在能力包或适配器远端工具已被发现或当前健康
已发现已取得并校验能力描述已向某个 Run 暴露
已可见描述进入某轮模型可见集合对应代码或连接一定已加载
已加载执行所需实现及连接已按契约准备当前主体已获准执行该动作
已获准执行当前动作通过 Policy 与前提检查后续动作也获得长期授权

它们是分别记录的状态，不能仅按一个“enabled”字段推断全部成立。目录还需保存模型用量计价配置，建立 Skill → Tool → Connector / Source 的依赖，支撑禁用传播。Policy Store 保存基于角色的访问控制（RBAC）、基于属性的访问控制（ABAC）与环境规则，观测配置保存 Trace Schema、采样和脱敏规则；它们与 Verifier 都要绑定当前目录版本，避免“有工具描述却没有执行约束”。

将能力标识、读写性质、环境和风险映射到 Policy 规则，检查审批角色、路由、沙箱约束与凭证作用域能否落实。未覆盖的风险能力保持关闭或要求人工判断，不能默认放行。此时只完成静态编译；具体目标资源、用户权限和审批事实仍要在动作发生时求值。

预算加载的是模板与上限，包括轮数、Token、费用、总时长、重试和并发；验收加载的是规则及实现，包括输出格式、证据要求、业务结果查询与产物检查。只有请求到来后，才生成本次 Run 的根预算与具体完成条件。

产物是与目录版本一致的 Policy、预算模板和 Verifier 规则集。工单助手可以注册 create_ticket 并绑定审批、幂等与回执规则，但这既不是一次业务批准，也没有创建工单。

例如 search_policy 绑定只读策略，create_ticket 绑定目标租户、项目范围、审批角色、稳定 Operation 与回执验证。规则编译同时检查审批服务缺失时的能力关闭行为，并把预算模板中的租户配额、重试上限与全局约束纳入一致配置。此时形成的是可执行的规则，不是一次具体审批结果。

14.3.3 就绪、能力发布与实例退出

启动链路是：加载配置与版本 → 初始化存储和观测 → 注册能力 → 编译规则 → 检查依赖 → 发布能力快照 → Ready。独立准备工作可以并行，发布前必须检查快照中的引用与依赖一致。下图给出整体依赖与就绪分支，本节按每一步的输入、产物和准入条件展开。

Ready 表示“当前实例可以履行已声明的服务契约”，需要同时说明角色、可用能力和版本。进程存活只能证明服务还在运行，不能证明任务可以受理；入口成功返回 accepted，也不能证明任务已经执行。

实例角色Ready 需要证明什么仍不能证明什么
API 实例可以校验请求、持久提交 Task / Run 及待调度记录，并提供状态查询下游 Worker 已完成任务、所有可选工具均健康
执行 Worker可以认领其声明支持的任务，取得相应规则、存储及执行依赖任意版本或任意租户的 Run 都可执行

API 可以先于 Worker Ready，但系统必须明确是否允许“持久接收、稍后执行”，并暴露积压和服务期限；没有这一契约时，不能把执行层整体不可用包装成完整就绪。就绪检查应有超时、最近检查时间与失败原因，依赖变化时可以撤销相关能力或退出 Ready。

按依赖图进行有超时的健康探测和契约检查，检查状态存储、模型端点、工具适配器、索引、审批与审计通道。使用健康接口、测试资源或无副作用查询；不能用创建真实工单或发送通知来检查启动。端点可达只说明连接条件，结果质量与任务权限仍由后续评测和执行检查负责。

发布前检查悬空引用，例如日志源被禁用后，依赖它的延迟调查流程不能仍标为完整可用。通过原子切换或等价的一致性机制发布快照，使新任务不会同时读到新版目录与旧版策略。快照不存放密钥值，也不成为长期授权。

每项检查保存结果、耗时、原因、检查时间和关联能力，最终产出依赖健康报告、禁用清单与待连接清单。快照同时记录标识、可用范围、降级原因与就绪时间。例如知识查询可用而审批通道不可用，可以只开放问答；若创建工单是该部署的必需承诺，则整个实例保持未就绪。

配置更新重走校验、依赖检查和快照发布，形成新版本；新 Run 绑定选定的 manifest 与能力快照，在途 Run 沿已记录版本继续，或在显式迁移边界切换。不能让一次默认值变更隐式改变旧任务的工作流、工具参数或补偿语义。发布记录必须能说明采用版本、兼容范围和回退条件。

多实例必须处理“Run 在快照 X 上创建，由只持有 Y 的 Worker 领取”的情况：Worker 声明可执行版本，调度只匹配兼容实例；否则加载并验证所需版本，或让该 Run 等待合适执行者。不可取得原制品或未证明兼容时暂停，不直接用 Y 解释 X 的事实。这是本书参考部署协议，不是 SDK 自动提供的保证。

回滚新任务路由与回滚在途状态是两件事。前者让新 Run 使用已验收的旧版本；后者必须保留既有 Operation、事件、预算和产物，经过兼容验证或明确迁移。紧急撤权、凭证失效、数据删除等当前安全事实不受旧快照豁免，执行前仍须校验。

Run 保存能力目录快照与制品摘要。Skill 可以绑定不可变包，远程工具服务未必支持固定实现，只能记录实际观察到的契约；不兼容变化应暂停受影响动作。停用能力时先阻断新调用，再处理在途请求、外部作业和子进程，不能通过删除目录项假装它们已消失。持续健康检查据此更新可用能力或撤销就绪，安全撤权优先于旧版本固定。

正常退出先关闭新接入和新认领，再处理在途工作。入口已接受的任务必须在持久状态中可查；Worker 在约定的排空窗口内完成当前可提交步骤，或记录稳定边界、未决 Operation 与后续处理责任。不能先清空内存再试图找回哪些任务已被承诺。

持久审批、外部作业和定时器不要求 Worker 一直占用进程，但其关联与恢复条件必须先保存。已发出的外部写请求不能因为进程将退出而被记作“未执行”；不确定结果交给 14.5 的对账路径。执行权按持久协议交还或到期，不能靠本地释放句柄证明资源端旧写已被隔离。

最后刷新可持久保存的事件、审计与用量，关闭连接。排空超时进入明确的强制退出策略，说明可能中断的计算和仍待核验的外部动作。实例退出不等于 Task 结束，系统通过持久事实决定后续接续。实例建立服务承诺后，请求仍要经过下面的受理协议，才能成为一项具体任务。

14.3.4 请求信封、去重与任务契约

入口接收用户请求、授权事件或队列消息，先识别它是新目标、当前任务的补充、继续执行，还是查询状态。可信信封绑定租户、主体、会话、环境、请求标识及关联标识；这些字段来自鉴权与路由，不能由模型或正文中的自述覆盖。

意图归一把“查一下为什么延迟，需要处理时先给我看草稿”变成契约：调查哪张工单、可访问哪些数据、时间范围、是否只读、预期证据与草稿格式，以及哪些信息必须澄清。缺少关键对象时先保存待澄清状态，不凭猜测启动写动作。一次消息不必对应新 Task，关联规则由入口契约明确规定。

请求去重键在租户与入口约定的作用域内唯一，并绑定规范化请求摘要。同键同内容返回原受理结果，同键异参报告冲突；不能仅凭自然语言相似度合并独立请求。

**C1：**在一个本地事务中建立 Task / Run，绑定契约与配置版本，保存请求去重结果及调度 Outbox，再返回 accepted 和查询身份。accepted 只承诺任务已被可靠受理。事务与投递之间的故障见 14.5.2。

14.3.5 路由、会话与受理责任

入口路由应区分目标定位与执行定位。目标定位确定租户、用户、会话及任务；执行定位寻找能读取对应状态、加载正确版本并访问指定执行环境的实例。身份来自认证和可信渠道映射，模型只辅助理解目标，不决定请求属于哪个租户或借用哪组凭证。

会话路由可以采用固定实例、共享存储或可迁移绑定。固定实例容易实现，但实例失效后，需要找到原状态和文件才能继续；共享存储降低迁移门槛，却仍需控制并发写入和执行权。保存一个会话 ID 只是保存索引，接收实例若没有原始历史、产物、版本和权限，就不能据此承诺恢复。

新消息到达时，接口明确采用哪一种语义：新建目标、补充当前任务、排队下一轮、请求中断后改向，或只查询状态。补充消息写成带序号的输入事件；当前步骤可以在安全边界读取新版本。若新信息改变已提交结论的前提，应将相关后继标为待复核，而不是在进程中的提示词里悄悄覆盖旧输入。

受理回执至少包含 Task、Run、受理状态和查询方式。同步请求可以在连接内等待，但连接断开不代替任务取消；异步接口返回后，执行责任由持久记录承担。接入层在容量不足时要决定拒绝、持久排队或按优先级降级，并公开队列与截止时间关系，不能接受无限期无法履行的任务。

请求去重也应保存生命周期。记录至少覆盖客户端允许的重试窗口和可能的延迟投递时间；旧键过期后的行为必须明确。不同入口可能承载同一业务事件，是否合并需要业务事件身份和契约，而不是根据文本相似度自动合并。用户明确发起独立执行时，保存新 Run 与原目标的关联，费用、版本和结果分别核算。

14.4 执行循环与任务收敛

工具动作循环补证；审批进入持久等待，候选答案经过验证后交付。本书参考设计，点击图片查看 SVG。

受理之后，控制层把任务装配为可执行的 Run，按照计划或有界循环驱动工作。本节展开带持久状态的参考执行协议，短时同步实现可以合并进程与调用边界。正常路径的关键是：每一步都能说清当前输入、允许的动作、接受的结果与下一次提交；合法等待会释放执行资源，完成需要验证与交付。

14.4.1 执行链路与提交边界

一次任务可归并为接入、装配、规划、决策、执行、验收交付六个阶段。上下文与决策可以循环，任务图也可以并行，但已经接受的事实都要经过明确的持久边界。以下 C1–C7 是本书对提交边界的编号，不是七个跨系统原子事务；一个编号可以包含本地提交与外部回执两个协议阶段。

Trace 记录“经过了哪里”，状态与领域事件记录“接受了什么事实”。普通 Trace 被采样或截断不应改变业务结果；C1–C7 的关键事实应能从持久记录核对，不能用诊断日志代替提交依据。

14.4.2 Run 装配、预算与资源隔离

装配读取 C1 绑定的 manifest 与契约，并结合当前身份与资源权限，生成本次 Run 的执行包：模型配置、允许请求的工具与 Skill、数据源范围、工作区、上下文规则、根预算及验收器。实例级目录可以很大，模型只看到本次任务需要且允许请求的子集；可见能力也不等于本次动作已获批准。

工作区绑定租户、任务、路径和可写范围。只读调查可以共享不可变材料，涉及修改时需要明确排他或隔离策略；Worktree 隔离文件版本，不隔离共享进程、凭证和网络。子任务只获得完成其契约所需的最小范围。

根预算包含轮数、时间、Token、费用、工具与并发额度。并发派发前预留额度，实际用量返回后结算并释放未用预留；在途费用未知时不能过早释放成可重复使用余额。重试、重新采样、查询核验、委派及孙任务共享同一根账本，子预算之和不能把总上限放大。预算耗尽的处理见取消与停止。

产物是带版本的 Run Binding 与执行包，保存身份、权限与凭证引用，不保存明文密钥。该包说明当前任务的装配结果，后续执行仍需检查当前授权与剩余预算。

把模型提议映射回可信能力与连接

模型返回的工具名必须映射回本 Run 绑定的可信注册对象，核对 Schema、版本、资源范围和已加载实现；不能把输出中的任意路径、命令入口或端点当作新工具直接执行。安装、发现、可见、加载与获准执行的区别见 能力目录。

Connector / Connection / Run Binding 的定义见 14.2.3。派发时从可信上下文取得 tenant_id/user_id/connection_id 与凭证引用，模型给出的项目、URL 或资源范围必须与绑定求交集。以项目 P 的读取绑定提出项目 Q 的写入时，不能自动切到另一组织的连接；子 Agent 只取得被收窄的委托绑定。

连接服务在派发前检查当前所有权与授权，明文凭据仅留在服务端或受控凭证提供方。连接凭据按当前授权解析，授权失效后的收敛见 14.5.6。

Agent 定义决定程序可提供的能力，Session 组织连续交互，Run 是某个 Task 的实际执行，可以关联 Session，也可以由授权事件独立触发。同一个 Session 默认串行提交共享历史；若多个 Run 并行，应为它们分配状态分支和写入目录，再通过版本检查与明确合并规则提交，防止后完成的结果覆盖较新的历史。

执行包的传递

工具实现以显式参数接收执行上下文，或使用能够跨异步任务正确传播的请求作用域。不能使用进程级 chdir、全局 current_session 或修改公共环境变量来切换请求。每次调用从上下文取得身份、目录、版本、截止时间和凭证引用；连接池可以共享，授权上下文按调用绑定。

文件修改任务可分配独立工作树或写入层，但目录隔离不保护共享数据库、网络服务和主机凭证。需要强保护时，利用文件权限、独立进程组、容器或沙箱限制可达范围；不同容器挂载同一个可写目录仍会发生冲突。取消只回收属于本次 Run 的进程、端口和临时授权，不能误杀其他任务。

预算预留可以表示为 available = limit - settled - reserved。派发前原子检查并增加预留，返回后按计量事件幂等结算；调用结果未知时保留相应在途额度，再查询费用或采用已声明的保守口径。不能把请求超时直接当作未计费，也不能让多个并发分支各自读取同一笔余额后全部放行。预算账本与状态提交需要足够的关联，才能解释中断后哪些费用已发生、哪些额度仍被占用。

14.4.3 规划、依赖图与并行汇合

根据任务契约、动作副作用、数据敏感度和环境选择控制方式。稳定的输入处理、权限判断和状态提交由确定性代码负责；模型承担解释、证据综合和允许范围内的动态选择。风险策略还要明确成功标准、自动执行边界与人工职责，不能只给任务贴一个“高风险”标签。

Router、Chain、State Machine、DAG、Plan-and-Execute 的选择见 14.4.3 模式选择。控制模式与编排可以组合，不能让选定一种编排方式隐式授予动作权限。

规划器根据契约和证据缺口提出步骤，例如读取工单时间线、检索制度、查询相关日志、解释延迟、生成跟进建议。Runtime 校验步骤是否可执行、依赖是否闭合、预算是否可承受，以及结果怎样验收，再接受计划版本。计划表达未来工作的假设，不表示这些工作已经完成。

在本书的任务图设计中，节点描述逻辑输入、输出、依赖与验收条件，激活后映射到一个或多个可追踪的 Step；一个包含内部 Loop 的复合节点还需关联其内部 Step。Attempt 是节点实际执行的尝试，不应在每次重试时变成新的逻辑节点。动态扩图保存修订版与新增依赖，后继只能消费当前计划中已接受的结果。

固定 Workflow 可以把有界 Agent Loop 作为一个节点，模型也可以在允许范围内细化未来计划。两者组合时明确外层与内层的重试、预算、取消、验收及状态归属。编排模式的定义与取舍见 14.4.3。

ReAct 让模型交替生成推理与行动，并通过外部观察补充信息；纯思维链（CoT）没有这种与环境交互的闭环。[6] 例如，“解释一个已有的排序证明”只需推理；“修复测试失败”则必须读取代码、修改代码并运行独立检查。需要注意的是，观察本身也可能失败，使用了工具并不能保证结果正确。

ReAct 关注每一步如何边推理边使用工具；Plan-and-Execute 关注整个任务如何先拆解、再执行；只读规划阶段 关注当前会话是否允许执行写操作。三者可以组合：在 只读规划阶段 下用 ReAct 做只读探索并产出计划；进入执行阶段后按 Plan-and-Execute 落地计划，而每个执行步骤内部仍可能用 ReAct 调用工具、观察结果并做局部修正。

Plan-and-Execute 先保存结构化计划，再执行和验证；计划包含节点、依赖、风险、预算与停止条件，计划外观察触发有界重规划。它不自动提供审批或只读保证；只读规划阶段 才规定本阶段禁止哪些写入。按风险审查计划，固定其版本和输入引用后进入执行，避免长对话里的草稿被误当作已批准步骤。

依赖关系不能以“上一个 Agent 发来一句完成”为准。父节点应读取子 Step 的权威状态，核对计划版本、输入 hash、必需产物和验收结论，再原子地提交“后继节点可运行”这一事实。如果状态已经提交而通知丢失，扫描器或重投可以重新发现后继节点；如果通知早到、重复或乱序，状态条件应阻止错误推进。通知用于提高响应速度，正确性由持久状态保证。

并行 join 需要明确必需分支、可选分支和超时策略。例如，日志与指标都是诊断的必需证据时，两者都通过才能形成结论；历史相似案例可以作为可选来源，查询失败时降级并标注缺失。一个必需分支失败后，是取消其他分支、保留已产出的证据还是等待人工，由工作流版本定义。任何一个先返回的分支都不能把整个任务提前宣告完成。

批处理还要保留单项身份。分片只是调度单位，一项业务动作不能因为分片重新切分就获得新的幂等键（idempotency_key）：已成功的项可以复用，结果未知的项先对账，尚未开始的项才能直接重排。父任务分别汇总成功、失败、未开始和待核验的项，最终产物能够追溯到输入项及其版本。这样即使只恢复一个失败的分片，也不会重复执行其他分片已经完成的副作用。幂等键与对账的细节见外部副作用。

受控的自由循环：Agent 节点嵌入固定工作流

固定工作流和动态 Agent 可以嵌套。例如在“接收告警、收集证据、形成建议、审批、执行、验证”这一固定流程中，证据收集节点允许 Agent 根据观察选择查询路径；但该节点仍然有输入契约、预算、可调用工具、输出 Schema 和外部验收。外层控制生命周期，内层负责局部探索；两层都不能各自无限重试，内层也不能独立宣布父任务完成。

内层节点交付给外层的是受控的结果引用和状态，而不是未经核验的完整聊天历史。内层返回 blocked、needs_input 或 unknown 时，外层应当区别处理：信息不足时可以补充查询；授权不足时必须停在授权边界；业务结果未知时必须核对原 Operation。如果把所有非成功状态都映射成一个 failure 再重启整张图，前面建立的恢复语义就会被破坏。

并发配额覆盖 Run、租户、工具、目标资源和全局，不能只用请求 QPS 限制大扇出任务。对独立分支可以并行派发；共享资源写入则需要串行、资源版本条件或明确合并。优先级和抢占只在安全边界生效，被抢占任务保存进度，在途 Operation 继续核验。Actor 与任务调度研究提供了并行工作的组织方式，业务状态与外部动作保证仍需要应用定义。[7]

批处理以 item_id 和输入版本保留单项身份，分片只是调度单位。分片重新切分后，已确认项复用，未知项先查询，未开始项再重排；父结果分别汇总成功、失败、未开始和待核验，不能因为某个批次返回成功就省略单项验收。

14.4.4 上下文、记忆与模型请求

Context Builder 读取当前契约、已提交进度和本轮证据缺口，从授权数据源与 Memory 中检索材料，执行访问过滤、版本核对、去重和预算选择，再组织模型输入。材料包含来源、权限、时间和引用标识；外部文档、网页与工具文本作为证据，不能提升为系统指令。

本轮上下文包包含任务目标、安全约束、当前状态摘要、选中的证据、方法说明、本轮工具 Schema 与剩余预算。长载荷进入受控 Artifact 存储，Run 与 Checkpoint 保存不可变引用、哈希和包版本，而不是只保存一句无法追溯的摘要。

发送模型请求前确认目标与约束未在压缩中丢失，权限过滤先于暴露，模型适配器负责协议转换与用量记录。记忆可帮助延续背景，但“记得已创建工单”不能替代 Operation 与业务回执。本节下表给出 Runtime 层的上下文契约，本节同时说明输入选择、版本与压缩后的约束。

上下文包的最小契约

内容必须保留的约束
用户目标与系统规则优先保留，不因压缩静默删除安全边界
当前任务状态从权威状态读取，区分已确认事实、候选与未决动作
证据与工具观察来源、时间、版本、可信级别和当前可见性
Memory按作用域读取，过期或冲突内容不得覆盖任务事实
能力 Schema仅暴露本轮允许请求的能力，暴露不等于授权执行
上下文包保存 package_id/version/hash、输入引用、裁剪与过滤记录

上下文包作为不可变、版本化引用随 Checkpoint 保存；恢复先检查载荷完整性与当前权限，再复用记录。哈希用于核对输入，不能证明证据正确。大载荷留在受控存储，模型只接收本步所需片段。文档、检索结果和工具文本均作为不可信数据隔离，不能借内容中的指令扩张权限。缺少关键证据时补检索、澄清或停止，不能靠摘要把缺口变成事实。

Memory 的读取与受控写入

读取 Memory 按租户、用户、项目与用途过滤，记录来源、版本和期限；过期或冲突内容不能覆盖任务事实。写入先形成候选，再按敏感度、冲突与证据审核，不能把一次工具失败或模型猜测直接沉淀为规则。任务可以引用某版记忆，但当前撤权、纠正和删除优先于历史可见性；子 Agent 只取得委托范围内的投影。删除和纠正事件需使相关缓存与后续读取失效；共享记忆只在审核后的范围发布。

输入版本与证据时间

一个执行阶段固定任务契约、方法说明、工具 Schema、模型参数和输入制品版本；外部状态以观察记录表达，附带查询范围、采集时间和资源更新时间。历史判断要使用对应时间的证据，不能用当前配置解释过去的行为。版本固定不豁免当前撤权和数据删除要求，恢复读取材料时仍需检查权限。

模型适配器把上下文包转换成目标协议，规范化文本、工具提议、结束原因、错误和用量。流式增量先组成完整结构，再交由后续校验，不能把未闭合 JSON 片段派发为调用。记录逻辑模型、实际服务返回的标识、请求参数、输入包引用和用量；供应商别名或远端实现可变化时，应如实说明重现限制。

调用失败是否重新采样由错误分类与总预算决定。模型切换也需检查工具 Schema、结构化输出、上下文限制和数据边界是否兼容；切换成功不是原任务完成的证据。已经被接受并驱动后继的输出在恢复时复用，不能通过重新采样改变先前已提交的决策。

14.4.5 动作裁决与审批等待

模型输出先解析为候选答案、工具调用或计划修订，再检查 Schema、工具标识、参数、目标对象及与任务的关联。结构有效只证明可以进入裁决，Policy 仍按当前主体、资源、环境、审批和预算决定是否执行。每个动作分别裁决，不能只在 Loop 开始前统一检查一次。

正常的 allow 路径携带沙箱、审计和凭证范围等约束交给执行引擎；ask 路径先保存待审批动作，绑定对象、规范化参数摘要、资源版本、审批角色与有效期，提交等待事件及交互通知，然后释放 Worker。批准事件经鉴权、去重并核验与待审批记录匹配后，记录决定，恢复可运行状态，执行前再次核对当前事实。

审批批准的是绑定的动作，不是整个会话的无限授权；目标或参数变化需重新裁决。deny、escalate、批准失效及审批超时的处理见 14.5.6。此处的等待是合法正常状态，不应伪装成一个持续占用进程的函数调用。

决策或约束语义责任边界

相同工具在测试环境与生产环境、公开文档与客户私密数据上可能得到不同裁决。批准之后草稿、目标、资源版本或连接授权变化，都要重新检查。输入、上下文、提议、工具、结果与输出的检查必须挂到对应执行边界，异常处理见 14.5。

生产 Agent 不能只有自动化路径，还需要以下几类人工控制点：

控制点触发条件与作用
确认（Confirmation）执行有副作用的动作之前，请发起任务的用户确认
审批（Approval）高风险动作需要指定角色批准，对应 Policy 决策 ask
中断（Interrupt）人可以打断正在运行的 Agent 循环
接管（Takeover）人接手任务，继续执行或关闭
升级（Escalation）风险过高、证据不足或预算耗尽时转交给人，对应 Policy 决策 escalate
回滚（Rollback）对可回滚动作生成回滚计划，或触发补偿流程
降级（Degrade）工具、模型或权限异常时，降级为只读建议模式

需要审批的典型动作包括高风险写入、对外发送消息、支付、权限变更、删除、公开发布，以及安全性无法确定的动作。人工控制并不意味着所有动作都要弹窗确认，合理的做法是按风险分层：低风险的只读任务自动完成，中风险动作请用户确认，高风险的生产动作进入审批，极高风险的任务直接拒绝或转人工。这样既不牺牲效率，也不会把生产责任交给模型。

审批绑定的对象

审批请求要向审批人展示目标、参数、影响、证据、风险、有效期以及可修改的选项。批准与拒绝都作为事件写入账本。一条审批记录至少绑定以下内容：

  • 具体动作及其规范化载荷的哈希；
  • 目标资源的版本；
  • 授权主体，即谁批准、以什么角色批准；
  • 有效期。

绑定参数哈希和资源版本，是为了让批准只对“这一个具体操作”有效。人工可以修改模型生成的参数，但修改后的结果要标记为 human-edited，并生成一个新的提案重新校验，不能沿用原来的批准。同理，原批准过期、参数改变或目标资源版本变化后，旧的决定一律作废，必须重新形成提案。需要澄清和需要审批也要分别表达：模型输出“用户已批准”，并不构成一个批准事件。

14.4.6 调度、工具调用与结构化观察

调度器从已接受的计划中选择依赖满足、预算及并发额度可用的 Step。通过 Outbox 把工作交给执行者，消费者建立持久接收记录，使执行责任可以在进程退出后被重新发现。

**C2：**Relay 在取得中间件确认后记录投递进度；消费者持久去重并保存可接续处理的责任后，才返回消费确认（ACK）。两者分别确认，ACK 不是业务完成。**C3：**认领事务检查 Step 可运行性与旧租约，原子保存执行者、租约和新的 owner_epoch，执行者据此开始本次 Attempt。重复投递与旧执行者竞争分别见 14.5.2、14.5.3。

执行引擎按已裁决的动作调用 Tool Runtime，后者再次校验参数、取得受限凭证并适配到业务 API、远程工具协议、Shell 或沙箱。只读结果形成带来源和调用关联的结构化观察（Observation）；业务写入先进入稳定 Operation，不能直接把模型调用标识当作业务幂等键。

**C4：**真正发出创建工单请求前，持久记录 Operation、原始业务意图、稳定幂等键、规范化参数哈希及审批关联。**C5：**后端确认创建后，保存工单编号、版本与回执证据，并核验其对应原 Operation。C4 与 C5 分属本地和外部边界，不构成跨系统原子提交；不确定窗口见 14.5.4。

外部异步作业、Webhook 和定时器走持久等待：保存原操作或作业身份、订阅条件、截止时间和预期事件，再释放 Worker。事件到达后先鉴权、去重并匹配当前等待，再安排后续推进；查询状态和重连沿同一 Run 进行，不新建任务。

工具执行接口

工具描述至少保存输入与输出 Schema、读写性质、资源范围、超时、错误分类、幂等能力、查询能力以及必要的补偿入口。方法说明可以告诉模型怎样选择工具，执行资格由可信目录、运行绑定和实际策略决定。协议适配器只解决如何调用，不自动保证权限、幂等或结果正确。

调用时从 Run Binding 读取连接与凭证引用，将模型参数中的资源范围与授权范围求交集。适配器按目标协议发送请求，采集资源端回执，再转换成统一观察。用户输入中的任意端点、路径或脚本名称不能成为可信注册对象；确需动态目标时，明确允许列表与校验规则，防止借工具访问未授权资源。

  "attempt_id": "attempt-2",
  "status": "partial",
  "data_ref": "artifact://evidence/v3",
  "scope": {"resource_id": "R1", "window": "requested-window"},

14.4.7 循环推进、持久等待与停止

执行结果经过输出 Schema、来源与权限检查后形成结构化观察。Runtime 接受观察和模型决策记录，更新当前事实，再决定下一轮是补证、生成答案还是等待已登记的外部事件。已提交的模型结果与候选动作必须可追踪，不能只存在进程中的消息数组里。

**C6：**在一个稳定 Step 边界，将验收过的结果引用、状态版本、领域事件及 Checkpoint 一致提交；需要派发后继时，同事务记录其 Outbox。大型载荷先完整写入并校验，再提交引用。中断后怎样识别最后一个有效边界见 14.5.5。

每一轮读取当前执行权、取消状态、预算和截止时间。停止条件来自任务契约和状态机：证据与结果满足验收条件则进入交付，合法等待则释放执行资源；无进展、超时或预算耗尽的路径见 14.5.6。心跳只证明活性，新增证据、已提交 Step、产物变化和 progress_seq 才证明任务推进。

本节描述正常推进，格式修复、拒绝、审批失效与结果未知等异常处理见 14.5。轮数、时间、Token、工具额度与取消状态始终来自当前持久 Run，候选模型输出必须经过校验和裁决才能成为执行请求。

下面的伪代码表示一个复合决策 Step 的推进：内部提议与操作分别持久记录，实现时也可拆为多个子 Step。示例聚焦正常控制分支，费用结算、异常捕获和后台续租由外围接口承担；状态更新采用当前版本条件，同一节点重试保留逻辑身份。

def advance_step(run_id, step_id):
    claim = state.claim_ready_step(run_id, step_id)
    run = state.read_current(run_id)
    lifecycle.require_runnable(run, claim)
    package = context.build(run, step_id)
    proposal = decisions.load_committed(run_id, step_id, package.version)
    if proposal is None:
        proposal = model.propose(package, budget.reserve_model(run_id))
        proposal = validate_proposal(proposal, package)
        claim, proposal = decisions.commit_if_current(claim, package.version, proposal)
    run = state.read_current(run_id)
    lifecycle.require_runnable(run, claim)
    if proposal.kind == "answer":
        checks = verifier.check(run.contract, proposal.result_ref)
        return state.commit_verification(claim, proposal, checks)
    if proposal.kind in {"needs_input", "revise_plan"}:
        return state.commit_control_proposal(claim, proposal)
    action = policy.evaluate_current(run, proposal)
    if action.requires_wait:
        return state.commit_wait(claim, action.wait_record)
    policy.require_allowed(action)
    operation = effects.record_intent_if_needed(claim, action)
    dispatch = state.authorize_dispatch_if_current(claim, action, operation)
    result = executor.execute_or_reconcile(dispatch)
    observation = validate_observation(result)
    if observation.requires_reconciliation:
        return state.commit_reconciliation_wait(dispatch, operation, observation)
    return state.commit_result(dispatch, observation, next_work=True)

候选决策在执行前保存，用于恢复和审计，但记录决策不是预先获得永久授权。commit_if_current 在冲突时终止本轮推进，成功时返回更新后的提交凭据；最终派发还要核对取消、授权和执行权。多个工具提议拆成独立受控动作，不把一次模型输出当作整批批准。结果未知进入核验等待，不能把整段函数无条件重跑。

等待记录至少包含等待类型、关联对象、事件匹配条件、截止时间、已消费事件和恢复节点。定时器存在持久库，由扫描器或调度器触发，不依赖某个进程里的 sleep。事件先鉴权去重，检查任务仍在等待该对象后才安排推进；先到事件也可保存为待消费输入，由等待登记事务匹配，避免订阅前后的事件丢失窗口。

用户补充信息、要求暂停或取消时，运行中的外部调用未必可以即时停止。Runtime 先保存控制事件，在安全点采用新状态，并向支持中断的后端传播信号。停止条件包括完成、等待、证据不足、无进展、预算耗尽、拒绝及取消；这些结果应可机读地区分。心跳持续而没有新证据、产物或状态变化时，进展检查可以暂停空转，而不是继续无限反思。

14.4.8 验收、产物与结果交付

模型提出最终答案后，Verifier 按契约检查格式、引用、事实与业务状态。只读调查要解释结论依赖哪些可访问证据，草稿要满足约定字段；批准创建工单的任务，还要关联已确认的工单编号与回执。模型的一句“完成”不能代替这些检查。

先完整保存产物、核对哈希及访问范围，再按当前状态版本与执行权提交完成。**C6 的任务完成边界：**Run 终态、最终产物引用、验收证据、关键事件与待交付 Outbox 一致提交。它证明任务结果可查询，不证明通知已送达。

**C7：**交付 Worker 按交付身份读取已提交结果，核验当前接收人、权限与版本资格，发送后保存渠道回执。渠道仅确认受理时记录“已受理”，只有契约能够证明送达时才记录“已送达”。同步查询、最终通知与服务器发送事件（SSE）均引用同一持久 Run 和产物版本；SSE 按事件游标续读，连接断开不改变任务结果。交付竞争和未知发送见 14.5.7。

Verifier 以 pass/needs_repair/reject 表达验收结果：知识问答核对引用与权限，诊断核对时间窗口及原因证据，业务处理核对真实状态与审批，分析任务核对统计口径和可复现查询。needs_repair 只能在剩余总预算内反馈 Loop；无法修复则拒绝或转人工，具体处理见 14.5.1。

运行时 Verifier 验收当前产物；离线评测使用数据集和失败样本比较版本质量，不能代替本次任务的检查。交付界面（Review Surface）展示结论、证据、不确定性、风险动作、产物版本或 diff、验证结果及反馈入口，不要求展示模型完整思维链。Observation 是执行事实的受控视图，界面读取已提交结果后才显示任务完成。

Runtime 的外部 API 至少分成八类：任务提交、运行查询、事件流、审批、取消、恢复、Artifact 和回放。

  • 提交接口接受目标、上下文、能力范围、预算、截止时间、优先级和幂等键；
  • 查询接口返回当前状态、进度、成本摘要、需要用户执行的动作和可见结果；
  • 事件流推送状态变化，但不暴露未经授权的内容；
  • 审批接口把人工决定写成事件；
  • 取消和恢复接口必须穿透模型、工具和等待队列；
  • Artifact 接口保存大段文本、文件和证据；
  • 回放接口用于调试和审计，不能重新触发真实的副作用。

输出也要区分最终答复、部分答复、工具结果、人工决定、失败和补偿，客户端不能靠判断文本是否为空来猜测状态。结构化错误包含 code、retryable、retry_after、run_id、step_id 和修复建议；敏感的内部错误只出现在受控的 Trace 中。AIP-194 对错误分类和重试语义的强调，同样适用于 Agent API [8]。

状态机、工作流和流式交付是三个不同的维度，可以同时存在。状态机限制合法的迁移，工作流组织步骤、依赖和错误处理，流式交付则把进度和输出增量发送给用户。流式还可能指节点之间的逐块计算，这时需要单独定义块边界、背压和重复处理。工具参数只收到部分 JSON 时，必须先缓冲，校验完整的提案后才能执行，不能把 token 流当作业务提交。

任务、结果和事件日志独立于连接保存。客户端断线只影响订阅，重连后按原 task_id 查询，不能自动创建新任务。WHATWG 规范规定，EventSource 重连时可以发送 Last-Event-ID [9]，但规范并不提供服务端的历史留存、持久任务或业务幂等。其他 SDK 或 HTTP 客户端是否记录游标需要自行实现，不能因为支持 SSE 就推断具备恢复能力。

本章采用每个 Run 单调递增的 run_seq 和全局唯一的 event_id，事件持久提交之后才发送到流上。客户端按身份和序号去重，断线后从最后确认的游标开始重放。状态写入与完成事件在同一数据库事务中关联提交；流投递失败并不撤销业务完成，查询接口返回权威的版本、终态和结果哈希。如果客户端先收到“完成”事件，查询结果却还落后，就按事件的提交水位重新查询权威数据源，或等待投影追上，不能凭文字或旧副本判断成功。

游标仍在保留期内时，服务端鉴权后补发事件；游标已经过期时，明确返回 cursor_expired 和可用范围，同时提供一份快照，包含 snapshot_version、last_included_seq 和完整结果的引用。客户端先用快照替换旧视图，再从水位之后继续订阅，避免把后半段文本拼接到错误的前缀上。载荷已删除、无法重建时，要说明恢复受限，不能静默发送残缺的尾段。重连时仍要重新校验当前权限：以前能看到的内容，在权限被撤销后不一定还能下载。

完成通知同样先提交事实，再由 outbox 投递，并携带稳定的 notification_id 和任务版本；接收端负责验签、防重放和幂等处理。回调目标要有白名单、超时设置、总重试预算和失败修复入口，通知中只携带最小摘要和受控的查询链接。通知失败不会把已完成的任务改为失败，通知到达也不能替代用户对最终结果的查询。流缓冲和事件读取都需要背压控制，慢客户端不能无限期地占用 worker 或原始敏感载荷。

14.4.9 多 Agent 的委派与父任务收敛

多 Agent 适用于可以独立验收的分工，例如不同证据范围的调查、独立方案审查或大任务分块。普通并行工具调用与模型路由不会自动产生新的责任人，只有确实需要独立上下文、角色能力或权限边界时，才引入子任务与交接。

协调者提出分工，可信控制层签发委派权限。子任务绑定根任务、父 Run、目标、输入版本、输出 Schema、验收条件、预算、截止时间与是否允许继续委派。有效权限取原用户当前授权、可转授范围、角色需求和工具实时策略的交集；角色名不授予权限，子 Agent 也不能通过父级或同伴绕开拒绝。

每个子任务拥有私有消息、执行上下文和可写范围。公共目标、硬约束和已确认事实由根责任层维护，角色只获得有权读取的投影；原始日志、凭证和整段历史不默认广播。共享状态不能成为全员可写字典，工作者追加证据候选与产物，协调层通过版本和验收条件把它们接受为公共事实。

汇合需要声明必需分支、可选分支、截止时间、冲突裁决和部分结果规则。子结果有分歧时比较输入范围、证据时间、版本与推断依据，不能简单多数投票。必要证据不足则继续补证、交付明确受限的结果或转人工，不把多个弱结论拼成确定答案。

如果多个子任务修改同一资源，优先使用唯一写入者；需要并行修改时，分别基于相同基线产出固定补丁或变更集，由集成者核对并验证组合结果。各自通过不等于合并后通过。迟到产物进入受控验收，不直接激活已经结束的父任务。

父任务维护整棵调用树的预算、委派深度和派生数量。父任务结束后停止新委派，对受管子任务传播控制状态，保存部分产物，并继续核验在途写入。独立授权且明确脱离父生命周期的任务可以继续，但独立关系由控制层记录，不能由子 Agent 自行宣布。

14.5.1 失败分类、重试与安全拦截

错误不能只按 HTTP 状态码分组。Runtime 至少要知道错误发生在哪个边界、是否可能产生副作用、哪个对象仍有执行权，以及剩余授权与预算是否允许继续。相同的网络超时，发生在只读检索和创建工单之后，会要求不同的处理。

处理顺序是：读取权威事实 → 限制继续扩大影响 → 判断是否可安全重复 → 校验当前权限与预算 → 记录下一步及责任。暂时故障不等于可重试；未知结果不等于失败；补偿也不等于删除历史。无法自动判定时，保存可查询的阻塞状态、原因、责任人和下次处理时间，不能无限循环或静默丢弃。

是否重试，必须根据错误类型决定。网络超时、限流和暂时不可用通常可以退避后重试；schema 错误、权限拒绝、用户取消、预算超限和确定性的业务错误不应自动重试；模型输出不合格时，可以有限次地重新采样，但每次都要新增 Attempt 并计入成本。AIP-194 默认只自动重试 UNAVAILABLE；本表把部分超时、限流纳入重试是本书在只读或明确幂等契约下的策略，不能仅凭“网络错误”就重试有副作用的请求 [8]。下表给出 Runtime 面对常见观察时的处理方式。

重试预算还必须覆盖整个调用树。HTTP 客户端、Agent SDK、工作流引擎和消息消费者如果各自执行最大重试，实际调用次数会成倍放大，远超业务预期。因此需要一个统一的根预算，把重新采样、工具重试、查询对账、委派和孙任务都计入同一账本。最接近具体错误的一层可以决定是否退避，上层仍负责总次数、总费用和最终停止。

把安全检查落实到执行边界

外部文档、检索结果和工具返回可能包含恶意指令。提示词注入的风险在于把数据内容误当成更高权限的指令；输入或输出扫描只能减少部分风险，不能构成完整隔离。[12] Runtime 因此在上下文中保留来源与可信级别，在工具入口核对身份和资源，在执行后端限制实际可达范围，并对输出与交付再次检查接收资格。

只读权限也需要限定资源和用途；允许查询一个项目不能借通用搜索工具读取所有项目。错误修复、换模型、改工具和委派都不能扩大原授权。敏感内容的脱敏要在进入模型或发送给接收人之前发生，不能只在日志展示时隐藏。权限拒绝作为结构化结果保存，供后续规划避开，而不是让模型自由寻找另一条高权限路径。

证据不足属于任务层面的失败条件。工具返回部分结果、数据来源冲突或引用无法支持结论时，验证器记录具体缺口，允许在剩余预算内补证或有限修复；不合格输出不能被格式正确掩盖。保存输入与检查结果后，才能判断缺陷发生在检索、工具契约、上下文、推理还是验收规则。

14.5.2 持久投递、去重与积压恢复

创建任务时，系统通常要做两件事：在数据库中写入 Task 和 Run，再向消息队列发送一条“任务已创建”的消息，唤醒调度器。如果这两次写入彼此独立、不加协调，就称为裸双写。数据库和消息队列不在同一个事务中，无论先写哪一个，都会留下一个故障窗口。

调整数据库写入与消息发布的顺序，只能在两个窗口之间选择，无法同时关闭它们；如果另有持久扫描器修复漏调度，该扫描器本身也构成接续协议的一部分。

Transactional Outbox 模式的做法是：把待发送的消息写入同一数据库中的 outbox 表，并与更新业务实体放在同一个事务里提交，再由独立的 Relay 进程把 outbox 中的记录发布到消息队列 [13]。这样，“任务存在”与“待发消息存在”要么同时成立，要么同时不成立，两个窗口都被关闭了。不过，Relay 本身仍可能重复发送，所以下游依然需要去重。

本章采用的参考契约是：在同一个数据库事务中写入 Task、Run、初始 Step、RUN_CREATED 事件和 outbox 记录，事务提交成功后，才向客户端返回 task_id、run_id 和查询入口。需要注意，单个关系数据库事务的原子可见性只覆盖该数据库内的操作 [14]；消息队列和第三方工具都不在这个事务之内。

客户端丢失受理回执后，沿用原 request_key 查询或重试。受理去重、消息去重和外部动作幂等分属不同边界；Outbox 持久存在只能证明工作可被重新发现，不能证明 Worker 已运行或业务已经生效。

Relay、CDC 与消费确认

Relay 有两种实现方式。一种是轮询已提交的 outbox 记录；另一种是变更数据捕获（Change Data Capture，CDC），即直接读取数据库的事务日志，把新提交的 outbox 行转成消息。一种 Outbox 事件路由实现使用事件身份供下游去重，使用聚合身份作为消息 key，让同一聚合的消息保持分区内顺序 [15]。这种顺序并非全局总序，connector 的重启、重放和 offset 管理仍需要运维投入。

采用轮询时，同一 aggregate 的消息需要按序串行认领与发布；跨 aggregate 可并行。仅对 outbox 行使用 SKIP LOCKED 分批认领不保证同一聚合的顺序；若选择不保序，消费者必须用 state_version 检测缺口、缓冲或重查权威状态，不能按到达顺序覆盖。[13]

支持行锁的数据库可以用 FOR UPDATE SKIP LOCKED 分批认领 Outbox；这种不一致视图适合队列表避开锁等待，不适合一般的一致性查询。[16] Relay 用短事务认领带期限的记录，在事务外发送，再条件更新发送标记；超期未确认的记录允许重投，不能持有长事务等待网络返回。

无论采用轮询还是 CDC，“发送成功”之后、“发送标记或 offset 提交”之前崩溃，都可能造成重复发送。Outbox 避免的是业务已提交而待发意图没有记录这一类丢失；实际推进仍依赖存储耐久性与 Relay 可用性。接收端用固定 event_id、Inbox 唯一约束、逻辑 Step 和当前版本去重，这就是幂等接收者（Idempotent Receiver）模式。[17]

消费确认（ACK）的时机同样重要。消费者应在同一个事务中保存 inbox 记录和可恢复的调度事实，提交之后再向消息队列确认。如果在确认前崩溃，消息会被重投，消费者发现记录已经持久化，就幂等地返回。ACK 不能早于必要状态的持久化；但也没有必要让消息队列的连接一直挂到数小时的执行结束。消费者只需把“待执行的 Step 及其归属”可靠地接走，后续执行由基于持久状态的调度器管理。消费者抢占失败、任务已经终结或消息已经过期时，分别记录处置结果，不能把重复消息当作新的 Run。

Outbox 需要监控以下指标：最早一条未发送记录的等待时间、重试次数、毒消息数量、CDC 延迟，以及 Task、outbox 与队列三者之间的差异。系统还要定期核对“已接收但没有可调度 Step”的任务。无法解析的消息进入隔离队列，并附上 schema 版本、失败原因和载荷的受控引用；修复传输或实现问题后沿用原来的 event_id 重放，不能换一个 ID 来掩盖重复。队列只是唤醒和传递机制，权威的执行状态保存在持久库中。消息队列短时不可用时，任务仍然可以查询；容量已满时，应当拒绝新的提交。

队列恢复与死信处理

消息系统恢复之后，不能立即释放全部积压。大量旧任务会同时申请模型、数据库连接和外部接口；如果每次失败又引发新的重试，就可能造成第二次过载。调度器应按租户、任务优先级、工具和目标资源控制并发，先过滤掉已经取消、过期或完成的工作，再在剩余预算内安排重试。队列年龄与未决 Operation 的年龄需要分别监控：前者反映工作没有被接走，后者反映外部业务事实还没有收敛。

死信队列保存不能自动处理的消息，但消息进入死信队列并不等于问题已经修复。每一项被隔离的工作都要能追溯到原任务、schema 版本、错误原因、载荷的受控引用、修复责任人和截止时间。重新投递时沿用原有的消息身份和业务身份；换一个 ID 让消费者“重新处理”，会绕过原有的去重机制。如果参数需要修改，应当形成明确的新提案并重新授权，不能改写旧消息后继续沿用旧的批准。

14.5.3 租约、执行权与迟到提交

worker 领取 Step 时获得一份带期限的租约（Lease），执行期间持续心跳续租；worker 失联后，控制面等租约过期再重新调度。数据库认领需要同时满足几个条件：Step 仍处于可运行状态，重试时间已到，旧租约已经过期，配额可用。满足条件后，认领事务原子地递增执行权代次，并写入新的执行者和租约到期时间。租约时间以服务端受控的时钟为准，执行权代次必须是持久保存的单调整数；随机生成的锁值不能充当 fencing token。

租约不能替代幂等。在网络分区下，旧 worker 可能在租约过期后恢复，并提交一份迟到的结果；外部工具也可能在 worker 失联后继续执行。为此需要 fencing。fencing token 是每次授予执行权时发放的单调递增编号，本章以 (tenant_id, run_id, step_id) 为节点执行权命名空间，owner_epoch 只在此范围可比；资源端按该命名空间记录最大代次。跨 Step 争用同一资源时，另发资源级单调 token 或由串行网关裁决，不能比较两个 Step 的本地计数。执行者的每一次写入都携带这个编号，由被写入的资源检查：凡是小于该命名空间已接受最大编号的写入，一律拒绝。fencing 方案要求每次写入携带单调 token，并由资源端负责拒绝旧 token [18]。

资源端在接受受保护写入或显式推进写屏障时，原子检查并更新最大代次；普通只读查询不推进屏障。下图假设工具支持独立屏障接口；若不支持，不能因 B 查询过就声称 A 的写已被隔离。这一显式屏障是本书参考协议的附加设计。

心跳只能证明执行者还活着，不能证明任务在推进。心跳中应包含进度序号（progress_seq）、资源占用、当前 Attempt、Checkpoint 和预计完成时间，但不上传敏感内容。只有进度序号的增长、已提交的产物和 Step 的变化才证明有进展；心跳正常而进度长期不变时，必须诊断依赖阻塞、空转和锁等待。控制面据此识别卡死、慢任务和预算超支，必要时暂停或迁移。迁移策略写在工作流中：尚未驱动已提交后继的模型 Step 可按新 Attempt 重算，否则复用记录结果；有副作用的 Step 先查询，人工 Step 继续等待或转入其他队列。

14.5.4 外部副作用、未知结果与补偿

幂等的责任必须落实到具体边界。Runtime 为每个逻辑业务调用保存 operation_id；消息仍可能重复，所以接收方要以稳定身份幂等接收；工具适配器负责把操作幂等键传给下游；真正拥有业务状态的订单、邮件、文件或支付系统，则必须决定对同一个键的重复提交如何返回同一个事实。如果下游只提供“尽力而为”的 HTTP 接口，Runtime 仅凭本地的去重表无法承诺业务幂等，因为请求提交后网络断开，会留下一个本地无法判定的未知状态。幂等接收者（Idempotent Receiver）模式把去重与消息接收边界绑定在一起 [17]；在 Agent 系统中，这一边界还要覆盖模型重试、队列的至少一次投递和人工重放。

幂等 API 的设计经验表明，稳定请求标识表达业务意图，同键异参应报告冲突，去重记录和业务变更由资源端原子处理。[19] 本章据此把 operation_id 与操作幂等键绑定到原业务动作，在模型重新采样、传输重试和 Worker 接管时保持不变。键可以是不透明标识，也可以关联租户、业务对象、动作与授权版本，但必须区分两次独立意图。

如果模型每次重试都重新生成操作参数，系统必须先比较规范化载荷：意图相同，就查询或去重；意图不同，就是一个新操作，可能还需要新的审批。规范化载荷的哈希只适合发现“同键异参”，不能单凭参数相同推断用户只想做一次。两次独立授权、参数恰好相同的购买，仍然代表两个业务意图。反过来，把“看起来相似”的自然语言当作幂等键会造成错误合并，为同一操作随机生成 UUID 又会造成重复副作用。

Operation 的事实状态决定了下一步可以做什么：

操作事实状态可采取的下一步禁止的推断
INTENT_RECORDED（已记录意图）重新验证审批和版本后发起，或先查询意图存在就当作业务已完成
SUBMITTED 或 UNKNOWN（已提交或结果未知）用原幂等键查询、对账并等待把超时当作未执行，换一个键重发
CONFIRMED_SUCCESS（确认成功）保存外部对象版本和证据，补记 Step用迟到的旧 worker 回执直接覆盖 Run 终态
CONFIRMED_FAILURE（确认失败）按错误类型和业务契约修复，或有界重试对所有 4xx 和 5xx 一律同样处理
COMPENSATING（补偿中）使用独立的补偿 Operation 和独立的幂等键删除主动作的历史，伪造“从未发生”
NEEDS_RECONCILIATION（待对账）指定责任人和截止时间，收集查询或人工证据没有查询能力就猜测成功或失败

外部查询返回“没查到”时，也要考虑下游的一致性和保留窗口：结果可能尚未可见，键可能已经过期，请求也可能仍在途中。只有下游契约足以确认“不存在”，并且重试是安全的，系统才继续用同一个键尝试；否则保留 UNKNOWN 状态。预算或审批到期时，未决事实不能被删除；系统停止新增动作之后，仍要核对已经发出的请求。

幂等记录也需要生命周期管理。短期通知可能只需在业务 SLA 窗口内保留键，财务、权限和数据删除类操作则需要更长的审计与重放窗口。记录至少保存 operation_id、载荷哈希、请求者、状态、外部引用、首次与最后一次观察时间、响应摘要、过期策略和责任人。删除过早，延迟到达的消息会再次造成副作用；永久保留，又会带来隐私和存储问题。保留期应结合下游重复投递的时间上界、合规要求和补偿窗口一起确定，并写进文档，不能依赖代码中的隐式约定。窗口过期后的恢复要先查询或转人工，不能把一个旧的幂等键当作新请求处理。

补偿为已发生的事实追加反向或缓解动作，拥有独立的授权、前置条件、幂等键、截止时间与验收。已发通知不能抹去接收人的阅读，恢复文件版本也可能覆盖后续人工修改。Saga 将局部事务及其补偿组织成长事务，提供协调思路，不承诺所有影响可逆。[20]

因此，补偿计划应在执行主动作之前就确定下来。工具注册表声明正常操作、成功证据、补偿操作、无法补偿的后果、人工责任人和最长等待时间，工作流在跨越不可逆边界之前检查这些字段和审批。对于没有安全补偿手段的高影响动作，设计上应改为预览、双人审批、延迟提交，或由业务系统提供事务性 API，不能把风险留给模型临场判断。

补偿完成也要按业务事实验收。HTTP 200、队列已接收或模型声称“已恢复”都不足以证明完成；Runtime 需要保存查询到的版本、外部对象状态或人工确认。如果主动作只完成了一部分，可以选择继续完成剩余部分、撤销已完成的部分，或交给人工处理，这三种选择对成本、可用性和用户预期的影响各不相同。工作流定义应把这一选择写成版本化的决策，不能让新 worker 在事故现场临时猜测。人工处理完成后，以事件关闭这项工作，不能直接修改历史状态。

14.5.5 Checkpoint、持久执行与版本恢复

长任务可能运行几分钟、几小时，甚至要等待人工或外部事件。进程内的状态和内存队列在重启后会丢失，所以 Runtime 需要持久化的事件、Checkpoint、定时器、信号和活动（activity）结果。一种持久工作流实现通过有序事件保存状态、活动结果、重试与定时器。[4] 自建数据库事件表也需承担同样的重放、版本和并发责任。

确定性重放与记录结果。 工作流重放必须用记录的模型、工具与外部观察结果重建决策；模型输出不确定，已经驱动下游提交的输出不能重新采样替换。一种方式把非确定的模型与工具调用封装成独立活动并记录结果，重放时由历史驱动确定性决策。[21] 另一种方式从节点检查点重新进入，未提交节点可能从头执行，因而必须保证副作用已有稳定身份和可核验结果。持久化也有同步、异步和仅在退出时保存的差异：同步保存缩小下一步前的丢失窗口，异步保存增加吞吐但可能丢失最近进度，仅退出时保存则无法兑现执行中崩溃后的续接。[22]

持久化并不意味着每个 token 都写一次数据库。模型的流式输出可以写入 Artifact、摘要或可恢复的偏移量；关键的状态迁移、工具请求、审批和结果则必须持久化。

恢复设计要先回答“恢复什么”，再选择存储技术。不同节点的恢复方式差别很大，如果把它们统统叫作 retry，不同的业务后果就会被压缩成同一个按钮。Runtime 应在 Step 的定义中声明恢复类别，并把分类与工具版本一起保存：

恢复类别典型节点恢复方式恢复前需要验收的条件
replayable（可重算）无副作用计算；未被已提交后继消费的模型调用纯计算重算；模型优先复用记录，重新采样另记 Attempt已驱动提交的模型结果不可替换；当前权限与预算有效
idempotent（可幂等重试）有明确幂等契约的工具动作；允许重新观察的检索保持逻辑调用身份；有外部写入时保持原 Operation数据版本与权限符合契约，写入幂等窗口仍有效

等待外部事件的节点，恢复时还要检查关联标识（correlation id）、签名、截止时间和取消状态。把所有 Step 交给一个通用的重试中间件，会遗漏上表中的业务条件。通用框架应提供状态、租约、超时和事件等基础设施，具体的恢复分类则属于工作流与工具契约。

恢复边界之间可能出现“请求已发出、事实未知”的窗口。此时沿原 Operation 查询并保存观察；查询不能消除不确定性时转入核验队列，禁止自动复制业务动作。可重算内容、已确认事实和未知副作用必须分别处理。

Checkpoint 是已验证进度和未决 Operation 的恢复索引，不保存完整进程内存，也不能撤销外部副作用。一个可用于恢复的 Checkpoint 至少包含：

  • Run 与工作流修订版，当前状态机节点；
  • 已完成和待完成的依赖，每个 Attempt 的记录；
  • 预算消耗与截止时间；
  • 上下文与记忆的不可变引用；
  • 已发出的 Operation，租约与 fencing token；
  • 审批状态和定时器。

Checkpoint 还要标明哪些字段是观察结果、哪些是模型给出的候选、哪些已经成为外部业务事实。没有这条界线，恢复 worker 可能把上一次模型的自然语言结论当作已提交的结果，或者在重放时漏掉已经开始的补偿。

写入点由恢复需求决定，不能只按固定分钟间隔保存。只读步骤可在完整结果边界提交；外部写入则分别记录意图、回执与补偿进展。密集写入增加存储成本，稀疏写入扩大进度丢失窗口，取舍应通过恢复实验验证。模型流可以保留偏移量和载荷引用，最终业务状态仍需独立提交。

提交 Checkpoint 时要遵守联合提交边界。同一数据库内的 Step 结果、状态版本、关键事件和完成通知的 outbox 记录，应尽量放在一个事务中提交。大型 Artifact 要先完整写入并校验哈希，再提交指向它的引用；不能先推进进度、事后再补载荷。恢复时，系统要校验 Checkpoint 引用的载荷是否存在、版本是否兼容、权限是否仍然有效；载荷缺失时，不能跳过该 Step 假装它已经完成。

Checkpoint 接口需要声明恢复粒度、持久化时机和重入范围，不能仅凭接口名称推断恢复能力。事件历史重放与节点快照是不同实现，二者都需要独立处理非确定调用、外部写入和版本兼容。

事件归档与快照压缩应保留恢复需要的状态、预算、版本、未决动作和引用，以及审批、补偿与安全事件。归档结果可以查询；重新激活须重新校验权限和预算，不能把已消耗额度清零。删除或保留载荷时同时处理引用与访问策略，避免快照保留一条实际已不可用的恢复路径。

恢复先读取最近一致边界，检查载荷、格式、版本与当前权限；再通过条件认领取得新执行权，隔离旧提交，按节点恢复类别安排执行。资源端写屏障和原 Operation 核验随后按副作用契约落实。不能从旧快照读取一个 owner 标识，就推断新进程已经拥有执行权。

Run 绑定工作流、输入、上下文和工具版本，恢复不能随默认值升级而改变节点、重试与补偿语义。旧制品不可用时，选择兼容适配、保留旧环境或在安全边界显式迁移；迁移记录旧值、新值、转换函数、检查结果和回退路径。未证明兼容时暂停，不用新定义重新解释旧动作。当前撤权、删除和紧急封锁始终优先于历史版本固定。

恢复动作与重规划的边界

恢复还原原执行的权威进度，重规划修改未来路线。新计划保存版本、变更原因、可复用证据、失效审批和受影响后继；未决 Operation、取消意图和已消耗预算继续保留。目标或授权变化需要明确接受，输入或资源版本变化使原验收失效。激活新计划时校验依赖，拒绝迟到的旧计划结果推进新汇合点。

事件到达时，Run 可能已经取消、超时或完成了版本迁移。处理器根据当前状态和事件版本，决定忽略、记录还是触发补偿，不能盲目地继续调用工具。外部事件的载荷是不可信的观察结果，进入模型之前必须经过 schema 和权限检查。在消息中间件只提供至少一次投递的前提下，状态机和幂等是正确性的基础。

14.5.6 取消、授权变化与人工接管

取消、截止时间到达或预算耗尽后，先持久记录停止推进的决定，阻止新的认领、模型调用、工具动作与委派，并向可中断的执行后端传播信号。进程收到信号不等于外部请求已撤销；任务终态与业务动作事实分开保存。

对于已经在途的 Operation，迟到成功仍需写入原账本并核验证据，但不能把已取消 Run 改回运行中。随后按当前权限决定是否补记、补偿或转人工。核验与安全收尾需有单独声明的责任和受控资源额度，不能以“预算已用完”为由丢弃事实，也不能借收尾无限执行新业务。

超时还要区分单次调用与整个 Run：前者可能只终止一个 Attempt，后者限制任务继续推进，两者都不能证明下游未执行。心跳存在但长期无事实增量时，按证据与参数指纹识别无进展候选，限制重规划，必要时暂停或转人工；不能只按同一工具出现次数判断循环。

面向用户明确展示“已停止继续执行”及“仍在核验的动作”，不要让一个 cancelled 标签掩盖已发生的副作用。

Policy 的 deny(action) 禁止当前动作，可以在原目标与权限内有界重规划；deny(goal) 表示目标本身不允许，记录 FAILED 及目标拒绝原因。escalate 转入 PAUSED 和待认领人工工作项，由指定角色判断或接管，不能被解释为普通的用户确认。

审批超时、批准过期或对象、参数、资源版本发生变化时，原批准不能直接复用。保存失效原因与原绑定关系，重新裁决并根据当前事实请求批准；拒绝不能通过改用另一个工具或子 Agent 绕开。重复审批事件按原身份返回既有决定，冲突决定进入明确的裁定流程。

无人接管、证据不足或无法安全自动处理时，任务保持可查询阻塞并公开责任与下次处理时间。人工可以批准一个有边界的风险选择，但不能把未知外部结果变成凭空确认。协议细节见 14.4.5。

Connection 授权失效时保存授权等待与原绑定，不能自动换成更宽权限连接。重新授权也不能证明先前写请求未发生：写入回执丢失仍沿原 Operation 与业务键查询；撤销连接不等于取消在途写入，无查询或幂等能力时转人工核验。

进入审批后，Step 转为等待批准，Run 标记 WAITING 并记录 wait_kind=approval，Runtime 释放 Worker，只保存持久订阅、恢复条件和截止时间。审批超时按契约暂停或失败，不会自动视为批准。重复决定、伪造回调和过期批准不能让任务重新开工；取消后，待审批动作随之失效。

接管的责任人

需要人工接管时，系统应当交付一份可以立即处理的工作项，包括：目标、当前状态、已确认与未知的事实、证据位置、建议的查询或补偿、允许执行的范围、责任人和截止时间。仅仅返回“请联系管理员”，并没有形成接管协议。人工队列需要支持认领、转派、到期升级和关闭证据；人员离线、交接班和重复点击，也都属于恢复设计要覆盖的情形。人工操作同样受租户、角色、双人复核和审计的约束。

人工修复不能直接把状态改为 ready。修复记录要包含原 Run、Operation、已确认和未知的事实、错误与版本、预算、建议的恢复点、风险、责任人和截止时间。操作者先通过权限检查和条件更新取得新的执行权代次，使旧执行的提交失效，再查询已经发生的副作用；然后按工具契约选择补记事实、恢复特定 Step、授权补偿，或继续核验。重复点击按同一 repair_id 幂等处理，批量恢复限速并观察容量，结果附上外部证据。MANUAL_REPAIR 表示核验工作项仍待处理，不是 Run 成功状态；到期未响应时按责任链升级。

可恢复的运行保留在 PAUSED 或 WAITING。COMPLETED、FAILED 和 CANCELLED 不经普通 resume 回到运行；用户明确要求重新执行时创建新 Run，并关联原动作与结果。补记外部事实只更新核验记录，不改变原执行终态；新执行也不能重复制造尚未核清的原业务意图。

当工具、模型或权限出现异常时，Runtime 可以把任务降级为只读建议模式：继续收集证据、给出建议，但不再发起有副作用的动作。降级本身是一次状态迁移，需要记录原因、生效范围和恢复条件；未决的 Operation 不会因为降级而消失，仍要按原契约查询或交给人工。

恢复后如何继续

批准、拒绝、修订参数、确认事实和授权补偿是不同事件，由同一控制面接受。继续之前复查取消、预算、权限和资源状态；人工回交附带证据，未决项保留核验与升级责任，不能直接修改数据库或把按钮点击当作完成依据。

14.5.7 交付与协作故障的收敛

**C6 完成、C7 未发送：**从已提交的交付 Outbox 继续发送，不重新执行任务或重算答案。**渠道已受理、本地未保存回执：**交付状态为未知，按原交付幂等键或渠道查询核对；渠道无去重和查询能力时，必须明确接受漏发或重复风险，不能承诺严格一次通知。

交付前检查当前代次、接收人、权限与产物版本；读取旧 Run 的查询仍关联其原结果，不应错误指向当前执行者。SSE 断线按持久游标续订，游标过期提供快照与重新同步入口，不能为了续流新建 Task。

接管还会与旧消息发送竞争。发送前在同一资源归属边界取得持久发送占用，接管检查该占用；旧代未发送消息失去资格，已经在途的发送则先核验收敛。Worker 租约过期不能自动清除“是否已发送仍未知”的占用。

若要求未知发送仍在途时立即接管，就必须接受旧消息晚到，或使用支持版本检查的交付渠道。界面应分别展示任务完成与通知状态，渠道失败不改写已验收的任务事实。

子 Agent 失联、超时或提交不合格结果时，协调者先读取子任务持久状态与已提交产物，区分没有开始、只读计算中断、已提交结果和存在未决副作用。可以局部重算的分支沿原子任务建立新 Attempt；有写入的分支先核对 Operation，不能重新委派就重置业务身份。

输入、契约或计划版本改变后，迟到结果可以进入历史审计，但只有满足当前节点验收条件的结果才能参与 join。重复交接消息持久去重；共享可写资源通过隔离、串行或版本合并处理，不能靠“Agent 已完成”推断冲突解决。

父任务取消时停止新委派，传播取消并保存各子任务状态；仍在途的写入、交付和补偿继续有明确责任。部分分支成功后，父任务按契约决定是否接受部分结果、等待、替代或人工处理，不能在缺少必要证据时宣布完整成功。

互相委派、重复审阅或嵌套 Loop 可能形成协作空转，根预算、委派深度与进展检查需要覆盖整棵调用树。只增加 Agent 数量不能增加总授权或预算。协作对象与交接契约见 14.4.9。

同一 message_id 携带不同载荷时拒绝并记录冲突；早到的依赖结果先保存，不跳过前驱验收；旧计划、旧执行权和旧输入的结果不能覆盖当前事实。消息去重阻止重复接单，Operation 幂等阻止重复业务生效，执行权校验阻止旧提交，三种机制不能用一个锁标志代替。

父任务处于终态并不代表所有远端操作都消失。协调层持续管理未决清单，明确由哪个 Run、核验工作项或人工责任人收尾；资源回收不能删除这份清单。受理新的调查或恢复分支时先核对旧动作，避免独立子任务在后台重复写入。

队列长度、并发、委派深度、消息体积和截止时间共同约束协作容量。恢复积压时按根预算与资源配额限速，永久错误转入有责任人的隔离队列。对迟到补充结果，要根据当前权限决定可否保留或展示；可以作为历史证据的产物，也不一定仍有资格参与当前任务汇合。

14.6 工程实现与渐进建设

能力扩展由需求触发，持久化、写入与并发各有独立的验收责任。本书参考设计，点击图片查看 SVG。

实现 Runtime 可以从单进程开始，按任务需要增加持久性、受控写入和并发。组件是责任边界，不是首版部署清单；每次引入新机制，都应明确它解决了什么失败、需要维护什么状态以及怎样验收。

14.6.1 最小实现与模块接口

先固定服务对象、可读取的材料、交付格式、允许动作、完成条件和失败出口。路径稳定时，用确定性代码组织输入、模型调用、输出验证与返回即可。最小实现仍需要身份、权限、有界执行和诊断，但可以使用请求内状态，并明确进程退出后不能继续原计算。

  context        # 授权证据、消息、记忆、输入版本

这个目录只示意逻辑分工，可以先合并成少量模块。模块之间使用明确的输入输出契约，客户端、连接池和只读描述可共享，用户上下文与执行状态按 Run 显式传递。用接口隔离存储与后端实现，使内存状态升级为持久存储时，不必重新解释任务、步骤和动作身份。

实现顺序可以从一条路径走通：接入建立执行上下文，Context Builder 筛选材料，模型返回候选，Verifier 核对要求，交付接口返回结构化状态和产物引用。错误具有稳定分类，取消和截止时间贯穿调用链。先观察目标完成率、证据质量、耗时与单位成功任务成本，再判断动态 Loop 是否带来收益。

这个阶段重点验证输入边界和失败行为：缺材料时是否说明缺口，无权限内容是否不可见，模型超时或格式错误是否有界停止，正常答案是否满足任务契约。不要因存在一个可运行的循环，就额外加入长期记忆、复杂计划图或多个角色。

业务代码需要的接口是“受理、推进、查询、控制、验收和交付”，而不是直接访问某个 SDK 的进程内消息数组。即使首版尚无持久库，也应让状态访问经过单一接口，分开领域状态、工具观察和用户展示，后续才能替换实现而保留语义。

14.6.2 从固定路径到受控工具循环

当用户开始问“为什么这张工单延迟”，固定上下文不再足够，就加入检索、工单查询和日志等只读工具。Runtime 需要工具目录、输入输出 Schema、逐动作权限与风险校验、超时和结构化 Observation。模型可以在有上限的循环内根据观察选择下一步；稳定的步骤继续由代码编排。此时状态仍可保留在一次请求中，工具失败要转为明确的观察或失败结果，不能无限重试。

新增工具首先补齐契约：输入输出 Schema、身份与资源范围、只读或写入性质、超时、可机读错误，以及结果的来源和时效。模型只看到本轮允许请求的能力，返回的名字映射回可信注册对象，每一次派发都重新裁决。固定的制度查询路径与动态调查可以共存，稳定步骤继续由代码执行。

在工单延迟调查中，可以先限定为读取工单时间线、制度和授权日志，要求结论引用具体证据；当信息不足时允许补查，但不允许顺带修改工单或通知客户。查询失败形成结构化观察，由 Runtime 根据原因决定补证、澄清或停止，不能让模型把失败文本解释成查询已成功。

这一阶段验证的是补证能力是否带来实际改善：是否覆盖更多有效来源，是否减少无依据结论，是否仍满足时间与成本限制。要同时检查无关查询、重复查询和错误来源；如果固定路径已经达到目标，保持固定 Workflow 就是合理结果。工具契约、任务装配与裁决按本章执行链路统一验证。

引入动态选择后，将确定性步骤留在代码里，让模型只决定确实未知的部分。能力目录先用静态描述即可，重点保证工具名映射可信、参数校验一致、权限每次求值、错误可被状态机理解。工具数量增加时再加入按任务筛选和延迟加载，不要让模型每轮都承担无关能力的选择成本。

模型接入层应保存完整调用生命周期：请求开始、首个增量、完成或异常、用量和取消结果。各层超时与重试共用根预算，避免适配器重试后外层又按完整额度重试。对大结果建立摘要与下钻接口，并用覆盖范围和完整性字段阻止“查询失败等于没有问题”的误判。

工具接入的验收比较固定基线与新循环在同一任务集合上的表现，检查新证据是否真实改善结果，同时观察无关查询、重复查询和长尾成本。需要保留简单路径作为可用的受限模式；来源异常时可以减少交付范围，但不能用模型推测填补证据。

14.6.3 增加持久任务与受控业务写入

当任务跨越请求、需要等待人工，或者进程重启后还要继续，就把请求内状态升级为持久任务状态。增加 Task / Run / Step 状态机、事件、Checkpoint 和恢复入口，让系统知道已完成什么、正在等待什么、下一步可以做什么。恢复前还要核对外部动作是否已经发生；Checkpoint 保存执行位置，幂等键、动作回执与对账机制共同避免重复副作用。长任务并不要求立刻拆成分布式系统，单进程配合持久存储也能先解决恢复问题。

变化的核心是把执行责任从当前进程移到持久记录：任务受理后可以按原 Task / Run 查询，稳定 Step 边界保存结果与版本，等待审批、定时器或外部作业时释放 Worker。恢复读取原契约、配置与事实，已接受的结果不因重启而被新的模型输出替换。

存储接口可用与重启后可恢复是不同的验收。可插拔持久化接口必须使用满足故障模型的实现，内存存储无法证明进程退出后的耐久性。[5]本场景应通过中断实际执行者、重新打开任务和读取产物来检查承诺：受理记录仍在、已提交结果仍可用、未决动作仍可核对，并且预算不从零重新开始。

只读长任务也需要考虑证据权限和时效。恢复时若材料已删除、授权已撤销或原工具版本不可用，应明确暂停或进入受控迁移；持久快照不赋予永久访问权。具体恢复边界见 14.5.5。

当业务要求“批准后创建跟进工单”，新增的是一项受控业务承诺。Runtime 需要保存草稿、目标项目、规范化参数、目标资源版本和批准主体，执行前核对当前授权；“认可调查计划”“草稿已生成”“批准创建”和“工单已创建”分别记账。

写入前建立稳定 Operation，绑定幂等键、参数哈希与审批关联；后端返回或可查询的工单编号和状态才构成成功证据。幂等 API 设计强调用稳定请求标识表达意图，并检测同键异参[19]。在本场景中，Runtime 还需沿同一意图核验未知结果，不能因重新采样、换 Worker 或用户重连就生成新业务动作。

验收要覆盖写入后的关键不确定窗口：后端已经成功但本地未记账时，能否查到原工单；重复请求是否仍关联原动作；批准过期或参数改变是否阻止旧批准继续生效；取消之后的晚到成功是否保留为事实。自动补偿同样需要独立权限和完成证据，不能假定关闭工单就抹去了外部影响。

若下游既不支持稳定幂等，也无法查询结果，先保留草稿与人工创建路径。可以减少自动执行范围，但不能用本地去重表替代资源端保证。相关意图、回执与补偿边界见 14.4.6 和 14.5.4。

持久化首版可以使用一个关系数据库保存任务、步骤、事件、等待和 Outbox，Worker 与 API 仍在同一进程。启动扫描器发现可运行步骤和到期等待；状态条件确保重复扫描不会制造新的逻辑动作。持久队列和多进程只是后续部署选择，不是实现恢复的前提。

引入写入前先做能力清单：目标资源是否支持稳定幂等、结果查询、资源版本和安全补偿。不同工具可能提供不同保证，Runtime 应按工具契约决定自动化范围。确认安全能力缺失时保留预览和人工执行，不让一个统一执行接口掩盖下游差异。

从只读调查升级到业务写入，验收必须增加未知结果、批准失效和取消竞态。对外声明的保证应能落到资源端证据：本地没有重复记录，不等于外部没有重复动作；任务可恢复，也不等于业务动作可以安全重放。

14.6.4 并发、分工与平台化的触发条件

并发增多时，先确定瓶颈位于排队、模型额度、工具限流、状态写入还是产物处理。为现有 Step 增加 Worker、隔离工作区和公平配额，通常不需要改变 Agent 的角色结构。队列、租约和执行权让工作可以分配，但 Task / Run、Operation 和根预算的归属保持不变。

例如制度调查与日志调查可以并行，但是否值得由两个 Agent 完成，要比较它们能否独立交付、是否需要不同上下文或权限，以及汇总是否增加错误和成本。两个普通并行工具调用已经足够时，无须再引入角色身份、信箱和交接协议。

确需多 Agent 时，接收方认领、提交结果与父任务验收分别保留事实。子 Agent 的“已完成”不能直接推进父任务，独立补丁分别通过检查也不能证明组合结果正确。沿 14.4.3 与 14.4.9 验证依赖和交接，再按 14.5.7 检查失联、迟到和取消后的收敛。

当多个应用都在重复实现能力注册、任务状态、审批或产物交付，可以逐项评估共享价值。先明确共享组件接收什么契约、持有什么状态、如何绑定版本，以及失败由谁处理，再决定是否独立部署。相同的模型调用代码并不意味着业务目标、权限与补偿语义也可以统一。

适合共享的通常是稳定机制，例如目录与版本管理、持久调度、观测接口和审批记录；业务完成条件、资源端幂等与补偿前提仍需由各应用及后端定义。共享后还要说明租户隔离、配额、公平性、依赖故障范围和旧版本保留策略，否则抽取组件可能把局部故障扩展到所有应用。

SDK 或框架选择同样按责任核对。可以使用现有循环、图和存储接口，但必须明确应用仍负责哪些契约。嵌套框架时尤其要避免双重重试、两套不一致状态和重复预算；迁移现有 Run 时保留原身份、Operation、审批与结果，不能为了切换实现而把在途任务当新任务提交。

平台化的收益应来自减少重复维护、缩短接入时间或改善已测得的任务结果。若只有一个应用，或者各应用的契约仍在频繁变化，继续保持应用内的清晰组件边界也可以；是否独立成服务应由部署与运维需求决定。

每个阶段都可以停留。机制没有改善完成质量、时延、成本或运维负担时，应缩小自动执行范围或调整设计。回退先阻止新动作，保留在途 Operation、查询与交付责任；不能关闭功能后把已发生的事实一并删除。配置、Prompt 和工具更新从经过验收的新版本生效，反馈形成改进候选，再经受控发布进入执行链。

本章小结

Agent Runtime 以任务契约组织目标，以版本化状态保存事实，以逐动作裁决限制执行。Session、Task、Run、Step、Attempt 和 Operation 分别表达连续交互、业务目标、执行、逻辑节点、尝试和外部动作；它们的身份不能因重试或迁移而混淆。执行循环通过可信能力完成工作，Checkpoint 和事件保存继续依据，幂等与资源端核验处理不确定副作用。取消、恢复与人工接管都在同一套状态和责任边界内推进，最后以验收过的产物与可查询的交付事实结束。
