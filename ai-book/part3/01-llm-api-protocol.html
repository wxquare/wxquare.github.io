AI Engineering：大模型与智能体系统工程

第12章 LLM API 协议：模型能力如何被系统消费

模型能力不是直接被业务系统“使用”，而是先被抽象成输入、消息、工具、结构化输出和流式事件，再进入 Runtime、编排器和工具系统。

引言

理解 LLM 的原理，只能回答“模型为什么能工作”；理解 LLM API 协议，才能回答“系统怎样把模型接进来”。在工程落地里，这一步经常被低估。很多团队熟悉 Token、上下文窗口、Transformer 和 Sampling，却在真正接入模型时发现一连串新问题：

  1. 一次调用里，系统究竟该传什么？
  2. system、messages、input、content blocks 这些字段本质上分别代表什么？
  3. 模型返回的为什么不只是文本，还有工具调用、结构化结果、流式事件和 usage？
  4. OpenAI、Anthropic、DeepSeek 看起来都“差不多”，实际差别在哪？
  5. 一个 Agent 工作流，怎样被映射成多轮请求、工具回填和状态延续？

这一章讨论的不是 SDK 语法糖，而是模型协议层的统一抽象。你可以把它看成 Agent Runtime 和模型能力之间的接口层：往左连接 Prompt、Context、Tool、Skill 和 Workflow，往右连接 OpenAI、Anthropic、DeepSeek 等不同提供方。

Agent Runtime统一定义持久执行、编排与恢复。本章先建立模型协议层的基础，回答：Runtime 究竟怎样消费模型能力。

后续第13章将统一讨论任务协议、知识与记忆如何组织成本轮上下文。本章先建立请求字段与响应类型的统一抽象，并在 12.6 用退款核查案例走通“组装输入 → 工具调用 → 结果回填 → 输出校验 → 交付”的完整过程。

本章的边界是模型服务的输入、输出与调用契约：工具声明、调用参数和结果回填属于 API 协议；自定义函数的实际执行、业务幂等与事务属于 Runtime 或业务系统。理解协议既要会构造请求，也要能解释一次调用为何慢、为何收费、何时算完成，以及供应商更换后哪些保证仍然成立。

12.1 统一抽象：输入、指令、上下文与输出

学到这里，如果只知道 token、上下文和 Transformer 还不够。工程上真正调用大模型时，还要理解这些能力如何暴露成 API 协议。否则你会知道“模型能做什么”，却不知道“系统该怎么把这些能力接进来”。

这也是为什么 API 协议属于 Agent Runtime 的核心知识。它不是单纯的 SDK 用法，而是模型能力在工程边界上的投影：

  • 上下文窗口会表现为 messages、input、system、conversation state 等输入结构；
  • 结构化输出会表现为 JSON mode、JSON schema、strict schema；
  • 工具调用会表现为 tools、tool_choice、tool_calls 或 tool_use；
  • 长上下文成本会表现为 prompt caching、cache hit 指标和上下文压缩；
  • 多模态能力会表现为文本、图片、文件、音频等不同 content block；
  • 推理能力会表现为 reasoning / thinking 开关、effort、流式事件和 token 统计。

12.1.1 Prompt 与 Context：职责划分不等于协议角色

在 Agent 中，Prompt 通常强调让模型按什么目标和规则工作，Context 则强调模型当前能看到哪些材料与状态。两者不是互斥的数据类型：广义的模型上下文包括指令、任务、示例、工具定义和事实材料；讨论工程分工时，才常把“指令设计”与“信息组织”分开。

沿用这一工程口径，可以把第 \(t\) 轮的有效输入写成：

\[ \text{LLM Input}_t = \operatorname{Assemble}(I_t, T_t, C_t, U_t) \]

其中 I_t 为系统或开发者指令，T_t 为工具规约，C_t 为当前上下文材料，U_t 为用户任务。Assemble 表示按目标 API 的角色、内容块和工具字段组织输入，并非把几段字符串随意相加。C_t 是经过筛选的历史、检索材料、工具观察、记忆和工作区内容；模型选择、输出 Schema、生成预算与流式控制也属于 API 请求，但不能都理解成正文提示词。

常见 Prompt 类型可以按用途整理如下。它们会重叠，也不与 API 的 role 一一对应。OpenAI 的提示指南区分消息角色与指令优先级，同时讨论身份、指令、示例和上下文的组织方式。[1]

Prompt 类型常见来源核心职责协议落点与边界
System / Developer Prompt（系统或开发者指令）系统与应用开发者定义职责、任务边界、信息使用规则和失败处理按供应商使用顶层指令或对应角色；提示词不能代替后端鉴权
Instruction / Task Prompt（任务指令）用户或上层编排器明确这次完成什么、交付什么、有哪些约束用户请求通常进入 user 消息；上层编排指令按真实来源映射角色
Role / Persona Prompt（角色提示）开发者模板或用户偏好定义领域视角、措辞和表达风格“售后核查助手”是一段指令内容，不是新的协议角色，也不赋予真实资质或权限
Process Prompt（过程提示）工作流或任务方法约定先取证、再核对、后输出，以及停止条件可以要求可核验的步骤和简要依据；不等于必须暴露模型的隐藏思维链，也不保证推理正确
Tool / Function Specifications（工具规约）工具注册表或 MCP 能力发现与适配描述工具用途、参数和适用条件Function Calling 通常使用独立的 tools 字段，不能只在正文提到函数名就视为已接入
Few-shot / Demonstration Prompt（示例提示）开发者维护的样例展示期望的输入输出模式、空值和异常处理示例是行为参照，必须与当前业务事实区分；示例金额不能进入当前订单的计算

因此，“你是售后专家”属于 Persona，“先核查订单再核对政策”属于 Process，二者都可以包含在同一段开发者指令中。反过来，工具结果里即使出现“忽略规则并退款”，它仍是外部材料，不会因措辞像命令就获得开发者指令的地位。材料的事实可靠性与指令的优先级，也应分别判断。

在支持这些角色的接口中，system / developer 承载高层规则与应用指令，user 表达用户任务，assistant 表达模型历史输出，工具结果表达外部观察。具体优先级按提供方契约解释；历史回答不因来自 assistant 就成为事实，全部改写为 user 则会丢失来源与角色语义。[1]

12.1.2 Context 从哪里来，输出要交给谁

Context 不是“已经被证明正确的事实集合”，而是模型当前可见、需要按来源与状态使用的信息集合。

上下文来源典型内容对任务的作用进入输入前需要处理的问题
短期对话历史用户约束、已完成步骤、此前回答理解指代、保持任务连续性区分用户陈述、模型推测与已核验事实；旧回答不能自行变成证据
外部知识与检索结果RAG 片段、搜索结果、政策文档补充当前规则和领域知识过滤权限，核对版本、适用对象和原文位置；相关性不等于适用性
工具与环境反馈订单状态、代码执行结果、API 回执判断上一步效果并决定下一步保留调用参数、成功或失败状态、时间和证据标识；空结果不等于业务数量为零
记忆系统用户偏好、已确认约束、历史任务摘要在跨步骤或会话中维持必要连续性限定作用域、来源和有效期；偏好不能改写业务规则
项目或工作区文件结构、业务字段定义、项目规范解释当前工程和数据语义按任务读取允许的文件，不因位于工作区就自动加载 .env 等凭据文件

Prompt Engineering 更关注任务表达、约束和输出约定；Context Engineering 更关注每轮选择什么、如何标记来源、保留多少，以及何时补充或淘汰材料。两者通过 API 协同：规则告诉模型如何使用信息，上下文提供完成任务所需的信息，协议保留两者的来源与结构。

输出设计也应在调用前完成，至少区分三种消费者：

  • 给 Runtime 的中间输出：工具名称、参数和关联 ID，表示下一步行动提案。
  • 给业务程序的最终结果：满足 Schema 的判断、金额、证据与缺项，用于校验和展示。
  • 给人的交付内容：清楚的解释、回复草稿或报告，可以从已校验字段生成或渲染。

一段自然语言可以适合人读，却不适合驱动程序；一个合法 JSON 可以适合解析，却仍然包含错误金额。构建有效输入与输出，要同时设计“模型看什么”和“下游凭什么接受结果”，具体的多轮映射见 12.6。

12.1.3 协议抽象：LLM API 本质上在传什么

不管是 OpenAI、Anthropic 还是 DeepSeek，主流 LLM API 本质上都是：

HTTP + JSON
  -> 提交上下文和控制参数
  -> 模型生成文本 / 结构化结果 / 工具调用
  -> 返回 usage、stop reason、可选流式事件

从抽象层看，一次调用通常包含六类信息：

抽象层典型字段作用
模型选择model选择能力、价格、延迟和上下文窗口
输入上下文messages、input、system把用户问题、历史、规则和证据送进模型
生成控制temperature、max_tokens、reasoning_effort控制采样、长度和推理预算
输出约束response_format、json_schema、strict让结果更像机器可消费契约
外部能力tools、tool_choice让模型提出工具调用，而不是只回答文本
运行形态stream、conversation state、cache决定是一次性返回、增量返回还是复用上下文

可以把它看成一个最小统一心智模型：

Request
  = 模型
  + 上下文
  + 输出约束
  + 工具定义
  + 推理与流式控制

Response
  = 最终文本 / 结构化结果 / 工具调用意图
  + token usage
  + stop reason
  + 可选 reasoning / streaming events

12.1.4 一次请求的生命周期与普通 API 的区别

一次典型的自回归生成请求，可以按下面的教学模型理解；实际服务可能把阶段重叠执行，不一定公开内部耗时：

客户端组装与发送 → 鉴权、校验和排队 → 输入处理（prefill）
→ 生成（decode，可能含不可见推理）→ 增量或完整响应 → 客户端验收

输入处理为当前上下文建立推理所需状态，生成阶段逐步产生后续内容。长输入、缓存未命中可能增加输入处理时间；长输出或更多推理计算可能增加生成时间。服务端工具和多模态处理还可能插入额外阶段。因此，首字慢与完整回答慢应分别测量，不能仅凭总耗时判断原因。[25][26]

LLM API 同样可以有严格的 HTTP 和类型契约，变化主要发生在生成内容层：相同输入未必产生相同文本，合法 JSON 未必包含正确事实，正常生成也可能是拒绝或工具调用。这要求客户端分别处理传输、协议、结构和应用验收，而不是用“状态码 200 且正文非空”代表成功。测试也应同时包含确定的协议断言与基于样本的质量评估。

12.1.5 Token 预算：上下文窗口不等于可输出长度

上下文窗口限制一次推理能容纳的输入与生成内容，最大输入和最大输出还可能有独立上限。对于采用共享上下文预算的模型，可用下面的保守条件做请求前检查；具体扣减方式以模型协议为准：

输入 token ≤ 模型最大输入限制（若单独规定）
生成预算 ≤ 模型最大输出限制
输入 token + 生成预算 + 预留余量 ≤ 上下文窗口

输入不只包括用户文字，还包括历史、指令、工具定义、Schema 及多模态内容。生成预算也不只用于可见答案：例如 OpenAI 的 max_output_tokens 会限制包含推理和不可见格式 token 在内的生成量，不能在统计 output_tokens 后再把其子项 reasoning_tokens 加一次。预算耗尽可能发生在任何可见文字产生之前，此时仍可能有输入与推理费用。[26][27]

假设某教学模型窗口为 32000 token，当前输入 22000，拟生成 6000，另留 1000 余量，则本轮预算合计 29000；但下一轮新增的工具结果仍可能使请求超限。这些是假设数字，不代表任何真实模型配置。发送前应用可调用供应商计数接口或使用匹配的 tokenizer 估算，不能把“一个汉字等于一个 token”作为通用规则。[27]

超限时应先减少无关材料、摘要旧历史或拆分任务，保留当前规则、关键事实与未完成的工具关联；摘要会丢信息，不能当作无损压缩。服务端自动截断也只是一种能力选项，必须确认删除方向和语义，不能为通过长度检查而悄悄删掉关键约束。缓存命中通常减少重复计算或费用，不扩大上下文窗口。

12.1.6 采样、推理预算与结果可复现性

在支持相应参数的模型上，temperature 调整候选 token 概率分布的尖锐程度，top_p 则按累计概率质量筛选候选集合。降低温度不等于提高事实正确率。通常先固定其中一个、调整另一个，便于判断变化来自哪里；不能把一套参数原样用于所有模型或推理模式。[3]

任务选参应以实际样本评估为依据：抽取和分类优先看字段正确率、漏项与拒绝处理；创作可以允许更多变化；复杂判断再比较推理预算对正确率、延迟和成本的影响。reasoning effort 控制模型投入的推理计算倾向，不是温度，也不是答案字数。更多推理不能补齐缺失证据，不保证效果单调提升；支持的档位及默认值均绑定模型。[26]

temperature: 0 也不是逐字复现契约。OpenAI 的 Chat Completions 参考页将 seed 标为已弃用的尽力确定性控制，并明确不保证确定性；不能将它视为所有 LLM API 的标准能力。[3]工程上应记录模型快照、完整请求或脱敏后可重建的输入、提示模板与 Schema 版本、SDK 版本、生成参数，以及接口提供的后端版本标识。固定这些条件有助于排查，仍不能据此承诺逐字一致。回归验收应优先检查结构、关键事实和业务结论，只有应用确实要求时才做文本精确比较。

12.2 主流协议核验：提供方、消息格式与客户端接口

本节按 2026-10-20 实际读取的官方文档整理，并对本地 sashabaranov/go-openai@v1.43.0 做了离线序列化核验。请求是围绕同一虚构订单自行编写的教学样例；省略鉴权值，未向真实模型端点发送请求。文档核验、SDK 序列化成功和端点兼容性实测是三类不同证据。

12.2.1 先分清提供方、协议形态与 Agent 产品

OpenAI、Anthropic、DeepSeek 是提供方；Responses、Chat Completions、Messages 是协议形态；Claude Code 是带工具执行、权限与会话管理的 Agent 客户端。同一提供方可以实现多种形态，同一客户端也可能连接不同提供方。OpenAI 同时维护 Responses 与 Chat Completions；DeepSeek 当前也正式记录了 Responses 和 Anthropic 格式的兼容范围。[2][3][4][5][6][7]

OpenAI 与 DeepSeek 的上述原生请求通常使用 Bearer API Key；Anthropic 官方请求示例使用 x-api-key，并显式传入 anthropic-version: 2023-06-01。正文示例只展示 JSON body，真实 HTTP 请求还需对应 URL、鉴权和内容类型。云平台托管入口、OAuth 代理或第三方网关应单独核验，不能套用这里的鉴权说明。[3][4][5]

12.2.2 content 为什么既可以是字符串，也可以是数组

字符串是纯文本的便捷表示；数组是带类型的内容块序列。不是 developer 固定用字符串、user 固定用数组；但允许哪些内容块，确实受协议、角色与模型限制。 input[] / messages[] 是消息或协议项列表，消息内部的 content[] 则是同一消息中的内容块，二者不是同一层。[2][3][4][5][8]

接口与位置字符串 / 数组约定纯文本块的 type重要限制
OpenAI Responses 输入消息便捷消息可用字符串或输入内容块列表input_text助手输出文本块使用 output_text；工具结果另有 function_call_output 项
OpenAI Chat Completionsdeveloper / system / user / tool 等角色按各自定义接受字符串或相应内容块数组textdeveloper、system、tool 的内容块限制为文本；user 的多模态类型按模型核验
Claude Messages消息 content 可用字符串或内容块数组；基础 system 也可用字符串或文本块数组text客户端工具结果位于 user 消息的 tool_result 块；不能写成 role: tool
DeepSeek Chat Completionssystem 的 content 为字符串；user 与 tool 可为字符串或受支持内容块数组textassistant 的 content 是字符串或 null；该接口列出的角色是 system / user / assistant / tool，不能直接套入 developer

例如，下面是 OpenAI Responses 的一条消息：

{
  "role": "user",
  "content": [
    {
      "type": "input_text",
      "text": "请核查订单。"
    }
  ]
}

而在 Chat Completions 与 Claude Messages 的文本内容块中，类型名应为 text：

{
  "role": "user",
  "content": [
    {
      "type": "text",
      "text": "请核查订单。"
    }
  ]
}

对于支持字符串简写的相应消息，两者也可以各自写成 "content": "请核查订单。"。这不代表两种接口可以混用 input_text 和 text。图片块的结构差别更大，例如 Responses 使用 input_image，Chat Completions 常用 image_url，Claude 使用 image 与 source。[3][4][9]

无论拆成几个文本块，它们仍共享当前消息的角色。把 Memory、Skill、知识库分别放进几个块，不会自动建立不同的权限、可信度或持久化语义；这些来源标签仍由应用解释。

多模态接入还要区分“能上传文件”与“模型能理解该内容”。图片可能通过 URL、内联数据或文件 ID 引用，但仍受模型、格式、尺寸与数量限制；图像 token 开销与处理方式有关，不能按 Base64 字符数计费。[9]音频要确认编码、采样率、时长，以及接口提供转写、理解还是语音生成。[35]视频则要核验是原生视频输入，还是应用自行抽帧并处理音轨，后者不能声称保留完整时间信息。文件引用也可能意味着文档输入、文本提取或检索，三者不能互换。例如 OpenAI 的 PDF 输入在视觉模型上可同时提取文字与页面图像，不只是读取一段纯文本。[36]模型支持、内容块表达、上传限制和计费单位应分别检查。

12.3 流式输出、结构化输出与 Tool Calling

结构化输出、流式返回和工具调用并不是三个孤立功能，而是模型被系统消费时最常见的三种“可编排输出形态”：

  • 流式输出解决交互延迟和事件驱动渲染；
  • 结构化输出解决机器可消费结果；
  • Tool Calling解决模型向外部世界发起行动请求。

在 API 层，它们分别表现为：

  • stream / streaming events
  • response_format / JSON schema / strict schema
  • tools / tool_choice / tool_calls / tool_use

真正的系统不会把这三者拆开看，而是放进同一个 Runtime 控制面：模型先返回文本、JSON 或工具调用意图，系统再根据当前任务协议决定是直接交付、继续追问、执行工具，还是把工具结果回填给模型。

12.3.1 流式输出改变交付时机，不保证推理更快

非流式请求通常在生成完成后返回完整对象；流式请求则持续返回文本、工具参数等增量及状态事件，消费者可以提前展示内容。流式通常改善用户感知延迟，但不保证降低排队时间、首 token 时间或总生成耗时。它也不保证每个 token 对应一个事件，或事件按固定间隔到达。[22]

12.3.2 依据消费者选择流式与非流式

场景选择依据消费边界
人在等待聊天、长文或代码流式有利于边生成边阅读已展示片段不代表最终答案已通过校验
后端抽取完整 JSON非流式更易接入；长耗时任务也可流式收集状态必须等对象完整后再做结构和语义校验
多步骤工作流可流式观察过程，步骤推进依赖完整结果不把半段参数或中间文本交给下一步执行
离线批量处理重点是吞吐、成本和逐项失败结果通常选择异步批量接口，而非逐 token 展示

因此，“机器消费”并不禁止流式，只意味着中间增量通常不具备可提交的业务语义；“有人等待”也不意味着可以边生成边执行外部动作。

12.3.3 长连接仍有超时、缓冲与背压

持续产生数据可能降低空闲超时风险，但不能绕过网关总时限；服务端正在推理而没有输出时，连接也可能长时间静默。网关缓冲可能把流式输出积攒成整块，慢客户端则可能造成背压。接入时应分别检查首响应、首事件、空闲读取和总耗时限制，明确缓冲上限与断开策略。用户取消或连接关闭，也不自动证明供应商已停止生成或计费。

12.3.4 流式输出在协议层意味着什么

从 API 协议角度看，流式输出不是“把完整响应切碎”，而是把模型生成过程显式暴露成一个事件流。

工程上常见的流式事件包括：

  • 文本增量 delta
  • 接口公开提供的 reasoning 摘要或 thinking 块增量（受模型与配置限制）
  • tool call 增量或工具调用完成事件
  • message 完成事件
  • usage 或 stop reason 结束事件

也就是说，流式模式下客户端处理的不再是“一个最终 JSON”，而是：

start
  -> delta
  -> delta
  -> delta
  -> tool_call / message / reasoning events
  -> completed

这也是为什么流式输出一旦进入系统设计，就不只是前端打字机效果，而是会影响：

  • 前端如何增量渲染；
  • 服务端如何转发和聚合事件；
  • Runtime 如何处理中途中断、取消和超时；
  • 日志和 trace 如何记录“过程输出”而不只是最终结果。

12.3.5 SSE分帧与完成判断

SSE是UTF-8文本，空行结束一帧，event给类型，data给载荷，id可用于EventSource的Last-Event-ID机制。TCP读取块不是帧边界；同一JSON甚至UTF-8字符可能跨读取块，必须增量解码、组帧再解析。WHATWG并未规定某模型服务必须保存重放日志。[21]

OpenAI Responses使用response.created、response.output_text.delta、response.completed等typed events；中途error或连接断开不能当正常完成。[22]Anthropic还区分content_block_stop、message_delta与message_stop；工具块结束不等于业务动作成功。[23]

下列是本书应用任务流的合法SSE教学样例，应用字段由Agent Runtime 的结果交付契约约定，不能冒充任何供应商原始流：

id: run-demo:41
event: step.completed
data: {"run_id":"run-demo","event_seq":41,"step_id":"s1","state_version":7,"artifact_ref":"answer-v1"}

id: run-demo:42
event: run.completed
data: {"run_id":"run-demo","event_seq":42,"state_version":8,"result_ref":"answer-v1","verification_ref":"check-v1"}

每帧后的空行不可省。前端按run_id/event_seq去重更新视图，再查询结果接口核对当前状态；这项回放保证来自应用的持久事件与保留策略，不来自SSE语法。

12.3.6 各协议的流式载荷与结束信号

SSE 只定义传输分帧，事件内容仍由各接口定义。下表中的结束信号先用于判断一次生成是否完整，再由 Runtime 判断是否需要执行工具或继续任务。

接口主要增量载荷结束与失败判断
OpenAI Responsesresponse.output_text.delta、response.function_call_arguments.delta 等类型化事件检查 completed / failed / incomplete 等终态，不能把 done 后缀的单个内容事件当整次成功
OpenAI Chat Completionsdata 中的 chat.completion.chunk，读取 choices[].delta处理 finish_reason 与 [DONE]，EOF 不能代替协议完成
Claude Messagesmessage_start，各 index 的 content_block_*，再到 message_delta最终 message_stop；检查 stop_reason 和 error，块结束不代表整条消息结束
DeepSeek Chat Completionschoices[].delta.content / reasoning_content / tool_calls处理 finish_reason 和 data: [DONE]
DeepSeek ResponsesResponses 风格的语义事件官方明确以 completed / incomplete / failed 事件结束，没有 [DONE]
Claude Code stream-jsonstdout 每行一个 Agent 事件 JSON，部分增量在 stream_event.event 中处理客户端最终 result 与进程结果；不是 SSE

这些边界分别来自各接口文档。[22][3][23][5][6][18]例如，OpenAI Chat Completions 的 include_usage 可产生额外的 usage chunk，其 choices 为空；DeepSeek 当前参考页则将 usage 放在 [DONE] 前最后一个仍含单个 choice 的结束 chunk 中。解析器不能假定所有兼容服务都采用相同的 usage-only chunk 结构。[3][5]

12.3.7 结构化输出：解析、结构与事实是三层保证

方法提供的约束仍需处理的问题
提示“请返回 JSON”表达输出意图可能夹带解释、Markdown 或无效 JSON
JSON mode在接口规定的正常条件下约束 JSON 格式不保证字段集合、类型和业务含义；仍需检查截断
JSON Schema 结构化输出支持模型在正常完成路径下遵循受支持的 Schema不支持的关键字、拒绝和未完成响应需单独处理；不保证事实正确
工具参数 strict约束调用参数的结构不约束最终答案，也不证明应当执行该工具

OpenAI 的 JSON mode 还要求上下文中有明确的 JSON 生成指令；Schema 模式只支持其规定的子集，不能把任意业务 Schema 原样提交。拒绝可能通过专门字段或内容类型返回，并不一定符合目标业务对象；达到生成上限也可能留下不完整内容。应用应先识别终态与拒绝，再提取完整对象并校验，不能遇到解析失败就一律重试。[11]

工具调用与最终结构化输出都可以承载机器可读数据，但用途不同：前者表达“希望调用哪个能力、参数是什么”，后者表达“交付给消费者的结果是什么”。tool_choice 可按支持范围禁用、自动选择、要求调用或指定工具；调用结果通过关联 ID 回填。自定义客户端函数由应用执行；供应商托管工具则可能在服务端执行，必须另查其生命周期、费用与数据边界。二者都不能仅凭模型输出就推导业务授权。[10]

12.3.8 SSE、WebSocket 与异步任务不是同一维度

形态适合的交互主要取舍
HTTP 非流式一次提交、等待完整响应简单，但长任务占用连接且缺少过程反馈
HTTP + SSE请求后单向接收增量，如文本聊天容易转发；取消或新输入通常需额外请求
WebSocket / WebRTC 会话持续双向输入输出，如音频交互需处理会话、打断、重连及媒体传输
后台生成任务单次生成耗时较长，通过任务 ID 查询状态连接与执行解耦；需核验轮询、取消和结果保留
Batch API大量可延后完成的独立请求用等待时间换吞吐或成本，需逐项收集结果

SSE、WebSocket 和 WebRTC 是传输选择，后台与 Batch 是执行和交付方式；支持异步并不意味着支持任意传输或事件续传。OpenAI Realtime 文档区分浏览器 WebRTC 与服务端 WebSocket 接入；后台模式与 Batch 另有独立的任务契约。[31][32][30]

记录原HTTP状态、provider错误码、request/response/call ID、attempt及可脱敏上下文。重试模型生成可能计费，也可能生成不同工具提案；不能因生成重试创建新的业务幂等键。参数/授权变化必须重新校验。

12.4.3 HTTP 成功、生成完成与结果可用

客户端应按层判断成功：HTTP 200 只说明已获得成功状态的 HTTP 响应，流中仍可能出现错误；协议正常结束说明本轮生成完成，内容仍可能是拒绝或工具请求；对象符合 Schema 后，还要通过应用验收。以 Chat Completions 为例，stop 可表示自然结束或命中停止序列，length 表示长度上限，tool_calls 表示提出工具调用。停止序列不等于结构化结果完整，长度截断也不能当作正常答案。[3]

重试前先确定错误是否可能自行恢复。临时限流、过载与部分网络故障可在剩余总时限内重试；余额或配额耗尽、鉴权失败、参数错误需要先修复条件。存在 Retry-After 时应按服务端约定等待，另加抖动；没有该提示时采用有上限的指数退避。不能仅看 429 或 5xx 的状态码决定无限重试。[29]

应用、网关与 SDK 应明确一个主要重试责任层，并核验 SDK 的实际默认行为，避免多层尝试相乘。连接超时、首响应等待、空闲读取和总 deadline 分别限制不同阶段；每次重试都消耗同一个总预算。网络超时不证明服务端没有处理请求，重新生成也可能产生新内容与额外费用；取消请求的发出与服务端确认取消，应记录为不同状态。

12.5 会话状态、工具关联与应用重连

12.5.1 多轮对话的三种状态模型

多轮对话通常靠再次提供历史，或由供应商将已保存的历史纳入新请求，不是模型权重在每次调用后记住用户。OpenAI Responses 同时提供显式历史、previous_response_id 响应链和 Conversations 会话对象等管理方式；不能据此假设其他兼容端点也保存状态。[24]

方式谁管理历史主要收益与代价
显式重传历史应用保存并组装必要协议项可控、易迁移；请求体较大，应用负责关联与裁剪
响应 ID 续接供应商按响应链恢复上下文少传重复请求体；依赖保存期限、可访问性及续接语义
持久会话对象供应商维护有独立 ID 的会话项便于跨请求使用；需要管理生命周期、并发写入与删除

减少上传字节不等于减少计费 token。OpenAI 明确说明，使用 previous_response_id 时链中历史输入仍计入输入费用，缓存折扣再按实际命中计算。[24]旧请求的顶层 instructions 也不会仅因续接 ID 自动继承，应逐轮设置当前规则。[1]应用应选择清楚的历史管理方式，避免既续接又重传同一历史；服务端保存会话也不意味着输入可以无限增长。

12.5.2 调用ID不是业务Operation

教学Responses输出项与回填项分别如下，output里的JSON字符串是工具已返回的观察，不能由模型编造。[10]

{"type":"function_call","id":"fc_demo","call_id":"call_demo","name":"lookup_document","arguments":"{\"document_id\":\"policy-7\"}"}

{"type":"function_call_output","call_id":"call_demo","output":"{\"status\":\"ok\",\"version\":\"v3\",\"evidence_ref\":\"ev7\"}"}

应用先校验完整arguments、工具版本与当前权限，再执行并关联结果；同一call_id冲突内容应拒绝而非覆盖。保留协议要求的相关输出项，缺结果不能伪装为已完成对话。call_id只关联一轮模型调用，业务Operation的稳定幂等键由Agent Runtime维护。Skill是应用加载的程序性上下文，不自动变成供应商原生工具或权限。

12.5.3 断线重连的两个层面

教学时序：客户端订阅应用run-demo，确认事件40后断线；服务端继续按权威Run状态执行，先提交Step/产物/Event 41，再形成终态Event 42；客户端重连携带40，授权检查后重放41、42并去重，最后查询run结果。游标过期时使用Runtime 快照与重新订阅契约，不伪造供应商续流。

如果断的是模型供应商连接且工具参数只收到一半，adapter把生成attempt记为stream_incomplete，不能据半个JSON执行工具。若已执行工具但结果未知，先查询Operation而不是重新生成后再执行一次。取消只表达停止意图，迟到结果仍需要写入事实账本。

Anthropic文档的续写策略随模型版本区分，部分工具/思考块不能按文本方式恢复；这种“带部分输出重新请求”不是从旧SSE事件ID重放，也不保证续写逐字相同。[23]应用事件回放的保留期、权限、重复和过期语义仍由Agent Runtime负责；OpenClaw Gateway的具体实现需独立核验。

12.6 完整案例：构建退款核查 Agent 的有效输入与输出

本例采用“查订单 → 查账务与政策 → 形成结构化结果”的三轮模型调用，展示同一个任务的输入如何逐轮变化。案例使用 OpenAI Responses 的字段形态；所有请求与响应均为教学片段，不是实际端点执行记录，也不构成完整可运行应用。

12.6.1 先把用户目标变成输入与输出契约

假设客服在 2026-10-20 10:00（UTC+08:00）发起任务：

帮我核查订单 O-2048 中商品 L1 的 150 元退款申请。
确认适用规则和当前可退上限，给客服一段中文回复草稿。
只做核查，不提交退款，不发消息。

任务看起来只要求一段回复，实际上需要同时解决订单定位、政策适用、退款余额和回复依据四个问题。运行前先定义下列契约，避免模型在生成时自行补齐业务口径。

契约本例约定
数据范围已登录客服有权读取演示商家 shop-demo 的该订单；身份与商家范围由服务端鉴权上下文绑定，不采用模型自报身份
查询对象只核查商品行 L1；金额均为 CNY，接口用整数分表示
资金口径商品行优惠后实付，减去该行已成功退款和仍占用额度的处理中退款；两类扣减互斥，不重复计数
政策口径查询适用于该商品类别、签收日期和退款原因的政策版本；客户声称质量问题不等于质量问题已核验
模型交付申请金额、资金维度可退上限、处理判断、问题清单、证据 ID 和回复草稿
完成条件证据足以报告上限与缺项，结构和业务检查通过，即可结束核查；无需等到退款被批准或执行
行动范围仅开放只读核查工具；退款提交与消息发送不在本次能力集合中，执行层也拒绝这些动作

尤其要区分：资金维度可退上限，不等于已经满足全部售后条件，更不等于批准退款。 本例的售后规则只是虚构商家的内部政策设定。

12.6.4 第一轮输出成为第二轮输入：先取订单事实

假设模型首轮返回以下响应核心字段；为聚焦消息流，省略服务端时间戳、usage 等元数据。output 中是调用请求，尚未查询到任何订单；status: completed 表示这一轮模型生成完成，不表示整个退款核查任务结束：

回填到模型的项如下，output 是序列化后的工具结果字符串：

}

本例选择显式维护输入历史，第二轮的输入组成因此是：

原始任务与材料包
  + response_1 中按协议要求保留的输出项
  + call_order 对应的 function_call_output
  → 第二轮模型输入

不能只把工具结果另写成一句“我查到了订单”，同时丢掉原调用及 call_id。若响应包含必须续传的 reasoning 项，也应由适配器按协议保留，不能只保留可见文本。[10]这不要求记录或展示隐藏思维链。

如果选择 previous_response_id 管理续接，应用应遵循相应状态契约，避免又重复拼接同一份历史。还要注意：此前请求中的 instructions 不会因使用 previous_response_id 自动沿用，后续请求仍需提供当前适用指令。[1]本例使用输入项保存 System 与 Skill，并在后续请求中保留这些输入项；若改用顶层 instructions，则逐轮显式设置。

\[ 18000 - 3000 - 2000 = 13000\text{ 分} = 130\text{ 元} \]

至此，首轮历史摘要中的“可能还能退 150 元”与当前账务发生冲突。正确处理是标记旧结论未核实，并在当前核查中采用权威账务快照；不是把两个数字平均，也不是因为旧结论出现在聊天历史中就继续沿用。若两个同级权威来源仍冲突，则保留冲突并停止形成确定金额。

第三轮输入继续保留第二轮必要输出，并新增两个分别关联的 function_call_output。此时 Context 已从“用户目标与待核实说法”变为“订单事实 + 当前账务 + 适用政策 + 已识别缺项”。工具输出在前一阶段是外部查询结果，在下一阶段就是模型的上下文。

12.6.6 第三轮生成结果：Schema 约束形状，应用核对事实

证据已足以完成本次核查。Runtime 在第三轮将 tools 置为空集合，并使用 Responses 的 text.format 指定最终结果 Schema；tool_choice 只在相应工具配置下设置。结构化输出约束最终结果，前两轮工具的 strict 则约束调用参数，两者解决不同问题。[11]

最终请求复用 12.6.3 已展开的 text.format，无需再定义另一套 Schema。应用移除工具选择配置并追加真实观察，示意如下；response.output 的输入转换按 SDK 和模型协议处理，不能丢失要求保留的项：

# 伪代码：request_1 是前面完整 JSON 解析后的对象；查询结果由 Runtime 真实取得。
request_2 = copy.deepcopy(request_1)
request_2["input"] += adapter.to_input_items(response_1.output)
request_2["input"].append(order_tool_output)

request_3.pop("parallel_tool_calls", None)

request_2 含原始四条消息、第一轮输出及订单观察；request_3 再增加第二轮输出、账务观察和政策观察。System 与 Skill 随保留的输入项继续存在，新的工具结果以独立协议项追加，不伪装成系统指令。样例假设应用已经核实证据足以结束查询，才进入最后一轮。

12.6.7 从模型响应到交付结果：让人和程序各取所需

校验后，后台保存结构化核查结果及其证据版本，客服界面展示以下内容：

核查结论：需要进一步处理。
申请金额：150 元；本次查询快照下的资金维度可退上限：130 元。
待处理问题：申请超出上限；缺少质量凭证；旧摘要中的金额未获当前账务支持。
依据：商品行 E-order、账务 L42 / E-ledger、政策 aftersale-v3 / E-policy。

给客服的回复草稿：
经核查，该商品目前资金维度可退上限为 130 元，低于本次申请的 150 元。
申请仍需补充质量凭证，暂不能确认满足全部售后条件。
以上为核查结果，未提交退款。

金额、状态与证据等关键展示字段可以由已校验对象通过模板渲染，草稿则明确标为待客服使用的文字。若保留模型自由生成的整段草稿，应另外检查它与结构化结论是否一致。任务至此结束，草稿不会因生成成功而自动发送；将来若新增退款执行任务，还需重新查验当时的账务与授权，不能把这个快照当成额度预留。

异常分支也属于输入与输出设计，而不是等上线后再补：

变化应进入下一轮的有效信息允许交付的结果
账务查询超时对应调用的明确错误、已有订单证据和缺失项max_refund_cents: null，说明无法核实上限，不把未知当零

输出 JSON 完整，但遗漏处理中占款校验错误与 E-ledger 的实际字段拒绝错误的 150 元上限，有限次修复或报告失败

通过这个案例可以看出，输入与输出并非两份孤立模板。Prompt 定义每一步的职责和契约，Context 随证据逐轮更新，API 保留指令、工具请求与结果的结构，Runtime 校验后才形成业务系统和人能够使用的交付物。

12.7 性能、成本、数据契约与迁移验证

12.7.1 分开测量首字、生成和端到端耗时

可以用下面的近似分解定位调用延迟；这是观测模型，不代表供应商一定暴露这些内部计时：

端到端耗时 ≈ 客户端准备 + 网络 + 排队 + 输入处理 + 生成 + 结果验收
首个可见文本延迟 ≈ 前置阶段 + 首个可见文本产生前的计算与传输

应分别记录首响应、首事件、首个可见文本和终态时间。HTTP headers 或 response.created 很快到达，不意味着用户已经看到答案；推理模型也可能在首个可见文本前花费计算。没有供应商遥测时，只能提出“排队或输入处理较慢”的假设，不能从客户端总时长精确反推内部阶段。[25][26]

现象优先核查候选改进与代价
首字慢网络、限流重试、输入长度、缓存命中和推理配置减少无关输入、复用稳定前缀、评估更低延迟模型或预算；需复测质量
首字快但完成慢输出量、推理量、事件间隔和慢客户端约束回答长度、减少冗余字段；不能靠截断破坏结果完整性
单次快但任务慢多轮请求及外部等待减少不必要调用；不能为少一轮而省略必要证据

比较时应按模型、输入和输出规模、推理配置、缓存状态分组观察 p50、p95 与失败率，不能把不同负载混成一个平均值。流式主要改变展示时机；优化效果必须在同一任务集上同时比较质量、延迟与费用。[25]

12.7.2 RPM、TPM 与并发限制共同决定容量

RPM 限制请求次数，TPM 限制 token 流量，并发限制约束同时在途的请求；图片、音频或长上下文还可能有独立额度。供应商的 token 限流口径未必等于最终账单，有时会结合请求长度估算与申请的输出上限预留资源，因此把输出上限随意设得很大也可能降低可接纳流量。具体以端点说明和响应 headers 为准。[29]

用均值作粗略规划，可推导稳定吞吐的教学上界：

请求/秒 ≤ min(RPM/60, TPM/(60×平均限流token/请求), 并发上限/平均占用秒数)

这个估算不能预测突发、长尾或短时间窗口限流。即使一分钟总量未超限，集中发送也可能触发限制。客户端应同时控制发起速率与在途数量，给重试预留余量，并结合剩余额度、重置时间和 Retry-After 调整节奏；多实例还需共享相应预算。服务额度也不等于费用预算，两者需要独立观测。[29]

12.7.3 成本核算、Prompt caching 与 Batch

费用应按实际计费桶求和：费用 = Σ（该桶用量 × 对应单价）。先确认普通输入、缓存读取、缓存写入、生成内容，以及图片、音频、托管工具是否分别收费。明细可能是总量的子项，也可能是独立计费项，不能把输入总量和全部缓存明细再次相加；推理 token 若已包含在生成量中，也不重复计费。[27][28]

Prompt caching 复用符合条件的输入前缀计算，不是把上次答案作为这次答案返回，也不是会话记忆。稳定指令和公共材料适合放在前部，动态内容尽量后置；工具定义、顺序和历史改写也可能影响命中。最低可缓存长度、缓存边界、保留时间、隔离范围及读写价格随模型而异，写入也可能收费。因此应观察实际 cached tokens、写入量和总费用，不以请求“看起来相似”判断命中，也不为凑缓存长度加入无用材料。[28]

Batch API 适合允许延后交付的大量独立请求。它可能提供独立限流和更低价格，但折扣、完成窗口与支持端点是产品条款，不是异步 API 的普遍性质。OpenAI Batch 通过 custom_id 对应输入与结果，输出顺序可能不同，还需区分请求级错误与整批任务状态。[30]

最终 usage 比本地按可见文字估算更适合核算，但流中断可能使客户端收不到结束 usage，不能据此记为零成本。[3]应记录请求 ID、attempt、实际模型、计费配置和“待核对”状态，在接口支持时取回最终对象，再与供应商用量报表或账单核对。任务费用包含失败与重试尝试；“每次成功回答的成本”应按总费用除以验收通过的交付数计算。

12.7.4 数据契约是端点选择的一部分

托管 API 接入前，应把下面几项分开核验，不能用“企业版”“不训练”或一个 store 参数代替全部承诺：

维度需要确认的契约
训练用途输入与输出默认是否用于训练，是否存在主动共享选项
保留生成结果、会话、上传文件、缓存和滥用监控日志各保留什么、多久
删除删除哪个对象、何时生效，关联文件和其他日志是否另行处理
区域静态存储位置与推理处理位置是否都满足要求，哪些能力支持该区域
第三方代理、网关和托管工具是否引入额外的数据处理方

例如 OpenAI 说明 API 数据默认不用于训练，除非主动选择共享；但同时区分滥用监控日志与应用状态，二者有不同保留规则。store: false 不能推导“所有数据零保留”，会话、文件、缓存、后台执行与零保留资格应按实际功能和账户配置核验。[33][32]

长期 API Key 应保存在服务端密钥管理设施中，按环境和项目隔离、限制权限并支持轮换；浏览器或移动端不能内置该长期密钥，直连能力应使用供应商明确支持的临时凭据机制。[34][31]默认日志保留模型与端点、请求 ID、版本、耗时、usage、结束原因和错误类别；完整正文、附件 URL 与工具结果按用途脱敏、授权访问和限定保留，不记录鉴权 headers。

12.7.5 用契约测试与质量回归证明迁移可用

“兼容”至少分为字段可发送、协议可消费和应用可接受三个层次。迁移前应固定能力清单与测试样本，而不是只验证一条问候语：

验证层能证明什么仍不能证明什么
官方文档核对声明支持的角色、参数、模型及限制目标账户与端点实际行为
SDK 序列化检查客户端确实发送了预期 JSON服务端接受字段且按语义执行
真实端点契约测试实际角色、Schema、工具关联、流终态、错误与 usage 行为所有任务的回答质量
固定任务集质量回归关键事实、结构、拒绝、延迟与成本的可比较表现未来模型更新后的表现

测试还应覆盖空内容、拒绝、长度截断、usage 缺失、并行调用关联，以及可控注入的断流、重复事件和未知事件；不能只测正常路径。升级时记录模型快照与别名、SDK、协议、提示模板、Schema hash 和适配器版本，重新核验关键能力。生产切换可基于脱敏样本回放或获得授权的少量流量验证，并保留回退配置；切换提供方本身也需要重新满足数据契约。这里给出验证方法，本章示例仍不代表已完成端点实测。

本章小结

LLM API 的接入契约覆盖输入组织、生成预算、输出类型、会话状态、终态与错误，也包括 usage、缓存及数据保留。降低温度不保证事实正确，Schema 合法不保证结论正确，HTTP 成功不保证生成完成，服务端续接也不代表历史免费。性能应分别测量首字、生成与端到端耗时，成本则按实际计费桶和全部尝试核算。

Provider Adapter 把消息、工具关联、完整输出与错误映射成应用可消费契约，同时保留供应商差异。SSE 只提供传输分帧，自定义工具执行和业务幂等仍属于 Runtime 与业务系统。兼容声明要有版本与分层验证，教学样例不能冒充端点实测。

构建有效的大模型输入，需要把任务指令、工具规约与带来源的材料组织到正确协议位置；构建有效输出，则要区分中间工具提案、最终结构化结果与面向人的表达。退款核查案例中的闭环是：组装当前输入 → 获取必要观察 → 更新上下文 → 生成契约内结果 → 核验事实和业务语义 → 渲染交付内容。
