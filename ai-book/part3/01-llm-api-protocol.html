第 13 章 LLM API 协议：模型能力如何被系统消费

一次调用怎样提交指令、上下文与工具定义，怎样区分文本、行动提议、拒绝和不完整结果？本章介绍模型通过 API 暴露的能力及其调用保证，供后续上下文、外部能力与 Runtime 使用。

理解 LLM 的原理，只能回答“模型为什么能工作”；理解 LLM API 协议，才能回答“系统怎样把模型接进来”。在工程落地里，这一步经常被低估。很多团队熟悉 Token、上下文窗口、Transformer 和 Sampling，却在真正接入模型时发现一连串新问题：

  1. 一次调用里，系统究竟该传什么？
  2. system、messages、input、content blocks 这些字段本质上分别代表什么？
  3. 模型返回的为什么不只是文本，还有工具调用、结构化结果、流式事件和 usage？
  4. OpenAI、Anthropic、DeepSeek 看起来都“差不多”，实际差别在哪？
  5. 一个 Agent 工作流，怎样被映射成多轮请求、工具回填和状态延续？

这一章讨论的不是 SDK 语法糖，而是模型协议层的统一抽象。你可以把它看成 Agent Runtime 和模型能力之间的接口层：往左连接 Prompt、Context、Tool、Skill 和 Workflow，往右连接 OpenAI、Anthropic、DeepSeek 等不同提供方。

第 17 章 Agent Runtime统一定义持久执行、编排与恢复。本章先建立模型协议层的基础，回答：Runtime 究竟怎样消费模型能力。

后续Agent 的上下文工程将统一讨论任务协议、知识与记忆如何组织成本轮上下文。本章先建立请求字段与响应类型的统一抽象，并在退款核查案例中走通“组装输入 → 工具调用 → 结果回填 → 输出校验 → 交付”的完整过程。

本章的边界是模型服务的输入、输出与调用契约：工具声明、调用参数和结果回填属于 API 协议；自定义函数的实际执行、业务幂等与事务属于 Runtime 或业务系统。理解协议既要会构造请求，也要能解释一次调用为何慢、为何收费、何时算完成，以及供应商更换后哪些保证仍然成立。

13.1 统一抽象：输入、指令、上下文与输出

图 13-2：一次模型调用的输入与输出

模型能力通过可调用的协议暴露给系统。接入时需要分别核验下列接口，而不能从模型名称推断全部能力：

  • 上下文窗口会表现为 messages、input、system、conversation state 等输入结构；
  • 结构化输出会表现为 JSON mode、JSON schema、strict schema；
  • 工具调用会表现为 tools、tool_choice、tool_calls 或 tool_use；
  • 长上下文成本会表现为 prompt caching、cache hit 指标和上下文压缩；
  • 多模态能力会表现为文本、图片、文件、音频等不同 content block；
  • 推理能力会表现为 reasoning / thinking 开关、effort、流式事件和 token 统计。

13.1.1 Prompt 与 Context：职责划分不等于协议角色

在 Agent 中，Prompt 通常强调让模型按什么目标和规则工作，Context 则强调模型当前能看到哪些材料与状态。两者不是互斥的数据类型：广义的模型上下文包括指令、任务、示例、工具定义和事实材料；讨论工程分工时，才常把“指令设计”与“信息组织”分开。

沿用这一工程口径，可以把第 \(t\) 轮的有效输入写成：

$$ \text{LLM Input}_t = \operatorname{Assemble}(I_t, T_t, C_t, U_t) $$

其中 I_t 为系统或开发者指令，T_t 为工具规约，C_t 为当前上下文材料，U_t 为用户任务。Assemble 表示按目标 API 的角色、内容块和工具字段组织输入，并非把几段字符串随意相加。C_t 是经过筛选的历史、检索材料、工具观察、记忆和工作区内容；模型选择、输出 Schema、生成预算与流式控制也属于 API 请求，但不能都理解成正文提示词。

内容职责不会一一映射到 role，按真实来源落到协议字段：[1]

内容典型协议位置需要保留的区别
应用规则、Persona、流程和受信示例提供方支持的 system/developer 或顶层指令同一位置可承载多种职责，优先级以提供方契约为准
用户任务user 或等效输入项用户目标不自动授予业务权限
函数规约tools、parameters/input_schema在正文提到函数名不代表工具已经接入
检索片段、记忆、工作区材料有来源标识的内容块外部材料不能通过措辞获得系统指令地位
历史模型输出assistant 与必要协议项历史回答不自动成为已验证事实
工具观察tool_result、function_call_output 或 tool 消息调用关联、结果状态与当前授权不能丢失
输出结构约束text.format、response_format 等Schema 不证明事实、权限或业务计算正确

角色与内容的组织方式由协议限定，事实可靠性由证据核验决定。把外部网页中的“忽略规则”包进系统指令，会改变来源语义；将所有内容压成一条 user 消息，则会丢失工具关联与历史角色。

13.1.2 Context 从哪里来，输出要交给谁

Context 不是“已经被证明正确的事实集合”，而是模型当前可见、需要按来源与状态使用的信息集合。

历史、检索、记忆与工作区材料的选择和可信度处理见第 14 章 上下文工程；工具能力与授权见第 16 章 外部工具系统。本章只保留映射到字段后的协议区别：工具观察要绑定调用标识，历史保留必要角色与内容类型，来源元数据由应用组织，不能假定提供方会识别一个名为 Memory 的业务字段。

Prompt Engineering 更关注任务表达、约束和输出约定；Context Engineering 更关注每轮选择什么、如何标记来源、保留多少，以及何时补充或淘汰材料。两者通过 API 协同：规则告诉模型如何使用信息，上下文提供完成任务所需的信息，协议保留两者的来源与结构。

输出设计也应在调用前完成，至少区分三种消费者：

  • 给 Runtime 的中间输出：工具名称、参数和关联 ID，表示下一步行动提案。
  • 给业务程序的最终结果：满足 Schema 的判断、金额、证据与缺项，用于校验和展示。
  • 给人的交付内容：清楚的解释、回复草稿或报告，可以从已校验字段生成或渲染。

一段自然语言可以适合人读，却不适合驱动程序；一个合法 JSON 可以适合解析，却仍然包含错误金额。构建有效输入与输出，要同时设计“模型看什么”和“下游凭什么接受结果”，具体的多轮映射见退款核查案例。

13.1.3 协议抽象：LLM API 本质上在传什么

不管是 OpenAI、Anthropic 还是 DeepSeek，主流 LLM API 本质上都是：

HTTP + JSON
  -> 提交上下文和控制参数
  -> 模型生成文本 / 结构化结果 / 工具调用
  -> 返回 usage、stop reason、可选流式事件

从抽象层看，一次调用通常包含六类信息：

抽象层典型字段作用
模型选择model选择能力、价格、延迟和上下文窗口
输入上下文messages、input、system把用户问题、历史、规则和证据送进模型
生成控制temperature、max_tokens、reasoning_effort控制采样、长度和推理预算
输出约束response_format、json_schema、strict让结果更像机器可消费契约
外部能力tools、tool_choice让模型提出工具调用，而不是只回答文本
运行形态stream、conversation state、cache决定是一次性返回、增量返回还是复用上下文

可以把它看成一个最小统一心智模型：

Request
  = 模型
  + 上下文
  + 输出约束
  + 工具定义
  + 推理与流式控制

Response
  = 最终文本 / 结构化结果 / 工具调用意图
  + token usage
  + stop reason
  + 可选 reasoning / streaming events

13.1.4 一次请求的生命周期与普通 API 的区别

一次典型的自回归生成请求，可以按下面的教学模型理解；实际服务可能把阶段重叠执行，不一定公开内部耗时：

客户端组装与发送 → 鉴权、校验和排队 → 输入处理（prefill）
→ 生成（decode，可能含不可见推理）→ 增量或完整响应 → 客户端验收

输入处理为当前上下文建立推理所需状态，生成阶段逐步产生后续内容。长输入、缓存未命中可能增加输入处理时间；长输出或更多推理计算可能增加生成时间。服务端工具和多模态处理还可能插入额外阶段。因此，首字慢与完整回答慢应分别测量，不能仅凭总耗时判断原因。[2][3]

LLM API 同样可以有严格的 HTTP 和类型契约，变化主要发生在生成内容层：相同输入未必产生相同文本，合法 JSON 未必包含正确事实，正常生成也可能是拒绝或工具调用。这要求客户端分别处理传输、协议、结构和应用验收，而不是用“状态码 200 且正文非空”代表成功。测试也应同时包含确定的协议断言与基于样本的质量评估。

13.1.5 Token 预算：上下文窗口不等于可输出长度

上下文窗口限制一次推理能容纳的输入与生成内容，最大输入和最大输出还可能有独立上限。对于采用共享上下文预算的模型，可用下面的保守条件做请求前检查；具体扣减方式以模型协议为准：

输入 token ≤ 模型最大输入限制（若单独规定）
生成预算 ≤ 模型最大输出限制
输入 token + 生成预算 + 预留余量 ≤ 上下文窗口

输入不只包括用户文字，还包括历史、指令、工具定义、Schema 及多模态内容。生成预算也不只用于可见答案：例如 OpenAI 的 max_output_tokens 会限制包含推理和不可见格式 token 在内的生成量，不能在统计 output_tokens 后再把其子项 reasoning_tokens 加一次。预算耗尽可能发生在任何可见文字产生之前，此时仍可能有输入与推理费用。[3][4]

假设某教学模型窗口为 32000 token，当前输入 22000，拟生成 6000，另留 1000 余量，则本轮预算合计 29000；但下一轮新增的工具结果仍可能使请求超限。这些是假设数字，不代表任何真实模型配置。发送前应用可调用供应商计数接口或使用匹配的 tokenizer 估算，不能把“一个汉字等于一个 token”作为通用规则。[4]

超限时应先减少无关材料、摘要旧历史或拆分任务，保留当前规则、关键事实与未完成的工具关联；摘要会丢信息，不能当作无损压缩。服务端自动截断也只是一种能力选项，必须确认删除方向和语义，不能为通过长度检查而悄悄删掉关键约束。缓存命中通常减少重复计算或费用，不扩大上下文窗口。

13.1.6 采样、推理预算与结果可复现性

在支持相应参数的模型上，temperature 调整候选 token 概率分布的尖锐程度，top_p 则按累计概率质量筛选候选集合。降低温度不等于提高事实正确率。通常先固定其中一个、调整另一个，便于判断变化来自哪里；不能把一套参数原样用于所有模型或推理模式。[5]

任务选参应以实际样本评估为依据：抽取和分类优先看字段正确率、漏项与拒绝处理；创作可以允许更多变化；复杂判断再比较推理预算对正确率、延迟和成本的影响。reasoning effort 控制模型投入的推理计算倾向，不是温度，也不是答案字数。更多推理不能补齐缺失证据，不保证效果单调提升；支持的档位及默认值均绑定模型。[3]

temperature: 0 也不是逐字复现契约。OpenAI 的 Chat Completions 参考页将 seed 标为已弃用的尽力确定性控制，并明确不保证确定性；不能将它视为所有 LLM API 的标准能力。[5] 工程上应记录模型快照、完整请求或脱敏后可重建的输入、提示模板与 Schema 版本、SDK 版本、生成参数，以及接口提供的后端版本标识。固定这些条件有助于排查，仍不能据此承诺逐字一致。回归验收应优先检查结构、关键事实和业务结论，只有应用确实要求时才做文本精确比较。

13.2.2 content 为什么既可以是字符串，也可以是数组

字符串是纯文本的便捷表示；数组是带类型的内容块序列。不是 developer 固定用字符串、user 固定用数组；但允许哪些内容块，确实受协议、角色与模型限制。 input[] / messages[] 是消息或协议项列表，消息内部的 content[] 则是同一消息中的内容块，二者不是同一层。[6][5][7][8][11]

接口与位置字符串 / 数组约定纯文本块的 type重要限制
OpenAI Responses 输入消息便捷消息可用字符串或输入内容块列表input_text助手输出文本块使用 output_text；工具结果另有 function_call_output 项
OpenAI Chat Completionsdeveloper / system / user / tool 等角色按各自定义接受字符串或相应内容块数组textdeveloper、system、tool 的内容块限制为文本；user 的多模态类型按模型核验
Claude Messages消息 content 可用字符串或内容块数组；基础 system 也可用字符串或文本块数组text客户端工具结果位于 user 消息的 tool_result 块；不能写成 role: tool
DeepSeek Chat Completionssystem 的 content 为字符串；user 与 tool 可为字符串或受支持内容块数组textassistant 的 content 是字符串或 null；该接口列出的角色是 system / user / assistant / tool，不能直接套入 developer

例如，下面是 OpenAI Responses 的一条消息：

{
  "role": "user",
  "content": [
    {
      "type": "input_text",
      "text": "请核查订单。"
    }
  ]
}

而在 Chat Completions 与 Claude Messages 的文本内容块中，类型名应为 text：

{
  "role": "user",
  "content": [
    {
      "type": "text",
      "text": "请核查订单。"
    }
  ]
}

对于支持字符串简写的相应消息，两者也可以各自写成 "content": "请核查订单。"。这不代表两种接口可以混用 input_text 和 text。图片块的结构差别更大，例如 Responses 使用 input_image，Chat Completions 常用 image_url，Claude 使用 image 与 source。[5][7][12]

无论拆成几个文本块，它们仍共享当前消息的角色。把 Memory、Skill、知识库分别放进几个块，不会自动建立不同的权限、可信度或持久化语义；这些来源标签仍由应用解释。

多模态接入还要区分“能上传文件”与“模型能理解该内容”。图片可能通过 URL、内联数据或文件 ID 引用，但仍受模型、格式、尺寸与数量限制；图像 token 开销与处理方式有关，不能按 Base64 字符数计费。[12] 音频要确认编码、采样率、时长，以及接口提供转写、理解还是语音生成。[13] 视频则要核验是原生视频输入，还是应用自行抽帧并处理音轨，后者不能声称保留完整时间信息。文件引用也可能意味着文档输入、文本提取或检索，三者不能互换。例如 OpenAI 的 PDF 输入在视觉模型上可同时提取文字与页面图像，不只是读取一段纯文本。[14] 模型支持、内容块表达、上传限制和计费单位应分别检查。

13.2.5 Claude：基础系统提示与中途更新

基础系统提示使用顶层 system；中途更新和强制工具选择是另两项能力。以下是 2026-10-26 读取官方文档后确认的限制，不是从模型命名推测的支持表：

  • 强制工具选择：官方工具实现指南列出 Claude Opus 5.5、Sonnet 5.5、Fable 5.1、Mythos 5.1 在模型层面不支持 tool_choice: {"type":"any"} 或 {"type":"tool","name":"..."}，会返回 400；auto 和 none 仍可用。另有手动 extended thinking（thinking.type=enabled）的限制，不能把“启用 thinking”与上述模型级限制混为一谈。auto 配合 strict 只能约束实际产生的参数，不能保证一定调用工具。[19]
  • 中途系统指令：专项文档明确列出 Opus 5.5、Sonnet 5.5 等支持中途 role: system，并明确排除 Sonnet 5；不能推广到所有 Claude 模型。携带内容的 system 必须紧跟 user（可含工具结果），或紧跟以服务端工具结果结束的 assistant；之后只能是 assistant 或数组结束，不能插在 tool_use 与 tool_result 之间。[18]
  • 工具结果后的用户新话语：对 Sonnet 5.5 和 Haiku 5.5，官方提醒紧跟工具结果的 system 可能被视为不可信文本而忽略，建议把用户新话语放在同一 user 消息、所有 tool_result 之后的独立 text 块中；Harness 提醒仍与用户话语分开。此建议不意味着可以把外部工具内容提升为受信指令。[18]
  • beta 边界：基础中途 system 无需 beta；Claude API 中途增删/定义工具使用 inline-tools-2026-09-15，仅引用已声明工具的旧变更方式另见原文；轮次级 clear_at 使用独立的 mid-conversation-system-clear-at-2026-08-21。支持 system 不代表同时支持这些 beta；暂停的服务端轮次也应先恢复，再变更工具。[18]

这类模型相关能力应进入适配器能力表；正文只展示基础协议，不建议为了缓存把第三方工具内容提升为系统指令。Claude 的最终结构输出与严格工具参数属于不同保证，需要分别核验模型。[17]

13.2.6 DeepSeek：形态兼容与行为兼容分别验收

DeepSeek 提供 Chat、Responses 与 Anthropic 格式入口；兼容表中的会话保存、developer 语义、并行工具、结构输出和参数忽略规则不能从 OpenAI/Anthropic 原实现继承。[8][9][10] 适配器对影响状态和输出保证的字段主动探测，关键约束缺失时拒绝或显式降级，不能把“不报错”当作语义生效。

2026-10-26 的 Chat Completions API Reference 将 system 的 content 定义为字符串，user/tool 定义为字符串或受支持内容块数组，assistant 定义为字符串或 null；不要把数组支持推广到所有角色。该参考页还明确规定，思考模式下 required 与指定工具的 tool_choice 返回 400，需先关闭思考模式。工具历史中的 reasoning_content 则按思考模式指南回传。[8][20]

Responses 兼容表单列了不同边界：接口无状态，previous_response_id 与 conversation 不支持，store 固定为 false；developer 按 user 处理，不能承接原实现的开发者指令优先级。parallel_tool_calls 被忽略且并行工具调用始终开启，不能靠 false 强制串行；reasoning 的明文可回传，但 encrypted_content 不支持。表中列出 tool_choice 支持，却未按思考模式细分，不能仅据此推定 Chat 的限制不存在或必然相同；采用该组合前应单独做契约测试。[9]

兼容验收分成传输、字段与行为三层。传输层确认鉴权、端点、流格式和断流后的错误入口；字段层确认 Schema 的实际序列化；行为层再检查强制工具选择、终态、拒绝、用量与会话续接。相同 HTTP 200 可以分别表示合法最终文本、需要执行的调用或未完成响应，适配器应产出统一的内部结果类型，而不是只统一 JSON 字段名。

一个可执行的契约测试应同时含成功和拒绝分支：无工具时正常回答；只允许指定工具时不选择别的工具；禁止调用时保留 tools 但没有新调用；无效 Schema 显式报错；流式拒绝与中途错误被辨认；超时后不把局部参数发送给执行器。这里列的是验收设计，未声称已经向各提供方运行这些测试。

13.2.7 Claude Code：调用 Agent 的接口，不是裸 LLM API

外部程序可以通过 Claude Code CLI 的 print 模式使用它，例如下面的教学命令；本文未实际执行这些命令：

claude -p "解释退款核查流程，不执行外部操作" --output-format json

--output-format json 返回 Agent 层的结果与会话元数据；配合 --json-schema 且成功产出结构化结果时，业务对象位于 structured_output，不是自然语言 result。拒绝或未得到合法结构化输出时该字段可能不存在，读取前必须检查。[21] 需要流式事件时，官方示例使用：

claude -p "解释退款核查流程，不执行外部操作" \
  --output-format stream-json --verbose --include-partial-messages

这个 stdout 流是 NDJSON：每行一个 JSON 对象，不是模型 HTTP 接口的 SSE。部分消息可把底层增量包装在 type: stream_event 的 event 中，但还包含 Agent 自己的消息与最终 result。--input-format stream-json 是客户端的输入模式，也不能直接理解成把 /v1/messages 的完整 body 写到 stdin。精确的输入封装、事件与字段应绑定 CLI / Agent SDK 版本。[22][21]

Claude Code 自己负责组织项目规范、Skills、历史、工具权限和模型请求，也可能按配置连接兼容提供方。因此，“向 Claude Code 提交任务”和“向 Claude Messages API 提交一次推理请求”是两个不同的系统边界。

图 13-4：流式工具参数何时可以解析

流式决定内容何时交付，结构约束决定输出如何被解析，工具调用表达候选行动。三者共同参与模型消费，但都不能代替业务授权与结果验收。

13.3.1 工具定义：名称、描述与输入 Schema

工具定义是应用交给模型的候选操作说明，工具调用是模型提出的结构化行动请求，工具结果则由应用实际执行后回填。API 定义这些对象怎样往返，不替应用实现业务能力、资源授权与副作用保证。下面集中说明模型侧契约；第 16 章业务能力设计解释定义背后的操作含义，第 17 章决定每轮可以暴露和执行哪些能力。

以退款只读核查为例，query(system, query) 只说明“查某个系统”，模型无法知道对象、输入格式与适用边界。get_order_line(order_id, line_id) 则表达清楚的只读操作。模型接口需要把名称、描述与输入结构一起提供，不能只给一个函数名，或在描述里隐藏额外参数。

定义部分面向模型表达什么不能证明什么
name当前候选动作的身份，宜采用明确的动作与对象名称名称对应的实现、来源和权限已经可信
description何时使用、输入含义及不适用场景文本中的“只读”已经被执行层强制落实
输入 Schema参数类型、必填项、枚举及提供方支持的结构约束对象归属、金额真实性、当前资源权限

OpenAI 的 strict=true 要求遵守支持的 Schema 子集，例如对象设置 additionalProperties=false、properties 中的字段列为必填；可选含义通过允许 null 等受支持形态表达。缺少约束时不能直接宣称严格模式已生效，也不能把一份任意 JSON Schema 当作所有提供方都支持的定义。[15]

tool_choice 决定本轮如何选择候选工具，不授予业务权限；并行调用选项决定模型能否提出多个调用，不会自动执行它们。具体可选值、模型支持和调用上限按端点核验。注册表中的来源、版本、风险、权限和超时等应用元数据不应直接塞进供应商不支持的字段；Runtime 先筛选能力，协议适配器再生成本轮原生定义。

13.3.2 调用提案、结果回填与关联约束

接收工具提案时，应保留工具身份、参数及协议调用标识。参数可能是 JSON 字符串，也可能已经是对象；解析后仍需经过结构、对象和当前授权校验。工具执行以后，应用将实际观察编码为相应协议的结果项，而不是让模型自己编造“调用成功”。[15][16]

模型接口提案中的标识与参数结果怎样关联
Responsesfunction_call 的 call_id、name、arguments使用 function_call_output 的相同 call_id，output 承载实际工具观察
Chat Completionsassistant 的 tool_calls 中，id 标识调用，function.arguments 表达参数role=tool 的 tool_call_id 指向原调用，content 承载观察
Claude Messagesassistant 的 tool_use 块以 id 标识调用，input 为参数对象user 内容中的 tool_result 以 tool_use_id 关联原工具块

保留必要的 assistant 输出项与历史，不能只发送一条无出处的工具结果。并行提案分别按标识回填，不按数组顺序猜配，也不把多个结果拼成一个失去关联的普通 assistant 回答。Responses 的短示例与业务幂等区别见13.5.2，完整的三协议顺序和结果位置见13.2.8。

结果包装与业务结果是两层结构：function_call_output、role=tool 或 tool_result 解决“这条观察属于哪次调用”；观察中的 status、coverage、effect 和来源字段才表达业务结果。例如一个字符串可以序列化包含 coverage.complete=false 的 JSON，但外层关联正确不代表数据完整。业务结果字段由16.2 结果语义定义，不是 LLM API 通用字段。

只把获准进入模型上下文的摘要、结构化观察和证据交给提供方，完整载荷与凭证留在受控系统。应用工具失败可以形成明确的错误观察，但不能伪造成空结果或成功；若响应在参数封口前中断，不执行残缺提案，也不制造一份假的工具结果来补齐。工具结果仍是外部数据，其中的指令不能提高权限或更改系统规则。

13.3.3 事件模型、工具参数拼装与完成判断

SSE 分帧不保证一次事件对应一个 token；供应商连接结束也不自动证明生成完成。消费者按协议保存输出项，并区分增量、条目封口、整体终态和错误。[26][27]

协议拼装键与参数来源封口后处理
Chat Completionschoice 与 delta.tool_calls[].index；首片可能才有 id/name，arguments 逐片拼接finish_reason=tool_calls 后检查所有调用身份和完整参数，保留多调用关联
Responsesresponse_id、output_index 和 item_id 关联输出项；累积 response.function_call_arguments.deltaarguments.done 给完整参数，再等待相关输出项/整体结果；不能把文本 done 当 response 完成
Claudecontent block index 关联 tool_use；input_json_delta.partial_json 为增量content_block_stop 后解析，message_delta/stop_reason 判断本轮；未知事件保留诊断信息

OpenAI 的指南明确说明工具调用增量按 index 聚合，id/name 等字段常只在首片出现。[15] 以下是独立于 SDK 的 Chat 参数累积教学函数，展示“不覆盖首片身份、不提前执行”；异常、协议终态和授权由外层处理。

import json

def append_tool_delta(buffers, delta):
    slot = buffers.setdefault(delta["index"], {"id": None, "name": None, "arguments": ""})
    if delta.get("id") is not None:
        if slot["id"] not in (None, delta["id"]):
            raise ValueError("conflicting tool identity")
        slot["id"] = delta["id"]
    fn = delta.get("function") or {}
    if fn.get("name") is not None:
        if slot["name"] not in (None, fn["name"]):
            raise ValueError("conflicting tool name")
        slot["name"] = fn["name"]
    slot["arguments"] += fn.get("arguments") or ""

def parse_closed_tool(slot, closed):
    if not closed or not slot["id"] or not slot["name"]:
        raise ValueError("incomplete tool proposal")
    return json.loads(slot["arguments"])

解析成功只表示候选结构完整，工具定义与结构约束见本节工具定义，实体、业务参数和权限仍由业务能力实现及Runtime 裁决检查。

流式取舍与连接约束

流式可提前展示文本，但不保证降低排队或总计算时间；推理阶段也可能没有可见文字。慢客户端需要有界缓冲与背压；超时层次与生成完成统一按 13.4.2 判断，结束 usage 缺失的计费处理见 13.7。

终止字段以对应端点版本为准。Claude 的具体原因参考终止原因指南，内容块参考 Messages 与流式文档。[25][7][28] HTTP 200 后出现 error 事件也必须进入错误通道；已输出文本不撤销这个错误。

应用任务进度 SSE 与供应商生成流是两条连接。应用的持久事件、游标重放和过期快照参考Runtime 结果交付；供应商断流不能由应用伪造续流能力。

13.3.4 结构化输出与保证边界

JSON 模式、Schema 约束和工具严格参数检查解决不同问题。结构化输出应选对应协议的字段，核验支持的 Schema 子集及模型；拒绝、截断和不完整终态仍需单独处理。[24][17]

检查层能证明什么仍需什么
JSON 可解析语法完整字段、类型、必填与额外属性检查
Schema 通过满足被支持的结构约束实体、金额、时效、权限、证据等业务校验
业务验收通过当前任务的必要断言成立明确提交、交付和后续状态

约束解码在生成过程中排除当前结构不允许的候选，Schema 需要先转成可执行的约束；因此提供方只支持特定子集，并可能有首次编译开销。结构保证绑定模型、端点和所支持的 Schema，不能把任意 JSON Schema 直接提交后视为等价。[24][17]

Claude 文档将保证限定为大多数情况：stop_reason=refusal 或 max_tokens 时，内容可能不符合 Schema。先检查终态，再解析业务对象；OpenAI 的拒绝可出现在 Responses 的 refusal 内容块，Chat Completions 使用消息的 refusal 字段，不能假定拒绝位于业务 JSON 中。工具 strict 约束调用参数，最终输出格式约束答案，两者不能互相替代。[24][17]

例如退款字段均合法，也可能忽略处理中占款或适用政策。本章只定义协议保证，业务反例与三层校验参考上下文任务契约。模型输出的置信度不能当作规则通过证明。

13.4.2 HTTP 成功、生成完成与结果可用

客户端应按层判断成功：HTTP 200 只说明已获得成功状态的 HTTP 响应，流中仍可能出现错误；协议正常结束说明本轮生成完成，内容仍可能是拒绝或工具请求；对象符合 Schema 后，还要通过应用验收。以 Chat Completions 为例，stop 可表示自然结束或命中停止序列，length 表示长度上限，tool_calls 表示提出工具调用。停止序列不等于结构化结果完整，长度截断也不能当作正常答案。[5]

13.5.1 多轮对话的三种状态模型

多轮对话通常靠再次提供历史，或由供应商将已保存的历史纳入新请求，不是模型权重在每次调用后记住用户。OpenAI Responses 同时提供显式历史、previous_response_id 响应链和 Conversations 会话对象等管理方式；不能据此假设其他兼容端点也保存状态。[23]

方式谁管理历史主要收益与代价
显式重传历史应用保存并组装必要协议项可控、易迁移；请求体较大，应用负责关联与裁剪
响应 ID 续接供应商按响应链恢复上下文少传重复请求体；依赖保存期限、可访问性及续接语义
持久会话对象供应商维护有独立 ID 的会话项便于跨请求使用；需要管理生命周期、并发写入与删除

减少上传字节不等于减少计费 token。OpenAI 明确说明，使用 previous_response_id 时链中历史输入仍计入输入费用，缓存折扣再按实际命中计算。[23] 旧请求的顶层 instructions 也不会仅因续接 ID 自动继承，应逐轮设置当前规则。[1] 应用应选择清楚的历史管理方式，避免既续接又重传同一历史；服务端保存会话也不意味着输入可以无限增长。

13.5.2 调用 ID 不是业务 Operation

教学 Responses 输出项与回填项分别如下，output 里的 JSON 字符串是工具已返回的观察，不能由模型编造。[15]

{"type":"function_call","id":"fc_demo","call_id":"call_demo","name":"lookup_document","arguments":"{\"document_id\":\"policy-7\"}"}

{"type":"function_call_output","call_id":"call_demo","output":"{\"status\":\"ok\",\"version\":\"v3\",\"evidence_ref\":\"ev7\"}"}

应用保留必要输出项并按 call_id 关联结果，同一调用的冲突内容应拒绝而非覆盖，缺结果不能伪装为完成。call_id 是协议关联标识，不是业务幂等键；动作已发出但结果未知时，由第 17 章 Runtime 沿原 Operation 核验，不能靠重新生成调用保证不重复。

13.5.3 生成断线与任务订阅断线

供应商生成流在终态前断开，只能记录未完成的 Attempt，不能执行半段参数，也不能假定 SSE 支持续传。应用任务订阅是另一条连接，重连不应触发重新执行；游标、重放和快照机制见第 17 章 Runtime 交付与订阅。

13.6 完整案例：构建退款核查 Agent 的有效输入与输出

假设客服在 2026-10-20 10:00（UTC+08:00）发起任务：

确认适用规则和当前可退上限，给客服一段中文回复草稿。

任务看起来只要求一段回复，实际上需要同时解决订单定位、政策适用、退款余额和回复依据四个问题。运行前先定义下列契约，避免模型在生成时自行补齐业务口径。

契约本例约定
数据范围已登录客服有权读取演示商家 shop-demo 的该订单；身份与商家范围由服务端鉴权上下文绑定，不采用模型自报身份

资金口径商品行优惠后实付，减去该行已成功退款和仍占用额度的处理中退款；两类扣减互斥，不重复计数
政策口径查询适用于该商品类别、签收日期和退款原因的政策版本；客户声称质量问题不等于质量问题已核验

完成条件证据足以报告上限与缺项，结构和业务检查通过，即可结束核查；无需等到退款被批准或执行
行动范围仅开放只读核查工具；退款提交与消息发送不在本次能力集合中，执行层也拒绝这些动作

尤其要区分：资金维度可退上限，不等于已经满足全部售后条件，更不等于批准退款。 本例的售后规则只是虚构商家的内部政策设定。

知识库片段是通用核查指南，尚不是本单的适用政策；Memory 只包含语言偏好，不包含“用户历史上退款成功，所以这次也能退”的推断。这个区别决定了模型仍须取回订单、账务与适用条款，而不能直接生成确定金额。

13.6.3 请求快照：System、Skill、知识与 Memory 同时出现

阅读请求前，先区分 API 的消息角色与应用定义的内容职责。role 是协议限定的枚举，不能任意命名；下面的 developer 是 OpenAI 定义的标准角色，不是本例为 Skill 自创的标签。对于这里的 Responses API，普通消息的角色包括：[1][11]

role 值含义本例中的用途
system系统层面的行为约束声明售后核查助手的基础职责与边界
developer应用开发者提供的规则、流程与输出要求承载应用选中的受信 Skill 方法指令
user用户请求或提供给模型的材料承载核查任务，以及按来源标记的知识、Memory 等材料
assistant模型回复；也可作为历史消息传回保留历史模型回复，本次初始请求未使用

可自定义的是 content 中的业务身份、规则和材料组织方式。 例如，"role": "developer" 中的角色值由协议规定，而 "content": "你是售后核查助手……" 中的身份与核查流程由应用定义。角色还参与指令优先级判断，例如开发者指令优先于用户指令；它不是仅用于展示的说话人名称。[11]

因此，Skill、知识与 Memory 都不对应新增的消息角色，不能写成 "role": "skill"、"role": "knowledge" 或 "role": "memory"。本例将受信 Skill 放入 developer 消息，将知识片段与 Memory 放入 user 消息的内容中；其中 knowledge_context、memory 等文本标签是应用约定，不是 API 原生角色，也不因标签名称获得更高的指令优先级。

工具结果也要遵循目标端点的结构：OpenAI Chat Completions 使用 role: "tool" 消息回填函数结果，Responses 则使用 type: "function_call_output" 条目，并通过 call_id 关联原调用。不能把其他端点的角色枚举直接套用到本例，其他工具类型也应使用各自规定的结果条目。[15]

Claude Messages API 也限定消息角色，但不沿用 OpenAI 的全部枚举与字段位置。 常规对话使用 user 和 assistant，初始系统指令通常放在顶层 system 字段；没有独立的 developer 角色。迁移本例时，应用可以把基础规则和受信 Skill 方法指令组织到 system 中，但不能直接复制 role: "developer"。[7]

内容职责Claude Messages API 的对应结构

13.6.6 第三轮生成结果：Schema 约束形状，应用核对事实

证据已足以完成本次核查。System、developer 等角色的相对优先级以所选提供方契约为准，不能仅凭字段名建立跨提供方排序。Runtime 在第三轮保留原有 tools，将 tool_choice 设为 none 禁止提出新调用，并使用 Responses 的 text.format 指定最终结果 Schema。结构化输出约束最终结果，前两轮工具的 strict 则约束调用参数，两者解决不同问题。[24]

本例为 OpenAI Responses 教学请求；DeepSeek Responses 兼容端点会忽略 parallel_tool_calls，不能用同一参数主张串并行保证。[9]

最终请求复用教学请求体已展开的 text.format，无需再定义另一套 Schema。应用保留工具定义、禁止新调用并追加真实观察，示意如下；response.output 的输入转换按 SDK 和模型协议处理，不能丢失要求保留的项：

# 伪代码：request_1 是前面完整 JSON 解析后的对象；查询结果由 Runtime 真实取得。
import copy

request_2 = copy.deepcopy(request_1)
request_2["input"] += adapter.to_input_items(response_1.output)
request_2["input"].append(order_tool_output)
response_2 = runtime.call_model(request_2)

request_3 = copy.deepcopy(request_2)
request_3["input"] += adapter.to_input_items(response_2.output)
request_3["input"] += [ledger_tool_output, policy_tool_output]
request_3["tool_choice"] = "none"  # 保留原 tools 定义，当前轮禁止新工具调用
response_3 = runtime.call_model(request_3)

request_2 含原始四条消息、第一轮输出及订单观察；request_3 再增加第二轮输出、账务观察和政策观察。工具结果以独立协议项追加。样例假设应用已经核实证据足以结束查询，才进入最后一轮。

判断一致性申请 15000 分大于上限 13000 分，且质量凭证缺失，必须报告对应问题修正或重新生成结果，不能以结构合法为由放行
证据与表述ID 存在且当前可访问，金额与政策引用对应；草稿不声称已退款或已发送ID 存在性可程序检查，语义支持还需规则、审查或评估；不能只检查“引用数组非空”

本例可采用“最多一次带明确错误的重新生成”作为教学预算策略。若仍不通过，则交付无法完成的原因和已有证据；这不是模型性能实测得到的通用重试次数。无论如何，重新生成只能改变候选回答，不能篡改工具观察或把未执行动作写成成功。

13.6.7 从模型响应到交付结果：让人和程序各取所需

校验后，后台保存结构化核查结果及证据版本，金额、状态与证据由同一对象渲染，不另造一份展示数据。自由生成的草稿仍要核对是否与结构化结论一致，并明确标为待客服使用的文字；草稿不会自动发送，查询快照也不构成额度预留。

超时、政策不适用、工具注入与输出验收失败时保留原调用关联、证据缺口和实际状态，按Runtime 失败分类选择补证、查询或停止；未知金额不能当零，未封口调用不能派发。

13.7 性能、成本、数据契约与迁移验证

图 13-8：分别计量延迟、缓存与治理

13.7.1 分开测量首字、生成和端到端耗时

可以用下面的近似分解定位调用延迟；这是观测模型，不代表供应商一定暴露这些内部计时：

端到端耗时 ≈ 客户端准备 + 网络 + 排队 + 输入处理 + 生成 + 结果验收
首个可见文本延迟 ≈ 前置阶段 + 首个可见文本产生前的计算与传输

本书将客户端开始请求至首个可观测输出 token 定义为端到端 TTFT；若提供方单独报告服务端 TTFT，必须保留其不同起点。首响应是 HTTP headers 到达，首事件是首个协议事件，首个可见文本可能晚于推理 token；这些时间点不能混算；应分别记录客户端请求起点、首响应、首事件、首个可观测输出 token、首个可见文本和终态。HTTP headers 或 response.created 很快到达，不意味着用户已经看到答案；推理模型也可能在首个可见文本前花费计算。没有供应商遥测时，只能提出“排队或输入处理较慢”的假设，不能从客户端总时长精确反推内部阶段。[2][3]

现象优先核查候选改进与代价
首字慢网络、限流重试、输入长度、缓存命中和推理配置减少无关输入、复用稳定前缀、评估更低延迟模型或预算；需复测质量
首字快但完成慢输出量、推理量、事件间隔和慢客户端约束回答长度、减少冗余字段；不能靠截断破坏结果完整性
单次快但任务慢多轮请求及外部等待减少不必要调用；不能为少一轮而省略必要证据

比较时应按模型、输入和输出规模、推理配置、缓存状态分组观察 p50、p95 与失败率，不能把不同负载混成一个平均值。流式主要改变展示时机；优化效果必须在同一任务集上同时比较质量、延迟与费用。[2]

13.7.2 RPM、TPM 与并发限制共同决定容量

RPM 限制请求次数，TPM 限制 token 流量，并发限制约束同时在途的请求；图片、音频或长上下文还可能有独立额度。供应商的 token 限流口径未必等于最终账单，有时会结合请求长度估算与申请的输出上限预留资源，因此把输出上限随意设得很大也可能降低可接纳流量。具体以端点说明和响应 headers 为准。[29]

用均值作粗略规划，可推导稳定吞吐的教学上界：

请求/秒 ≤ min(RPM/60, TPM/(60×平均限流token/请求), 并发上限/平均占用秒数)

这个估算不能预测突发、长尾或短时间窗口限流。即使一分钟总量未超限，集中发送也可能触发限制。客户端应同时控制发起速率与在途数量，结合 13.4.1 的剩余额度和重置头调整节奏；多实例限流由 Runtime 统一协调。服务额度也不等于费用预算，两者需要独立观测。[29]

13.7.3 成本核算、Prompt caching 与 Batch

费用应按实际计费桶求和：费用 = Σ（该桶用量 × 对应单价）。先确认普通输入、缓存读取、缓存写入、生成内容，以及图片、音频、托管工具是否分别收费。明细可能是总量的子项，也可能是独立计费项，不能把输入总量和全部缓存明细再次相加；推理 token 若已包含在生成量中，也不重复计费。[4][31]

Prompt caching 复用符合条件的输入前缀计算，不是把上次答案作为这次答案返回，也不是会话记忆。稳定指令和公共材料适合放在前部，动态内容尽量后置；工具定义、顺序和历史改写也可能影响命中。最低可缓存长度、缓存边界、保留时间、隔离范围及读写价格随模型而异，写入也可能收费。Anthropic 缓存按 tools→system→messages 形成前缀，工具变化会影响后续命中，读写计费需按其模型与 TTL 说明核对。[32] 因此应观察实际 cached tokens、写入量和总费用，不以请求“看起来相似”判断命中，也不为凑缓存长度加入无用材料。[31]

Batch API 适合允许延后交付的大量独立请求。它可能提供独立限流和更低价格，但折扣、完成窗口与支持端点是产品条款，不是异步 API 的普遍性质。OpenAI Batch 通过 custom_id 对应输入与结果，输出顺序可能不同，还需区分请求级错误与整批任务状态。[33]

最终 usage 比本地按可见文字估算更适合核算，但流中断可能使客户端收不到结束 usage，不能据此记为零成本。[5] 应记录请求 ID、attempt、实际模型、计费配置和“待核对”状态，在接口支持时取回最终对象，再与供应商用量报表或账单核对。任务费用包含失败与重试尝试；单位成功成本按统一成本口径计算，本章只解释 usage 与提供方计费字段。

13.7.4 数据约束参与端点选择

训练用途、保留、删除、区域、第三方处理和密钥管理是端点选择的前提。store:false 不表示所有日志零保留，基础 API 兼容也不表示满足相同数据政策；完整检查表与凭据边界参考治理中的数据边界。[34]

13.7.5 用契约测试与质量回归证明迁移可用

第三方 sashabaranov/go-openai@v1.43.0 的 ChatCompletionMessage.MarshalJSON 将非空 Content 序列化为字符串，将非空 MultiContent 序列化为同一个 content 字段的数组；非空 Content 与非 nil MultiContent 同时设置会报错，空内容还可能因 omitempty 被省略。Chat 的 Tool.Function 产生嵌套 function；Responses 应使用 NewResponseFunctionTool 等方式产生扁平字段。该版本 ResponseTool 实际是 Tool 的别名，不会仅因换到 Responses 请求就自动转换嵌套定义。[35][36] 这些是固定版本的源码与离线序列化结论，不是端点实测；升级后重新检查 JSON，不能由 Go 的 any 或序列化成功推导服务端支持。

“兼容”至少分为字段可发送、协议可消费和应用可接受三个层次。迁移前应固定能力清单与测试样本，而不是只验证一条问候语：

验证层能证明什么仍不能证明什么
官方文档核对声明支持的角色、参数、模型及限制目标账户与端点实际行为
SDK 序列化检查客户端确实发送了预期 JSON服务端接受字段且按语义执行
真实端点契约测试实际角色、Schema、工具关联、流终态、错误与 usage 行为所有任务的回答质量
固定任务集质量回归关键事实、结构、拒绝、延迟与成本的可比较表现未来模型更新后的表现

测试还应覆盖空内容、拒绝、长度截断、usage 缺失、并行调用关联，以及可控注入的断流、重复事件和未知事件；不能只测正常路径。升级时记录模型快照与别名、SDK、协议、提示模板、Schema hash 和适配器版本，重新核验关键能力。生产切换可基于脱敏样本回放或获得授权的少量流量验证，并保留回退配置；切换提供方本身也需要重新满足数据契约。

本章小结

图 13-9：协议消费的验收链

LLM API 的接入契约覆盖输入组织、生成预算、输出类型、会话状态、终态与错误，也包括 usage、缓存及数据保留。降低温度不保证事实正确，Schema 合法不保证结论正确，HTTP 成功不保证生成完成，服务端续接也不代表历史免费。性能应分别测量首字、生成与端到端耗时，成本则按实际计费桶和全部尝试核算。

Provider Adapter 把消息、工具关联、完整输出与错误映射成应用可消费契约，同时保留供应商差异。SSE 只提供传输分帧，自定义工具执行和业务幂等仍属于 Runtime 与业务系统。兼容声明要有版本与分层验证，教学样例不能冒充端点实测。

构建有效的大模型输入，需要把任务指令、工具规约与带来源的材料组织到正确协议位置；构建有效输出，则要区分中间工具提案、最终结构化结果与面向人的表达。退款核查案例中的闭环是：组装当前输入 → 获取必要观察 → 更新上下文 → 生成契约内结果 → 核验事实和业务语义 → 渲染交付内容。
