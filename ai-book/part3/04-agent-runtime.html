AI Engineering：大模型与智能体系统工程

第 17 章 Agent Runtime：架构、执行编排与可靠性工程

Agent Runtime 负责把用户目标转成受控的执行过程：建立任务契约，绑定身份、能力和预算，驱动模型与工具，保存已经确认的进度，并在失败、等待或中断后决定怎样继续。模型提供候选判断，Runtime 使这些判断成为可追踪、可恢复和可验收的行动。

本章消费第16章 外部工具系统提供的能力契约，说明 Runtime 怎样组织执行、跨层安全控制、等待与恢复。组件可以合并在一个进程中，也可以按需拆分；对象名、字段、伪代码、提交协议和数值均为本书参考设计，不是产品标准。故障时序用于解释约束，不代表完成了真实系统的故障注入或性能测试；未注明实测来源的限额与时间仅为示例。

17.1 Runtime 的职责与边界

Runtime 的设计从任务承诺开始。用户交付一个目标，系统需要说明是否受理、当前做到哪里、正在等待什么、哪些动作需要批准、结果依据什么成立。一次模型请求成功，只能说明获得了输出；任务是否允许继续、动作是否已生效、结果能否交付，需要应用维护的事实和规则来回答。

本章贯穿第14章 ALR 案例档案中的同一次教学运行：ALR-20260429-017、run_0429_017 和 trace_label=trace_20260429_017。对象为 prod/order-service，观察窗为 2026-04-29 10:35–10:50（Asia/Shanghai，即 02:35Z–02:50Z）。E12 的 P95 从 210ms 升至 2.1s 仍是未核验候选，不进入已确认事实，也不证明部署或数据库是根因。能力仅限只读调查，以及持有绑定草稿和资源版本的有效审批后创建跟进工单 INC-4821，不提供重启或回滚。报告完成、建单确认和通知送达分别记录；建单回执丢失时沿原 Operation 核验。这些身份、数值与结果均为虚构教学设定。

17.1.1 从模型输出到任务承诺

模型具备选择工具、综合证据和修订计划的能力，为动态任务提供了基础。MRKL 与 Toolformer 分别研究模块组合与模型学习调用工具的机制。[1][2] 本书据此区分能力描述与执行授权：即使模型能提出某个调用，Runtime 仍要把它限制在可信系统允许的范围内；后一句是本书的工程边界，不是这两篇论文给出的安全保证。

承诺Runtime 必须维护什么可检查的结果

控制行动当前主体、资源范围、策略和必要批准每次动作具有可核对的裁决，不因模型换路线而越权

验证并交付验收依据、产物版本、访问资格和交付状态可以区分计算完成、业务生效与通知结果

这些承诺可以由普通函数和请求内状态实现，也可以依靠持久调度。关键是如实声明故障后的行为：只支持请求内计算时，不能把响应中的“处理中”当作重启后仍可继续的承诺；只有完成持久受理后，才可以向调用方承诺任务身份和查询入口长期有效。

任务目标还会发生变化。用户补充一个条件，可能是在修改当前任务，也可能是在提出独立目标。系统应保存被接受的修订，并使未来动作采用新约束；已经发生的外部动作不能因目标改变而从历史中消失。持续触发的任务还需规定触发条件、有效期限、资源访问范围和通知方式，一次授权不能自动延伸成无限期行动权。

17.1.2 Agent Loop、Harness、Workflow 与 Runtime

这几个术语观察的是不同层次，实际实现可以重叠。先区分它们的职责，有助于判断某个 SDK 或自建模块究竟提供了什么。

概念关注的问题与 Runtime 的关系
Agent Loop如何根据当前观察提出下一步行动，何时继续或结束是决策与行动循环，不独立拥有用户授权和业务事实
Harness如何为模型组织上下文、工具、约束、验证和反馈是围绕模型的工作环境，可以承担 Runtime 的部分实现
Workflow步骤之间有什么顺序、分支、依赖和失败出口定义路径，可嵌入一个或多个有界 Agent 节点
Orchestrator谁激活节点、分配分支并汇总结果承担协调职责，需要依赖状态与执行权机制
Runtime一个任务如何从受理走到执行、等待、恢复和交付负责端到端生命周期与责任边界

固定 Workflow 的路径由代码预先规定，动态 Agent 的下一步由模型结合观察决定；复杂任务可以将两者组合。[3] Runtime 同时支撑这两种执行方式，不要求所有任务都动态规划，也不要求有工具的任务都循环多轮。

模型适合解释、摘要、候选计划、证据归纳和允许范围内的路径选择。身份认证、租户归属、额度预留、状态提交和业务回执核验则需要明确规则。工具返回“已执行”、模型输出“已完成”、界面收到最后一段文本，都需要放到任务契约中判断其真实含义。

Runtime 与宿主环境也有边界。Runtime 决定动作资格和执行限制，操作系统、容器、沙箱以及资源端负责真正限制文件、进程、网络和业务资源的可达范围。目录命名、角色提示词和工具列表可以减少误用，但不能替代底层访问控制。

17.1.3 设计约束与责任边界

模型负责基于当前输入提出候选解释、计划、工具动作或结束建议；Runtime 负责检查这些提议是否满足任务契约、权限、预算和验收要求。模型可以帮助理解意图，但不能自行补造用户授权；可以建议任务完成，但不能仅凭自己的判断改写权威终态。

因此必须区分三种权力：提出下一步、批准执行、确认事实。Agent Loop 与 Planner 承担提议职责，Policy 与人工控制承担授权职责，状态管理与 Verifier 接受有证据的结果，业务后端提供外部动作的事实依据。任何替代工具或子 Agent 都沿用这些边界。

这些特性解释了为何需要独立的状态、授权与验收组件；“让模型参与判断，由系统承担责任”是本书的设计原则，不能理解为模型天然具备可靠风险判断能力。

上述约束决定三个设计原则。第一，系统记录的状态必须能解释模型当前依据什么继续；第二，每个动作都在实际派发时核验资格，不能把循环入口的一次检查当作永久许可；第三，失败状态要保留不确定性，超时和取消不能证明外部动作没有发生。

可靠性也包含活性：系统既要阻止错误动作，也要让正常工作能够完成，让阻塞有责任人和处理期限。对所有失败一律暂停会造成无人处理的积压；对所有失败一律重试则会扩大成本和副作用。后续架构与状态模型要同时表达自动推进、持久等待、人工处理及最终收敛。

控制面：管理任务事实与执行条件

控制面持有 Task / Run 的权威状态，决定任务契约、依赖关系、执行资格与完成条件。它归并入口与意图、规划与调度、策略与人工审批、配置与能力注册、持久状态、上下文与记忆策略等职责。能力注册说明可用的 Model、Tool、Skill 和 Source 及其版本，不等于授权；模型可以参与意图理解和规划，但候选计划、候选动作与已提交事实必须分开保存。

执行面：完成受控计算并返回证据

执行面包括上下文装配与模型调用、工具与环境执行、结果验证与交付。它根据控制面提供的任务、版本和权限工作，返回结构化观察、验证结果、产物与回执。执行 Worker 可以保留当前调用句柄、进程信息和局部缓存，但这些局部状态不能替代持久任务事实，也不能成为它自行推进全局 Run 状态的依据。

横切能力：约束并记录各组件的工作

预算与资源控制贯穿模型调用、工具执行和委派，统一约束 Token、费用、时间、并发、配额和截止时间；身份与凭证把主体和资源范围绑定到本次运行；Trace、Audit、指标与告警记录因果、用量和裁决证据。各自的预算、授权和审计记录仍须有明确归属，不能形成另一套相互冲突的任务状态。

这里的 Runtime 是上述职责的整体，而不是与 Agent Loop、Execution Engine 并列的另一个执行节点。“控制面 / 执行面”划分的是决策与执行责任，不是按组件名称机械划分进程：例如 Verifier 的规则归控制面管理，检查可以在 Worker 中运行，检查结果由控制面接受；上下文访问规则与实际检索也可以分别部署。底层数据库、消息系统、对象存储与沙箱属于外部依赖，但它们怎样提交、恢复和强制访问边界，决定了 Runtime 能兑现哪些承诺。

逻辑上的控制面可以直接调用同进程执行器，也可以通过持久调度驱动远程 Worker。网络边界增加了失败窗口，拆分部署后还需要明确请求去重、调用超时与结果未知的处理，不能把进程内函数调用的假设直接搬到 RPC 上。

17.2.2 模块接口与执行契约

组件传递带身份、版本、约束和输入引用的不可变数据。入口提交受理身份；Context Builder 返回上下文包；模型返回提议；Policy 返回当前裁决；执行器返回观察；状态接口条件提交进度，Verifier 判断验收。执行骨架与 C1–C7把这些接口连成正常路径。

每个接收方验证可信身份，不能因为载荷含 tenant_id 或 authorization_ref 就接受。敏感连接、实现地址和凭证引用来自运行绑定，不能由模型拼接。错误通道保留发生层次、可重试提示、可能效果和关联对象；等待返回持久记录与触发条件。

嵌套工作流约定唯一的总预算、重试与取消责任。局部节点可以修复本层失败，但不能重置根额度、放宽权限或直接完成父任务。业务操作与结果语义由外部能力设计定义，模型侧工具包装与关联由第 13 章定义。

图中最需要注意的是 Operation 与 Attempt 的关系：一个业务动作可以被多次尝试推进或查询，但它的身份不随尝试变化。Event 记录 Run 上已经被接受的状态变化，Checkpoint 是从这些事实中整理出的恢复索引，Artifact 则承载不适合放进状态表的大载荷。

这些身份必须分开的原因在于，它们在不同的时机变化。一个 Run 可以由不同 worker 接续，经历多次重连才完成，所以线程、进程、连接与 Run 不能共用一个身份字段。如果把 Task 和 Run 混为一个 id，系统就无法区分“重试”和“重新运行”，计费会出错，不同版本的执行历史也会互相覆盖。

本节先使用 Task、Run、Step、Operation 四个稳定对象。Session 记录交互，Attempt 记录一次尝试，Event/Checkpoint/Artifact 分别提供变化记录、恢复索引和版本化载荷；它们在后续执行与恢复中逐步展开。执行权代次和两种幂等键的字段约束在执行权与迟到提交处定义。

例如，同一个工单 Connector 可服务多个组织；Connection A 属于租户 A，Run R 仅绑定项目 P 的读取与待审批创建权限。后续每次调用都使用这个受限绑定，而不是由模型输入的 URL 或项目名自由选择连接。绑定如何参与派发见 本次执行的能力绑定。

17.2.4 状态机与条件提交

状态机定义对象允许处于哪些状态，以及哪些变化具有业务意义。Run 的执行状态、Step 的推进状态、Operation 的外部结果和用户界面的展示状态是不同维度：例如 Run 已取消，仍可能存在需要核验的在途 Operation；界面中的“处理中”也不应成为后端状态的权威来源。下表先说明事实归属，随后定义状态迁移与提交规则。

信息权威来源及管理责任不能替代它的信息
目标与约束Task 契约及明确接受的修订模型猜测、未确认的历史摘要
执行状态与执行权控制面接受的持久状态、领域事件与版本记录Worker 内存、连接存活或队列可见性
业务副作用Operation 账本中关联的资源端回执与核验事实模型宣称成功、工具调用已发出
可供继续使用的执行依据Checkpoint 引用的已提交事实、配置和产物SDK session ID 或一份对话摘要
对话与跨任务信息消息存储与受治理的 Memory任务事件账本；两者不互相替代
诊断与审计证据Trace、Audit、指标及其关联记录不能仅凭普通 Trace 重建全部任务事实

Run 的状态维度

状态含义允许的后续处理
QUEUED已受理并等待调度取得执行资格后进入运行，或接收取消
RUNNING正在推进可执行步骤继续、进入等待、暂停、取消或提交终态
WAITING已登记审批、输入、事件或定时器满足匹配条件后恢复，超时按契约处理
PAUSED当前禁止自动推进，但保留恢复可能明确恢复授权和条件后重新排队

COMPLETED任务完成条件已经通过并提交保持终态；通知重试独立处理
FAILED当前执行无法按契约完成保留证据；修复或重新执行采用明确入口
CANCELLED当前执行承诺已经结束核验在途外部事实，不再激活普通后继

WAITING 另存 wait_kind，区分等待输入、审批、人工核验、工具作业和定时器；FAILED 另存错误与恢复分类。结果完整性、通知状态和 Operation 事实通过独立字段表达，避免把几十种组合塞进同一状态枚举。运行仍在进行时，已经有部分产物也不表示进入完成终态。

Step 的状态可以细化为等待依赖、可运行、执行中、等待外部结果、已完成和失败；其迁移需要满足计划版本、输入版本及验收条件。Attempt 只记录本次尝试的开始、结果和用量，Operation 则独立记录外部动作是否发生。子 Step 的失败不一定使整个 Run 失败，是否允许修复或部分交付由父契约决定。

除 Task 与 Run 外，Step、Operation、Artifact、事件与幂等索引均绑定 tenant_id；查询和唯一约束包含租户，不能仅靠全局随机 ID 代替隔离。

同一个 Run 可能同时被恢复 Worker、取消请求、回调和定时器更新。处理并发有两类方案：actor 等单写者机制把命令交给唯一有效写入方串行处理；CAS 允许多个请求竞争提交，但只接受符合当前版本和状态条件的迁移，失败者重读后决策。两者都要防止过期执行者写入，不能把“采用 CAS”直接称为物理单写者。本章以下以 CAS 加执行代次作为参考实现。

一次状态迁移在同一事务中检查当前状态、state_version 和执行权代次，全部满足才更新状态并追加事件；冲突者重读后再决定合并或停止。这种比较并设置（compare-and-set，CAS）返回新的提交版本。事件表采用唯一约束 (tenant_id, run_id, run_seq)，序号仅在对应租户的 Run 内递增，由服务端分配；客户端墙钟不决定因果顺序。

RUN_CREATED、STEP_STARTED、APPROVAL_REQUIRED 和 RUN_COMPLETED 等事件追加记录已接受的变化，投影必须可重建，重复和乱序回报通过序号、Attempt 与版本检查。持久工作流可依据有序历史重建推进位置。[4] 这不意味着外部生效一次：分布式锁会过期，消息可能重复，资源端也可能继续处理旧请求，需分别使用执行权与Operation协议。

运行终态与业务事实要分开保存。CANCELLED 表示不再继续这次执行，而外部工具晚到的成功仍然是真实发生的事实。系统可以追加核验事件或补偿事件来解释它，但不能为了让界面看起来整齐而删除它。反过来，远端成功也不能让已取消的 Run 自动回到 RUNNING 并继续后续动作。终态保护的是执行承诺，账本保留的是业务世界中已经发生的变化。

17.2.5 存储职责、事件与观测

对话历史保存“说过什么”，Memory 保存受治理的跨任务信息，执行事件保存已接受的变化，Operation 账本关联外部动作与核验事实。摘要里的“已创建工单”不能替代对应 Operation 与资源端证据。

状态表也不必承载所有内容。任务目标、当前版本、依赖关系、执行权和未决操作需要可查询，因此放在状态表中；长文本、文件、工具原始载荷和报告进入受控的 Artifact 仓库；事件则保留状态变化的因果。读取 Artifact 时要再次检查当前权限，曾经进入过某个 Run 的内容，并不意味着永远可见。内容哈希可以证明载荷是否发生变化，但它不能代替鉴权，也不能证明业务含义正确。

单次执行的恢复状态与跨任务共享信息应采用不同的存储契约；内存实现可以验证接口，但无法证明进程重启后的耐久性。[5] 在本章的参考设计中，状态、事件、Artifact 与记忆可以共用底层存储，但各自的提交、删除、权限和保留规则必须分别定义。

消息存储保留原文与来源血缘，模型只读取本轮上下文包，不直接消费全部历史；包引用与过滤记录应可审计。

ReAct 的结构化候选动作和观察必须由状态机接受；不保存或展示完整思维链，也不把自由文本当作迁移。循环判据见派发与提交，模式定义见17.4.2 编排模式、依赖图与汇合。

Trace 记录组件、耗时与用量，Audit 保存谁触发、批准或执行了什么，两者关联 Task、Run 与 Operation。诊断记录可能采样、截断或延迟，不能代替执行账本；强审计记录先走可确认的持久路径，再异步导出视图。敏感正文进入受控载荷，日志仅留必要索引，日志访问本身也受权限控制。

运行指标应从这些对象派生：排队时长与执行时长分开，模型、工具、审批等待和交付各有耗时；成功任务成本包含失败尝试与核验；UNKNOWN Operation 的数量和年龄独立于 Run 成功率。否则进程都正常、终态都好看，也可能掩盖长期无人处理的外部事实。

17.3.1 启动入口与装配顺序

Runtime 可以由本地 CLI、桌面/IDE 宿主、HTTP 服务或后台 Worker 进程启动。入口不同，启动职责仍可归为同一条装配链：确定实例角色与工作区，解析有效配置，校验能力来源与策略，建立基础设施客户端，装配能力目录，最后决定是否对外就绪。启动不需要先调用模型；模型负责的任务理解与工具选择发生在受理之后。

本地 CLI 往往在一个进程里同时承担入口、调度和执行；服务端可将 API、调度器和 Worker 分开启动。API 启动时主要证明可以可靠受理与查询任务，Worker 主要证明能认领并执行自己支持版本的任务，不能要求每个 API 副本都启动所有本地 MCP Server。组件归属由部署角色决定，同一份配置先裁剪为本实例需要的依赖图。

17.3.3 基础设施、模型适配器与执行后端

配置通过校验后，Runtime 按本实例角色建立状态库、事件、Outbox、Artifact、Memory/检索访问与观测客户端。它检查所需结构版本和访问范围，不让每个进程在启动时竞争执行生产数据库迁移；迁移由发布流程协调。状态库可连通不代表持久受理已可用，还须检查事务、所需表与本角色权限是否满足约定。

模型适配器先解析提供方、端点、协议、模型引用、超时、重试与额度设置，向凭证服务取得受限调用句柄，并检查所选接口和功能是否兼容。初始化 SDK 或 HTTP 连接池不等于已经发送推理请求，也不证明模型服务一定可用；是否执行最小探测由部署策略决定，不能为了每次健康检查反复发起付费生成。限流、模型不可用与协议错误仍由任务运行时按分类处理。

执行后端同时确认工作区、临时目录、文件读写范围、网络出口、进程限制与必要的隔离设施。必需沙箱无法落实时不暴露执行能力；启动成功也不能赋予某次 Run 更大的权限。观测客户端此时建立实例启动事件与配置摘要，实际调用再关联 Run、Step、Attempt 和 Operation，不提前生成虚假的任务成功记录。

17.3.4 Skill 发现、元数据索引与按需加载

Skill 装配器按允许的来源扫描目录或读取已发布包的索引，例如 skills/incident-diagnosis/SKILL.md。它先解析名称、描述、入口位置与必要元数据，核对来源、版本、路径和体积限制，检查发布记录中声明的工具/运行环境依赖，再形成可检索目录。重名项按显式的命名空间或覆盖规则解决，不能依赖不稳定的文件遍历顺序。

启动期的“加载 Skill”通常应拆成三步理解：发现时建立元数据索引；任务选择后读入对应版本正文；执行到某个分支时再取参考资料、模板和脚本。三步的具体实现见第 16 章渐进式加载。目录中存在 SKILL.md 不代表正文已经进入模型请求，更不代表包中的脚本已执行。

指令文件与 Skill 的生命周期也不同。AGENTS.md 等工作区规则按宿主声明的作用域形成指令链；Skill 是按任务选择的能力包。Runtime 为两者分别保存实际使用的来源和版本，限制总上下文预算，不在启动时把全部 Skill、附件、历史记录和工具结果一次性塞给模型。

发现、可见、加载和授权是四个不同状态。某个 Skill 可能已被索引，却因环境不符、依赖未就绪或当前用户无权使用而不可见；也可能正文已读入，但其中建议的建单动作仍须单独审批。依赖可延迟准备时记录 pending 及激活条件，失败时明确禁用或等待，不能让模型猜工具名来绕过装配。

17.3.5 MCP Client、Server 与工具目录初始化

Host 为每个 Server 维护一个 Client 的 1:1 逻辑关联；同一远程 Server 可以服务多个 Host / Client，独立 Client 并不等于独立租户或单独的服务部署。初始化时分别记录 Server 身份、协议适配、传输句柄与当前授权范围，不能把它们折叠成一个含义不明的“已连接”。[6]

Runtime 按可信 Server 定义创建 MCP Client 适配器，先核对来源、传输、端点或启动命令、协议兼容范围、超时及网络策略。对于本地 stdio Server，受控执行器在允许的工作目录与最小环境中启动子进程，标准输出交给协议解析，标准错误等诊断输出进入受控日志；不能把普通日志混入协议通道。对于远程 HTTP Server，Client 准备 TLS、代理、连接池与第一跳认证设施，通常不负责启动远端服务。

这里的“初始化”指宿主装配动作，不等于所有版本都发送 initialize。本书第 16 章采用的 2026-07-28 MCP 规范不以 initialize 建立协议会话：请求携带版本与 Client 能力，Client 可先调用 server/discover 了解 Server，再请求 tools/list 并处理不兼容版本。旧版 2025-11-25 及更早的握手路径才是 initialize → initialized。版本与传输兼容须沿第 16 章协议版本边界实现，不把两套生命周期拼成固定流程。[7]

工具发现完成后，Host 校验工具名、输入/输出契约、来源与风险声明，写入带可见范围和新鲜度信息的能力目录；声明的只读、破坏性或幂等提示不作为权限证明。列表若与调用身份相关，只能在对应主体、租户与权限范围内缓存，不允许用一个高权限启动账户的目录作为所有用户的可用工具集。

MCP 目录缓存还须保留 ttlMs、cacheScope、Server 来源、契约版本及对应授权上下文。到期刷新与授权撤销分别处理，不能让 TTL 延续旧权限，也不能将 A 的工具列表交给 B。支持相应协议能力时，目录变更订阅通过 subscriptions/listen 的 POST 流接收；进度等请求内通知按对应响应流处理，更新目录后重新裁剪当前任务的工具集。[8][9]

装配策略可以选择 eager 或 lazy。eager 在实例就绪前准备本角色必需的传输与发现；lazy 只注册端点、契约引用和初始化条件，首次被选中时再做认证、发现与兼容检查，准备与调用裁决完成前不派发业务动作。两者都要有超时与错误状态：discovered、transport_ready、auth_required、available、disabled 可作为本书参考状态，连接建立本身不能直接跳到“已授权调用”。

本地 Server 启动失败、协议不相交、工具契约漂移或授权失效时，分别记录原因。必需依赖失败阻止对应角色就绪，可选服务只关闭相关能力；身份未知或尚未登录的用户连接可以等待任务期准备。重连只恢复传输，不自动重放结果未知的写操作，业务核验仍沿原 Operation。

第一跳认证与账号连接等待

HTTP Client 访问受保护 Server 时，按 401 / WWW-Authenticate 取得资源授权元数据，核验授权服务器与资源受众后发起对应授权事务。403 / insufficient_scope 挑战指出所需 Scope 时，Client 计算已请求范围与挑战范围的并集，但是否允许申请仍由组织策略、用户同意和本次任务决定；获得新令牌后有界继续调用，不让模型靠改参数自行扩权。Token 使用 Authorization 头，不放进 URL、工具参数、模型上下文或普通日志。[10]

多授权服务器场景要防止 issuer 混淆。跳转前，Client 从已验证的授权服务器元数据取得 issuer，与 PKCE verifier、state（若使用）绑定到同一事务；兑换授权码前按下表检查授权响应（包括错误响应）。支持位指元数据字段 authorization_response_iss_parameter_supported。[10][11]

元数据支持位响应含 iss响应不含 iss
true解码后与预先绑定的 issuer 做简单字符串比较；不匹配即拒绝拒绝
false 或未提供仍须比较；不匹配即拒绝按其他授权校验继续，不凭空判定 iss 失败

不对 issuer 做大小写、端口或尾斜杠归一化，也不根据回调临时改选 Token 端点；issuer 不匹配时不能继续处理或展示响应中的错误信息。这与 state、PKCE 和资源受众检查分别防御不同的问题；缺少 iss 时仍须落实 RFC 9700 的防混淆要求。[12][10]

stdio 不套用 HTTP OAuth 流程：Host 为获准子进程提供必要的最小环境，并检查凭证继承与实际隔离；本地桥接访问远端 API 时，Connector 的下游身份仍独立绑定。第一跳 Client 认证成功也不证明第二跳业务账号已经连接，二者分别记录等待、撤销和错误。Server 的凭证校验与资源授权见16.4.5。[10]

17.3.6 Connector 适配器、凭证提供方与业务连接

Connector 把外部业务 API 映射为工具能力，可以直接嵌入 Runtime，也可以运行在远程 MCP Server 后面。前者由本实例初始化适配器、API 客户端和连接服务；后者由服务提供方装配，Host 只校验自己到 MCP Server 的契约与认证，不能假定能读取或管理远端下游凭证。

启动期通常只准备 Connector 的静态部分：加载适配器版本，校验 API 基址、资源映射、超时、分页、限流和幂等契约，连接凭证提供方，并检查 Connection 存储可访问。无副作用的健康或权限探测要限定范围；不能为了证明“初始化成功”而创建工单、发送消息或导出业务数据。

用户授权属于动态部分。只有知道当前调用者、租户、组织与操作后，连接服务才解析该主体的 Connection，取得或刷新必要凭证，并核验下游账号、Scope、资源归属及撤销状态。长期服务账号也须限定环境与资源，不能把它放进全局模型上下文或默认分给全部 Run。OAuth 回调与两跳授权的具体实现见第 16 章 Connector 认证。

“适配器已注册”“凭证设施可用”“用户已连接账号”“具体动作获准执行”分别记录。缺少用户授权时进入可解释的 auth_required，由受信界面引导连接；拒绝或取消后不继续尝试其他人的凭证。对 ALR，启动时可以登记只读诊断和工单适配器，但建单连接就绪仍不产生创建 INC-4821 的批准，草稿和资源版本的审批绑定保持不变。

17.3.7 能力快照、就绪检查与退出

各装配器返回版本、契约、依赖和状态，由启动协调器汇成能力快照，关联生效配置摘要与发布 manifest。快照固定“本实例准备了什么”，用户和任务范围决定“本次可以用什么”；后者仍需在动作派发时复核。远程服务无法固定实现版本时，保存观察到的目录快照并验证行为契约，不宣称仅保存一个 URL 就能重现历史执行。

角色Ready 必须证明什么不代表什么
API能持久受理并查询任务，容量与兼容版本路由有效所有 Worker 或可选工具都可用
Worker能认领并加载自己支持版本的工作，必需依赖和执行边界已准备可以执行任意 Run 或复用历史授权
本地执行器工作区、文件、网络、进程与资源约束能够落实目录隔离已经保护所有外部资源

就绪检查区分进程存活、角色可服务和能力可用。必需依赖失败时该角色 NotReady；可选来源失败时记录降级能力与原因，缺失能力的任务应拒绝、等待或路由到兼容实例，不能受理后让模型凭空完成。身份绑定型或 lazy 能力保留准备状态，首次使用的等待与失败进入任务轨迹，不以一个全局绿色状态掩盖。

允许排队后执行时应公开期限与积压，不能无界接受任务。新 Run 固定被选中的 manifest、配置和能力版本引用，绑定当前主体与预算；所需 Connection 按该主体解析，未授权的连接保持等待，不阻塞与其无关的已获准调查。实例重启不能替旧 Run 静默升级能力。配置热更新先构建并验证候选快照，成功后再供新任务使用；在途 Run 的迁移、兼容与当前撤权统一按17.6.5 版本恢复处理。

退出采用 drain：先停止新接入和认领，再提交可恢复边界，登记未决 Operation、等待与交付责任。先停止任务生产者与依赖使用者，在状态与观测依赖仍可用时持久化必要审计和用量，最后按依赖逆序关闭 MCP 子进程、连接池及客户端。排空超时不能把可能已发出的请求记为未执行；退出实例不等于结束 Run。

17.3.8 受理：信封、去重与路由

入口接收用户请求、授权事件或队列消息，先识别它是新目标、当前任务的补充、继续执行，还是查询状态。可信信封绑定租户、主体、会话、环境、请求标识及关联标识；这些字段来自鉴权与路由，不能由模型或正文中的自述覆盖。

意图归一把“查一下为什么延迟，需要处理时先给我看草稿”变成契约：调查哪个告警、可访问哪些数据、时间范围、是否只读、预期证据与草稿格式，以及哪些信息必须澄清。缺少关键对象时先保存待澄清状态，不凭猜测启动写动作。一次消息不必对应新 Task，关联规则由入口契约明确规定。

请求去重键在租户与入口约定的作用域内唯一，并绑定规范化请求摘要。同键同内容返回原受理结果，同键异参报告冲突；不能凭自然语言相似度合并独立请求。记录覆盖客户端重试和延迟投递窗口，过期后的行为由入口契约规定。跨入口合并同一事件需要可信业务身份；独立执行另建 Run 并保留关联。

C1： 在一个本地事务中建立 Task / Run，绑定契约与配置版本，保存请求去重结果及调度 Outbox，再返回 accepted 和查询身份。accepted 只承诺任务已被可靠受理。事务与投递之间的故障见 17.6.2 持久投递、去重与积压恢复。

路由区分目标定位与执行定位：前者确定租户、用户、会话和任务，后者寻找能读取对应状态、加载正确版本且访问指定环境的实例。模型辅助理解目标，不决定租户或凭证。

受理回执至少包含 Task、Run、受理状态和查询方式。同步请求可以在连接内等待，但连接断开不代替任务取消；异步接口返回后，执行责任由持久记录承担。接入层在容量不足时要决定拒绝、持久排队或按优先级降级，并公开队列与截止时间关系，不能接受无限期无法履行的任务。

def advance(tenant_id, run_id, step_id):

17.4.1 Run 装配、预算与资源隔离

装配读取 C1 绑定的 manifest 与契约，并结合当前身份与资源权限，生成本次 Run 的执行包：模型配置、允许请求的工具与 Skill、数据源范围、工作区、上下文规则、根预算及验收器。实例级目录可以很大，模型只看到本次任务需要且允许请求的子集；可见能力也不等于本次动作已获批准。

工作区绑定租户、任务、路径和可写范围。只读调查可以共享不可变材料，涉及修改时需要明确排他或隔离策略；Worktree 隔离文件版本，不隔离共享进程、凭证和网络。子任务只获得完成其契约所需的最小范围。

根预算包含轮数、时间、Token、费用、工具与并发额度，派发前原子预留，实际用量返回后按计量事件幂等结算并释放未用额度，available = limit - settled - reserved。费用未知时保留在途预留，不能把超时当作未计费。重试、重新采样、查询核验、委派和孙任务共用同一根账本；HTTP 客户端、SDK 与工作流不能各自重试而放大调用次数。最接近错误的一层负责退避，根责任层负责总次数、费用与停止。预算耗尽的收尾见取消与停止。

产物是带版本的 Run Binding 与执行包，保存身份、权限与凭证引用，不保存明文密钥。该包说明当前任务的装配结果，后续执行仍需检查当前授权与剩余预算。

把模型提议映射回可信能力与连接

模型返回的工具名必须映射回本 Run 绑定的可信对象，核对 Schema、版本、资源范围和实现；不能把输出中的任意路径、命令入口或端点当作新工具。业务操作边界见第16章 外部能力设计，本轮选择与定义装配见工具暴露。

Connector / Connection / Run Binding 的定义见对象身份。派发时从可信上下文取得 tenant_id/user_id/connection_id 与凭证引用，模型参数必须受限于绑定。以项目 P 的读取绑定提出项目 Q 的写入时，不能自动切到另一组织的连接；子 Agent 只取得被收窄的委托绑定。

连接服务在派发前检查当前所有权与授权，明文凭据仅留在服务端或受控凭证提供方。连接凭据按当前授权解析，授权失效后的收敛见 17.6.6 取消、授权变化与人工接管。

Agent 定义决定程序可提供的能力，Session 组织连续交互，Run 是某个 Task 的实际执行，可以关联 Session，也可以由授权事件独立触发。同一个 Session 默认串行提交共享历史；若多个 Run 并行，应为它们分配状态分支和写入目录，再通过版本检查与明确合并规则提交，防止后完成的结果覆盖较新的历史。

17.4.2 编排模式、依赖图与汇合

规划器根据契约和证据缺口提出步骤，例如读取工单时间线、检索制度、查询相关日志、解释延迟、生成跟进建议。Runtime 校验步骤是否可执行、依赖是否闭合、预算是否可承受，以及结果怎样验收，再接受计划版本。计划表达未来工作的假设，不表示这些工作已经完成。

在本书的任务图设计中，节点描述逻辑输入、输出、依赖与验收条件，激活后映射到一个或多个可追踪的 Step；一个包含内部 Loop 的复合节点还需关联其内部 Step。Attempt 是节点实际执行的尝试，不应在每次重试时变成新的逻辑节点。动态扩图保存修订版与新增依赖，后继只能消费当前计划中已接受的结果。

ReAct 让模型交替生成推理与行动，并通过外部观察补充信息；纯思维链（CoT）没有这种与环境交互的闭环。[13] 例如，“解释一个已有的排序证明”只需推理；“修复测试失败”则必须读取代码、修改代码并运行独立检查。需要注意的是，观察本身也可能失败，使用了工具并不能保证结果正确。

Plan-and-Execute 先保存结构化计划，再执行和验证，计划外观察触发有界修订；其节点内部仍可使用 ReAct。产品的只读 Plan mode 则是权限策略，不是编排模式：计划已接受不等于动作已批准。

依赖关系不能以“上一个 Agent 发来一句完成”为准。父节点应读取子 Step 的权威状态，核对计划版本、输入 hash、必需产物和验收结论，再原子地提交“后继节点可运行”这一事实。如果状态已经提交而通知丢失，扫描器或重投可以重新发现后继节点；如果通知早到、重复或乱序，状态条件应阻止错误推进。通知用于提高响应速度，正确性由持久状态保证。

并行 join 需要明确必需分支、可选分支和超时策略。例如，日志与指标都是诊断的必需证据时，两者都通过才能形成结论；历史相似案例可以作为可选来源，查询失败时降级并标注缺失。一个必需分支失败后，是取消其他分支、保留已产出的证据还是等待人工，由工作流版本定义。任何一个先返回的分支都不能把整个任务提前宣告完成。

批处理还要保留单项身份。分片只是调度单位，一项业务动作不能因为分片重新切分就获得新的幂等键（idempotency_key）：已成功的项可以复用，结果未知的项先对账，尚未开始的项才能直接重排。父任务分别汇总成功、失败、未开始和待核验的项，最终产物能够追溯到输入项及其版本。这样即使只恢复一个失败的分片，也不会重复执行其他分片已经完成的副作用。幂等键与对账的细节见外部副作用。

受控的自由循环：Agent 节点嵌入固定工作流

固定告警流程可在取证节点嵌入有界 Agent Loop。外层控制生命周期，内层按节点契约探索并交付结果引用和机读状态，不另建无限重试或自行完成父任务。blocked、needs_input 与 unknown 分别进入阻塞、补充输入和原 Operation 核验，不能一律变成 failure 后重启整张图。

并发配额覆盖 Run、租户、工具、目标资源和全局，不能只用请求 QPS 限制大扇出任务。对独立分支可以并行派发；共享资源写入则需要串行、资源版本条件或明确合并。优先级和抢占只在安全边界生效，被抢占任务保存进度，在途 Operation 继续核验。并发组织不提供业务幂等，外部动作保证仍由应用和资源端契约定义。

17.4.4 动作裁决与审批等待

模型输出先解析为候选答案、工具调用或计划修订，再检查 Schema、工具标识、参数、目标对象及与任务的关联。结构有效只证明可以进入裁决，Policy 仍按当前主体、资源、环境、审批和预算决定是否执行。每个动作分别裁决，不能只在 Loop 开始前统一检查一次。

allow 携带沙箱、审计和凭证范围等约束交给执行引擎；ask 则在同一事务中保存审批绑定、WAITING(approval)、通知意图和恢复条件，并释放 Worker 与执行权。批准事件经鉴权、去重并匹配原绑定后，只把步骤变为可认领；即使仍由原 Worker 继续，也必须重新认领并推进 owner_epoch，不能沿用等待前的提交凭据。

审批只覆盖绑定动作，不能授予整个会话无限权限。超时不视为批准；取消使待审批动作失效。冲突决定进入明确裁定流程，伪造、过期或重复回调不激活新执行。deny 与 escalate 的任务收敛见17.6.6。

审批绑定的对象

审批请求要向审批人展示目标、参数、影响、证据、风险、有效期以及可修改的选项。批准与拒绝都作为事件写入账本。一条审批记录至少绑定以下内容：

  • 具体动作及其规范化载荷的哈希；
  • 目标资源的版本；
  • 授权主体，即谁批准、以什么角色批准；
  • 有效期。

派发前检查当前权限、取消、期限、参数哈希和资源版本。批准过期、草稿或目标改变时保存失效原因，重新裁决并按需请求新批准。人工修改参数标记为 human-edited 并形成新提案，不能沿用旧批准；模型声称“用户已批准”不构成批准事件。待审批记录与决定均保留历史，不能只覆盖一个布尔值。

MCP 补输入、账号授权与动作审批分别等待

Server 返回 resultType=input_required、inputRequests 及可选的 requestState 时，Host 先核对来源、交互模式与本次请求关联，再将其转为应用层等待。下面的 WAITING(input) / WAITING(auth) 是本书状态设计，不是 MCP 协议状态名；协议只规定补输入的请求与续交表达。[8][14]

续交使用原逻辑请求的 inputResponses 和必要的 requestState，不会创建另一份用户目标，也不构成对修改后载荷的自动批准。状态引用不进入自由文本摘要或被当作用户身份凭据。若存在已派发但结果未知的写入，先沿原 Operation 核验；不能把协议续交当作无条件重发写请求的许可。[8]

17.4.5 派发、观察与完成提交

调度器从已接受的计划中选择依赖满足、预算及并发额度可用的 Step。通过 Outbox 把工作交给执行者，消费者建立持久接收记录，使执行责任可以在进程退出后被重新发现。

C2： Relay 在取得中间件确认后记录投递进度；消费者持久去重并保存可接续处理的责任后，才返回消费确认（ACK）。两者分别确认，ACK 不是业务完成。C3： 认领事务检查 Step 可运行性与旧租约，原子保存执行者、租约和新的 owner_epoch，执行者据此开始本次 Attempt。重复投递与旧执行者竞争分别见 17.6.2 持久投递、去重与积压恢复、17.6.3 租约、执行权与迟到提交。

执行引擎按已裁决的动作调用 Tool Runtime，后者再次校验参数、取得受限凭证并适配到业务 API、远程工具协议、Shell 或沙箱。只读结果形成带来源和调用关联的结构化观察（Observation）；业务写入先进入稳定 Operation，不能直接把模型调用标识当作业务幂等键。

C4 分两步： 先持久记录 Operation 的 INTENT_RECORDED、稳定幂等键、规范化参数哈希与审批关联；再由 authorize_dispatch_if_current 在条件事务中核验当前状态、执行权、授权绑定、资源版本和预算，提交派发记录及 SUBMITTED。事务确认持久成功后，执行器才可以发送该动作的任何网络请求字节，SDK 的自动发送与重试也必须服从这一入口。事务失败或提交结果不明时不发送，先重读原记录。

SUBMITTED 表示本地已承诺派发、恢复时必须按“可能已发送”处理，不是下游收到或受理的证明。首次从 INTENT_RECORDED 转入 SUBMITTED 的当前调用可以取得发送模式；重入发现已有 SUBMITTED/UNKNOWN 时只取得核验模式，沿原身份查询，不再次取得“首次发送”资格。状态提交与远端发送无法原子化，这是主动保留不确定性而不是消除故障窗口。

核验后若仍允许重试，走独立的 authorize_retry_dispatch_if_current(claim, operation, evidence_ref)，而不是复用旧派发资格。该接口在条件事务中绑定原 Operation、原键、原载荷及“未生效且不再在途”的核验证据，复查当前执行权、批准、资源前提、截止时间与预算，创建新发送 Attempt 和唯一派发记录，将当前效果状态记为 SUBMITTED；持久提交确认后才返回该 Attempt 的发送凭据。普通重入仍只核验，不能再次领取已经使用或结果不明的凭据；旧 Attempt 的失败及核验证据作为历史保留，不退回 INTENT_RECORDED。下游不允许原键继续尝试时不进入此接口，按外部效果与修复边界处理。

本地事务也不能锁住远端资源或召回已经获准的在途包。执行器发送前复查停止信号，实际写入携带资源版本与执行代次，由支持条件写入的资源端原子检查；不支持时必须披露检查与执行之间的竞态，限制自动化并保留核验责任，不能把派发记账解释成跨系统授权原子性。

C5： 按原 Operation 保存并核验工单编号、版本与回执证据，才确认外部事实。完整状态机与发送前后崩溃的处理见17.6.4。

外部异步作业、Webhook 和定时器走持久等待：保存原操作或作业身份、订阅条件、截止时间和预期事件，再释放 Worker。事件到达后先鉴权、去重并匹配当前等待，再安排后续推进；查询状态和重连沿同一 Run 进行，不新建任务。

调用适配层：组件与调用链路

执行引擎中负责单次受控工具调用的实现称为调用适配层（Tool Runtime）。它属于 Agent Runtime 的执行面，消费本 Run 的能力绑定与派发裁决，不另建任务调度、审批或恢复系统。

启动阶段已经装配工具目录、MCP Client 与 Connector 适配器，见17.3 启动与任务受理。调用阶段通过本次 Run 的受信绑定解析工具、校验参数、取得受限凭据，再由 Executor / Adapter 适配到 API、CLI、MCP 或沙箱，最后规范化结果并形成观察。下图表示逻辑组件链路；实际发送仍须满足前述 C4 派发提交与当前授权，不把通过一次参数校验当作持续有效的执行资格。

循环推进、持久等待与停止

执行结果经过输出 Schema、来源与权限检查后形成结构化观察。Runtime 接受观察和模型决策记录，更新当前事实，再决定下一轮是补证、生成答案还是等待已登记的外部事件。已提交的模型结果与候选动作必须可追踪，不能只存在进程中的消息数组里。

C6： 在一个稳定 Step 边界，将验收过的结果引用、状态版本、领域事件及 Checkpoint 一致提交；需要派发后继时，同事务记录其 Outbox。大型载荷先完整写入并校验，再提交引用。中断后怎样识别最后一个有效边界见 17.6.5 Checkpoint、持久执行与版本恢复。

每轮读取当前执行权、取消状态、预算和截止时间。验收通过才进入完成，合法等待释放执行资源；无进展、超时或预算耗尽见取消与停止，心跳与进度判据见执行权。

下面的伪代码表示一个复合决策 Step 的推进：内部提议与操作分别持久记录，实现时也可拆为多个子 Step。示例聚焦正常控制分支，费用结算、异常捕获和后台续租由外围接口承担；状态更新采用当前版本条件，同一节点重试保留逻辑身份。

def advance_step(tenant_id, run_id, step_id):
    claim = state.claim_ready_step(tenant_id, run_id, step_id)
    run = state.read_current(tenant_id, run_id)
    lifecycle.require_runnable(run, claim)
    proposal = decisions.load_committed(tenant_id, run_id, step_id)
    if proposal is None:
        package = context.build(run, step_id)
        proposal = model.propose(package, budget.reserve_model(tenant_id, run_id))
        proposal = validate_proposal(proposal, package)
        claim, proposal = decisions.commit_if_current(claim, package.version, proposal)
    run = state.read_current(tenant_id, run_id)
    lifecycle.require_runnable(run, claim)
    if proposal.kind == "answer":
        return verify_and_complete(claim, proposal)
    if proposal.kind in {"needs_input", "revise_plan"}:
        return state.commit_control_proposal(claim, proposal)
    action = policy.evaluate_current(run, proposal)
    if action.requires_wait:
        return state.commit_wait_and_release(claim, action.wait_record)
    policy.require_allowed(action)
    claim, operation = effects.record_intent_if_needed(claim, action)
    dispatch = state.authorize_dispatch_if_current(claim, action, operation)
    return execute_or_reconcile_and_commit(dispatch)


def execute_or_reconcile_and_commit(dispatch):
    # 写动作仅凭当前 Attempt 已持久提交的首次或重试派发资格发送；普通重入先核验。
    result = executor.execute_or_reconcile(dispatch)
    observation = validate_observation(result)
    if observation.requires_reconciliation:
        return state.commit_reconciliation_wait(dispatch, observation)
    return state.commit_result(dispatch, observation, next_work=True)

决策槽位按 (tenant_id, run_id, step_id) 唯一，保存包版本但不以包版本作为查找键。两个执行者可以各自产生候选，只有符合版本和执行权的提交被接受；冲突者停止并重读，不执行自己的候选。提交前崩溃可重新采样，提交后恢复则复用。明确重规划新建逻辑 Step，但保留原 Operation 与历史。commit_if_current 与意图记录成功后均返回更新凭据，dispatch 同样携带其提交后的版本；派发仍重新核验资格。多个工具提议拆成独立受控动作，不把一次输出当成整批批准。

等待记录至少包含等待类型、关联对象、事件匹配条件、截止时间、已消费事件和恢复节点。定时器存在持久库，由扫描器或调度器触发，不依赖某个进程里的 sleep。事件先鉴权去重，检查任务仍在等待该对象后才安排推进；先到事件也可保存为待消费输入，由等待登记事务匹配，避免订阅前后的事件丢失窗口。

用户补充、暂停或取消先保存为控制事件，在安全点采用新状态，并向支持中断的后端传播信号。完成、等待、证据不足、无进展、预算耗尽、拒绝和取消须可机读地区分，不能都转换成重试。

结果验收与完成提交

模型提出最终答案后，Verifier 按契约检查格式、引用、事实与业务状态。只读调查要解释结论依赖哪些可访问证据，草稿要满足约定字段；批准创建工单的任务，还要关联已确认的工单编号与回执。模型的一句“完成”不能代替这些检查。

先完整保存产物、核对哈希及访问范围，再按当前状态版本与执行权提交完成。C6 的任务完成边界： Run 终态、最终产物引用、验收证据、关键事件与待交付 Outbox 一致提交。它证明任务结果可查询，不证明通知已送达。

上述两段推进代码都调用下面的唯一完成入口。Verifier 只产生检查证据，不能自行提交终态：

def verify_and_complete(claim, proposal):
    run = state.read_current(claim.tenant_id, claim.run_id)
    lifecycle.require_runnable(run, claim)
    artifact = artifacts.persist_and_verify(proposal.result_ref, scope=run.scope)
    checks = verifier.check(run.contract, artifact, required_operations=run.required_operations)
    if not checks.passed:
        return state.commit_verification_failure(claim, proposal, checks)
    return state.commit_completion_if_current(
        claim, expected_version=run.state_version,
        artifact_ref=artifact.ref, verification=checks,
        require_all_mandatory_work_resolved=True,
        terminal="COMPLETED", append_event=True, delivery_outbox=True,
    )

最后一个接口在同一事务中复查版本、执行权、取消与验收绑定，并确认必需节点和 Operation 已满足契约、没有必需的 UNKNOWN 或未决工作，再提交 Step 结果、Run 终态、Checkpoint、事件和交付 Outbox。检查期间发生并发变化则提交失败，重新读取；不能只凭一份较早的 pass 强行完成。报告草稿、外部建单和通知是独立事实：当前任务要求建单时，没有可信 INC-4821 回执就不能走此完成路径。

Verifier 以 pass/needs_repair/reject 表达验收结果：知识问答核对引用与权限，诊断核对时间窗口及原因证据，业务处理核对真实状态与审批，分析任务核对统计口径和可复现查询。needs_repair 只能在剩余总预算内反馈 Loop；无法修复则拒绝或转人工，具体处理见 17.6.1 失败分类、重试与安全拦截。

运行时 Verifier 验收当前产物；离线评测使用数据集和失败样本比较版本质量，不能代替本次任务的检查。交付界面（Review Surface）展示结论、证据、不确定性、风险动作、产物版本或 diff、验证结果及反馈入口，不要求展示模型完整思维链。Observation 是执行事实的受控视图，界面读取已提交结果后才显示任务完成。

17.4.6 交付接口、事件游标与通知

C7： 交付 Worker 按交付身份读取已提交结果，核验当前接收人、权限与版本资格，发送后保存渠道回执。渠道仅确认受理时记录“已受理”，只有契约能够证明送达时才记录“已送达”。同步查询、通知和服务器发送事件（SSE）均引用同一持久 Run 与产物版本，连接断开不改变结果。

Runtime 的外部 API 至少分成八类：任务提交、运行查询、事件流、审批、取消、恢复、Artifact 和回放。

  • 提交接口接受目标、上下文、能力范围、预算、截止时间、优先级和幂等键；
  • 查询接口返回当前状态、进度、成本摘要、需要用户执行的动作和可见结果；
  • 事件流推送状态变化，但不暴露未经授权的内容；
  • 审批接口把人工决定写成事件；
  • 取消和恢复接口必须穿透模型、工具和等待队列；
  • Artifact 接口保存大段文本、文件和证据；
  • 回放接口用于调试和审计，不能重新触发真实的副作用。

输出也要区分最终答复、部分答复、工具结果、人工决定、失败和补偿，客户端不能靠判断文本是否为空来猜测状态。结构化错误包含 code、retryable、retry_after、run_id、step_id 和修复建议；敏感的内部错误只出现在受控的 Trace 中。错误信封的设计可参考 AIP-193，自动重试策略另参考 AIP-194，两者不能互相代替。[15][16]

状态机、工作流和流式交付是三个不同的维度，可以同时存在。状态机限制合法的迁移，工作流组织步骤、依赖和错误处理，流式交付则把进度和输出增量发送给用户。流式还可能指节点之间的逐块计算，这时需要单独定义块边界、背压和重复处理。工具参数只收到部分 JSON 时，必须先缓冲，校验完整的提案后才能执行，不能把 token 流当作业务提交。

任务、结果和事件日志独立于连接保存。客户端断线只影响订阅，重连后按原 task_id 查询，不能自动创建新任务。WHATWG 规范规定，EventSource 重连时可以发送 Last-Event-ID [17]，但规范并不提供服务端的历史留存、持久任务或业务幂等。其他 SDK 或 HTTP 客户端是否记录游标需要自行实现，不能因为支持 SSE 就推断具备恢复能力。

本章采用每个 Run 单调递增的 run_seq 和全局唯一的 event_id，事件持久提交之后才发送到流上。客户端按身份和序号去重，断线后从最后确认的游标开始重放。状态写入与完成事件在同一数据库事务中关联提交；流投递失败并不撤销业务完成，查询接口返回权威的版本、终态和结果哈希。如果客户端先收到“完成”事件，查询结果却还落后，就按事件的提交水位重新查询权威数据源，或等待投影追上，不能凭文字或旧副本判断成功。

游标仍在保留期内时，服务端鉴权后补发事件；游标已经过期时，明确返回 cursor_expired 和可用范围，同时提供一份快照，包含 snapshot_version、last_included_seq 和完整结果的引用。客户端先用快照替换旧视图，再从水位之后继续订阅，避免把后半段文本拼接到错误的前缀上。载荷已删除、无法重建时，要说明恢复受限，不能静默发送残缺的尾段。重连时仍要重新校验当前权限：以前能看到的内容，在权限被撤销后不一定还能下载。

完成通知同样先提交事实，再由 outbox 投递，并携带稳定的 notification_id 和任务版本；接收端负责验签、防重放和幂等处理。回调目标要有白名单、超时设置、总重试预算和失败修复入口，通知中只携带最小摘要和受控的查询链接。通知失败不会把已完成的任务改为失败，通知到达也不能替代用户对最终结果的查询。流缓冲和事件读取都需要背压控制，慢客户端不能无限期地占用 worker 或原始敏感载荷。

交付故障与接管

C6 已提交但 C7 未发送时，从原交付 Outbox 继续，不重算答案或重跑任务。渠道可能已受理而本地回执缺失时，保留未知发送状态，沿原 notification_id 查询或按渠道幂等契约恢复。渠道无去重和查询能力时，明确接受漏发或重复风险，不能承诺严格一次通知。协作故障独立放在委派与父任务收敛。

交付 Worker 发送前先持久登记派发占用；接管者读取原记录，只有可靠证据证明未派发且旧执行者已被隔离，才可重新派发。可能已发送时先核验，租约到期不能自动清除未知占用。若必须在旧发送仍在途时接管，就要接受旧消息晚到，或使用支持版本检查的渠道。交付前仍检查接收资格，查询旧 Run 保持指向其原结果，不因执行者变更而指向新产物。

17.4.7 多 Agent 的委派与父任务收敛

多 Agent 适用于可以独立验收的分工，例如不同证据范围的调查、独立方案审查或大任务分块。普通并行工具调用与模型路由不会自动产生新的责任人，只有确实需要独立上下文、角色能力或权限边界时，才引入子任务与交接。

协调者提出分工，可信控制层签发委派权限。子任务绑定根任务、父 Run、目标、输入版本、输出 Schema、验收条件、预算、截止时间与是否允许继续委派。有效权限取原用户当前授权、可转授范围、角色需求和工具实时策略的交集；角色名不授予权限，子 Agent 也不能通过父级或同伴绕开拒绝。

每个子任务拥有私有消息、执行上下文和可写范围。公共目标、硬约束和已确认事实由根责任层维护，角色只获得有权读取的投影；原始日志、凭证和整段历史不默认广播。共享状态不能成为全员可写字典，工作者追加证据候选与产物，协调层通过版本和验收条件把它们接受为公共事实。

交接阶段持久记录推进条件

消息中使用独立的 message_id 去重，用 correlation_id 关联一次交接，用 causation_id 表达因果；这些字段不替代 Operation 的业务身份。关联标识模式提供请求与响应的对应关系，而发布确认与消费确认仍是不同事实。[18][19] 回执丢失后查询原交接，不能因重发就建立第二个子任务。

汇合需要声明必需分支、可选分支、截止时间、冲突裁决和部分结果规则。子结果有分歧时比较输入范围、证据时间、版本与推断依据，不能简单多数投票。必要证据不足则继续补证、交付明确受限的结果或转人工，不把多个弱结论拼成确定答案。

如果多个子任务修改同一资源，优先使用唯一写入者；需要并行修改时，分别基于相同基线产出固定补丁或变更集，由集成者核对并验证组合结果。各自通过不等于合并后通过。迟到产物进入受控验收，不直接激活已经结束的父任务。

父任务维护整棵调用树的预算、委派深度和派生数量。父任务结束后停止新委派，对受管子任务传播控制状态，保存部分产物，并继续核验在途写入。独立授权且明确脱离父生命周期的任务可以继续，但独立关系由控制层记录，不能由子 Agent 自行宣布。

协作故障与迟到结果

子 Agent 失联、超时或结果不合格时，先读取原子任务的持久状态与产物，区分未开始、只读计算中断、已提交结果及未决副作用。可重算分支沿原子任务建立新 Attempt；写入分支先核对原 Operation，不能因重新委派重置业务身份。消息去重只阻止重复接单，Operation 幂等处理重复业务生效，执行权检查拒绝旧提交，三者不相互替代。

同一 message_id 携带不同载荷时拒绝并记录冲突；早到的依赖结果先保存，不跳过前驱验收。输入、契约或计划变化后，迟到产物可进入有权限的历史审计，但只有满足当前节点验收条件的结果才能参加 join，不能仅因“完成得更晚”就覆盖当前事实。

父任务取消或结束后，协调层保留未决清单及核验责任，不因资源回收而删除。部分分支成功时按契约接受受限结果、等待、替代或人工处理，不宣告缺少必需证据的完整成功。互相委派、嵌套 Loop 和重复审阅需遵守根预算与进度检查，不能靠增加角色扩大授权。

队列长度、并发、委派深度、消息大小和截止时间共同限制协作容量；恢复积压按资源配额限速，永久错误进入有责任人的隔离队列。历史产物能被保留，不代表仍有资格展示或参与当前任务汇合。

17.5 安全与授权：跨层控制与执行边界

安全与授权贯穿整个执行过程。第 16 章定义工具契约、接入鉴权与隔离实现，本节说明 Runtime 怎样把这些能力接入实际派发；第 18 章再将执行证据用于评测、审计和发布门禁。模型可以帮助理解意图、识别可疑内容和提出动作，可信组件仍要决定允许什么、怎样执行以及资源端接受什么。

本节沿用 ALR 的虚构教学运行，不增加重启、回滚或默认通知能力。下文的边界、记录与验证用例属于本书参考设计，不代表某个 Coding Agent 产品默认具备，也不代表已经完成红队实测。产品默认值、平台覆盖与版本差异见第 19 章。

17.5.1 威胁模型与跨层职责

任务执行时，每跨过一个边界，都要回答一个不同的安全问题：入口要确认谁发起任务；Runtime 要判断这次任务允许做什么；执行后端要限制进程可以访问什么；工具服务和下游要判断当前请求能否操作目标资源；交付时还要检查内容能否发送给指定接收人。模型负责理解任务并提出行动，具体权限由可信组件落实。

要验证的不是模型会不会口头拒绝，而是即使它提出调用，秘密能否被读取、数据能否未经授权发送。需要分别追踪两条路径：

路径 A：恶意日志 → 模型 → Shell 读取秘密 → Shell 直接联网外发
                           ↑ 文件/环境变量边界     ↑ 网络出口控制

路径 B：恶意日志 → 模型 → Shell 输出秘密 → 模型上下文 → MCP / 浏览器 / 消息工具外发
                           ↑ 读取与返回值边界             ↑ 独立调用授权、数据外发与资源端控制

路径 A 需要同时收窄可读数据与网络出口。路径 B 即使 Shell 断网仍可能成立：秘密已经进入上下文，另一个工具可能拥有联网或发送权限。摘要、Memory、检索和子 Agent 转述不能将数据提升为授权；只在某一条 Shell 命令上阻断 curl，也不能证明其他解释器或工具无法外发。后续小节沿时序图展开这些身份、裁决、执行和数据流边界。

17.5.2 身份、授权来源与策略上限

一次 Agent 任务通常涉及三种不同身份。登录模型产品的身份用于模型访问、计费或组织归属；本地执行身份是工具进程所用的 OS 用户及被收窄的权限；业务访问身份是 MCP / API 验证的用户、服务账户或云 IAM 主体。产品登录成功不代表拥有业务资源权限，选定一个工作目录也不会自动创建低权限 OS 用户。

认证与授权回答不同的问题：认证确认请求来自哪个主体，授权决定该主体能否对这次目标资源执行具体动作。Runtime 的服务身份或 MCP Bearer 只能证明请求来自受信服务，不能单独证明本次 Run 有权读取某个团队、租户或环境的数据。模型参数中的 team、workspace_id、session_key、角色声明和用户消息可以表达查询目标或关联线索，却不能自行授予权限。Runtime 应从经验证的任务与调用者上下文构造不可变的请求级授权上下文；团队归属或资源范围缺失、矛盾、无法解析时拒绝访问。并发任务的身份不能放在可变全局变量中共享。

在图中的任务受理阶段，入口验证发起主体；涉及服务间调用时，还要验证调用服务的工作负载身份。可信身份映射及服务端策略共同装配任务范围，例如主体、租户、Run、允许的环境、资源和动作。跨服务传递时，接收方须能验证上下文的来源、受众和有效期，并防止调用方自行扩大范围。任务需要新的资源时，应按有权主体的授权流程更新范围；派发时仍要复核当前权限及撤权。

共享高权限 Token 会使下游只看到服务账户。若要按真实用户、租户和对象授权，连接服务必须通过可信身份映射与受限凭证传递这层约束，不能让模型提交 user_id="admin" 便改变主体。第 16 章共享 MCP 权限隔离说明接入侧的具体实现。

17.5.3 调用裁决与审批边界

模型输出的工具名和参数只是提案。Runtime 从可信会话、任务、工具注册表及当前策略装配裁决输入：主体 + 工具来源 + 实际参数 + 目标资源 + 环境 + 当前授权 + 有效批准。Schema 检查负责结构，Policy 检查负责权限，执行后端与资源端继续实施各自的限制。

本书参考设计在派发前完成以下检查，具体顺序可随后端调整，但任何实际执行的参数都必须处于有效裁决范围：

  1. 解析工具身份与规范化参数，核对资源归属、副作用、数据敏感度及任务范围。
  2. 检查不可放宽的禁止规则和当前授权；命中禁止时保存拒绝，不靠换工具或申请普通确认绕过。
  3. 若策略要求审批，按17.4.4 动作裁决与审批等待保存绑定动作的等待记录；有权主体批准后仍需重新核验。
  4. 工具、Hook 或人工改变参数、草稿、目标与资源版本后，对实际载荷重新裁决；旧批准不覆盖新内容。
  5. 按本次允许范围选择执行后端、凭证和出口；要求的隔离无法落实时拒绝执行，而不是静默降级。

裁决结果必须由执行层落实：allow 附带具体的资源、凭证和隔离约束；ask 进入与动作绑定的审批等待；deny 阻止该动作；escalate 将判断交给有权主体。权限不足或策略明确禁止时，模型不能改用其他工具绕过。授权服务不可用时，系统应停止派发并记录不可用原因，待服务恢复后重新裁决，不能将检查失败当作允许。

审批决定谁可以接受具体影响，隔离决定执行后进程能触及什么。两者是独立维度：不弹窗可以是既有授权和受限环境下的正常自动化；批准一次命令，也不能证明它在沙箱里运行或内容适合外发。

自动审查、分类器和注入检测可参与风险判断、减少不必要的交互，但它们也可能误判。本书不以模型判断代替组织禁止规则、隔离和资源端鉴权。命令前缀或字符串规则同样只是有限匹配：解释器、脚本、重定向及嵌套调用都需要纳入验证，不能把“未匹配危险命令”视为安全证明。

审批应绑定规范化后的实际计划，而不是一个可复用的 approved=true 标记。审批人看到的目标、环境和载荷必须已展开默认值；派发时，执行端重新计算载荷摘要并核对审批主体、有效期及目标资源版本。工具、Hook 或执行器在审批后改变任何影响动作含义的参数，都要重新裁决。即使审批仍有效，目标也可能在等待期间发生变化。资源端支持条件写入时，应在写入时原子比较版本或 ETag；只在发送前读取一次版本无法消除并发变化。无法实施原子条件时，必须保留这一竞态并限制自动执行。审批授权这项具体意图，执行结果和未知状态沿用17.6.4 外部副作用、未知结果与补偿的操作记录处理。审批绑定的字段与等待状态见17.4.4 动作裁决与审批等待。

授权还应区分资源写入和对外发送。例如，诊断任务可以获准读取 live 指标，并在策略允许时回复任务绑定的原线程；这不等于获准修改 live 订单或配置。回复属于独立的 external_send 动作，应单独校验接收人、内容、数据敏感度和批准范围；读取权限不能自动带来发送权限，发送权限也不能扩大可读取的资源范围。

17.5.4 执行隔离、网络与凭证

时序图中的“仅允许后派发”还要求执行引擎落实裁决附带的限制。引擎必须知道限制作用于哪个进程和工具，不能只保存一个 sandbox=true。派发记录至少要能解释文件读写范围、网络路径、凭证来源与隔离后端；隔离无法建立时，本次动作不应静默降级执行。业务写入还须先完成本章 C4 派发记账，再允许发出请求；这一记录不证明下游已经接收。具体隔离与 SSRF 控制见第 16 章授权、沙箱与能力交付。

文件读取与写入分开验证。允许写工作区不代表工作区之外的秘密不可读；禁写目录中的文件仍可能被读取。凭证也可能来自继承环境变量、挂载、配置、缓存或既有浏览器会话。优先由独立连接服务或凭证代理持有秘密，仅返回任务需要的结果；必须给执行进程凭证时，按用途和资源收窄，检查子进程继承，避免秘密进入模型与 Trace。

命令进程即使拿不到 Token，也可能借助凭证代理使用其权限，形成混淆代理（Confused Deputy）。代理不应是接受任意 URL、路径或认证头的通用转发器。默认不向 Shell 暴露代理的 socket、端口或管理接口；确需访问时，只开放固定业务操作，由代理根据可信工作负载身份和当前 Run 逐次校验工具、动作、目标资源与环境，再使用短期、限定范围的凭证。模型或命令自报的 Team、用户和授权范围不能作为依据；代理还应限制请求参数、目标、频率和响应规模并留下脱敏审计，下游继续验证资源权限。

网络允许列表只限制目标的一部分属性。即使获准访问某个代码托管或对象存储域名，目标资源也可能由攻击者控制。域名放行不能证明接收人、租户、路径与正文可以外发；代理规则还须实际覆盖连接，直接 socket 或无沙箱路径不能旁路。

17.5.5 跨工具数据流与下游鉴权

图中的 MCP 调用跨过两个授权边界：Runtime 对模型提案作出裁决，工具服务收到请求后仍须验证可信调用身份、任务范围、实际操作和目标资源。服务端解析目标环境、租户、服务和对象，检查权限后才构造下游查询。下游服务再独立验证身份、Token 受众与有效期、所需 Scope、对象归属及具体操作权限。MCP 协议、客户端允许调用、工具的 readOnlyHint 或 approved=true 参数都不能代替这些检查。接入与两跳授权的实现见第 16 章服务端授权。

多团队共用 MCP Server 或下游服务凭证时，允许调用日志工具，只说明该能力可见；共享服务令牌说明服务具有下游访问能力。团队 A 能否读取团队 B 的服务，仍由服务端策略按本次任务的可信身份与目标判断。授权过滤必须落在服务端查询或资源访问入口，并覆盖批量目标、分页游标、缓存结果和附件；显式跨团队值班可以通过受限授权开放。模型修改 team 或 session_key 不能扩大范围，目标不明确或授权服务不可用时也不能放行。

若服务端需要识别客户端已完成的高风险审批，应由可信组件传递可验证的批准记录或凭据，绑定调用者、操作、资源、参数与有效期，并控制重复消费；不能把模型生成的说明当作证明。服务端仍须执行当前业务权限校验。对于审批后建单，授权仅覆盖被批准的草稿与目标，查询同一个 Operation 的结果也不能借机修改内容。

工具结果回到 Runtime 之后，授权检查仍会继续。 工具服务先按可信调用身份限定对象与字段，返回前最小化和脱敏；Runtime 将结果作为观察保存，保留来源、数据身份以及超时或部分失败等状态。日志中出现的指令、链接或身份声明仍是不可信数据。模型可以据此提出下一次查询，但每次调用的工具、参数和目标都必须重新裁决；对已派发写入的效果不明，应沿原 Operation 核验，而不是因模型建议而直接重发。

路径 B 的关键是秘密跨过了工具返回边界。Runtime 应把“数据能否读取”“能否进入模型”“能否由另一工具发送”分开处理。只读日志工具仍可能返回 Token 或个人信息；授权读取某字段不自动授权把它放入工单、消息或外部网页表单。交付时，发送网关再次检查实际接收人、目标资源、内容、数据敏感度和批准；目标地址不能因为出现在日志、Runbook 或摘要里就变成获准目的地。后置输出过滤不能撤销已经完成的上传，检查必须覆盖每次发送边界。第 18 章数据出口治理说明累计读取与外发评测。

错误修复、委派、重试和恢复都保持相同原则：换一条技术路径不会扩大授权。若某任务不允许向外发送日志，不能由子 Agent 摘要后再交给消息工具发送；如果撤权，连接缓存和恢复后的待执行动作必须重新检查当前资格。撤权与人工接管协议负责停止和保留未决责任。

17.5.6 安全验证与审计证据

17.6.1 失败分类、重试与安全拦截

错误不能只按 HTTP 状态码分组。Runtime 至少要知道错误发生在哪个边界、是否可能产生副作用、哪个对象仍有执行权，以及剩余授权与预算是否允许继续。相同的网络超时，发生在只读检索和创建工单之后，会要求不同的处理。

处理顺序是：读取权威事实 → 限制继续扩大影响 → 判断是否可安全重复 → 校验当前权限与预算 → 记录下一步及责任。暂时故障不等于可重试；未知结果不等于失败；补偿也不等于删除历史。无法自动判定时，保存可查询的阻塞状态、原因、责任人和下次处理时间，不能无限循环或静默丢弃。

是否重试，必须根据错误类型决定。网络超时、限流和暂时不可用通常可以退避后重试；schema 错误、权限拒绝、用户取消、预算超限和确定性的业务错误不应自动重试；模型输出不合格时，可以有限次地重新采样，但每次都要新增 Attempt 并计入成本。AIP-194 默认只自动重试 UNAVAILABLE；本表把部分超时、限流纳入重试是本书在只读或明确幂等契约下的策略，不能仅凭“网络错误”就重试有副作用的请求 [16]。下表给出 Runtime 面对常见观察时的处理方式。

MCP 断流、重连与长作业恢复

MCP 传输恢复只恢复通信条件，不重新授予业务调用资格。2026-07-28 的 HTTP 路径不提供旧 GET 通知入口、Last-Event-ID 和 SSE 事件重投机制；重新提交请求时使用新的 JSON-RPC id，逻辑意图、业务 Operation、稳定幂等键与原载荷约束保持关联。只读请求可在当前授权与预算内按契约重试；写请求断流先保留未知状态并查询原动作，不因连接恢复自动再发。[9]

关闭 HTTP SSE 响应流构成请求级取消信号，Server 应尽快停止，但取消仍不能证明先前副作用未发生。Client 停止本地等待、Server 停止处理、下游撤销写入是不同事实；晚到结果仍关联原 Operation，不能通过新建调用身份掩盖。旧版兼容路径按对应版本的恢复承诺处理，不套用新版结论。

若 Server 显式支持 io.modelcontextprotocol/tasks 扩展，Runtime 保存远端任务句柄与本地 Run / Operation 的关系；按扩展使用 tasks/get 轮询、tasks/update 补输入，不把旧 tasks/result 当作新基线。句柄、轮询和续交都重新检查主体与授权，轮询完成只触发结果检查，不直接宣告本地任务验收通过。扩展版本独立固定，缺少支持时不能让模型猜方法名继续。[21]

17.6.2 持久投递、去重与积压恢复

创建任务时，系统通常要做两件事：在数据库中写入 Task 和 Run，再向消息队列发送一条“任务已创建”的消息，唤醒调度器。如果这两次写入彼此独立、不加协调，就称为裸双写。数据库和消息队列不在同一个事务中，无论先写哪一个，都会留下一个故障窗口。

调整数据库写入与消息发布的顺序，只能在两个窗口之间选择，无法同时关闭它们；如果另有持久扫描器修复漏调度，该扫描器本身也构成接续协议的一部分。

Transactional Outbox 模式的做法是：把待发送的消息写入同一数据库中的 outbox 表，并与更新业务实体放在同一个事务里提交，再由独立的 Relay 进程把 outbox 中的记录发布到消息队列 [22]。这样，“任务存在”与“待发消息存在”要么同时成立，要么同时不成立，两个窗口都被关闭了。不过，Relay 本身仍可能重复发送，所以下游依然需要去重。

本章采用的参考契约是：在同一个数据库事务中写入 Task、Run、初始 Step、RUN_CREATED 事件和 outbox 记录，事务提交成功后，才向客户端返回 task_id、run_id 和查询入口。需要注意，单个关系数据库事务的原子可见性只覆盖该数据库内的操作 [23]；消息队列和第三方工具都不在这个事务之内。

客户端丢失受理回执后，沿用原 request_key 查询或重试。受理去重、消息去重和外部动作幂等分属不同边界；Outbox 持久存在只能证明工作可被重新发现，不能证明 Worker 已运行或业务已经生效。

Relay、CDC 与消费确认

Relay 可以轮询已提交的 Outbox，也可以通过变更数据捕获（CDC）读取事务日志。Debezium Outbox Event Router 默认把事件 id 放入消息 header，把 aggregateid 用作 Kafka 消息 key，文档将后者与分区内顺序关联。[24] 这不是跨分区总序，也不证明多个并发生产者已按业务因果提交。本书因此要求同一租户的 Run 使用一致聚合键、维持该键的分区路由，并以持久 run_seq 检查缺口和重复；改变分区或路由需另外处理顺序迁移。Connector 重启、重放与 offset 管理也不能省略。

采用轮询时，同一 aggregate 的消息需要按序串行认领与发布；跨 aggregate 可并行。仅对 outbox 行使用 SKIP LOCKED 分批认领不保证同一聚合的顺序；若选择不保序，消费者必须用 state_version 检测缺口、缓冲或重查权威状态，不能按到达顺序覆盖。这是本书对并发认领的推导；PostgreSQL 对 SKIP LOCKED 的不一致视图说明见 [25]。

Relay 用短事务认领带期限的记录，在事务外发送，再条件更新发送标记；超期未确认的记录允许重投，不能持有长事务等待网络返回。

无论采用轮询还是 CDC，“发送成功”之后、“发送标记或 offset 提交”之前崩溃，都可能造成重复发送。Outbox 避免的是业务已提交而待发意图没有记录这一类丢失；实际推进仍依赖存储耐久性与 Relay 可用性。接收端用固定 event_id、Inbox 唯一约束、逻辑 Step 和当前版本去重，这就是幂等接收者（Idempotent Receiver）模式。[26]

消费确认（ACK）的时机同样重要。消费者应在同一个事务中保存 inbox 记录和可恢复的调度事实，提交之后再向消息队列确认。如果在确认前崩溃，消息会被重投，消费者发现记录已经持久化，就幂等地返回。ACK 不能早于必要状态的持久化；但也没有必要让消息队列的连接一直挂到数小时的执行结束。消费者只需把“待执行的 Step 及其归属”可靠地接走，后续执行由基于持久状态的调度器管理。消费者抢占失败、任务已经终结或消息已经过期时，分别记录处置结果，不能把重复消息当作新的 Run。

Outbox 需要监控以下指标：最早一条未发送记录的等待时间、重试次数、毒消息数量、CDC 延迟，以及 Task、outbox 与队列三者之间的差异。系统还要定期核对“已接收但没有可调度 Step”的任务。无法解析的消息进入隔离队列，并附上 schema 版本、失败原因和载荷的受控引用；修复传输或实现问题后沿用原来的 event_id 重放，不能换一个 ID 来掩盖重复。队列只是唤醒和传递机制，权威的执行状态保存在持久库中。消息队列短时不可用时，任务仍然可以查询；容量已满时，应当拒绝新的提交。

队列恢复与死信处理

消息系统恢复之后，不能立即释放全部积压。大量旧任务会同时申请模型、数据库连接和外部接口；如果每次失败又引发新的重试，就可能造成第二次过载。调度器应按租户、任务优先级、工具和目标资源控制并发，先过滤掉已经取消、过期或完成的工作，再在剩余预算内安排重试。队列年龄与未决 Operation 的年龄需要分别监控：前者反映工作没有被接走，后者反映外部业务事实还没有收敛。

死信队列保存不能自动处理的消息，但消息进入死信队列并不等于问题已经修复。每一项被隔离的工作都要能追溯到原任务、schema 版本、错误原因、载荷的受控引用、修复责任人和截止时间。重新投递时沿用原有的消息身份和业务身份；换一个 ID 让消费者“重新处理”，会绕过原有的去重机制。如果参数需要修改，应当形成明确的新提案并重新授权，不能改写旧消息后继续沿用旧的批准。

17.6.3 租约、执行权与迟到提交

在 run_0429_017 的 Worker A 崩溃后，Worker B 取得新执行权；此时才需要区分原业务身份与新的尝试身份。

本章使用以下术语：

  • 执行权代次（owner_epoch）：某个 Step 每次成功授予新的执行权时递增的持久单调整数；首次授予、租约到期后的重新认领、迁移与强制接管都属于新授予，同一有效租约内续租、调用重试及同一认领请求的幂等重放不推进代次。持有最新代次的执行者才有权提交该 Step 的结果，旧代次的写入一律拒绝。
  • 规范化载荷（canonical payload）：把请求参数按固定规则整理后的形式，例如字段排序、去除无语义的空白、统一默认值。对它计算的哈希（payload hash）用来判断两次请求的参数是否真正相同。
  • 幂等键（idempotency key）：调用方为同一意图提供的稳定标识，重复提交时据此返回同一结果。本章区分两种范围：接入层的任务幂等键（字段 request_key），用于避免重复创建 Task；Operation 传给下游的操作幂等键（字段 idempotency_key），用于避免同一业务动作重复生效。

除身份外，每个对象还要保存足以恢复和审计的字段。Run 保存入口请求、模型与工具版本、租户、预算、截止时间、权限、状态、父任务和 trace id。Step 保存输入引用、输出引用、尝试次数、开始与结束时间、资源消耗、错误、幂等键和补偿动作。大段文本不直接嵌入状态表，而是存入 Artifact 仓库或消息存储，通过哈希和版本引用，以免状态表无限膨胀。

worker 领取 Step 时获得一份带期限的租约（Lease），执行期间持续心跳续租；worker 失联后，控制面等租约过期再重新调度。数据库认领需要同时满足几个条件：Step 仍处于可运行状态，重试时间已到，旧租约已经过期，配额可用。满足条件后，认领事务原子地递增执行权代次，并写入新的执行者和租约到期时间。租约时间以服务端受控的时钟为准，执行权代次必须是持久保存的单调整数；随机生成的锁值不能充当 fencing token。

租约不能替代幂等。在网络分区下，旧 worker 可能在租约过期后恢复，并提交一份迟到的结果；外部工具也可能在 worker 失联后继续执行。为此需要 fencing。fencing token 是每次授予执行权时发放的单调递增编号，本章以 (tenant_id, run_id, step_id) 为节点执行权命名空间，owner_epoch 只在此范围可比；资源端按该命名空间记录最大代次。跨 Step 争用同一资源时，另发资源级单调 token 或由串行网关裁决，不能比较两个 Step 的本地计数。执行者的每一次写入都携带这个编号，由被写入的资源检查：凡是小于该命名空间已接受最大编号的写入，一律拒绝。fencing 方案要求每次写入携带单调 token，并由资源端负责拒绝旧 token [27]。

执行者应在租约结束前留出时钟误差、派发与取消传播的安全余量；剩余有效期不足时不开始新写入。余量由部署测量决定，不给出通用毫秒值。资源端在接受受保护写入或显式推进写屏障时，原子检查并更新最大代次；普通只读查询不推进屏障。下图假设工具支持独立屏障接口；若不支持，不能因 B 查询过就声称 A 的写已被隔离。这一显式屏障是本书参考协议的附加设计。

心跳只能证明执行者还活着，不能证明任务在推进。心跳中应包含进度序号（progress_seq）、资源占用、当前 Attempt、Checkpoint 和预计完成时间，但不上传敏感内容。只有进度序号的增长、已提交的产物和 Step 的变化才证明有进展；心跳正常而进度长期不变时，必须诊断依赖阻塞、空转和锁等待。控制面据此识别卡死、慢任务和预算超支，必要时暂停或迁移。迁移策略写在工作流中：模型 Step 只有在尚无已接受决策记录时才可按新 Attempt 重算；已有决策槽位必须复用，即便后继尚未提交。改变已接受决策必须显式重规划，创建新 Step 或分支并保留原 Operation 与历史，不能只增加 Attempt；有副作用的 Step 先查询，人工 Step 继续等待或转入其他队列。

17.6.4 外部副作用、未知结果与补偿

幂等的责任必须落实到具体边界。Runtime 为每个逻辑业务调用保存 operation_id；消息仍可能重复，所以接收方要以稳定身份幂等接收；工具适配器负责把操作幂等键传给下游；真正拥有业务状态的订单、邮件、文件或支付系统，则必须决定对同一个键的重复提交如何返回同一个事实。如果下游只提供“尽力而为”的 HTTP 接口，Runtime 仅凭本地的去重表无法承诺业务幂等，因为请求提交后网络断开，会留下一个本地无法判定的未知状态。幂等接收者（Idempotent Receiver）模式把去重与消息接收边界绑定在一起 [26]；在 Agent 系统中，这一边界还要覆盖模型重试、队列的至少一次投递和人工重放。

幂等 API 的设计经验表明，稳定请求标识表达业务意图，同键异参应报告冲突，去重记录和业务变更由资源端原子处理。[28] 本章据此把 operation_id 与操作幂等键绑定到原业务动作，在模型重新采样、传输重试和 Worker 接管时保持不变。键可以是不透明标识，也可以关联租户、业务对象、动作与授权版本，但必须区分两次独立意图。

如果模型每次重试都重新生成操作参数，系统必须先比较规范化载荷：意图相同，就查询或去重；意图不同，就是一个新操作，可能还需要新的审批。规范化载荷的哈希只适合发现“同键异参”，不能单凭参数相同推断用户只想做一次。两次独立授权、参数恰好相同的购买，仍然代表两个业务意图。反过来，把“看起来相似”的自然语言当作幂等键会造成错误合并，为同一操作随机生成 UUID 又会造成重复副作用。

Operation 的事实状态决定了下一步可以做什么；MANUAL_REPAIR 是有责任人的人工工作项，不属于 Run 或工具 Attempt 的成功终态。主操作部分生效时保留其效果明细，再决定继续、补偿或人工，不用单一失败值抹平。

第一行的“未发送”只在所有动作出口都受派发事务控制的前提下成立；绕过入口的 SDK、后台重试或旧实现会破坏该推断，需作为迁移风险处理。后四行均不能从本地账本推断远端未执行。

外部查询返回“没查到”时，也要考虑下游的一致性和保留窗口：结果可能尚未可见，键可能已经过期，请求也可能仍在途中。只有下游契约足以确认未生效且不再在途、允许原键重试，系统才通过 C4 的 authorize_retry_dispatch_if_current 持久提交新的派发 Attempt，再继续用原键尝试；否则保留 UNKNOWN 或转人工。预算或审批到期时，未决事实不能被删除；系统停止新增动作之后，仍要核对已经发出的请求。

Stripe API v1 会缓存已开始执行请求的首个状态与响应，包括 500；其文档另行说明 API v2 的重试语义。[29] 因此“确认未生效”不保证原键能继续推进。只有可靠证据证明旧请求结束且未生效、下游明确要求更换提交键并经重新授权，才可通过显式修复协议记录旧键与新键映射，仍关联原业务意图；普通重试、接管或一次“未找到”都不得擅自换键。

幂等记录也需要生命周期管理。短期通知可能只需在业务 SLA 窗口内保留键，财务、权限和数据删除类操作则需要更长的审计与重放窗口。记录至少保存 operation_id、载荷哈希、请求者、状态、外部引用、首次与最后一次观察时间、响应摘要、过期策略和责任人。删除过早，延迟到达的消息会再次造成副作用；永久保留，又会带来隐私和存储问题。保留期应结合下游重复投递的时间上界、合规要求和补偿窗口一起确定，并写进文档，不能依赖代码中的隐式约定。窗口过期后的恢复要先查询或转人工，不能把一个旧的幂等键当作新请求处理。

补偿为已发生的事实追加反向或缓解动作，拥有独立的授权、前置条件、幂等键、截止时间与验收。已发通知不能抹去接收人的阅读，恢复文件版本也可能覆盖后续人工修改。Saga 将局部事务及其补偿组织成长事务，提供协调思路，不承诺所有影响可逆。[30]

因此，补偿计划应在执行主动作之前就确定下来。工具注册表声明正常操作、成功证据、补偿操作、无法补偿的后果、人工责任人和最长等待时间，工作流在跨越不可逆边界之前检查这些字段和审批。对于没有安全补偿手段的高影响动作，设计上应改为预览、双人审批、延迟提交，或由业务系统提供事务性 API，不能把风险留给模型临场判断。

补偿完成也要按业务事实验收。HTTP 200、队列已接收或模型声称“已恢复”都不足以证明完成；Runtime 需要保存查询到的版本、外部对象状态或人工确认。如果主动作只完成了一部分，可以选择继续完成剩余部分、撤销已完成的部分，或交给人工处理，这三种选择对成本、可用性和用户预期的影响各不相同。工作流定义应把这一选择写成版本化的决策，不能让新 worker 在事故现场临时猜测。人工处理完成后，以事件关闭这项工作，不能直接修改历史状态。

17.6.5 Checkpoint、持久执行与版本恢复

Temporal 要求 Workflow 按历史确定性重放，非确定的 API、模型与数据库调用放在 Activity；允许重试的 Activity 可能多次执行或部分执行，不能从完成记录推断外部生效一次。[31][32] 本书据此复用已提交决策，并用 Operation 与下游契约核验效果，不把应用账本当作框架自动提供的保证。

节点快照是另一种恢复粒度。LangGraph 的 interrupt 恢复从原节点开头重新执行，显式从旧 Checkpoint replay 也会重执行其后节点，包括模型和 API；不能理解成进程指令指针续跑。其 sync 在下一步前保存，async 边执行下一步边保存、崩溃可能丢最近进度，exit 只在执行退出（包括错误或 interrupt）时保存，无法保证执行中崩溃后的续接。[33] 因此接入时须声明重入范围；本书同一 Run 已接受的决策不因重入而被重新采样替换，探索其他结果另建显式分支。

Runtime 在 Step 定义中保存恢复类别，不能把下面不同的业务后果压成一个 retry 按钮：

Checkpoint 是已验证进度与未决 Operation 的恢复索引，不是完整进程内存或撤销能力。它关联 Run、工作流修订版、当前节点、依赖、Attempt、预算与截止时间、不可变上下文/产物引用、审批、定时器和未决动作，并区分候选、观察与已确认事实。历史租约和 token 仅供审计，不能据此复用执行权。

写入遵守C6 提交契约：载荷完整持久化并校验后，同库结果、版本、事件、Checkpoint 与必要 Outbox 一致提交，不采用“尽量同事务”的弱约定。只读计算在完整结果边界保存，写入分别记录意图、派发、回执与补偿；模型 token 不必逐个落库。密集提交增加成本，稀疏提交扩大重算窗口，需通过恢复实验选择。

恢复先读取最近一致边界，核对载荷存在性、完整性、格式、版本及当前权限；再条件认领取得新执行权，按表中类别恢复，并对未决副作用落实资源端屏障与原身份核验。等待事件还需验证签名、关联、期限与取消状态。载荷永久缺失或语义不兼容时暂停，不跳过节点，也不从旧快照读取 owner 就宣布获得执行权。

归档与压缩须保留这些恢复依赖、预算和审批、补偿、安全事件；删除载荷时同步更新引用与可恢复性，不能保留一条实际不可用的恢复路径。重新激活不清零已耗额度。

Run 绑定工作流、输入、上下文和工具版本，恢复不能随默认值升级而改变节点、重试与补偿语义。旧制品不可用时，选择兼容适配、保留旧环境或在安全边界显式迁移；迁移记录旧值、新值、转换函数、检查结果和回退路径。未证明兼容时暂停，不用新定义重新解释旧动作。当前撤权、删除和紧急封锁始终优先于历史版本固定。

Temporal Worker Versioning 是具体参照：pinned Workflow 在同一 Worker Deployment Version 上完成，另一版本的 Worker 不能随意接管其任务，所以仍承载旧执行的版本必须保留可用 Worker。部署环境无法支持该方案时，官方将 Patching 列为代码演化的另一条路径，具体 SDK 规则仍需按语言与版本核对。[34] 这是来源对代码演化的说明；本书据此要求 manifest、契约、模型参数、工具 Schema 和输入制品引用可定位，迁移记录还须保留未决 Operation。固定引用也不保证供应商别名、远端服务或实时数据能够逐字重现，不替代当前权限与审批检查。

恢复动作与重规划的边界

恢复还原原执行的权威进度，重规划修改未来路线。新计划保存版本、变更原因、可复用证据、失效审批和受影响后继；未决 Operation、取消意图和已消耗预算继续保留。目标或授权变化需要明确接受，输入或资源版本变化使原验收失效。激活新计划时校验依赖，拒绝迟到的旧计划结果推进新汇合点。

事件到达时按当前状态和版本决定记录、忽略或转核验，不能盲目继续工具调用；补偿仍需独立授权。

17.6.6 取消、授权变化与人工接管

取消、截止时间到达或预算耗尽后，先持久记录停止推进的决定，阻止新的认领、模型调用、工具动作与委派，并向可中断的执行后端传播信号。进程收到信号不等于外部请求已撤销；任务终态与业务动作事实分开保存。

对于已经在途的 Operation，迟到成功仍需写入原账本并核验证据，但不能把已取消 Run 改回运行中。随后按当前权限决定是否补记、补偿或转人工。核验与安全收尾需有单独声明的责任和受控资源额度，不能以“预算已用完”为由丢弃事实，也不能借收尾无限执行新业务。

超时还要区分单次调用与整个 Run：前者可能只终止一个 Attempt，后者限制任务继续推进，两者都不能证明下游未执行。无进展的识别与迁移判据见17.6.3。

面向用户明确展示“已停止继续执行”及“仍在核验的动作”，不要让一个 cancelled 标签掩盖已发生的副作用。

Policy 的 deny(action) 禁止当前动作，可以在原目标与权限内有界重规划；deny(goal) 表示目标本身不允许，记录 FAILED 及目标拒绝原因。escalate 转入 WAITING(human_review) 和待认领人工工作项，由指定角色判断或接管，不能被解释为普通的用户确认。

无人接管、证据不足或无法安全自动处理时，任务保持可查询阻塞并公开责任与下次处理时间。人工可以批准一个有边界的风险选择，但不能把未知外部结果变成凭空确认。审批绑定、失效与重新认领统一见17.4.4 动作裁决与审批等待，拒绝不能通过换工具或子 Agent 绕开。

Connection 授权失效时保存授权等待与原绑定，不能自动换成更宽权限连接。重新授权也不能证明先前写请求未发生：写入回执丢失仍沿原 Operation 与业务键查询；撤销连接不等于取消在途写入，无查询或幂等能力时转人工核验。

接管的责任人

需要人工接管时，系统应当交付一份可以立即处理的工作项，包括：目标、当前状态、已确认与未知的事实、证据位置、建议的查询或补偿、允许执行的范围、责任人和截止时间。仅仅返回“请联系管理员”，并没有形成接管协议。人工队列需要支持认领、转派、到期升级和关闭证据；人员离线、交接班和重复点击，也都属于恢复设计要覆盖的情形。人工操作同样受租户、角色、双人复核和审计的约束。

人工强制接管须经角色授权，在同一事务中撤销旧租约并授予新代次，可以早于自然到期，但不能只改 owner 后跳过资源端隔离与在途对账。修复记录关联原 Run、Operation、已确认和未知事实、版本、预算、建议恢复点、风险与责任期限；先核验原动作，再决定补记、恢复特定 Step、授权补偿或继续核验，不直接把状态改为 ready。重复点击按 repair_id 幂等返回原决定，批量恢复限速。MANUAL_REPAIR 不是成功状态，关闭须附外部证据，到期未处理按责任链升级。

可恢复的运行保留在 PAUSED 或 WAITING。COMPLETED、FAILED 和 CANCELLED 不经普通 resume 回到运行；用户明确要求重新执行时创建新 Run，并关联原动作与结果。补记外部事实只更新核验记录，不改变原执行终态；新执行也不能重复制造尚未核清的原业务意图。

当工具、模型或权限出现异常时，Runtime 可以把任务降级为只读建议模式：继续收集证据、给出建议，但不再发起有副作用的动作。降级本身是一次状态迁移，需要记录原因、生效范围和恢复条件；未决的 Operation 不会因为降级而消失，仍要按原契约查询或交给人工。

恢复后如何继续

批准、拒绝、修订参数、确认事实和授权补偿是不同事件，由同一控制面接受。继续之前复查取消、预算、权限和资源状态；人工回交附带证据，未决项保留核验与升级责任，不能直接修改数据库或把按钮点击当作完成依据。

本章小结

Agent Runtime 启动时先解析生效配置与策略，再初始化基础设施、能力目录和连接设施，通过就绪检查后才受理并绑定任务。它以任务契约组织目标，以版本化状态保存事实，以逐动作裁决限制执行。Session、Task、Run、Step、Attempt 和 Operation 分别表达连续交互、业务目标、执行、逻辑节点、尝试和外部动作；它们的身份不能因重试或迁移而混淆。安全与授权由 Runtime 串联上下文、工具、执行后端与下游服务共同实施；调用批准、进程隔离与业务鉴权各自保护不同边界，跨工具数据流仍须逐次核验。执行循环通过可信能力完成工作，Checkpoint 和事件保存继续依据，幂等与资源端核验处理不确定副作用。取消、恢复与人工接管都在同一套状态和责任边界内推进，最后以验收过的产物与可查询的交付事实结束。
