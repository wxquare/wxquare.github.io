第 16 章 外部工具系统：Skills、Tools、MCP 与 Connectors

怎样把指标、日志与工单 API 构建成 Runtime 可以安全使用的能力？本章从能力提供方说明工具契约、注册发现与渐进加载、Skills、MCP、Connector，以及风险双轴和沙箱。模型提出调用，能力系统交付接口与保证，第17章 Agent Runtime负责调度、审批等待、重试与恢复。贯穿案例沿用第14章的 ALR 档案：ALR-20260429-017、run_0429_017、trace_20260429_017，调查对象为 prod/order-service，观察窗为 2026-04-29 10:35–10:50（+08:00，即 02:35Z–02:50Z）；调查只读，有效批准后可创建跟进单 INC-4821，不提供重启或回滚。

16.1 概念边界与接入选择

图 16-1：外围能力从提案到受控调用

选择接入方式之前，先区分调用提案、能力契约、方法包和执行通道；它们分别回答不同的问题。

16.1.1 从调用协议到受控行动

第13章 LLM API 协议解释模型怎样提出调用，以及应用怎样关联并回填结果；模型输出本身既不是执行，也不是授权。[2] 对 ALR 案例，工具系统必须把日志工具名解析到可信注册对象，提供参数、身份、资源和输出契约，Runtime 才能据此裁决调用。

各层的产物和责任如下。

本文用“能力”统称可提供的操作或方法；Skill 是方法包，Plugin 是扩展分发包，capability profile 是运行可选配置；MCP capabilities 专指协议特性声明。它们不共用一个 enabled 或授权含义。

几条关系需要特别说明：

  • Skill 与 Tool：Skill 负责方法，Tool 负责行动。告警诊断 Skill 指导 Agent 按取证路径调用日志、指标和部署工具，但 Skill 本身不带来任何权限。
  • Skill 与 Workflow：发布流程中不能跳过的审批，应由 Workflow 或工具的 Policy 实现。把提示里的步骤当作确定性编排，等于把系统应保证的约束交给模型自觉遵守。
  • Skill 与 MCP：Skill 的文件格式不依赖 MCP。Skill 既可以引导 MCP 工具，也可以引导 CLI 或 API；MCP 的 Prompts 是 Server 提供的模板，由 Host 按自身机制使用，与 Skill 不是同一种东西。
  • Connector 与 MCP：Connector 是集成实现，MCP 只是可选的暴露协议。Connector 可以不经过 MCP，直接被应用的 Tool Runtime 调用；一个 MCP Server 也可以聚合多个 Connector。MCP 工具规范规定的是工具发现、调用和结果结构，并不意味着它已经替你完成下游账号授权、业务 ACL 或写入幂等[3]。

一个典型的扩展包结构如下：

Plugin（扩展包）
  ├─ Skill（方法包）
  ├─ MCP Server 配置 / Connector 定义（外部能力入口）
  ├─ Tool Schema（可调用操作的契约）
  └─ 脚本、模板与资产（辅助资源）

无论能力以哪种形式接入，它能否安全可靠地工作，仍取决于 Schema、Policy、沙箱（Sandbox）、Trace 和评估。MCP 不替代 Tool Runtime，扩展包也不替代 Skill。

16.1.3 接入方式选择：API、CLI、MCP、Connector 与 Browser Use

选择接入方式，要同时回答“怎样调用外部系统”和“由谁维护集成”。这五项处于不同层级：API 是外部系统提供的程序接口，CLI 是可执行的命令入口，Browser Use 通过页面交互执行；MCP 是客户端与工具服务之间的标准协议，Connector 是针对某个外部系统的集成实现。Connector 可以直接被应用调用，也可以通过 MCP 暴露；MCP Server 内部还可以执行 CLI。因此，它们既可以作为接入方案比较，也可以组合使用。

无论采用哪条路径，模型都只提出工具名和参数；Agent Runtime 负责找到处理代码、检查权限并执行，再把结果交回模型。采用 MCP 时，MCP Client 承担协议通信；直接接 Connector 时，由应用的工具处理代码调用集成接口，不要求 Connector 实现 MCP。[2][3]

接入方式实际调用入口谁提供与维护优势与适合场景主要限制与责任
API 直连工具处理代码通过 HTTP 或 SDK 请求外部 API外部系统提供 API；Agent 开发团队维护调用代码可精确选择接口、字段和业务行为，适合自研 Runtime 与定制流程开发团队处理认证、分页、限流、错误转换和版本适配；可用能力仍受 API 与账号权限限制

MCPHost 中的 MCP Client 连接本地或远程 MCP ServerServer 开发者维护工具实现；自部署者运维服务，托管服务由提供方运维标准化发现、参数和结果，适合一套工具供多个兼容客户端复用客户端支持与服务能力可能不同；协议不能替代下游授权、幂等和审计，也不保证工具覆盖全部 API
ConnectorRuntime 调用已有集成提供的工具；也可由 MCP Server 调用集成代码集成可由 Agent 产品厂商、外部服务厂商或开发团队提供；例如 OpenAI 提供 Gmail 集成复用账号连接、API 适配和结果转换，适合已有集成足以覆盖的邮件、文档和工单操作能力范围、更新节奏、部署与凭证管理取决于提供方；现成 Connector 的引用未必能直接迁移到其他客户端
Browser Use浏览器自动化工具读取页面并执行点击、输入等动作目标服务维护页面；Agent 开发者或自动化工具提供方维护交互实现适合只能通过网页完成的操作，或必须核对页面状态的任务页面、定位器、登录和交互等待都会影响稳定性；通常步骤更多，需核验最终页面与业务结果[36][37]

以 GitHub 为例，API、CLI 与 MCP 的差异在于谁负责适配。 API 直连由你的工具代码调用 GitHub REST 或 GraphQL；CLI 路径由 Runtime 执行 GitHub 提供的 gh，例如 gh api；MCP 路径则由 MCP Client 调用 GitHub MCP Server 暴露的工具，再由 Server 访问 GitHub。GitHub 提供远程托管与本地运行的 MCP Server；选择远程服务不意味着要在自己的电脑上启动服务进程。[39][40]

以 OpenAI 提供的 Gmail Connector 为例，接入时复用的是已有集成。 用户安装并启用 Gmail 插件，再完成 Google 账号连接，Codex 才能在相应权限下使用邮件工具；安装插件和账号授权是两个独立动作。邮件操作由 Gmail 集成访问 Google Gmail API 完成。这里说明的是调用职责，不能仅凭“Connector”名称或工具名中的 mcp，判定 OpenAI 连接服务内部是否使用标准 MCP，也不能推断本机启动了 Gmail MCP Server。[41]

安装与配置的内容也不同：CLI 通常需要安装命令程序并建立登录态；手动配置 MCP 是登记服务启动命令或远程地址，并按需配置认证与工具范围；现成 Connector 的接入则可能只需启用插件、引用已注册集成并连接账号。自建 Gmail MCP Server 是另一种方案，其开发者或部署者还需处理 Google OAuth、服务运行与工具实现；这些维护成本不能套用到现成 Gmail Connector 上。

选择时可按以下条件判断：

  • 已有 Connector 足够用：优先复用，先确认提供方、账号身份、工具范围，以及结果和副作用能否核验。
  • 需要精确业务行为，且由自己维护 Runtime：考虑 API 直连，或把公共适配逻辑封装成自己的 Connector。
  • 执行环境已有成熟 CLI：通过受控进程复用；能取得 JSON 等结构化输出时，避免解析面向人的终端文本。
  • 同一套能力要供多个兼容客户端使用：考虑用 MCP 暴露自建 Connector，或连接可信提供方的 MCP Server。
  • 现有程序接口无法完成任务，或任务需要页面交互：考虑 Browser Use，并处理登录、定位、等待和效果核验。

上述条件可以组合。例如 CLI + Skill 复用命令与操作方法，MCP + Connector 把具体业务集成提供给不同客户端。Skill 规定方法，MCP 统一接入协议，Connector 落实下游集成；权限控制、写入审批与审计需要在每条执行路径中实现，不因选择了 MCP 或现成 Connector 而自动具备。

16.2 业务能力设计：操作边界、结果语义与可靠性保证

图 16-2：业务能力契约：操作范围、输入归属、结果语义与可靠性声明。

模型怎样接收工具定义、生成参数并关联返回结果，统一见第 13 章工具调用协议。本节站在能力提供方一侧，回答一个业务操作实际承诺什么：操作对象与范围、哪些输入可被提出、结果能证明什么，以及失败或重复调用会产生什么效果。这份契约可以经函数、CLI、MCP 或普通 API 交付，不依赖某一种模型消息格式。

模型接口的 Schema 是业务契约的结构投影，不能代替业务权限、完整性和副作用保证。工具提供方定义并实现这些保证，Runtime 按任务绑定、当前权限与预算使用，业务系统继续承担最终资源鉴权。

16.2.1 操作粒度与业务边界

一个工具应围绕可独立解释和验证的业务操作，而不是暴露无限制的系统入口。名字、参数和结果都要对应明确对象，使调用者知道何时适用、何时不适用，以及怎样核验执行结果。

操作设计问题或保证ALR 中的处理
query(system, query)混合日志、指标和任意查询语言，难以统一范围、成本和资源校验拆为各数据源的有界操作
prometheus_query_range明确数值指标、时间范围、查询分辨率与数据源限制不承担日志读取、建单或生产变更
loki_search明确服务、环境、窗口、字段与分页边界返回获准日志页和剩余覆盖缺口
create_incident_ticket明确项目、草稿、资源版本、防重与回执语义只执行有效批准绑定的建单动作

粒度过大使参数变成任意程序或多种隐含操作，粒度过小又把大量业务步骤交给调用者重组。可以将稳定的只读取证流程封装为 diagnose_latency_incident(alert_id)，但必须交付内部来源、失败和覆盖证据；不能在“诊断”名称后隐藏建单、发送消息或回滚。组合能力的副作用覆盖内部最高影响，数据敏感度覆盖可触达数据，内部调用仍落实各自的资源约束。

协议中的名称、描述与输入 Schema 怎样表达这些边界，见13.3.1；Skill 怎样描述多步方法见16.3。本节不重复供应商字段和消息包装。

16.2.2 业务参数与可信调用绑定

工具契约要区分可由调用者提出的业务条件，以及只能由可信系统绑定的身份、连接和授权信息。参数结构合法，只表示候选值可以被解析，不表示它属于当前主体或能用于当前任务。

输入类别可以怎样产生实现必须检查什么
服务、告警、环境、查询窗口用户指定或模型在任务范围内提出可信实体映射、归属、时间与查询限额，不因名称合法就放行
租户、用户、Connection 与凭证已验证会话、连接服务与可信派发上下文当前所有权、用途、Scope 与撤销状态，不接受参数自报身份
草稿内容、目标项目与资源版本模型可以提出候选，可信批准记录绑定实际载荷实际执行内容与批准、对象和版本一致
Operation、幂等键、截止时间与预算Runtime 或受信调用方提供键作用域、载荷一致性与当前执行条件，不能让模型重生成身份

参数约定还应写明单位、时区、边界和缺省行为。例如金额使用整数分，时间窗标明起止语义与时区，日志工具声明最大窗口和分页规则。自由文本查询语言也须通过受限构造或可靠的范围校验执行，不能只在描述里写“不要查询其他项目”。身份字段不应伪装成模型必须填写的业务参数，实际资源约束必须被实现和下游查询消费。

动态工具集合属于消费侧行为。能力提供方交付来源、版本、适用环境、依赖、风险与可用状态等元数据；Runtime 如何按任务阶段筛选和映射这些能力，统一见本轮工具暴露。工具路由与编排由 Runtime 按任务推进，能力提供方只交付它所消费的契约。

16.2.3 结果语义、覆盖范围与来源证据

结果至少区分“查询成功且完整”“查询成功但仍有缺口”“没有匹配数据”“查询失败”和“写入效果未知”。成功状态不能替代这些业务含义：空数组可能是没有匹配，也可能是过滤后无可见数据；网络超时更不能被编码成“没有异常”。

以下 JSON 是本书应用层 ToolResult 信封示意，不是任何 LLM API 或 MCP 的原生结果类型。call_id 在这里用于应用调用关联；它如何映射供应商的调用标识，由协议适配层处理。

{
  "call_id": "call_logs_01",
  "status": "partial",
  "summary": "已返回当前有权读取的日志页，仍有下一页",
  "data_ref": "artifact://run_0429_017/logs/1",
  "coverage": {"complete": false, "missing": ["remaining_pages"]},
  "effect": {"disposition": "none", "operation_id": null},
  "truncated": false,
  "next_cursor": "opaque-scoped-cursor",
  "error": null,
  "provenance": {"service": "order-service", "window": "02:35Z/02:50Z", "source_version": "logs-snapshot-1"}
}
字段语义与消费者
statussuccess/error/partial；描述本次工具返回，不替代 Operation 事实
coveragecomplete 为 true/false/null，missing 说明未覆盖部分；空结果与查询失败分开
effect.dispositionnone 用于只读；not_dispatched、applied、not_applied、partial、unknown 分别说明派发与效果，写操作关联 operation_id
truncated当前载荷是否被裁剪；分页未取尽由 coverage 和 next_cursor 表示，不混用
next_cursor可继续读取的授权游标；不保证剩余内容在续读时仍可见
data_ref/provenance受控原始数据与来源、实体、版本、时间范围；模型通常只读摘要和必要证据
error分类码、retryable 提示、provider_request_id 与安全诊断；Runtime 拥有最终重试责任

写入发出后丢失回执返回 OUTCOME_UNKNOWN 和 effect.disposition=unknown，不能映射成“确认未生效”。不完整读取也不能当作没有异常。敏感凭据、内部连接句柄与完整私密载荷不进入模型或普通日志。

coverage 描述本次数据覆盖，effect 描述外部动作效果，两者相互独立。日志查询返回 partial 仍可提供有用证据，但不能据此确认整个窗口没有错误；建单请求失去回执则提供原操作与资源查询入口，不能用一条失败消息证明工单不存在。data_ref 是受控原始载荷引用，不自动授予读取资格；来源还应保留对象、版本与时间，便于回读和核验。

统一错误分类见Connector 错误接口：语法或范围无效用 INVALID_INPUT，限流用 RATE_LIMITED，越权用 PERMISSION_DENIED，原始提供方码保存在安全诊断字段。retryable 只提供判断依据，不决定当前任务的重试次数和预算。可裁剪结果保留 truncated 与覆盖标记，超过硬限制而必须拒绝时明确要求缩小范围。

相同 ToolResult 可以投影为模型可读内容、结构化程序结果或审计引用。供应商要求的结果包装与调用关联见第 13 章，MCP 的 structuredContent、isError 与 JSON-RPC error 编码见16.4.3，派发后怎样形成 Observation 与更新状态见第 17 章。不能把三者写成一种格式。

16.2.4 副作用、敏感度与可靠性声明

工具应声明实际行为和数据属性，而不是先写一个“自动允许”标签。下面是本书注册表使用的两条分类轴，值域沿用全书约定，不是 MCP 原生等级：

轴取值需要说明的业务含义
side_effectread_only不改变目标业务状态；说明读取对象、范围与返回内容
side_effectcompensatable_write会改变业务状态；说明可用补偿及不能消除的影响
side_effectexternal_send会把内容交付给接收方；说明发送对象、内容和送达保证
side_effecthard_to_reverse无可靠补偿或影响较大；明确效果、恢复限制与责任边界

data_sensitivityinternal数据限组织或项目使用；说明归属与预期消费者
data_sensitivitysensitive涉及个人信息、客户载荷或受限业务记录；说明字段和派生数据范围
data_sensitivitysecret密码、Key、Token、私钥等凭证；声明专用凭据消费通道，不作为模型观察返回

一个接口混合多种行为时，按最高副作用保守登记，或拆成独立工具；多类数据按最高敏感度登记。未知分类不能填成低风险。prohibited 是策略裁决，不是第三条分类轴；执行进程可能由代理注入凭证，也不代表模型可以读取 secret。

分类之后，还应交付可验证的可靠性保证：

保证项能力提供方应声明并验证什么不能承诺什么

本例 loki_search 是“只读 × 敏感”，建单是“可补偿写入 × 内部”；通知由能力集之外的交付系统处理，重启和回滚不提供。MCP annotations 只是对行为的声明，不能代替以上实现核验，协议字段说明见16.4.2。

能力提供方描述性质，Runtime 按当前身份和任务实施控制：分类对应的控制基线与审批见17.5.3，持续验收见第 18 章。Connector 写入契约落实下游保证，Runtime 恢复处理已经派发的未知效果。

单次调用的组件链路、Attempt / Operation 映射、重试准入与工具指标统一见17.4.5 调用适配层。本章交付工具及其业务契约，由 Agent Runtime 在执行循环中消费。

16.3 Agent Skills：从工具调用到能力复用

工具让 Agent 能够行动，Skill 则把完成一类任务的方法组织成可复用的能力包。Anthropic 提出的 Agent Skills 把指令、脚本和资源放进一个目录，并按任务需要加载。[4]

本节沿用告警诊断案例，依次讨论 Skill 的组成、SKILL.md 的写法、从案例提炼能力、注册表、渐进式加载、门控与 Tool Policy 的分工，以及版本化生命周期和常见失败模式。

16.3.1 为什么有了 Tool Calling 还需要 Skill

查询天气通常只需一次工具调用，而“排查线上延迟升高”需要协调多个动作：确认服务和时间窗口，查询指标与日志，对比部署变更，检索历史案例，最后形成带证据的诊断。能调用这些工具，不等于能把它们组织成可靠的工作方法。

如果每次都让模型从零规划，它可能漏查部署、把时间上的相关性当成因果，或在证据不足时直接建议重启。Skill 的价值在于沉淀容易遗漏的步骤、判断条件和交付标准，让下一次任务复用经过验证的方法。

Skill 是可被 Agent 发现并按需加载的能力包：它用程序性指令、工具使用约定和配套资源，描述某类任务应该如何完成、如何处理失败，以及如何证明已经完成。

“程序性”强调的是行为路径，Markdown 并不会像代码一样被强制执行。因此，评价一个 Skill 要看它能否改善真实任务中的行为，而不是看说明是否完整、措辞是否强硬。

16.3.2 Skill 的组成：入口、指令与可复用资源

Agent Skills 格式以 SKILL.md 为入口，文件由 YAML 前置元数据（Front Matter）和 Markdown 正文组成；脚本、参考资料和资产都是可选资源。[5]

图 16-3：Skill 组成：SKILL.md 的元数据用于发现，正文提供执行指令；scripts 提供确定性操作，references 提供按需知识，assets 提供产物材料

组成回答的问题告警诊断示例
SKILL.md 前置元数据这是什么能力，什么时候使用？名称 incident-diagnosis；描述延迟、错误率和告警排查场景
SKILL.md 正文按什么路径完成，如何验证？先对齐时间窗口再取证；报告区分事实、假设和未知项
scripts/哪些操作应复用确定性实现？校验报告中的证据编号和时间格式
references/当前任务需要查阅哪些领域知识？指标口径、日志字段、部署事件说明
assets/产物需要哪些模板或素材？事故报告模板、图标和报告样式

目录只添加任务确实需要的资源。三类资源的使用方式也不同：参考资料按需读入上下文；脚本通过工具执行，不必每次把源码读进模型；资产通常作为输出材料，需要时再检查。脚本输出、报错和被读取的文件仍会占用上下文，“外化为文件”并非零成本。

同一条规则只维护一个事实源。例如，指标口径放在 references/metrics.md，正文只说明何时读取，不复制整套定义，否则两处内容会在更新中逐渐漂移。有些客户端还会使用额外的 UI 或平台配置文件，但它们不是所有 Skill 通用的必需文件。

Skill 与 Tool、Workflow、Memory、Plugin 的边界见 概念边界总表。这里只强调一点：Skill 指导模型选择步骤，自身不能授予任何权限；不能跳过的审批应由 Workflow 或 Tool Policy 保证。

通用规范的必填字段为 name 与 description：name 长度为 1–64 字符，使用小写字母、数字和连字符，与父目录同名，不能以连字符开头或结尾，也不能出现连续连字符；例如 incident-diagnosis 合法，-incident、incident-、incident--diagnosis 不合法。description 长度为 1–1024 字符；可选 license、compatibility（提供时为 1–500 字符）、字符串映射 metadata；allowed-tools 是实验字段，不能被当作所有宿主的强制授权。[5] Claude Code 特有的控制字段属于产品扩展，不回填为通用规范要求。

# 告警诊断

## 输入与前置条件
- 确认服务、环境、告警和时间窗口；缺失且无法从告警确定时先澄清。
- 根据当前环境确认指标、日志和部署查询工具可用。

## 执行步骤
1. 读取告警，确认影响范围；按 references/metrics.md 核验指标口径。
2. 查询同一时间窗口的延迟、错误率和流量，记录证据编号。
3. 按 references/log-fields.md 查询脱敏日志，核对部署和配置变更。
4. 交叉检查证据，区分已证实事实、根因假设和待验证项。
5. 使用 assets/incident-report.md 组织报告。
6. 通过执行工具运行 scripts/check_report.py 检查证据引用；
   再人工或由 Agent 核对证据是否真正支持结论。

## 行为边界与失败处理
- 不读取或输出凭证和个人敏感信息，不自动重启、回滚或修改配置。
- 证据不足时继续取证，或明确报告未知；不把时间相关性写成确定根因。
- 工具失败时报告缺项和影响，不能改用未授权通道绕过限制。

## 完成标准
- 报告包含时间窗口、影响范围、证据、假设、未知项和后续建议。
- 每个关键判断可追溯到证据；资源或校验不可用时不得声称已验证。

description 是发现入口，必须写明能力和适用场景。如果“何时使用”只写在正文里，Agent 决定是否加载时可能看不到。描述也不宜塞入完整步骤：一般经验是，摘要写得过细，Agent 容易凭摘要直接执行，跳过正文中的约束。

正文要把容易走错的分支写清楚：输入不全怎么办，工具失败如何降级，证据不足如何表达。示例中的校验脚本只能检查引用结构，不能证明根因正确，后者仍要回到原始证据。

16.3.4 从真实案例提炼 Skill

先收集具体请求，再抽取可复用步骤，比先写一份“大而全”的专家指南更容易划清边界。

来源适合提炼的内容需要排除的问题
专家 SOP、团队 Runbook稳定流程、检查项、失败分支过期命令、隐含权限和口头约定
成功 Trace、Diff、复盘有证据的步骤和验证方法偶然成功、错误归因、敏感数据
项目规则构建、审查和交付约定无条件复制为全局规则
官方或开源 Skill目录组织、资源复用和工具惯例平台依赖、不可信脚本、许可限制

以告警诊断为例，正例有“支付服务 P95 突增”“发布后错误率上升”，负例有“生成上月流量报表”“直接重启服务”。正例帮助确定流程，负例帮助限制误触发。如果一组案例需要完全不同的输入、工具和完成标准，就应考虑拆分 Skill。

案例中反复出现的确定性操作提炼为脚本，领域细节拆到参考资料，固定的产物结构沉淀为资产，正文只保留核心决策路径。复用的是经过核验的方法，而不是某一次任务的结论。

16.3.5 Skill 注册表：版本与运行条件

小型本地技能库可以先用目录、Git 和变更记录管理。多人共享、多环境部署时，再引入注册表，记录谁负责、哪一版经过验证、支持哪些运行条件。

下面是一条注册表记录示例。注册表字段不是 SKILL.md 的标准字段，写进注册表也不会自动产生权限控制：

name: incident-diagnosis
version: "1.4.0"
owner: sre-platform
status: published
artifact_digest: "sha256:<能力包内容摘要>"
scope: [staging, prod]
side_effect: read_only
data_sensitivity: sensitive
dependencies:
  tool_contract: observability-v3
  runtime_profile: incident-reader-v2
validation:
  suite: incident-diagnosis-regression-v5
  evidence: "eval://incident-diagnosis/1.4.0"
previous_stable: "1.3.2"
changelog: "补充日志查询失败时的降级路径"

记录中的版本、摘要和验证集均为示例值，side_effect 与 data_sensitivity 采用工具风险分级的口径；本条只登记会接触敏感日志的只读调查 Skill，批准后建单是能力组合中的另一个写工具，不能继承这里的只读标签。几条要求如下：

  • 发布单元覆盖整个能力包。 正文、脚本、参考资料和资产一起发布，并关联不可变包、内容摘要、来源和验证证据，不能只记录一个可移动的标签。只给 SKILL.md 打版本号、却在原位置覆盖脚本，就无法还原历史行为；同理，不能只校验 SKILL.md，然后运行被覆盖的脚本或未锁定的依赖。
  • 外部依赖记录契约或快照。 外部工具和知识源无法打包时，记录兼容契约或快照标识。
  • 任务记录实际使用的组合。 一次任务应记录选中的 Skill 版本、工具契约和模型、Runtime 配置，才能区分“Skill 改动导致回归”“工具接口变化”和“模型升级改变了执行行为”。

责任人维护边界并负责升级验证，注册表负责追溯，实际调用权限仍由 Runtime 决定。Skill 与工具、MCP 服务、策略组合成任务配置时的记录方式，见 能力使用治理。

16.3.6 渐进式加载：先发现，再展开，最后按需取用

Agent Skills 的格式规范将发现元数据、激活指令和按需资源分开；文档中的 token/行数建议不是所有客户端共同的硬上限。实际装配由宿主实现，不能从目录里存在 SKILL.md 推导正文已经进入模型上下文。[4][5]

图 16-4：Skill 渐进式加载

阶段暴露内容需要验证
发现名称、描述、来源与必要元数据相关能力能被找到，无关任务不误触发

宿主实现存在差异：Codex、Claude Code 与 Hermes 的来源目录、触发方式和正文加载入口要按对应版本核验，不能把一个平台的自动触发行为写成格式保证。[6][7][8][9][10] 迁移时先验证发现和激活，再验证工具/脚本依赖；客户端不支持的能力应显式报告。

一次告警任务先按描述选诊断能力，读执行规则，再按证据缺口加载指标口径或日志字段。只运行一个格式检查脚本时，保留必要结果，不把全部源代码与历史事故预加载。元数据索引本身也占预算，大型技能库可以检索，但不能无限追加所有能力。通用上下文预算与压缩见上下文工程。

16.3.7 自由度、门控与 Tool Policy

Skill 的约束强度应与任务的变化空间和出错代价相匹配。文本原则、模板和脚本分别对应不同程度的自由度：

自由度适用场景合适的控制方式
高解释异常、提出诊断假设原则、案例、证据要求，保留判断空间
中按统一口径查询、组织事故报告参数化模板、字段说明、检查表
低格式转换、报告引用校验经过验证的脚本、结构化输入输出

门控应写成可观察的条件，例如：“未确认服务、环境和时间窗口前，不进入日志查询；证据不足时，不把假设标记为根因。”复杂流程可以用流程图或检查表表达分支与回路，减少提前结束任务的机会。

需要强调的是，Skill 中的门控只是行为指令，Tool Policy 才是运行时的强制边界。HARD-GATE 之类的标签没有通用的强制执行语义。生产写操作的授权、审批和审计必须由 Runtime 或确定性编排器实现（见 Agent Runtime Policy 引擎）。例如，Skill 可以要求“创建事故单前确认内容”，Runtime 仍要检查用户是否授权、参数是否合规、操作是否幂等。注册表中的副作用与数据敏感度和 Skill 自述的工具限制，都要由系统解释并落实，不会自动生效。

16.3.8 Skill 生命周期：发布、迭代与退役

本节为本书的工程治理模型，Agent Skills 格式本身不规定完整发布流程。版本单元覆盖正文、脚本、参考资料和资产，关联不可变摘要、责任人和验证证据；工具契约与模型变化也要重新验证。

16.3.9 常见失败模式与回退

失败模式表现修复方向
描述宽泛或只写在正文无关任务触发，相关任务却未加载用正反例收窄描述，单独测试选择行为
把知识库塞进正文每次加载大量无关细节正文留决策路径，领域知识按需引用
规则多处重复正文、脚本和附录口径不一致明确事实源，用引用代替复制
自由度错配脆弱操作临时生成；判断任务机械照表确定性部分脚本化，推理部分保留判断
把门控当权限写了“禁止”却仍能调用高风险工具用 Runtime Policy、审批和沙箱（Sandbox）实施边界

Skill 缺失、资源不可读或工具不可用时，报告缺项，只在既有授权内完成可独立验收的步骤，不能退到更宽的 Shell 或任意 HTTP 通道。工具版本或 Schema 变化时暂停受影响动作，刷新定义并重新核验参数与授权；切换 Skill 不会清空执行事实，恢复见第17章。

16.3.10 Skill 与 MCP 的关系

Skill 可以引导 MCP、CLI 或 API；MCP Prompts 提供由 Host 选择的模板，并不自动成为 Skill。方法包与接入协议可以独立升级，组合时须重新验证工具依赖、加载行为和权限，不能从格式兼容推导运行兼容。职责对照见概念边界，接入机制见MCP。

16.4 MCP：服务端能力封装与交付

本节从能力提供方出发：怎样将已经定义的工具契约和 Connector 业务实现，封装成可被不同 Runtime 接入的 MCP Server。交付内容包括能力定义、handler、协议与部署配置、逐请求授权和兼容测试；MCP 不替代 Connector 的下游业务语义，也不替代 Host 的任务控制。[11]

阅读顺序是角色边界、能力定义、服务端组装、协议部署、认证授权、测试发布。Client 初始化与目录缓存见17.3.5，模型调用与观察回填见17.4.5，交互等待和断流恢复也分别由 Runtime 管理。本节沿用 2026-07-28 协议基线；以下服务内分层、ALR 示例与伪代码属于本书设计，不是 MCP 规定的应用架构。

tools/list 读取当前身份可见的定义，tools/call 将名称解析到受信 handler；Resources 和 Prompts 使用对应的注册表。业务 handler 接收已经校验的业务参数和可信授权上下文，调用 Connector，再将业务结果映射为 MCP 响应。下面是框架无关的组装伪代码，函数名只表达职责，不是可直接运行的 SDK 示例：

定义阶段：
  connectors.register("logs", LogsConnector(config.logs, credential_provider))
  tools.register(log_tool_definition, handler=search_logs_handler)
  resources.register(runbook_definition, reader=read_runbook)
  prompts.register(report_template_definition, renderer=render_report_template)

处理 tools/call：
  principal = authenticate(request)                  # 不从工具参数取身份
  tool = tools.require(request.name)                # 仅解析已注册能力
  input = tool.validate(request.arguments)
  grant = authorize(principal, tool.action, input)   # 当前工具与资源权限
  result = tool.handler(input, grant, connectors)   # Connector 强制消费 grant
  observation = filter_and_validate(result, grant)
  return encode_mcp_result(observation)

这里的 Tool Registry、权限包装与 handler 都属于 Server 内部实现，不能与 Host 侧的目录缓存、任务 Policy 和调度器混为一谈。Server 内授权的完整边界见下文，Connector 如何处理下游 API、分页、账号和错误见16.5。

结果编码也是服务端契约。 Server 将允许交付的结构化结果放入 structuredContent，声明 outputSchema 时保持一致；文本内容提供可阅读说明，兼容场景下按规范提供结构化内容的序列化表示。协议层错误与工具执行错误分开编码，正常返回的 JSON-RPC result 不自动表示业务成功。[3]

handler 的结果服务端交付不得隐去的信息

Server 仅请求当前缺少的输入，不在 form 中索取密码、API Key 或 Token；需要敏感交互时使用受控带外页面。若 Client 不支持所需模式，应明确报告不能完成该交互，不降级为明文表单。补输入结果和状态句柄要绑定主体、用途和时效；具体交互等待、取消与继续见17.4.4。[17]

旧传输的兼容细节分别参照对应规范，不能把多个版本的会话、通知与恢复字段混在同一条路径。[18][19][20] Tasks 扩展的版本独立演进，发布时需固定兼容范围，不把它当作所有 Server 的必需功能。[21]

stdio 与 HTTP 各自遵循协议与认证边界，不能给 stdio 套用 HTTP OAuth 流程。Server 所需环境与凭证引用应明确交付，Host 的实际注入、子进程启动与隔离见17.3.5。HTTP 响应流与订阅的具体契约见传输规范。[22][23] API Gateway 继续承担原有入口的认证、配额与审计，增加 MCP 接口不能绕过业务网关或默认取得数据库超级权限。

发现响应的 ttlMs 与 cacheScope 表达缓存约定，返回集合仍取决于本次授权；Server 不依赖连接上此前的请求保存隐式身份。[3] 部署说明应分别写明服务可用性、工具目录变化与业务效果保证，不能将 HTTP 可连通或请求级取消解释成任务完成、写入撤销或自动重试安全；消费端恢复见17.6.1。

16.4.5 服务端认证与资源授权

HTTP 第一跳授权按 OAuth 2.1 draft-ietf-oauth-v2-1-13 及规范引用执行：资源元数据使用 RFC 9728，resource/audience 绑定使用 RFC 8707，授权码流程落实 PKCE 与适用的安全条件。Client ID Metadata Documents 是推荐的客户端注册机制，DCR 已弃用，仅作旧授权服务器兼容。Token 通过 Authorization 头传递，不放查询串。[23]

授权服务器身份契约。 多授权服务器部署要固定资源元数据与允许的 issuer、资源受众及 Token 校验方式。授权响应 iss 的有条件比较不能被简化为“所有响应缺少 iss 都失败”，也不能对 issuer 做大小写或尾斜杠归一化；Client 的元数据支持位判断与回调检查统一见17.3.5 的第一跳认证。Connector 第二跳按同样的 issuer 识别规则处理，具体流程见Connector 认证。[24]

受保护 HTTP 资源在缺少有效令牌时通过 401 / WWW-Authenticate 说明授权入口；Scope 不足时按规范提供 403 / insufficient_scope 挑战。服务端始终检查令牌受众、有效性与本次操作权限，不能把 Client 已连接或已同意扩权当作校验结果。Client 的授权事务与有界继续调用见第 17 章。[23]

工具、Resource 和 Prompt 的描述不能作为新的授权依据，服务端返回内容仍须按用途过滤。协议安全指南强调请求验证与凭据边界，提示文本不能替代资源端访问控制。[25]

多个团队可以共用服务部署和工具定义，权限边界由每次请求的可信身份与当前授权建立。图中 tools/list 和 tools/call 是两类独立请求，每次都先认证；两条路径读取同一策略来源，分别控制工具可见范围和本次资源访问。拒绝发生在业务内容读取或写入之前，Connector 只执行授权范围内的访问。

隔离层次与部署选择。

“每个 Workspace 一个 MCP Server”需要先说明 Server 指什么。Workspace 是宿主的配置与协作空间，不天然等于团队或租户；租户是本系统定义的数据授权边界，二者的归属关系必须由服务端验证。

层次保存或管理什么隔离意义
服务部署 / HTTP 端点进程、网络入口、依赖与运行配置共用端点可以服务多个租户，但要逐请求认证与授权
进程内 Server 对象SDK 工具定义、handler 与协议配置按工具集合创建多个对象只是实现方式，不形成数据安全边界

独立进程 / 容器 / 存储执行环境、故障域和数据载体可加强隔离，仍需同步约束凭据、网络、存储与业务授权

对可信的固定工具集，可先采用共享部署，在请求级实施租户授权。只有工具定义与处理器配置完全一致、且不捕获租户身份、凭据或业务状态时，才适合按规范化工具集合复用 Server 对象；缓存需要容量与淘汰上限。工具定义相同，不代表可以共享结果缓存。运行不受信代码、连接独立内网或要求专属凭据与故障域时，再采用独立执行环境。

MCP Server 的生产实现分为协议层、工具层、授权/配额层和 Connector 层。协议层处理版本与消息；工具层绑定 handler 并校验契约；授权层决定主体和资源范围；Connector 将范围落实到实际数据源。API Gateway 继续承担既有 API 的权限、限流与审计；接入 MCP 不应绕过网关或直接获得数据库超级权限。

两阶段授权：发现时过滤，执行时重验。

以虚构的团队 A、B 为例：A 的 Agent 可以使用日志工具，但只能读取获授权的服务。logs:read 表示工具能力，不能单独证明其有权查询 B 的服务。服务端应同时判断主体、工具动作、目标资源与当前条件；默认拒绝，并在每次请求上验证权限。后两项是 OWASP 的通用授权原则。[26]

入口验证令牌后构造只读的 Principal，包含主体、租户及委托范围。JWT 校验签名、issuer、audience 和有效期；不透明令牌通过受信服务查询状态。团队归属取自已验证声明或服务端映射，不能相信模型参数、普通团队请求头或未经核验的 Workspace ID。代表用户执行时，有效权限还要受用户当前权限与本次委托约束，不能只使用 Agent 服务账号的权限。HTTP 第一跳机制沿用本节前述授权契约。[23]

发现时过滤用于减少无效选择和工具元数据暴露。本书设计的可见集合为：

可见工具 = 已启用工具 ∩ 服务端当前授权工具 ∩ Workspace/Agent 配置选择

配置选择只能缩小范围。tools/list 返回该集合，任务期的二次裁剪由 Host 完成；没有授权工具时返回空集合或按接入策略拒绝，不能把空列表解释成“全部开放”。2026-07-28 允许工具列表随本次请求的授权变化，不能依赖同一连接上先前请求留下的隐式状态。[3]

执行时重验负责这一次具体访问。调用者可能绕过发现直接构造 tools/call，工具列表也可能在撤权后仍留在缓存中；所以执行入口必须读取当前策略，再检查工具资格、配置边界与目标资源。下面是应用层伪代码，错误编码需映射到实际 SDK 和传输契约，不是新增 MCP 方法：

handle_tool_call(request):
    principal = authenticate(request.credentials)       # 失败即拒绝
    policy = load_current_policy(principal)             # 不可验证即拒绝
    tool = registry.require(request.tool_name)
    require_explicit_policy(tool)                       # 新工具默认不开放
    require_tool_access(principal, policy, tool)
    profile = resolve_verified_profile(principal, request.profile)
    require_profile_access(profile, tool)
    input = tool.validate_input(request.arguments)
    target = tool.resolve_target(input)                 # 解析可信资源身份/归属
    grant = authorize_resource(principal, policy, tool.action, target)
    require_allowed(grant)
    result = tool.execute(input, grant)                 # 查询强制使用授权范围
    return validate_and_filter_output(result, grant)

统一包装适合执行身份、工具权限与审计检查；具体资源规则由工具或适配器声明。配置归属必须经过验证，不能任意选择他人的 profile。resolve_target 如需查元数据，只能通过受控内部查询解析归属，不能先向调用者返回对象内容再判断权限。策略或归属服务不可用时停止受保护调用。授权结果应成为查询层强制消费的约束，避免 handler 校验后又用原始参数扩大范围。Resources 的列举与读取、Prompts 中受保护内容的获取也应沿用相同边界，不能只保护 tools/call。

工具类型查询与返回必须落实的资源边界
按 ID 读取 / 批量读取用获授权租户与对象 ID 联合查询；逐项约束关联对象，不能因 ID 难猜而省略授权
日志 / 指标服务端解析获授权项目、服务、环境；使用受限查询构造器，不能靠给任意查询字符串拼接过滤条件
知识检索在召回阶段应用知识库与文档 ACL，摘要、引用和结果缓存沿用该范围
发消息 / 写工单校验目标空间、对象、发送身份和动作权限；写入时约束资源版本或原子校验，避免检查后归属改变
通用脚本 / 组合工具内部每个子调用继承受限上下文，不能换用更高权限身份绕过边界

第二跳优先使用用户委托或租户受限凭据，由受信 Connector 选择，不能由模型指定任意凭据引用。若下游只能提供宽权限服务账号，适配器就承担完整的资源约束；无法可靠限定范围的工具先不开放。跨团队共享需显式授权关系。凭据取得、两跳授权与撤销细节见 Connector 开发。

因此，A 无日志权限时不展示日志工具，直接调用也被拒绝；A 有日志权限时可以看到工具，但查询 B 的未共享服务仍在读取业务内容前被拒绝。发现过滤改善选择，执行授权守住资源边界，两者使用同一策略来源。

状态、缓存与并发。 共享 Server 对象不保存“当前团队”、当前 Token 或请求参数。工具列表、结果、分页游标与幂等记录按必要的主体、租户及资源授权范围分区；读取受保护缓存时仍检查当前资格，TTL 不能延长已撤销的权限。业务句柄、requestState 与任务扩展句柄也绑定主体、用途和有效期，续交时重验，不能把句柄本身当作认证凭据。[27][25]

服务端审计保存主体、租户、工具、资源引用、策略版本、裁决与下游回执，不保存明文令牌；拒绝消息不泄露他人对象是否存在。缓存与查询过滤保护的是服务实际交付的数据，Host 的上下文过滤只能作为另一层控制，不能补救服务端已经越权返回的内容。

16.5 Connector 开发：从业务 API 到可治理的 Agent 集成

图 16-8：Connector 把业务 API 变为能力

MCP 接入讲如何向 Host 暴露能力；把业务系统真正接进来，还需要一层集成实现，即 Connector。MCP 是可选的暴露协议，Connector 是集成实现。

本节以企业工单系统为案例，按开发顺序展开。Connector 在任务中的绑定、撤销与结果未知恢复属于 Runtime 职责，见Agent Runtime Connector 运行时。

16.5.1 Connector 与 MCP：开发视角的关系

概念边界见 概念边界总表。Connector 负责认证适配、请求转换和结果归一化，并配合连接服务管理授权；有些平台称之为 App、Integration 或数据源适配器。工单系统提供几十个 REST 接口，不意味着要向模型暴露几十个函数：开发的第一步是挑出任务需要的业务能力，定义稳定的输入、输出和失败语义，再把下游 API 接到后面。

Connector 可以不经过 MCP 直接由 Tool Runtime 调用，一个 MCP Server 也可以聚合多个 Connector。MCP 工具规范只规定工具的发现、调用和结果结构，不负责下游账号授权、业务 ACL 或写入幂等。[3]

集成分两类：在线行动型按任务查询或改变外部状态；知识摄取型把外部数据同步进索引，需要管理同步水位、删除传播和 ACL 更新，不能用旧索引代替实时业务检查。本节以前者为主。

16.5.2 业务能力与部署边界

企业工单 Connector 的最小版本只做三件事：在获准项目中搜索工单、读取一条可见工单、创建一条经过批准的跟踪单。批量修改、删除、任意查询和任意 HTTP 请求暂不实现，以免一次性暴露底层系统的全部权限。

先写能力契约表，再决定用 API、SDK 还是 MCP 实现：

能力模型提供的业务输入可信上下文提供输出与执行要求
tickets.search关键词、页大小、可选游标租户、用户、Connection、获准项目有界结果、来源、分页状态；不返回未授权对象
tickets.get工单 ID同上对象版本、可见字段、来源链接；无权时按提供方规则隐藏对象存在性
tickets.create标题、描述、优先级同上，另加绑定草案的审批和稳定的 Operation ID确定的远端对象 ID，或明确的失败、结果未知状态

进程内适配器适合单一应用；远程 Connector 服务便于多个 Runtime 共享账号管理、出站策略和配额，但要明确调用者认证、委托校验、网络可达性和运维责任。MCP 只是与 Host 互通的入口，不决定部署方式。

16.5.4 认证：连接外部账号与两跳授权

Connector 可以复用平台的凭据服务，不必自己保存 Token，但仍要明确谁发起授权、谁处理回调、凭据属于谁、哪些动作触发增量授权。下面以委托用户的 OAuth 授权码流程为例；服务账号、API Key 等方式需另行设计隔离、轮换和撤销。

  1. 用户在可信界面选择工单组织，连接服务创建一次性授权事务，绑定当前用户、租户、目标组织和回调地址。
  2. OAuth 客户端生成与事务绑定的 PKCE 挑战和防跨站请求伪造的 state，重定向到受信的授权端点。RFC 9700 要求公共客户端使用 PKCE，并建议机密客户端采用，优先使用不暴露 verifier 的 S256。[1]
  3. 回调处理器验证事务状态、时效和回调目标；提供方支持 RFC 9207 时，按第一跳同样的 issuer 校验规则检查授权响应 iss，只使用本事务已绑定的授权服务器和 Token 端点，再携带原 verifier 交换授权码。通过可信的提供方接口核实外部账号、组织和实际授予的 Scope，不能只信用户输入的组织名。[24]
  4. 凭据服务加密保存 Token，只返回不能直接用于调用的连接记录引用；模型、会话文本、日志和追踪载荷都接触不到原始凭据。
  5. 调用时按 Connection 解析凭据，由凭据服务协调刷新；新的 Refresh Token 应连同版本号原子更新，避免并发请求用旧值覆盖新值。
  6. 授权失效或 Scope 不足时，返回可识别的等待或拒绝结果；增量授权必须重新经过用户和管理员策略，不能自动申请全部权限。

两跳授权。 通过 HTTP MCP 暴露 Connector 时，一次调用涉及两段独立的授权：

第一跳：Host → MCP Server第二跳：Connector → 下游 API
OAuth 客户端HostConnector 服务
资源方MCP Server工单系统等下游 API
Token 受众MCP Server下游 API
依据MCP 2026-07-28 授权规范[23]下游 API 提供方的授权规则

两跳可能使用不同的授权服务器、Client ID 和 Scope。MCP 授权规范只描述第一跳，不能当作下游 API 的授权实现。由此得出三条规则：

  • MCP Server 必须校验 Token 的目标受众，不接受并非为自己签发的 Token。
  • 访问下游 API 时使用单独获取的 Token，禁止原样透传入站 Token。[23]
  • 以代理身份调用下游时，防范混淆代理（confused deputy）风险。[25]

使用 MCP Elicitation 时，项目、分类等非敏感选择可走 form；密码、API Key、Token 不得由 form 索取。Server 作为第三方 OAuth 客户端时按 url 模式引导用户进入带外授权页，Connector 在可信回调处理凭据，MCP 只接收同意/拒绝/取消的结果；单凭 URL 被打开或用户选择 accept 不能建立有效 Connection。[17]

例如，inputRequests 内的第二跳授权请求可采用下列形态；URL 是本书教学占位端点，不含 Token、个人信息或预认证凭据，连接页面必须先验证当前用户与征询事务一致：

{
  "method": "elicitation/create",
  "params": {
    "mode": "url",
    "message": "连接工单账号以申请指定项目的建单权限；连接后仍需单独批准草稿。",
    "url": "https://tickets-mcp.example.com/connect"
  }
}

账号授权不能替代对具体写入的动作审批。

16.5.5 适配器：身份、传输与业务映射分离

建议拆成四个模块：连接服务负责身份绑定和凭据，传输客户端负责受控网络请求，业务适配器负责字段映射和错误转换，Tool 或 MCP 层负责能力暴露。这样更换 Host 或传输协议时不必重写工单逻辑。下面的伪代码展示搜索路径的职责和调用顺序。

class TicketsConnector:
    def __init__(self, **deps):  # connections、credentials、transport 等由平台注入
        self.__dict__.update(deps)

    async def search(self, args, ctx):  # ctx 来自认证后的 Runtime
        binding = await self.connections.require_binding(ctx, action="tickets.search")
        self.policy.require_current_permission(binding, "tickets.search")
        query = self.mapping.validate_search_input(args)
        provider_cursor = self.cursors.resolve(  # 校验游标绑定与有效期
            args["cursor"], binding=binding, query=query
        )
        handle = await self.credentials.resolve_for(binding)  # 仅供传输层使用
        response = await self.transport.request(
            endpoint_profile=binding.endpoint_profile,
            method="GET",
            path="/tickets",
            credential_handle=handle,
            params={
                "query": query.text,
                "projects": binding.allowed_projects,
                "limit": query.page_size,
                "cursor": provider_cursor,
            },
            deadline=ctx.deadline,
        )
        result = self.mapping.search_response(response)
        visible = await self.policy.filter_and_redact(result.items, binding)
        await self.connections.require_binding_still_current(binding)
        next_cursor = self.cursors.issue(result.next_cursor, binding=binding, query=query)
        await self.audit.record_safe(action="tickets.search", binding=binding,
                                     provider_request_id=result.request_id)
        return {
            "status": "partial" if result.has_more else "success",
            "call_id": ctx.call_id,
            "effect": {"disposition": "none", "operation_id": None},
            "error": None,
            "provenance": {"provider_request_id": result.request_id},
            "coverage": {"complete": not result.has_more, "missing": ["remaining_pages"] if result.has_more else []},
            "truncated": False,
            "next_cursor": next_cursor,
            "summary": self.mapping.safe_summary(visible),
            "data_ref": await self.artifacts.store_visible(visible, binding=binding),
        }

几处要点：

  • ctx 由认证后的 Runtime 提供。require_binding 要验证连接所属租户、调用者使用权、Run 委托、连接状态、动作 Scope 和资源范围。
  • 游标绑定连接、资源范围、查询和授权版本；handle 不能序列化进模型消息或日志。
  • transport 要限制目标域名与重定向，校验 TLS，设置超时和响应大小上限，并注入凭据；出口控制的完整做法见 网络出口控制。失败时抛出已归类的错误，由 Tool 层转换为 Observation，而不是用 except Exception: return [] 把鉴权失败伪装成“无结果”。
  • 对象级授权由提供方执行，平台的委托和字段规则由 filter_and_redact 另外执行。使用服务账号时，平台必须有可落实的请求者授权机制，例如受控的项目映射。接口无法提供所需隔离时，应限制能力或拒绝接入，不能把全量内容送进模型再要它忽略越权结果。

适配器的返回值可以封装为 ToolResult Envelope；通过 MCP 暴露时，再映射到 MCP 的工具结果与错误约定。CONNECTION_REQUIRED 等错误分类是本书的应用层约定，不是 MCP 自带的统一错误码。

16.5.6 写操作：审批、幂等与结果未知

tickets.create 核验当前 Connection、业务参数和批准引用，接收 Runtime 提供的 Operation 与稳定幂等键，映射下游请求并返回效果证据。它必须交付以下可核验的下游能力，而非只声明一个 idempotent=true：

契约项必须声明的内容不支持时的边界
键映射与作用域Operation 到提供方键的稳定映射；按租户、账号或端点划分的唯一范围业务关联标记只能帮助查找，不证明唯一
同键同参并发重复请求是否复用同一结果，失败是否缓存本地锁不能证明远端生效一次
同键异参比较哪些规范化参数；必须拒绝冲突并映射为 INVALID_INPUT，不得静默覆盖或复用错误结果提供方不校验时由适配层阻断；无法保证则禁用该重放能力
保留窗口去重记录保存多久、从何时计时、过期后的语义；没有保证时明确为未知窗口到期不允许声称仍能安全重放
查询入口按原键/远端作业 ID/对象 ID 查询；一致性延迟、在途状态与权威程度“未找到”不等于确认未执行；无法核验须披露并转人工
结果与补偿同步效果回执、异步接受句柄、资源版本；补偿前提和新增副作用接受不等于完成，补偿也不是抹去历史

回执丢失返回 OUTCOME_UNKNOWN、原 operation_id 和安全查询引用，不换键重发。完整未知结果状态机、发送前持久化与接管算法见第17章派发协议和外部效果恢复。

16.5.7 分页、限流、缓存与增量事件

分页。 游标要绑定连接、调用主体（或等价的授权边界）、资源范围、查询指纹和有效期，不能拿其他租户或旧授权下的游标续读。提供方返回下一页 URL 时，传输层要验证目标、防止凭据跨域泄漏，不能让模型拼接 URL。

限流信号。 GitHub 的 REST API 最佳实践介绍了按分页信息遍历、处理限流提示和条件请求的做法[31]，但这是特定提供方的规则，不是通用默认值。Connector 按实际的应用、账号或组织维度声明配额并透出 Retry-After 等提供方提示；SDK 内部重试必须关闭或显式计入同一调用契约，调度与预算由 Runtime 统一控制。

缓存。 除了 TTL，还要处理授权变化：只按 query 做缓存键，可能把甲用户的结果给乙用户。即使共享原始数据缓存，读取时也要重新检查可见性，禁止跨权限复用已裁剪的结果。对象删除、共享范围变化和断开连接都应触发失效。

增量事件。 如果增加 Webhook 或知识同步，建议采用独立链路：

提供方事件 → 校验原始请求签名与来源约定
          → 持久接收事件，按投递 ID 去重
          → 异步更新对象、ACL、删除标记和同步水位
          → 失效查询缓存，必要时调度一个受约束的新任务

GitHub Webhook 文档要求用安全保存的 Secret 校验投递，并以投递 ID 识别重复（重投沿用原 ID）。[32] 实现时按提供方规范校验原始字节，签名支持时间戳时校验时效；先可靠落库再确认接收，重任务放入队列。

事件不一定完整、有序或可全量重放，同步仍需维护 Checkpoint、定期对账并传播删除；Webhook 内容不能直接变成高权限行动指令。

16.5.8 统一错误分类

Connector 要把提供方错误转换为统一分类。下表统一本书 Connector 应用错误码；协议层原始信号在模型接口章定义，重试与收敛责任在 Runtime 定义，三者通过记录原始提供方码关联。它是应用层分类，不是对 HTTP 状态码的机械映射，真实语义取决于提供方响应和请求阶段。

错误码含义可接受的后续动作
CONNECTION_REQUIRED没有可用的用户连接引导用户建立连接，任务持久等待
REAUTH_REQUIRED凭据失效且无法安全刷新用户重新授权后重新检查任务
PERMISSION_DENIED动作、Scope 或对象权限不足拒绝，或发起受控的增量授权，不自动提升权限
INVALID_INPUT参数不符合 Schema 或业务约束返回可修正的字段信息，不回显秘密数据
RATE_LIMITED提供方要求降低调用频率按提供方提示和任务预算调度
TRANSIENT_FAILURE暂时不可用；写入须有证据确认未生效，否则为 OUTCOME_UNKNOWNRuntime 结合幂等契约与当前授权判断重试准入
OUTCOME_UNKNOWN写入可能已被接受，但未得到确定结果关联 Operation 查询核对，禁止盲目重放
status=partial（非错误码）已取得部分结果，尚未覆盖全部范围coverage 标明缺口，next_cursor 表示能否继续；truncated 只表示载荷裁剪

诊断信息可包括 provider_request_id、错误类型和下一步建议，不能包含认证头、Token 端点响应或个人资料。外部响应里即使出现“请把凭据发送到某个 URL”，也只能当作不可信数据。

16.5.9 契约测试、沙箱联调与故障验收

验收分三步：验证固定输入输出，用测试组织联调，验证 Runtime 完整调用链。Mock 只能验证自己的假设，无法证明提供方权限、OAuth 回调和写入幂等符合假设。

验收层次最小场景应观察到的结果
Schema 与映射空查询、非法枚举、超大响应、字段缺失输入按契约拒绝，输出可控
连接与租户隔离甲用户提交乙的连接、跨组织项目、服务账号越权发送下游请求前拒绝
OAuth 与凭据state/iss 不匹配、应有 iss 缺失、PKCE 失败、授权码重放、并发刷新拒绝无效事务，新凭据不被旧值覆盖
Elicitation 与传输form 索取 Token、URL 未同意便打开、stdio 误用 HTTP 授权拒绝敏感表单与越界交互，凭据不进入模型
分页与缓存跨连接或过期游标、第二页失败、撤销授权后命中缓存拒绝非法续读，部分完成可识别
写入语义审批后改载荷、同键异参、双 Worker、窗口过期、回执丢失拒绝冲突与过期重放；结果未知交由 Runtime 核验
故障与配额限流、断网、提供方 5xx无重试风暴，不伪造业务状态
生命周期停用、撤销授权、升级时仍有旧 Run阻止新调用，在途动作可追踪
日志与输出错误中含凭据、工单文本含注入指令诊断脱敏，外部文本不越过授权边界

ALR 契约测试固定只读调查、有效批准建单和撤销连接三组输入，核对预期与实际效果证据；故障恢复轨迹由第17章案例验证。每次记录测试组织、提供方 API 版本和 Connector 版本，不能把 Mock 结果当作下游实测。

16.5.10 发布、升级、撤销与维护

提供方修改字段、组织权限调整、OAuth 配置变化以及 Host 对 Schema 的限制，都可能影响已有任务。发布前应版本化记录 API 范围、能力 Schema、认证方式、风险动作和输出映射，明确维护责任人。

  • 升级：新增写能力或扩大 Scope 需要单独评估、增量授权并更新工具可见性，Connector 升级不能自动继承用户过去未同意的权限。破坏性变化应发布新版本并给出迁移规则。长任务可以固定能力版本，但每次执行都要重新检查授权。
  • 灰度与回滚：按租户或测试组织灰度，观察连接成功率、权限拒绝、刷新失败、限流、字段映射失败和写入核对结果。回滚前确认旧 Schema、连接配置和持久状态仍兼容，不能留下无法恢复的 Operation。
  • 断开连接：先在本地禁止新调用，再按提供方能力撤销 Token，关闭订阅与同步，使缓存和委托失效，并按数据保留策略处理已摄取的材料。RFC 7009 定义了 Token 撤销，但本地停用、远端凭据失效和内容清理需分别追踪。[33]

最终的验收问题是：一个未参与实现的 Runtime，能否只凭契约知道怎样调用、用谁的权限、何时等待、失败后怎样恢复、怎样证明动作已完成？如果仍依赖“让模型自己理解”或“超时再试一次”，Connector 还没有形成可靠的工程边界。

16.6 授权、沙箱与能力交付

图 16-9：授权与沙箱是独立防线

工具契约描述能力与风险，Policy 裁决具体调用，但实际读取、写入和外发发生在底层进程、浏览器和网络请求中。本节定义工具侧的隔离实现、网络出口与回归测试；这些控制怎样与任务授权、组织上限和下游鉴权协同，统一见17.5 安全与授权。

16.6.1 沙箱的职责：限制文件、网络、进程和凭据

只读 API 的安全边界主要来自服务端身份、对象与字段权限，工具 Schema 只约束参数结构，不能证明调用有权执行。一旦 Agent 能运行 Shell、读写文件、启动浏览器或连接 MCP Server，还需要限制“外部进程能接触什么”，沙箱随之成为 Tool Runtime 的基础设施。

沙箱是 Agent 工具执行的环境边界，借助操作系统、容器、网络代理或远程隔离环境，把模型的错误限制在可承受范围内。

它不替代权限系统和审批：权限系统判断工具能否被调用，审批判断这次高风险动作是否被用户接受，沙箱限定工具被调用后底层进程最多能碰到哪里。

本书建议按以下四个维度设计执行边界；它们可以由沙箱、凭证服务与网络设施共同实现，并非任一产品默认都覆盖：

隔离维度作用典型策略
文件系统分别限制读取与写入写入限于工作区；单独拒读秘密路径，不把工作区写限制当作秘密读取限制
网络防外泄和恶意下载默认禁网，按域名 allowlist 放行，接入代理和审计
进程与系统调用限制子进程能力macOS Seatbelt、Linux namespace / bubblewrap、Docker、Firecracker、gVisor
凭据限制 Token 可见性最小权限、短期凭据、按工具注入，密钥不进模型上下文

按任务威胁模型核对四类边界：只隔离文件系统，恶意命令仍可能把可读文件发出去；只隔离网络，Agent 仍可能破坏本机配置。只给 Shell 断网，还不能阻止模型把已读取的数据交给其他联网工具；跨工具路径见Runtime 数据流控制。

本书建议凭据代理按可信认证上下文绑定 tenant / run / tool / resource / expiry，只注入当前动作所需的短期最小权限凭据；模型、事件和 Trace 不保存明文秘密。疑似泄露时停用工具、隔离受影响 Run，再吊销或轮换凭据并保存脱敏审计证据；远端撤销尚未确认时持续阻断新调用，不能只删除日志。

16.6.2 易混淆的概念：Prompt、审批、Docker 与 API RBAC

Claude Code 文档把沙箱（运行边界）与权限规则（工具授权）分开说明，适用平台需单独确认。[34][35]

沙箱是一组运行时约束，不等于“在 Docker 里跑命令”：

容易混淆的概念为什么不等价
Prompt 约束只能影响模型选择，不能约束子进程的真实能力
用户审批审批是决策点，沙箱是执行边界；审批疲劳时仍需强制边界兜底
Docker 容器只是实现方式之一，默认配置仍有网络、挂载、环境变量和特权风险
只读文件系统只读既不能阻止网络外传，也处理不了凭据泄露和供应链脚本
API RBAC控制业务 API 权限，沙箱控制本地进程、文件、网络和凭据

成熟的 Runtime 不应只有一个 sandbox: true 开关，而应把沙箱写成可审计的策略对象：

sandbox_policy:
  filesystem:
    allow_read:
      - "./"
    allow_write:
      - "./"
      - "/tmp/agent-task-*"
    deny_read:
      - "~/.ssh"
      - ".env"
      - "**/*secret*"
  network:
    default: "deny"
    allow_domains:
      - "github.com"
      - "registry.npmjs.org"
    deny_private_ip_ranges: true
  process:
    timeout_seconds: 300
    max_child_processes: 32
    blocked_commands:
      - "sudo"
      - "rm -rf /"
      - "chmod -R 777"
  credentials:
    inject_per_tool: true
    expose_to_model: false
    redact_in_logs: true

其中 blocked_commands 是字符串黑名单，换种写法或经脚本间接执行即可绕过，只是辅助防线。真正的边界由文件、网络和进程隔离提供：命令即使漏过匹配，也写不出工作区、连不到未授权地址。

策略对象还便于复盘：调用在哪个目录运行、允许哪些域名、是否注入凭据、哪些访问被拒绝，都有据可查。

16.6.4 浏览器自动化的边界

针对跨站泄露、下载文件和访问内部系统等风险，环境层面应使用独立的浏览器 profile、域名 allowlist、隔离的下载目录和 Cookie 分区。

此外还要防止点错对象。Playwright 的 Locator 在动作时重新定位元素，并做可操作性检查（可见、稳定、可交互）[36][37]，但这不能证明点中的是正确的业务对象，旧定位更不能当作授权。

以在测试租户创建工单草稿为例：

  • 动作前：读取当前 URL、登录租户、页面内容与表单对象，按角色和名称定位；页面跳转、列表重排或按钮复用后重新读取，不复用旧坐标。
  • 动作中：填入草稿后再次核对对象和参数；提交所需的授权在执行层确认。
  • 动作后：检查工单 ID、租户、状态和已提交字段，必要时查询权威记录；“按钮已点击”或弹出提示只证明界面有反馈。
  • 超时：结果未知时先查询，不再次点击制造重复工单。

测试断言应覆盖旧 Locator、错误租户、遮罩层、意外导航、表单变化和回执丢失。

16.6.5 网络出口控制

Agent 的网络请求可能被诱导访问内网或云元数据服务，即服务端请求伪造（SSRF）。OWASP 指南建议同时处理输入校验、重定向和网络层限制[38]，MCP 安全指南也提醒授权发现和服务端请求存在 SSRF 风险[25]。本节讲 SSRF 与出口控制，数据外发治理见Agent 治理与调优 出站安全。

阶段控制措施必测的失败场景
URL 解析标准解析器，限定 scheme、host、port，拒绝混淆编码和 user-info，按业务 allowlist 放行file、gopher，自带凭据，另类 IP 写法，未授权端口
DNS 与地址校验全部 A / AAAA 记录，拒绝 loopback、私有网段、link-local、元数据地址；出口重验实际连接 IPDNS rebinding、IPv4 映射 IPv6、解析后换地址
重定向默认禁用；必要时逐跳重查目标和权限，限制次数允许域 302 到内网、跨域带凭据
建连与出口受控代理或防火墙限制目标 IP 和端口，网络隔离与审计，校验 TLS校验后被代理重新解析、直接 socket 绕过
数据最小化最少请求字段，按目标域隔离凭据，限制响应大小、时长和类型内部文档被上传、超大响应耗尽资源

只读 HTTP 和 GET 也会泄露信息，域名正则不能单独防御 SSRF。MCP 和 Skill 只描述访问方式，业务授权、数据外发和网络控制仍须分别验证。

16.6.6 执行环境的四个层级：路径、进程、容器与远程执行器

从轻到重有四种执行环境：

层级形态适合场景代价
路径沙箱（Path Sandbox）限制工作区读写本地代码编辑、简单测试不能完整隔离依赖和网络
进程沙箱（Process Sandbox）系统级文件、网络、进程限制本地 CLI、构建、脚本执行平台差异明显，配置复杂
容器或虚拟机（Container / VM）Docker、Kubernetes Job、云端工作区依赖安装、长任务、多 Agent 并行启动成本、镜像维护、缓存治理
微虚拟机或远程执行器（MicroVM / Remote Runner）Firecracker 微虚拟机、远程隔离机器不可信代码、多租户、高风险自动化成本更高，调试和交互复杂

个人 Coding Agent 常从“路径沙箱 + 审批”起步；企业平台需要多租户隔离、凭据代理、出口审计和可销毁工作区，因此逐步走向容器或远程执行器。

执行环境默认不提供容器特权、宿主机 socket、云元数据服务或跨租户网络；仅靠路径隔离或容器 namespace 不能证明这些入口已关闭。高风险、不可信代码应评估 microVM 等更强隔离，并验证宿主机挂载、网络出口和凭据代理的实际限制；gVisor 属于用户态内核隔离方案，不是 microVM。

16.6.7 沙箱与审批

风险等级以 风险分级 为准，各等级对应的沙箱边界如下：

风险等级沙箱边界
只读×内部数据只暴露必要读取路径，禁写；网络按来源允许列表
只读×敏感数据如 loki_search：只读身份、字段脱敏、受限数据引用、留存和出口控制；禁写不等于不会泄露
可补偿写入×内部数据工作区可写，有限网络，不注入敏感凭据
外发或难逆副作用 × 对应数据敏感度隔离容器、最小凭据、开启审计
策略禁止的副作用/敏感度组合不向通用 Agent 暴露，走专用流程

审批并非越多越安全：低风险动作反复审批造成疲劳，高风险动作只靠沙箱又把业务责任交给了技术边界。因此在当前授权内用沙箱支持自动化，高风险组合另加有效批准，关键业务交给专用流程；只读敏感查询仍须目的、对象和字段授权，不能仅因只读就自动放行。审批协议见第17章人工控制。

本书建议按任务约束预先定义可自主执行的边界，例如：本地工具前置配置系统级沙箱，云端 Agent 在一次性工作区执行并以 patch 或 PR 交付。

16.6.8 沙箱回归测试：文件、网络、凭据与 MCP Server

生产级 Agent 应验证沙箱到底拦住了什么，至少包含以下回归测试：

文件系统测试：
- 在测试夹具中放置模拟私钥，并将其路径设为拒读；尝试读取必须失败。
- 写入工作区外的目录，必须失败。
- 读取项目内允许的文件，必须成功。

网络测试：
- 访问 allowlist 中的域名，应按策略成功。
- 访问未知公网域名，必须失败或触发审批。
- 访问 127.0.0.1、169.254.169.254 和内网 IP，必须按策略阻断。

凭据测试：
- 工具进程不能看到未授权的环境变量。
- 工具输出和 Trace 中不能出现 Token 明文。

MCP 测试：
- 未批准的本地 MCP Server 不能启动。
- Server 启动命令必须完整展示并可审计。
- Server 不能访问未授权的文件路径和网络目标。

以上是应显式建立的测试策略，不是 workspace-write 等产品模式天然提供的保证。使用合成秘密与受控目标，分别验证每种文件、执行与联网工具，避免读取真实私钥；某一前置规则拦截也不能代替后续隔离层的独立验证。跨工具外发、组织策略放宽与隔离失效的验收见17.5.6 安全验证。这些测试应进入 Runtime 的 CI，每次调整沙箱、权限规则、MCP 配置、浏览器自动化或远程执行器后都要重跑。

16.6.9 能力组合的交付与兼容

能力提供方交付固定版本的 Skill、Tool 契约、Server 与依赖环境；Runtime 按本轮身份加载和使用。完整发布组合及门禁归治理发布控制，本节保留能力侧验收边界。

交付物/阶段必须检查失败出口
准入与发现来源、命名空间、启动配置、工具描述拒绝来源或隔离安装，不自动启用
资源加载路径、版本、体积与递归上限缺少依赖即报告不可用，不让模型猜工具名
连接绑定请求者、组织、scope、撤销状态禁止复用其他主体凭据
契约兼容参数、返回、作用域、副作用与默认行为即使 Schema 未变，行为改变也需重新验收
动作派发当前授权、审批、执行环境和预算拒绝越权，不以发现成功代替允许调用
升级与回滚候选制品、灰度范围、在途 Operation未知写入先对账；旧版不能撤销既有副作用

能力 profile 记录不可变版本、实际协商的 MCP 协议、策略修订和回归集；Connection 在运行时绑定，凭据不写进组合。远程服务无法钉版本时保留观察快照并验证行为契约。任务轨迹需能解释“当时可见什么、加载了什么、实际调用什么、谁授权、外部产生什么事实”，仅返回 200 或模型自称遵守 Skill 不构成验收。工具选择与能力调优实验见治理与调优。

生产停止路径须明确新调用禁用和在途事实的交接接口；能力版本回滚不撤销已发生的外部效果，执行交接按第17章恢复协议，发布停止条件按第18章发布控制验收。

16.7 案例：告警诊断 Agent 的工具架构

图 16-10：告警案例的能力提供方产物

下面将契约、Skill、MCP、Connector 和沙箱组装成同一次 ALR 调查的能力配置，检验交付物能否被 Runtime 消费。

16.7.1 场景输入与任务目标

用户输入如下：

请调查 ALR-20260429-017：prod/order-service 在
2026-04-29 10:35–10:50+08:00 的延迟异常。
告警候选 E12 称 P95 从 210ms 升到 2.1s，尚未核验；请分析可能原因。

一份合格的诊断结果应包含五部分：结论、证据、置信度、下一步建议，以及需要人工审批的动作。

16.7.2 工具集合设计

下表列出本案例 Skill 需要的工具。动作性质与数据敏感度采用双轴风险表；以下策略是本例配置，不是所有工具的通用风险标签。

工具能力风险等级默认策略与说明
get_alert_details读取告警详情只读×内部数据自动执行；根据 alert_id 获取指标、时间窗口和服务
list_recent_deployments查询最近部署只读×内部数据自动执行；只读部署记录
prometheus_query_range查询时序指标只读×内部数据自动执行；查询延迟、错误率、QPS 和资源使用
kubernetes_get_pods查询 Pod 状态只读×内部数据自动执行；只读 Kubernetes 状态
search_runbooks搜索历史案例只读×内部数据自动执行；检索内部 Runbook
loki_search搜索日志摘要只读×敏感数据日志可能含敏感信息，返回前须脱敏，访问范围由策略授权
create_incident_ticket创建事故单可补偿写入×内部数据仅在当前权限允许且有效批准绑定草稿与资源版本后派发
restart_service / rollback_deployment重启/回滚难逆或高影响动作×内部数据不进入本例能力集，批准建单也不会授予修复权限

这组工具有意把读取、写入和高风险修复动作分开：Agent 可以自动收集证据，但不能自动重启服务或回滚。生产数据库写入、权限变更这类当前任务策略禁止的能力根本不暴露给该 Agent。

16.7.3 对应 Skill：引用而非另起格式

工具集合只说明 Agent 能做什么，不能保证它按正确顺序做。本案例对应的 Skill 采用 示例中的 incident-diagnosis/SKILL.md：前置元数据（Front Matter）中的 description 负责发现，正文写输入与前置条件、执行步骤、行为边界和完成标准。

Skill 只描述方法，不承担授权。工具白名单、禁用工具（如本例的 restart_service）以及各工具的风险等级由工具注册表与 Policy 配置，见 Skill 生命周期与Agent Runtime Policy 裁决。三者的分工是：

  • Tool Runtime 提供能力边界；
  • Skill 提供任务方法；
  • Policy 决定哪些动作真正可以执行。

16.7.6 合格报告标准与教学设定中的偏差

合格报告需核对部署记录（本例 02:35Z 完成）、指标（02:37Z 开始异常）和 payment-client 日志，只能将时间接近写成待验证假设；资源指标正常不能直接排除全部数据库问题。每条证据带调用、版本和时间范围，缺证据就披露缺口。

教学设定中的 v42 运行未完成 deployment mapping 与 owner 核验便采用了 Runbook v2，错误推断连接池耗尽，验证器漏拦；人工批准了建单并不证明这份诊断正确。错误草稿与上述质量标准形成对照，failure-0099怎样转成eval-incident-0099和 v43 门禁，参考治理失败闭环。
