AI Engineering：大模型与智能体系统工程

第17章 成熟 Coding Agent 内部实现：Codex CLI、Claude Code 与 OpenCode

成熟的 Coding Agent 不是“会改代码的模型”，而是一个持续组织上下文、调度工具、约束副作用并验证结果的工程运行时。

资料核验日期：2026-10-22。 本章从三个产品观察 Coding Agent 的运行机制，但开源状态并不相同：Codex CLI 与 OpenCode 有公开源码；Claude Code 核心程序闭源。本章对 Codex CLI、OpenCode 的实现描述以对应公开仓库为依据，对 Claude Code 只描述 Anthropic 官方文档公开的产品行为与接口。无法由公开源码或官方资料确认的模块边界、数据结构和内部算法，会明确标为“系统推导”，不作为实现事实。[1]

17.1 先看共同问题：让模型参与工程闭环

17.1.1 从代码生成到可审查交付

普通代码生成器以文本片段为主要产物。Coding Agent 的产物则存在于仓库和执行环境：它读取文件、发起模型请求、调用工具修改代码、运行命令，再把工作结果交给人审查。模型回答只是交付说明，不能代替真实的文件差异和验证结果。

对比三个产品时，可以先抽象出一条不绑定具体实现的工作路径：

flowchart LR
    A[用户任务] --> B[建立会话和任务上下文]
    B --> C[读取规则与代码证据]
    C --> D[模型选择下一步]
    D --> E{需要工具吗？}
    E -- 是 --> F[权限裁决与工具执行]
    F --> G[记录结果并反馈给模型]
    G --> D
    E -- 否 --> H[候选完成]
    H --> I[检查差异和验证证据]
    I --> J[向用户交付]

这是本书用于分析产品的共同模型，不代表任何一个产品的源码模块图。它把关注点分成四层：

层次核心问题不能混为一谈的事实
任务与上下文这一轮模型要解决什么、能看到哪些信息？磁盘文件存在，不代表已进入上下文
模型与工具模型提出什么行动，运行时如何执行？模型生成工具调用，不代表工具已经成功
权限与隔离哪些动作可以执行，动作影响到什么范围？获得审批不等于进程被沙箱约束
验证与交付哪些证据足以支持“完成”？模型说测试通过，不等于测试进程实际成功

17.1.2 一轮工具调用不是整项任务

一次模型响应可以只含解释，也可以含一个或多个工具请求。运行时要把工具请求解析为可执行操作，检查参数与权限，调用本地或外部能力，将结果归入会话，再决定是否继续采样。Coding Agent 的主循环因此是一个受控状态机，不是单次提示词调用。

可以把一次任务视作以下状态迁移：

输入任务
  → 整理当前上下文
  → 请求模型产生下一步
  → 若有工具调用：授权、执行、记录结果
  → 将观察结果带回后续上下文
  → 继续循环或形成候选完成
  → 对照需求、差异和验证结果审查

工具可能失败、超时、被用户拒绝或被中断。可靠运行时必须把这些情况作为不同结果回送，而不是把失败输出包装成成功。取消也不一定撤回已经发生的外部副作用；远端请求、数据库写入和命令进程都需要自己的恢复语义。

17.1.3 本章采用的证据等级

后面的产品章节会把陈述分成三类：

  • 源码事实：可以定位到公开仓库中的实现或类型定义；
  • 官方文档事实：官方文档描述的功能、调用方式或边界；
  • 系统推导：根据公开证据抽象出的架构解释，便于学习，但不能当作产品内部的精确实现。

产品资料会持续变化。Codex 的链接指向 OpenAI 官方文档和公开仓库主分支；OpenCode 部分采用官方 V2 文档和公开开发分支；Claude Code 部分按官方滚动文档记录。讨论默认值、权限模式和功能开关时，应以对应版本和入口为准，不从一篇文章推断所有部署。

17.1.4 运行时组成：界面、会话、模型与执行环境

第14章给出了通用 Runtime 组件参考设计。本章把它对应到三个产品，回答两个具体问题：哪些组件留在本机或服务进程中，输入第一条任务前后分别发生什么？ 本节以本地编码场景为边界，资料核验于 2026-10-22；Codex 采用公开 App Server 接口，Claude Code 采用官方行为文档，OpenCode 采用 V2 文档。下面分别展开每个产品的实现边界与启动过程。

先分开三个时间尺度：进程启动准备服务与连接，会话初始化选择工作区、配置并建立或恢复历史，轮次启动把新输入送入模型与工具循环。它们可以连续发生，也可以相隔很久。一个后台服务能承载多个会话，一个会话可以执行多轮；恢复历史不会自动恢复旧命令进程，更不会把磁盘文件恢复到历史时刻。

17.2 Codex CLI：公开源码中的 Runtime 与协议边界

17.2.1 先划清 Codex 的开源范围

OpenAI 将 Codex CLI、Codex SDK 和 App Server 等列为开源组件，同时明确 IDE 扩展与 Codex Cloud 不开源。因此，准确的说法是“Codex CLI 开源”，而不是“Codex 的所有产品和服务都开源”。公开仓库让人能追踪 CLI/runtime 的代码，但不意味着云端模型或托管服务实现也在仓库内。[1]

仓库中的 Rust 核心 crate 自述为 Codex 的业务逻辑实现，并面向多种 Rust UI 使用。由此可以从源码分析 CLI 的会话、工具与安全边界；分析范围仍要限制在仓库实际公开的组件。[21]

17.2.2 Session 与 Turn：运行时的两个时间尺度

Codex 的源码把长期会话和一次执行轮次分开管理。Session 保有线程、历史、配置、上下文和服务等生命周期较长的状态；Turn 则承接当前用户输入、模型采样、工具执行和中断等短期状态。源码中的 Session 与 Turn 结构、相关队列和取消令牌可以直接检视。[15]

在核心执行路径中，turn 逻辑反复向模型发起 sampling。若返回工具调用，运行时执行相应工具并把结果送回后续采样；若返回助手消息，则记录并检查该轮是否结束。这个源码注释给出了最小 Agent Loop 的清晰实现证据。[22]

这个区分很有用：会话可以继续存在，而某个 turn 已经结束；turn 也可以被中断或接收追加输入，而无需把整段会话重建。对持久化、统计、恢复和取消而言，Session 与 Turn 不是同一个状态对象。

17.2.3 Core、TUI 与 App Server：同一 Runtime 的不同接入面

Codex 的协议 crate 定义 UI 与核心之间使用的类型，并描述内部 Core/TUI 通信和外部 App Server 通信。文档还说明，该协议尽量承载数据类型，而不把主要业务逻辑塞入协议层。[23]

App Server 暴露结构化协议，供更丰富的界面和客户端驱动 Codex。CLI/TUI 与外部客户端因此可以围绕相对稳定的请求、事件和状态同步协作。App Server 的源码与 README 可用于确认公开的传输方式和协议边界。[24]

从系统设计上看，这种边界把“如何呈现任务”与“如何执行任务”解耦：前端不需要复制一套模型循环，Runtime 也不必绑定单一 UI。这里的“解耦”是对公开协议和 crate 职责的架构总结，不代表所有界面共享完全相同的功能。

17.2.4 Tool Router：工具声明不等于执行权限

Codex 核心包含 Tool Router，负责把模型可见的工具请求关联到具体执行路径。工具输入在执行前还可能经过审批、环境选择、沙箱和策略检查。相关源码把路由、审批与沙箱分别放在不同文件中，能观察到它们是多个相邻的责任点，而不是一个“工具权限开关”。[16]

这体现了两种不同的控制：

  1. 审批控制回答某个动作是否需要用户或策略决策；
  2. 执行隔离回答获准动作实际能读写哪些路径、连接哪些目标或启动什么进程。

同意运行一个命令，不会让该命令自动变安全；沙箱允许某个路径，也不代表命令本身符合业务意图。审查时应分别看决策和执行环境。

17.2.5 Context Compaction：保存任务连续性，不是无损记忆

Codex 源码中包含上下文窗口、自动压缩和压缩任务等实现。压缩需要在上下文预算受限时继续推进对话，它对历史做选择或归纳，必然可能丢失细节。公开代码可用于追踪压缩的触发与恢复流程，但不能把摘要当成工作区当前状态的事实来源。[25]

因此，压缩后的任务状态应重新对照仓库：文件是否仍是记录中的版本、差异是否变化、测试是否针对当前差异运行。历史摘要可以缩短恢复路径，无法证明磁盘、Git 或远端系统仍与旧描述一致。

17.2.6 多 Agent 与共享状态

Codex 仓库公开了 Agent、子任务、协作和消息传递相关代码。理解这类功能时，首先要区分“上下文分开”与“工作区分开”：前者避免共享完整对话，后者避免并行写入同一批文件。一个只读子任务即使与主 Agent 共用目录，也不一定产生写冲突；两个 Agent 即使使用独立上下文，也不因此获得隔离文件系统。[15]

跨 Agent 的消息还可能迟到、被取消或落到不同 turn。源码状态里对当前轮是否继续接收子 Agent 消息有明确建模，这说明协作交付不仅是“spawn 后等待”，还涉及消息归属、终止条件和晚到结果的处理。[15]

17.2.7 从 Codex 源码得到的架构观察

Codex 的公开实现适合观察一种“核心 Runtime + 前端协议 + 受控工具执行”的组织方式。它将会话、turn、协议、工具路由、安全策略、状态持久化和 UI 接入拆为可追踪的 crate 或模块。这个拆分有助于源码审计，也带来跨模块状态协调的复杂度。

不应从源码开放推断模型开放，也不应把主分支今天的实现当作永久稳定接口。源码分析最好记录具体文件和核验日期；如果结论依赖某个 feature gate、协议版本或运行平台，还要把前提写在结论旁边。

17.2.8 启动过程：从启动服务到首个 Turn

以客户端启动 codex app-server 的公开协议路径为例，可以沿下面的顺序观察。它展示一个可验证的接入边界，不要求所有 Codex 界面都用同一种进程部署方式。

阶段初始化或执行动作完成后得到什么

协议硬顺序是连接 → 握手 → 建立或恢复 Thread → 启动 Turn。initialize 每个连接执行一次，不能把它当成每轮模型调用前的初始化。turn/completed 还可能表示中断等状态，不能仅凭事件名认定需求已实现。[2]

配置和指令也有各自的加载边界：Codex 从用户及可信项目的 .codex/config.toml 等层解析配置；未受信任项目的项目配置层会被跳过。AGENTS.md 按全局与项目路径构造指令链，并受大小上限约束。因此，“目录下有配置或说明文件”不等于“本次会话已经采用它”。[3][4]

当前 App Server 文档还说明默认会启动本地 Code Mode host，也可指定远端 host。它是 App Server 向执行宿主发起连接的方向；--listen 则控制客户端怎样连入 App Server。这两条连接不能混为一条，更不能把模型服务端点当成命令执行宿主。具体执行能力与可用参数应绑定实际安装版本。[2]

17.3 Claude Code：基于官方文档分析闭源产品

17.3.1 GitHub 仓库公开，不代表核心程序开源

Anthropic 的 Claude Code GitHub 仓库是公开可访问的，但仓库许可证写明版权归 Anthropic 所有、保留所有权利，并指向 Anthropic 商业服务条款；它不是可按常见开源许可证使用的核心实现源码仓库。公开仓库中的 README、变更记录、示例和插件材料，不能替代未公开的 CLI 实现。[26] [27]

因此，本节不从非官方逆向、泄露代码或社区猜测补写内部细节。即使某个细节听起来符合常见 Agent 设计，只要官方文档没有证实，也会标作“系统推导”，而不是 Claude Code 的确切实现。

17.3.2 官方公开的 Agent Loop

Anthropic 官方文档把 Claude Code 的工作描述为收集上下文、采取行动、验证结果三个阶段。阶段会按任务需要交错：理解代码的问题可能只需检索，修复任务则会多次穿插编辑和验证。官方也直接将 Claude Code 描述为围绕模型提供工具并管理上下文的 Harness。[5]

文档可确认的概念循环如下：

理解用户任务
  → 读取项目与代码上下文
  → 选择文件、搜索、命令等工具
  → 观察工具结果并调整方案
  → 验证实现
  → 继续行动或向用户说明结果

这描述的是公开的产品行为，不是私有函数调用图。可见的工具包括文件读取、编辑、搜索和命令执行；扩展层还支持 Skills、MCP、Hooks 与 Subagents。工具结果成为后续决策的新观察，因此人可以在循环中途纠正方向。[5] [28]

17.3.3 Session、Context 与历史压缩

Claude Code 官方文档说明，对话、工具使用和结果会保存在本地 Session 文件中，用于恢复、继续或分叉；每个新 Session 默认有新的上下文窗口。切换 Git 分支会改变模型能读取的工作区文件，但不会自动改写会话历史。[5]

上下文包含对话、文件和命令结果、项目指令、载入的 Skill 与系统指令。接近窗口限制时，Claude Code 会清理旧工具输出，必要时摘要对话；官方提示早期的详细指令可能在压缩后丢失。MCP 工具定义默认可延迟加载，Skills 也可按需载入；Subagent 使用独立上下文，主会话接收摘要。[5]

可迁移的工程原则是保存稳定约束与任务事实的区别：项目规范适合放进持久指令，动态代码事实应回到仓库重新读取。会话日志和摘要能帮助恢复工作，但都不能证明当前工作区与历史描述一致。

17.3.4 扩展层：Skills、MCP、Hooks 与 Subagents

Anthropic 的公开文档把 Skills 作为可复用知识与工作流，把 MCP 作为外部服务连接，把 Hooks 作为生命周期事件上的自动化，把 Subagents 作为隔离上下文中的委派任务。插件可以把多种扩展打包分发。它们连接到 Agent Loop 的不同位置，不能因名字都叫“扩展”就当成同一类工具。[28]

  • Skill主要把做法和领域知识按需提供给模型；
  • MCP将外部系统的工具或资源接入；
  • Hook在某些生命周期事件上触发脚本、提示或其他动作；
  • Subagent将边界明确的工作交给独立上下文；[29]
  • Plugin是扩展的打包和分发形式。

这些是官方公开的功能语义。内部如何注册、调度和持久化扩展，若没有公开源码或官方实现说明，不在本章中作源码级断言。

17.3.5 Permissions 与 Checkpoints：授权、约束和恢复各司其职

权限模式与规则决定哪些工具调用可以执行、哪些需要询问或拒绝。官方文档还说明 Hooks 可以参与工具生命周期。权限配置不是同一层的全部安全机制：它回答工具调用是否被放行，却不单独定义命令进程可访问的所有资源。[19]

Claude Code 的官方文档描述了文件编辑前的 Checkpoint，可用于回退被跟踪的文件变化；数据库、API 和部署等远端副作用不能由文件回退撤销。这个边界适合作为一般 Agent 系统的提醒：恢复能力必须与副作用类型对应。[5]

官方公开的是产品行为、配置与生命周期事件，没有公开足以重建整个核心程序的源码。下面按依赖关系归纳启动过程；表格不是私有函数调用顺序，也不表示所有准备动作严格串行。

17.4 OpenCode：开源、模型提供商无关的 Client/Server Runtime

17.4.1 版本边界：区分 OpenCode 1 与 OpenCode 2

OpenCode 官方文档当前同时说明 1.x 和 2.x 版本线。两条线使用相同的命令名，但配置结构与实现已有变化；本节以核验日的 OpenCode 2 官方文档和公开开发分支为准，不把 V1 的旧配置字段套用到 V2。仓库声明项目为开源并采用 MIT 许可证。[30]

17.4.2 Client/Server：把界面放在服务端之上

OpenCode V2 的 CLI 文档说明，默认会发现或启动当前用户的共享后台服务，本地客户端连接该服务；--standalone 使用私有服务，--server 连接指定服务。后台服务拥有会话、配置、集成、权限与工具执行，公开 API 支持程序化接入。旧版“启动 TUI 时启动一个服务”的描述不能直接套用于 V2 默认行为。[31]

这个结构使会话与模型运行不必由单一终端界面独占。服务端成为会话、请求和事件的接口边界，客户端则负责展示与交互。对比 Codex，二者都公开了服务/协议边界；对比闭源的 Claude Code，OpenCode 的具体协议和代码路径可以直接检视。

17.4.3 Provider 抽象：让模型接入成为可替换部分

OpenCode 的模型文档描述了多家 LLM Provider 与本地模型支持；Provider 层负责把选定模型信息和请求交给相应服务。模型目录与接口转换在代码中也有对应实现。[32]

这个架构让 Agent Harness 与某一个模型供应商不必完全绑定，但不能保证所有 Provider 的工具调用、上下文长度、流式行为和多模态支持完全一致。适配层把差异归纳为接口，不会消除底层协议差异；系统仍要处理模型能力声明和实际响应之间的不一致。

17.4.4 Session Runner 与 Tool Registry：模型循环和工具执行

OpenCode V2 的源码可看到 Session Runner、LLM 运行逻辑和工具服务的组织方式。工具系统负责注册工具、构造模型可见的定义、执行工具并规范化结果；Session Runner 再把模型输出和工具结果纳入会话过程。[17]

从源码结构可归纳出一次循环：

接收 Session 输入
  → 准备选定 Provider/Model 与工具定义
  → 发送模型请求
  → 识别工具调用或文本输出
  → 执行工具并收集结果
  → 将结果追加到会话并继续，或结束当前回应

这条链是基于公开实现路径的系统概括。具体工具集合、模型协议转换、输出截断和异常恢复会随版本演进，应回到 V2 源码核对，不能用旧版的文件名或配置细节描述当前实现。

17.4.5 Agent 与 Permissions：把角色配置和动作裁决放在一起

OpenCode 文档区分 Primary Agent 与 Subagent。Primary Agent 面向用户承接主会话；Subagent 用于专项委派。Agent 配置可以指定模型、提示、可用工具和权限。权限支持 allow、ask、deny，并可按工具、Shell 命令、文件范围等规则细化。[33]

V2 文档进一步描述 Permissions 与 Policies。规则会在匹配资源时允许、拒绝或请求审批；具体判断层次与 V1 的权限字段并不完全相同。比较权限设计时应关注谁作出决定、规则如何匹配、拒绝是否可被更宽的配置覆盖，以及授权后由哪层执行隔离。[18]

Agent 角色本身不是安全沙箱。将编辑工具标为 deny 能缩小调用面，但系统还需要确认 Shell 能力、外部目录访问和插件工具是否在另一条路径上提供相同副作用。

17.4.6 会话、快照和回退

OpenCode V2 的配置文档说明，Agent 操作期间会通过快照跟踪文件变化，以支持会话内撤销与恢复。服务端也为 Session 提供消息、分叉、终止、差异、总结和回退等公开接口。[31] [34]

这些接口表明 Session 不只是聊天文本列表；它还要承载消息、工具过程、当前状态和可视化差异。但文件快照仍不能撤销所有外部副作用。数据迁移、API 请求和远端仓库操作需要单独的幂等、补偿或审计设计。

17.4.7 OpenCode 的实现特征

从 V2 公开实现看，OpenCode 把 Client/Server、Session Runner、Provider 适配、Tool Registry、权限策略和多种界面组织为开放系统。它的优势是读者可以顺着源码和协议验证设计；代价是跨 Provider 与多客户端支持带来额外适配和兼容工作。

可迁移的观察不是“任何开源 Agent 都天然更安全”，而是源码可见提升了实现可审计性。安全结论仍要检查有效配置、执行边界、依赖和实际运行路径。

17.4.8 启动过程：连接服务与装配会话

OpenCode V2 的默认启动方式是发现或启动当前用户的共享后台服务，然后让本地客户端连接它；该服务拥有会话、配置、集成、权限和工具执行。--standalone 使用私有服务，--server 连接指定 URL。不能把旧版本“每次 TUI 启动时附带一个服务”的描述直接套到 V2 默认行为。[9]

阶段初始化或执行动作完成后得到什么
选择连接方式CLI 采用共享服务发现 / 启动，或按参数选择私有服务、指定服务客户端到目标服务的连接；连接已有服务时无需重新启动后台进程
准备工作区配置服务端按工作区处理生效配置、项目指令与相关集成当前工作区的配置与指令范围；不是所有客户端共享同一项目上下文
选择 Agent 与模型确定主 Agent 和 Provider / Model，使用已有凭证，缺少连接条件时通过 /connect 等入口补齐可用于该会话的角色、模型和访问条件

上述顺序是依据服务职责、配置、Provider 与 Session 接口作出的依赖概括，不承诺各子系统的内部构造顺序。配置中声明 Provider 并不证明已持有有效凭证；/connect 完成账户接入后，还要选择模型。项目指令采用 AGENTS.md，下层目录的说明可随文件读取和目录探索加入；V2 不以 CLAUDE.md 作为回退。[10][11][12][35]

权限也在服务端执行路径上继续发挥作用。V2 的 permissions 规则对动作与资源返回 allow / deny / ask，ask 等待客户端决定。因此，工具出现在目录中、服务已经启动、某个客户端已经连接，都不足以证明这次工具调用已经获准或完成。[36][37]

17.5.2 开源能回答“怎么实现”，不能单独回答“是否可靠”

公开源码让人可以检查工具执行、策略配置、恢复行为和错误处理，但代码存在不代表部署时启用了正确配置；默认功能存在也不代表每个版本和入口行为相同。源码审查还不能替代运行时验证、依赖审查、权限测试和真实故障演练。

闭源产品也不是完全不可分析。官方行为文档、协议说明、配置接口和故障边界仍能支持严谨的系统比较。需要做的是把“可观察事实”和“内部猜测”分开，而不是用开源标签替代证据质量。

17.5.3 成熟 Coding Agent 的共同设计经验

从三个实现及公开接口中，可以归纳出几条工程原则：

  1. 把 Session、Turn 和工作区状态分开。 会话记录是上下文资产，当前工作区是外部事实，当前轮次是短时执行状态。
  2. 把模型计划与工具执行分开。 模型提出行动，运行时解析、授权、执行并记录结果。
  3. 让拒绝与失败成为一等结果。 被用户拒绝、被策略拒绝、工具失败、网络失败和任务取消都必须被准确反馈。
  4. 将审批与隔离分层。 审批决定是否允许某类操作，隔离限制实际进程的影响范围。
  5. 设计有损压缩后的恢复流程。 摘要保存目标、证据、差异、验证和待办；恢复时仍需回到仓库核实。
  6. 委派要明确上下文与写入归属。 子 Agent 的总结不是最终证据；并行修改还要解决文件冲突与集成验证。
  7. 验证当前差异而非接受模型自述。 报告“测试通过”时要能追溯命令、退出状态和对应代码版本。
  8. 让可审查的交付成为主界面。 diff、命令结果、权限决策和未覆盖范围应能被人核对。

什么证据能证明完成？测试结果、diff、会话状态、交付协议
哪些功能只在托管环境可用？云端 API、认证层、服务端调用和开源清单

这套阅读顺序先定位运行闭环，再追踪关键边界。公开代码会随着版本改变，因此结论应绑定提交、版本或核验日期；没有公开证据时，明确写“未知”比补造一套内部架构更可靠。

本章小结

Codex CLI、Claude Code 与 OpenCode 都把模型放进了包含上下文、工具和验证的工程循环，但源码透明度不同：Codex CLI 与 OpenCode 可以沿公开代码追踪运行时，Claude Code 只能根据官方文档分析其外部机制与配置边界。

三者共同说明，成熟 Coding Agent 的核心并不是某个特别长的系统提示词，而是把任务、状态、权限、执行、恢复和验证组织成一个能被用户审查的闭环。要评价系统是否可靠，应检查工具真正做了什么、动作被限制在哪里、任务状态如何恢复，以及完成结论有何证据。
