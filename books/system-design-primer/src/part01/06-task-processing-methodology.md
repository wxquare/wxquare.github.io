# 第 6 章 任务处理方法论：从同步执行到可恢复的 Workflow

> 任务处理解决的不是某个业务对象如何流转，而是一段工作如何被拆分、调度、执行、暂停、恢复和治理。本章以供应商数据同步为主案例，建立同步请求、异步消息、Batch / 分布式 Job 与 Workflow 的统一选型框架。

前两章分别讨论关键业务动作的一致性，以及业务对象跨阶段的生命周期。本章处理第三类问题：一个可执行任务如何可靠跑完。例如，扫描超时订单、生成日报、同步供应商库存、重建索引和执行历史数据修复，都需要明确执行边界、进度记录和恢复机制。

## 6.1 问题定义：任务为什么会失控

许多任务最初只是一个函数、一个 Cron 或一条消息消费逻辑。数据量小、依赖稳定时，这种实现能够工作；一旦执行时间变长、对象数量变多或外部依赖开始抖动，问题会以相似的方式出现：

- 同步请求一直不返回，线程和连接被长期占用。
- 一个消息消费者同时完成拉取、转换、发布和通知，失败后无法判断应从哪里重试。
- 全量任务中途失败，只能从头执行，重复写入和重复调用不断累积。
- 任务状态散落在日志、队列和开发者记忆中，运维人员无法判断它是否仍在安全推进。
- 下游限流或主库繁忙时，重试反而放大流量，最终影响正常业务。

任务处理的核心问题因此不是“如何让代码在后台运行”，而是：

> 在进程会重启、消息会重复、依赖会超时、数据会局部错误的现实里，如何让一段工作仍以可解释、可恢复、可审计的方式完成。

先把本章与相邻主题分开。第 4 章中的资源释放可能由一个任务触发，但该任务不定义库存和订单如何最终一致；第 5 章中的订单状态机可能等待一个定时任务发起命令，但该任务不拥有订单生命周期语义。任务系统负责可靠执行，领域系统负责业务事实。

## 6.2 约束与指标：先明确什么算“跑得对”

任务是否需要专门治理，不应只看耗时，更要看它是否跨越了调用边界、是否处理大量对象、是否存在高风险副作用，以及中断后是否必须恢复。

| 约束维度 | 关键问题 | 常见信号 |
| --- | --- | --- |
| 执行跨度 | 调用结束后工作是否仍需继续？ | 请求超时、后台推进 |
| 对象规模 | 是否要遍历大量独立对象？ | 分页、分片、批次、游标 |
| 依赖稳定性 | 上游或下游是否可能限流、超时或异步确认？ | 退避、轮询、超时处理 |
| 副作用风险 | 重复执行是否会导致重复写入、重复扣费或污染数据？ | 幂等键、对账、审计 |
| 恢复要求 | 失败后能否从安全位置继续？ | Checkpoint、租约、失败池 |
| 治理要求 | 是否需要暂停、取消、优先级和人工接管？ | 操作台、权限、告警 |

指标也必须在设计前写清楚。不同任务的指标不同，但至少应包括以下几类：

- **完成性**：输入对象是否全部被处理；允许跳过的条件是什么。
- **正确性**：输出是否满足校验规则；重复执行后是否保持同一事实。
- **时效性**：一次 Run 的截止时间、分片的最大处理时长和积压上限。
- **资源边界**：允许占用的并发、连接、CPU、内存以及外部接口配额。
- **可恢复性**：失败后可从哪里继续；人工处理的最大存留时间是多少。

没有这些约束，“任务成功”常常只意味着进程退出码为零，而不意味着每个对象都处理正确、每个副作用都可追溯。

## 6.3 核心模型：Task、Run、Step、Shard 与 Checkpoint

无论最终使用脚本、消息队列还是调度平台，都建议先持久化执行事实。一个最小但足够通用的模型包含五层：

| 实体 | 含义 | 例子 |
| --- | --- | --- |
| Task | 可复用的任务定义 | “供应商 A 的库存同步” |
| Run | 某次实际执行实例 | “2026-09-20 02:00 的第 1842 次运行” |
| Step | Run 内有不同职责的阶段 | 拉取、校验、发布、对账 |
| Shard | 可独立调度、重试的工作切片 | 城市、ID 范围、页码或时间窗口 |
| Checkpoint | 可安全恢复的位置 | 已完成分片、最后游标、输入快照版本 |

`Task` 表达“要做什么”，`Run` 才表达“这次究竟处理了什么”。Run 应保存输入范围、配置与规则版本、发起来源、开始时间、截止时间和最终摘要。不要用一个全局任务状态覆盖历史运行记录，否则无法区分今天正在执行的任务和昨天遗留的失败。

`Step` 的边界应按责任和失败语义划分，而不是按代码函数随意切分。比如数据同步中的 Fetch 只负责忠实获得原始数据，Normalize 只负责字段映射，Validate 只负责质量检查，Publish 才负责把经过验证的数据交给正式读模型。这样某个阶段失败时，系统可以精确恢复而不必重做已验证的工作。

`Shard` 是扩展性与故障隔离的核心。好的分片应能独立估算工作量、可单独重试、可追溯输入范围，并且不会因并行而破坏业务约束。常见切法包括供应商 / 商家维度、ID 范围、时间窗口、分页游标和哈希桶。分片太大，失败恢复成本高；太小，调度开销和状态数量又会过大。

Checkpoint 必须表示已经落地且可验证的事实。先完成该分片的幂等写入与状态持久化，再推进 Checkpoint；仅把页码打印到日志，或在落库前更新游标，都不能安全恢复。

状态迁移也应是显式契约。Run 可以经历 `PENDING`、`RUNNING`、`PAUSED`、`SUCCEEDED`、`FAILED`、`CANCELLED`、`MANUAL_REVIEW` 等状态；Shard 则需要区分 `PENDING`、`RUNNING`、`RETRYABLE`、`SUCCEEDED`、`FAILED` 和 `CANCELLED`。这些状态不是为了增加表字段，而是为了避免两种常见误判：把“已入队”当成“执行成功”，以及把“某个分片失败”当成“整次运行已经无价值”。

| 状态 | 含义 | 允许的下一步 |
| --- | --- | --- |
| `PENDING` | 计划已创建，尚未开始 | 领取、取消、暂停 |
| `RUNNING` | 已被执行器领取，租约有效 | 成功、可重试失败、暂停、取消 |
| `RETRYABLE` | 瞬时失败，等待退避后重投 | 重试、转人工、取消 |
| `MANUAL_REVIEW` | 自动路径无法安全收敛 | 人工确认、重试、终止 |
| `SUCCEEDED` | 输出与 Checkpoint 已确认 | 只允许查询和审计 |

状态变更必须同时携带原因、发生时间、操作者或执行器标识、关联错误和版本号。这样任务不但能恢复，也能解释“为什么这次同步在凌晨三点停止”“哪一次重试导致它重新开始”“是谁批准了带异常的数据发布”。状态历史最好追加保存，而不是只覆盖当前状态；当前状态服务于调度，历史服务于审计、复盘和容量优化。

```text
Task
  -> Run
      -> Step
          -> Shard
              -> Checkpoint
```

## 6.4 参考架构：调度、执行、状态与观测如何协作

一个可演进的任务系统不必一开始就有独立平台，但其职责应当清晰。下面是一种通用参考架构：

```text
Trigger / Scheduler
  -> create Run and shard plan
  -> persist intent and dispatch work

Queue / Dispatcher
  -> apply priority, quota and delayed retry

Worker Pool
  -> claim shard with lease
  -> execute idempotently
  -> persist result and checkpoint

State Store / Object Ledger
  -> Run, Step, Shard, input snapshot, errors, audit trail

Observability and Operations
  -> metrics, alert, DLQ, pause, cancel, replay, manual recovery
```

调度器只负责创建运行实例、规划分片和发出可执行意图；不要让它在内存里长时间循环处理全部数据。执行器只负责领取可执行分片、在租约内完成工作、持久化结果并续租或释放；不要让它自行猜测全局进度。状态存储保存权威的运行事实；消息队列用于分发，不应成为唯一状态来源。

领取分片时应使用租约或心跳。Worker 取得 `RUNNING` 状态后定期续租；若进程崩溃，租约到期，调度器即可把分片重新投递。由于“执行中崩溃”和“执行完成但确认写入丢失”都可能发生，重新投递是正常路径，幂等性仍然是前提。

对于需要可靠异步交接的请求，可在本地事务中写入 Run 意图和 Outbox 事件，再由投递器发布消息。这样避免“数据库已创建任务但消息没发出”或“消息先发出但任务记录不存在”的断裂。消费者仍必须幂等，因为可靠投递不等于端到端恰好一次。

## 6.5 方案选型：同步、消息、Batch 与 Workflow 的边界

任务形态应随复杂度升级，而不是按技术偏好选择。

| 方案 | 最适合的问题 | 核心能力 | 最容易失控的点 |
| --- | --- | --- | --- |
| 同步请求 | 少量工作、即时反馈、请求内闭环 | 调用简单、错误直接返回 | 长时间阻塞与超时 |
| 异步消息 / Consumer | 单笔独立副作用、可延迟完成 | 解耦、削峰、快速接入 | 演化成大 Consumer |
| Batch / 分布式 Job | 大量对象推进、局部恢复 | 分片、并行、Checkpoint | 只有任务级状态，无法定位局部失败 |
| Workflow | 阶段依赖、等待、门禁和人工处理 | 状态持久化、定时、可视化治理 | 建模和运行成本过高 |

**同步请求**适合校验、查询和小范围写入。它的关键是及时给出确定结果；一旦执行时长不可预测、需要大量 I/O 或要在请求结束后继续推进，就应交给异步机制。

**异步消息**适合一条消息可以独立完成的动作，例如刷新某商品索引、发送一封通知或补写非关键投影。消息体应包含事件 ID、业务主键、幂等键、发生时间与输入版本。调用方得到的是 `accepted`，不是已完成；应通过 `run_id` 或业务请求号查询最终状态。

**Batch / 分布式 Job**适合全量同步、ETL、对账、重建索引和历史修复。它的核心是把“跑完所有对象”拆成可观察、可重试、可恢复的分片推进。只要任务需要从失败位置继续，或需要统计部分成功和部分失败，就不应再是一段没有状态的长循环。

**Workflow**适合出现明确阶段依赖、外部等待、审批门禁、发布保护或人工转派的场景。它不是 Batch 的替代品：一个 Workflow 阶段内部仍可能启动数千个 Batch 分片；它也不是领域状态机的替代品：业务对象的权威状态依然由领域服务维护。

实际选型时，按下面的顺序提问通常比先比较框架更有效：

1. 调用方是否必须在当前请求得到最终结果？如果必须，优先同步；如果只需确认受理，建立异步交接边界。
2. 每个对象能否独立完成？如果可以且副作用单一，使用消息消费者；如果必须在大量对象上反复推进，引入 Run、分片和 Checkpoint。
3. 失败后是重跑一个对象、一个分片还是整个阶段？恢复粒度决定分片模型与状态存储，而不是由 Worker 数量决定。
4. 是否存在阶段依赖、质量门禁、外部等待或人工裁决？这些需求稳定出现时，再升级为 Workflow。
5. 是否会影响线上可售数据、资金或关键配置？风险越高，越需要暂存、版本化发布、对账和权限隔离。

任务接口的契约也应随方案变化。同步接口通常返回业务结果；异步提交接口返回 `run_id`、当前状态和查询地址；管理接口至少支持查询进度、暂停、取消和受控重试。无论接口形态如何，都要把“已受理”“执行中”“局部失败”“已完成”和“待人工处理”区分开，避免调用方把一次入队成功误解为业务成功。

## 6.6 完整案例：供应商数据同步如何设计

假设平台每天从供应商拉取酒店、房型、价格和库存。供应商接口按城市分页，存在限流和游标过期；同步结果需要经过质量校验后才能覆盖线上可售数据。

### 6.6.1 输入与运行计划

调度器创建一条 Run，固化供应商、同步范围、规则版本、输入快照时间和截止时间。随后按城市与数据量生成 Shard；每个 Shard 记录起始游标、预计页数、优先级和最大重试次数。计划阶段要保证分片不重叠、覆盖范围可解释；如果配置缺失或范围异常，应在真正拉取之前拒绝这次 Run。

### 6.6.2 拉取与暂存

Worker 领取分片后，以供应商配额为上限拉取分页数据。原始响应应保留引用或压缩快照，至少保留来源请求号、拉取时间和规则版本；这使后续出现争议时可以区分“供应商返回错误”与“平台转换错误”。

转换结果先写入暂存区，并用 `run_id + shard_id + source_object_id` 作为业务幂等键。这里的目标不是立刻覆盖正式数据，而是让重复拉取、分片重试和 worker 重启都不会制造额外记录或覆盖其他 Run 的结果。

### 6.6.3 校验与发布门禁

校验分为对象级和批次级。对象级校验检查必填字段、日期范围、币种、引用关系和价格异常；错误对象进入失败池，但不必阻塞全部城市。批次级校验检查缺失比例、数据量突变、价格波动阈值和关键字段覆盖率；超过阈值时应阻断发布，保留暂存版本并生成待处理任务。

| 阶段 | 成功判据 | 可恢复点 | 失败策略 |
| --- | --- | --- | --- |
| Plan | 分片完整且不重叠 | 分片计划已持久化 | 拒绝运行并修正配置 |
| Fetch | 原始数据可追溯、游标已确认 | 最后一页已暂存 | 限流退避；永久错误转失败池 |
| Normalize | 字段映射完成 | 对象级暂存结果 | 隔离坏数据并记录规则版本 |
| Validate | 质量阈值通过 | 校验报告已保存 | 超阈值阻断发布、转人工 |
| Publish | 正式版本切换完成 | 发布版本号 | 回退版本或冻结影响范围 |
| Reconcile | 输入、暂存、发布数量可核对 | 差异报告已保存 | 发起补数或再次核验 |

发布应使用版本化或原子切换策略。例如全部校验通过后，将当前正式版本从 `v18` 切到 `v19`；若只能按城市发布，则每个城市仍需有独立发布版本和回退点。不要把暂存数据直接逐行更新到线上主表，否则中途失败可能让用户看到一半新数据、一半旧数据。

### 6.6.4 对账与结束

Run 结束前进行对账：输入对象数、成功转换数、隔离错误数、发布数和下游可见数是否满足预期。某些差异可以在容忍范围内结束，某些差异必须把 Run 标为 `MANUAL_REVIEW`。只有全部必需阶段收敛，并且差异已被解释或转入明确的后续任务，Run 才能进入 `SUCCEEDED`。

这个案例说明，成熟同步系统的价值不在于“能拉到数据”，而在于每次运行都有输入快照、过程事实、质量门禁、发布边界和可审计的修复入口。

## 6.7 故障与治理：默认假设会重复、会超时、会中断

### 6.7.1 幂等与结果未知

任何分片都可能被重复执行：消息至少一次投递、租约超时、进程在提交确认前重启都可能造成重复。因此，所有写操作都应以业务幂等键保护。数据库可用唯一约束、条件更新或 `UPSERT`；外部接口应携带稳定请求号并支持查询结果。

最危险的状态是“结果未知”。一次调用超时不代表下游没有完成，正确动作是先按幂等键查询结果；确认已完成则推进状态，确认未执行才重试，仍无法确认则进入对账或人工处理。直接重发可能导致重复占用资源或重复发布。

### 6.7.2 重试、超时与失败池

重试必须分类：网络抖动、短暂限流和临时不可用可以指数退避并加入抖动；字段非法、映射缺失、权限拒绝属于永久错误，应直接进入失败池；超过重试预算的错误也应停止自动尝试。无限重试不会提高可靠性，只会让故障扩散。

超时至少分为单次调用、分片执行和整次 Run 三层。单次超时保护连接与线程，分片超时防止死循环或异常大数据，Run 截止时间避免旧任务和下一轮长期重叠。超时触发后，要先判断是否存在结果未知的副作用，再决定取消、重试或对账。

失败池或 DLQ 不应是垃圾桶。每条记录至少保存原始输入引用、错误分类、尝试次数、最近错误、首次失败时间和推荐动作。运维人员应能按范围重试、修复输入后重放、跳过或终止；所有动作记录操作者、理由、前后状态和影响范围。

### 6.7.3 并发、限流与背压

任务系统常见事故不是完全不跑，而是跑得太快。并发度应按被保护资源设置：供应商接口配额、租户范围、数据库连接池、发布能力和分片大小都可能需要独立限制。月度索引重建不应与实时库存修复共享同一资源池；紧急补数可以有受控加急通道，但不能绕过限流和审计。

背压意味着下游处理不过来时，上游主动减速。队列积压、分片等待时间、接口 `429` 比例、数据库连接池使用率、发布延迟和重试率都是重要信号。超过阈值后，可以降低拉取并发、延长退避时间、暂停新 Run 或只保留高优先级任务。隐藏积压只会推迟故障暴露。

### 6.7.4 暂停、取消、恢复与人工接管

暂停表示保留 Run、分片和 Checkpoint，稍后继续；取消表示不再领取新工作，并让已运行的分片在安全边界退出。不要把强行杀进程当作正常取消机制，因为它会把状态留在未知位置。Worker 应在页、批或对象边界检查控制标记，在完成当前原子单元并写入 Checkpoint 后退出。

恢复程序应先回收过期租约，再扫描 `RETRYABLE`、长期 `RUNNING` 和 `UNKNOWN` 分片。对未知外部副作用先查询或对账，确认安全后再投递。人工接管也必须是受控状态迁移，而不是直接改库：操作台应展示进度、最近错误、外部请求号和建议动作，并留下完整审计。

### 6.7.5 顺序、版本与数据一致性

任务并行化后，另一个常被忽略的问题是顺序。并不是所有对象都要求全局顺序，但同一酒店、同一商品或同一账务账户的连续更新，常常需要按版本收敛。解决方式不应依赖“队列看起来是有序的”：扩容、重放、延迟投递和人工补发都会破坏全局接收顺序。

更可靠的做法是让每个对象携带来源版本、更新时间或单调递增序号；写入时只接受不旧于当前版本的数据。对于供应商同步，可把 `supplier_version`、源更新时间和 Run 输入快照记录在暂存对象上，发布时进行条件更新。这样即便较旧 Run 的慢分片晚到，也不会覆盖较新 Run 已发布的结果。

```sql
UPDATE staged_inventory
SET quantity = :quantity,
    source_version = :source_version,
    updated_at = :updated_at
WHERE supplier_id = :supplier_id
  AND source_object_id = :source_object_id
  AND source_version <= :source_version;
```

上面的示例只表达条件更新思想；实际比较依据必须符合来源系统语义。如果上游版本不可信，不能伪造一个“看似有序”的时间戳，应保留原始快照、运行批次和冲突记录，并把无法自动判定的新旧关系转入人工核验。

任务定义本身也会演进。字段映射、分片规则、质量阈值和发布策略变化时，新的 Run 必须固化自己的配置版本；历史 Run 则按照创建时的规则继续解释。把配置写成全局可变值，会导致一次规则发布后，昨天失败的 Run 在今天重试时得到不同结果，审计与复盘将失去依据。

### 6.7.6 观测、告警与对账闭环

可观测性不只是给任务打印一条“开始 / 完成”日志。它应让任何值班人员在几分钟内回答：这次 Run 是否在推进、停在哪个 Step、哪些 Shard 受影响、下游是否正在被压垮、是否需要暂停或介入。

| 层级 | 必备事实 | 主要告警 |
| --- | --- | --- |
| Run | 开始时间、截止时间、总进度、输入版本、最终摘要 | 长期未结束、总体失败率超阈值 |
| Step | 耗时、输入 / 输出数量、异常率、等待原因 | 阶段耗时突增、质量校验不通过 |
| Shard | 租约、重试数、处理速率、Checkpoint、最近错误 | 租约长期占用、重复失败、无进度 |
| 下游 | 队列积压、接口限流、连接池与发布延迟 | 背压触发、配额耗尽、发布阻塞 |

所有日志、指标和追踪都应携带 `task_id`、`run_id`、`step_id`、`shard_id`、幂等键与外部请求号。没有这些关联键，面对一条异常酒店记录时，团队只能在多个系统中靠时间范围猜测它属于哪次同步。

最后必须有对账闭环。供应商同步至少应核对输入对象数、成功转换数、隔离错误数、暂存数、发布数和下游可见数；索引任务应核对主库版本与索引版本；对账任务则应核对业务恒等式。在线运行负责快速推进，对账负责发现遗漏、重复和错位；发现问题后，应创建新的、可审计的修复 Run，而不是让人直接修改结果表。

### 6.7.7 发布保护与回滚边界

数据类任务最危险的一步通常不是拉取，而是发布。发布前应明确最小质量门槛，例如关键字段覆盖率、错误对象比例、价格或库存波动阈值、与上一版本的差异上限。门槛不是为了追求零错误，而是为了阻止明显异常的数据被自动扩大。

发布策略应当可逆：全量场景可采用版本切换，分域场景可按城市或供应商维度保留上一有效版本；一旦发现异常，回滚对象是“可售数据版本或发布开关”，而不是尝试删除所有已传播的消息。若发布后已触发外部副作用，应把回滚建模为新的补偿任务，记录影响范围、执行进度和验证结果。

任何自动发布都应有停止条件：质量阈值被突破、下游错误率持续上升、回滚次数超过上限或人工确认未完成时，系统暂停后续发布并报警。这样，任务系统才既能自动运行，也能在最坏情况下限制影响半径。

## 6.8 方法论总结：按问题升级，而不是按潮流堆组件

任务处理方案最常见的演进路径是：同步调用 → 异步单元任务 → 带分片与 Checkpoint 的 Batch → 带阶段治理的 Workflow。每次升级都应该对应新的真实矛盾：请求被阻塞时异步化；出现全量重跑和局部失败时引入分片；出现等待、门禁、发布风险和人工处理时再引入 Workflow。

可以把本章压缩为八条判断：

1. 先定义任务的输入、输出、成功判据和资源边界，再讨论使用什么框架。
2. 只要中断后必须恢复，就需要持久化 Run、分片和可信 Checkpoint。
3. 只要存在副作用，就把重复、延迟和结果未知当作默认路径设计。
4. 任务级成功不等于对象级成功；批量任务必须能解释局部失败。
5. 队列负责分发，状态存储负责事实；日志不能替代正式状态。
6. Batch 解决大规模推进，Workflow 解决阶段依赖与治理，二者经常组合。
7. 重试、限流、背压、失败池和对账共同构成可靠性，而不是事后补丁。
8. 暂停、取消、恢复和人工接管必须有权限、审计和受控状态迁移。

当这些边界被明确后，任务系统就不再是一组“后台脚本”，而是一套能够跨故障、跨时间、跨人员交接持续收敛的执行机制。
